# AI支援開発ガイド

## 目的

Memoriaでは、ChatGPTを要件整理・設計検討・GitHub上の調査に、ローカルのCodex CLIまたはIDE拡張を実装・検証に利用します。Codex Cloudは前提にしません。

各リポジトリは独立したGit履歴とリリース単位を維持します。AI支援による変更でも、複数リポジトリを一つのGitリポジトリへ統合しません。

## リポジトリと責務

| リポジトリ | 責務 | 主な契約 |
| --- | --- | --- |
| `memoria-web` | Web UI、認証済み画面、GraphQLクライアント | GraphQL schema、ユーザー向け用語 |
| `memoria-api` | GraphQL API、ドメインロジック、永続化、オブジェクトストレージ | GraphQL schema、DB/storage contract |
| `memoria-design` | プロダクト用語、設計、横断的な意思決定 | プロダクト全体の設計上の正本 |
| `memoria-IaC` | AWSリソースと実行環境 | runtime、network、IAM、storage |

## ローカルワークスペース

各リポジトリを同じ親ディレクトリへ個別にcloneします。

```text
memoria/
├── memoria-api/
├── memoria-web/
├── memoria-design/
└── memoria-IaC/
```

Git管理はリポジトリごとに独立させます。Codexは変更対象のリポジトリを作業ディレクトリとして起動します。

```sh
cd memoria/memoria-web
codex
```

複数リポジトリに変更が必要な場合も、一度に一つの作業ルートを扱い、リポジトリごとにブランチ、コミット、PRを分けます。

## コンテキストの優先順位

AIが判断に利用する情報は次の順に扱います。

1. ユーザーが現在のタスクで明示した要件
2. 対象リポジトリの`AGENTS.md`
3. このリポジトリにあるプロダクト設計と用語集
4. 対象リポジトリのREADME、実装、テスト
5. IssueおよびPRに残されたタスク固有の判断

設計資料と実装が一致しない場合、AIは差異を報告し、推測で片方を正しいものとして更新しません。

## 標準ワークフロー

1. ChatGPTで目的、受け入れ条件、影響リポジトリを整理する。
2. プロダクトIssueを作り、必要ならリポジトリ別のサブタスクへ分割する。
3. 対象リポジトリでCodexを起動し、`AGENTS.md`と関連コードを読ませる。
4. AIに実装だけでなく、変更計画、リスク、検証方法も提示させる。
5. ローカルで生成、静的検査、テスト、ビルドを実行する。
6. リポジトリごとにDraft PRを作り、関連PRと適用順序を相互リンクする。
7. CI結果と人間のレビューを確認してからマージする。
8. 長期的に有効な設計判断をこのリポジトリへ反映する。

## プロンプトの最小要素

依頼には少なくとも以下を含めます。

- 達成したい結果
- 対象リポジトリ
- 受け入れ条件
- 変更してよい範囲
- 実行すべき検証
- 互換性、セキュリティ、データ移行上の制約

例:

```text
memoria-webで画像一覧の空状態を実装してください。
既存のMantineとi18nのパターンを使い、API契約は変更しません。
Storybookと単体テストを追加し、TypeScript、Biome、Vitest、Next buildを通してください。
実装前に影響範囲と検証計画を示してください。
```

## リポジトリ横断変更

GraphQL schema、認証、ファイル保存、インフラ、ユーザー向け用語の変更は横断変更になりやすいため、次を明示します。

- 契約の所有リポジトリ
- 影響を受けるリポジトリ
- 後方互換性
- PRのマージ順序
- deployおよびmigrationの順序
- rollback方法

GraphQL契約は原則として`memoria-api`で先に定義し、互換期間を設けて`memoria-web`を追随させます。破壊的変更を単独PRで行いません。

## 安全境界

AIは明示的な許可なしに次を実行しません。

- 本番・ステージング環境へのdeployまたはdestroy
- DB migration、データ削除、バックアップ復元
- シークレットや認証情報の作成・変更・表示
- IAM権限の拡大
- 外部サービスへのメッセージ送信
- 既定ブランチへの直接push
- 失敗したテストの削除やsnapshotの無検証更新

## 完了条件

変更は以下を満たしたときに完了候補となります。

- 受け入れ条件を満たしている
- 対象リポジトリの`AGENTS.md`に記載された検証が成功している
- 生成元と生成物が同期している
- テストが追加または更新されている
- セキュリティ、互換性、migrationへの影響が説明されている
- 横断変更では関連PRと適用順序が記載されている
- 必要な設計資料が更新されている
- 人間がdiffと検証結果を確認している

## 導入後の改善候補

初期監査では、次を独立したIssueとして扱う価値があります。

- `memoria-api`のDevbox（Go 1.24）とGitHub Actions（Go 1.22）の統一
- `memoria-web`へのCI追加（Biome、TypeScript、Vitest、Next build）
- `memoria-design`のパッケージマネージャーとlockfileの統一
- `memoria-IaC`のルートと`src/`に分散したNodeパッケージ構成の整理
- 各リポジトリのbranch protectionと必須チェックの設定
