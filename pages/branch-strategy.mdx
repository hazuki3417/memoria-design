# ブランチ運用規約

## 目的

Memoriaでは、個人開発・小規模プロダクトに適した簡易Git Flowを採用します。4リポジトリは独立して管理しますが、ブランチの意味、PRの向き、リリース判断を統一します。

ステージング・テスト専用ブランチは設けません。環境を追加する必要が生じた場合は、ブランチではなくGitHub Environmentsやデプロイ設定による分離を検討します。

## 長期ブランチ

| ブランチ | 役割 | 直接push | 通常の変更元 |
| --- | --- | --- | --- |
| `main` | 本番リリース可能な安定版 | 禁止 | `develop`からのリリースPR |
| `develop` | 次回リリースへ向けた日常開発の統合先 | 禁止 | 作業ブランチからのPR |

`main`は本番環境そのものではなく、本番へリリース可能であり、本番へ反映されたコードを追跡する安定ブランチです。実際に本番で稼働している版は、デプロイ履歴やリリースタグで確認します。

各リポジトリの既定ブランチは`develop`とします。

## 作業ブランチ

通常の作業ブランチは、最新の`develop`から作成します。

| 接頭辞 | 用途 |
| --- | --- |
| `feature/*` | 新機能 |
| `fix/*` | 通常の不具合修正 |
| `docs/*` | ドキュメント |
| `refactor/*` | 挙動を変えない内部改善 |
| `chore/*` | 設定、依存関係、保守作業 |
| `hotfix/*` | 本番向け緊急修正 |

ブランチ名は作業内容が分かる短いkebab-caseとします。人間による手動開発とChatGPTによる支援のどちらでも同じ規則を適用し、作業者や利用ツールをブランチ名へ含めることは必須にしません。

## 通常開発

1. 最新の`develop`から作業ブランチを作成する。
2. 実装、ローカル検証、またはChatGPTによる支援作業を行う。
3. 作業ブランチから`develop`へDraft PRを作成する。
4. CI、差分、受け入れ条件を確認する。
5. 人間の承認後にPRをマージする。
6. マージ済みの作業ブランチを削除する。

通常の機能・修正PRを`main`へ直接作成しません。

## リリース

1. `develop`がリリース候補として検証済みであることを確認する。
2. `develop`から`main`へのリリースPRを作成する。
3. 変更内容、関連PR、互換性、migration、デプロイ、rollback方法を確認する。
4. CI成功と人間の承認後にマージする。
5. 本番デプロイの成否を確認する。
6. 必要に応じてSemVer形式のリリースタグを付ける。

`main`へのマージと本番デプロイを自動連携する場合でも、実際の稼働版はデプロイ履歴で確認します。

## 緊急修正

本番障害など、通常の`develop`経由では間に合わない場合に限り`hotfix/*`を使用します。

1. 最新の`main`から`hotfix/*`を作成する。
2. 必要最小限の修正と検証を行う。
3. `main`へのPRを作成し、人間が承認する。
4. 本番反映後、同じ修正を`develop`へPRで同期する。
5. `main`と`develop`の両方へ反映されたことを完了条件とする。

## `master`の廃止

新たに`master`を作成しません。既存の`master`が見つかった場合は、削除前に次を行います。

1. `main`とのcommit差分を確認する。
2. `master`だけにある変更をPRで`main`へ統合する。
3. 既定ブランチ、CI、デプロイ、README、外部連携の参照を`main`へ変更する。
4. 未完了PRや必要なタグが残っていないことを確認する。
5. 人間の明示的な承認後に`master`を削除する。

履歴を失う可能性があるため、差分未確認の削除やforce pushは行いません。

## リポジトリ横断変更

複数リポジトリへ変更が必要な場合も、リポジトリごとに作業ブランチとPRを作成します。各PRに次を記載します。

- 関連する他リポジトリのPR
- 契約の所有リポジトリ
- マージ順序
- デプロイおよびmigrationの順序
- 後方互換性
- rollback方法

各リポジトリの`develop`へ互換性を保って統合し、リリース時に必要な組み合わせと順序を人間が確認します。

## 保護規則

GitHub上では、少なくとも`main`と`develop`に次の保護を設定します。

- 直接pushを禁止する
- PR経由の変更を必須にする
- 必須CIの成功を要求する
- unresolved conversationがないことを要求する
- force pushと削除を禁止する
- `main`のマージは人間の明示的な承認を必須にする

個人開発でGitHub上の独立したreview approvalを必須にできない場合でも、PR差分とCI結果を人間が確認した記録を残します。

## インフラストラクチャの追加規則

`memoria-IaC`では、`main`へのマージだけで無条件に本番適用しません。

- PRでは`cdk synth`と必要な`cdk diff`を確認する
- 本番deployは対象環境を確認し、人間が明示的に承認する
- `cdk destroy`は通常のCI・リリースフローから除外する
- stateful resourceの置換・削除にはbackup、migration、rollback計画を必要とする
