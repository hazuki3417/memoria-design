# 旧設計資料の精査状況

> 状態: 初期設計・要精査  
> 注意: このページに挙げる資料は、現行仕様または廃止決定を表しません。

## 目的

AI支援開発の導入前から存在する資料を、情報が古いという理由だけで削除せず、設計意図、検討経緯、将来利用の可能性を個別に確認します。現行実装との不一致は、削除条件ではなく精査の開始条件です。

## 判定基準

各資料は次を確認してから、現行設計への統合、履歴資料として保存、更新、または削除を判断します。

1. Memoria固有の要求・制約・設計意図が含まれるか
2. 現行実装、合意済み将来設計、未実装案のどれに該当するか
3. 他資料へ情報が完全に移行されているか
4. 採用しなかった理由や検討経緯として価値があるか
5. 削除により将来の判断材料が失われないか

## 要精査の資料

| 領域 | 主な資料 | 現時点の扱い |
| --- | --- | --- |
| S3 path・派生file | `/s3-design` | 新storage設計への移行は一部のみ。具体pathを再評価する |
| Relay Connection | `/schema/graphql`と`pages/schema/_drawio/` | cursor paginationの要否と現行schemaを照合する |

| Micro Service／Memoria Record | `/micro-service/memoria-record` | 構成前提は古いが、未移行の要求・制約がないか再確認する |
| Component | `/component` | 現行Web構成と照合し、再利用可能なUI原則を抽出する |
| Validation | `/validation` | 新API validation設計へ完全移行できているか確認する |
| Log・APM | `/log-design`、`/dam-apm-design` | observabilityへ移行した情報と未移行情報を確認する |

| DB test pattern | `pages/_drawio/test-design/` | repository testの具体patternとして残す価値を確認する |
| Tips | `/tips`、`/component/tips` | Memoria固有の知見か一般論かを項目単位で確認する |

## 削除の完了条件

削除は、情報が古い、実装にない、別構成へ変わったという理由だけでは行いません。必要情報の移行先、非採用判断、その理由を記録し、参照価値がないことを確認できた場合に限ります。
