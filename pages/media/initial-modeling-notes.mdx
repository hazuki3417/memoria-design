# 初期モデリング記録

> 状態: 初期設計・参考資料  
> 移行元: `pages/_drawio/modeling.drawio.svg`

## 目的

このページは初期draw.ioに記載されていた検討内容を、検索・差分確認できる形で保存します。現在の設計判断と矛盾する内容も、検討経緯として削除しません。

現在の正本は[Media設計](./index)と[Media設計判断](./design-decisions)です。このページのテーブル名や属性を、そのまま実装要件として扱いません。

## 初期の概念

- 現実世界の人物とUserを1対1として扱う
- UserとAuthを分離する
- Contentをアップロードした人、管理する人、著作権者を別概念として検討する
- Content管理者をUserまたはCommunityとする
- User削除によるContent消失を避けるため管理委譲を導入する
- Communityを家族やサークルに近い閉じた空間とする
- Community内部は開かれた共有空間とする
- GroupをDAGとして扱う

現在はContentをMediaへ変更し、著作権者は管理対象外としています。

## 初期の物理データモデル案

### 管理主体

| 初期テーブル案 | 初期の責務 |
| --- | --- |
| `content_custodian_user` | User管理Contentの現在状態 |
| `content_custodian_communities` | Community管理Contentの現在状態 |
| `content_delegations_user` | UserからUserへの委譲履歴 |
| `content_delegations_communities_user` | CommunityからUserへの委譲履歴 |
| `content_delegations_user_communities` | UserからCommunityへの委譲履歴 |

現在状態と委譲履歴は、書き込み時には同時に扱う一方、読み取り責務が異なるため独立させる考えでした。現在は論理概念をCustodyとMedia Eventに整理しており、物理テーブル構造は未確定です。

### Access

`i_content_access`は、Custodianを表すテーブルを閲覧検索へ流用せず、UserまたはCommunityから閲覧可能なContentを検索するための案でした。

初期案では次の理由が記載されています。

- Custodianは管理責任を表し、閲覧範囲を表さない
- Custodian経由でCommunity内Contentを取得すると複雑になる
- 現在の関連をAccess側へ投影して読み取りを単純化する

現在はUser管理MediaとCommunityの多対多公開を`Media Community Access`として整理しています。

### Community

| 初期テーブル案 | 初期の責務 |
| --- | --- |
| `community_memberships` | 現在の参加状態 |
| `community_membership_histories` | 参加・脱退履歴 |
| `community_owners` | 現在のCommunity管理者 |
| `community_owners_histories` | 管理者の追加・除去・委譲履歴 |

Community管理者はMembershipに参加していることを前提とし、一般参加者とは別種のUserではなく付加情報として扱う考えでした。`owner`は法的所有者と誤解されるため、今後はAdministratorまたはManagerへの変更を検討します。

### Group

| 初期テーブル案 | 初期の責務 |
| --- | --- |
| `image_groups` | Group本体 |
| `image_group_relations` | 親子Group関係 |
| `image_group_images` | GroupとImageの関連 |
| `user_image_groups` | User用Group |
| `community_image_groups` | Community用Group |

この構造は現行PostgreSQLへ一部反映されています。今後はMedia Groupへ一般化します。

## 初期のデータパターン

### Group

- 単純なGroupに複数Imageを所属させる
- 「旅行 > 日本 > 東京」の木構造
- 「沖縄」を「旅行」と「夏」の両方へ所属させるDAG
- 同じImageを複数Groupへ所属させる

現在の[Mediaデータパターン](./data-patterns)へ移行済みです。

### Custodian

検討された組み合わせ:

- 1 User
- 複数User
- 1 Community
- 複数Community
- 1 Userと1 Community
- 複数Userと複数Community

複数管理は技術的には可能でも、責任と将来の課金が複雑になるため、現在は1 Userまたは1 Communityだけを許可します。

### Delegation

- UserからUser
- UserからCommunity
- CommunityからUser
- 管理主体の現在状態を更新する
- 誰から誰へ委譲したかを履歴へ残す
- Uploader、Custodian、著作権者を分離する

現在は著作権者を管理せず、Community間直接委譲も提供しません。委譲時は既存公開をすべて解除します。

## 初期のユースケース整理

### 検討済みと記載されていたもの

- ContentをUserからUserへ委譲する
- ContentをUserからCommunityへ委譲する
- ContentをCommunityからUserへ委譲する
- Communityへ参加する
- Communityから脱退する
- UserをCommunity管理者へ任命する
- UserをCommunity管理者から除外する

### 未検討と記載されていたもの

- Contentを投稿・削除・更新する
- Communityを作成・削除・更新する
- Userを登録・更新・削除する
- Communityを検索する
- メールで招待する
- 永続または期限付き招待リンクを発行する

Media範囲のレビュー結果は[Media関連ユースケース](./use-cases)を参照します。Community範囲は今後レビューします。

## 初期のCommunity思想

- Communityは家族やサークルなど現実世界の集団に近い
- 外部から閉じられ、内部ではMediaを共有する
- Community内部にprivateな部分や限定Groupを作らない
- 細かなMedia ACLを設けない
- 限定共有が必要なら別Communityを作る
- Userは複数Communityへ参加できる
- Communityは誰かの法的所有物でなくても、システム上の管理者は必要
- Community作成者を初期管理者とする案
- 管理者はCommunity参加者であることを前提とする

Media公開に関する部分はレビュー済みです。Community作成者、管理者不在、招待、閉鎖の詳細は未レビューです。

## 初期の削除・archive案

物理ファイル:

- main bucketからarchive bucketへ移す
- 削除イベントをLambdaなどで検知する
- アプリケーション本体からarchive処理を分離する

DBレコード:

- main schemaとarchive schemaを用意する
- 同じテーブルと関連をarchive側へ保持する
- triggerやprocedureで移す

懸念:

- 仕組みの存在が忘れられる
- テストが難しい
- archiveからの復元が複雑
- 本体とarchiveの整合性管理が必要

レビューの結果、利用者向け復元、論理削除、archiveは導入しない方針へ変更しました。障害復旧バックアップだけを別の運用設計として扱います。
