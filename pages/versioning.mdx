# バージョニング規約

> 状態: 現行

## 目的

Memoriaを構成する各リポジトリの変更規模と互換性を、Semantic Versioning 2.0.0の考え方に基づいて表現します。

## 基本形式

バージョンは`MAJOR.MINOR.PATCH`で表します。

```text
1.4.2
```

| 要素 | 更新条件 |
| --- | --- |
| MAJOR | 後方互換性のない公開契約・利用方法の変更 |
| MINOR | 後方互換性を維持した機能追加 |
| PATCH | 後方互換性を維持した不具合修正 |

Gitタグは先頭に`v`を付けます。

```text
v1.4.2
```

プレリリース識別子（`alpha`、`beta`、`rc`など）は使用しません。正式リリースとして扱えない状態は`develop`で管理し、リリース可能になってから`main`へ反映します。

## リポジトリごとの独立管理

次のリポジトリは、それぞれ独立したバージョンを持ちます。

- `memoria-web`
- `memoria-api`
- `memoria-design`
- `memoria-IaC`

リポジトリ間でバージョン番号をそろえません。他のリポジトリがリリースされたことだけを理由にバージョンを更新しません。

```text
memoria-web     v0.8.2
memoria-api     v0.5.0
memoria-design  v0.3.1
memoria-IaC     v0.4.3
```

この組み合わせは正常です。リポジトリ間の互換性は、同じ番号ではなくAPI契約、関連PR、適用順序、リリースノートで管理します。

## 初期開発

公開仕様が安定するまでは`0.y.z`を使用します。

- 最初の開発版は、既存タグやReleaseがなければ`v0.1.0`を基準とします。
- 初期開発中の互換性を保証しない変更はMINORを更新します。
- 後方互換な不具合修正はPATCHを更新します。
- 公開仕様を安定版として宣言する段階で`v1.0.0`とします。

例:

| 変更 | 更新例 |
| --- | --- |
| 初期開発中の機能追加・互換性変更 | `v0.2.3 → v0.3.0` |
| 初期開発中の不具合修正 | `v0.3.0 → v0.3.1` |
| 安定版の破壊的変更 | `v1.4.2 → v2.0.0` |
| 安定版の後方互換な機能追加 | `v1.4.2 → v1.5.0` |
| 安定版の後方互換な修正 | `v1.4.2 → v1.4.3` |

## リポジトリ別の互換性

バージョンは各リポジトリが外部へ提供する契約への影響で判断します。

| リポジトリ | 主な判断対象 |
| --- | --- |
| `memoria-web` | URL、画面遷移、利用者が認識する機能・操作方法 |
| `memoria-api` | GraphQL、認証、データ、ファイル・ストレージ契約 |
| `memoria-design` | 承認済み設計、公開URL、ドキュメント利用方法 |
| `memoria-IaC` | CDKの外部入力、デプロイ方法、既存環境との互換性 |

同じ横断変更でも、各リポジトリで同じ更新種別になるとは限りません。APIの破壊的変更に追従するWeb変更が、Web利用者にとって後方互換であれば、Web側のMAJOR更新は必須ではありません。

複数種類の変更を一度にリリースする場合は、最も影響が大きい変更を採用します。

## ドキュメント変更

単純な誤字修正、構成整理、説明の明確化だけでは、原則として新しいプロダクトリリースを作りません。

次の場合は変更の影響に応じてバージョン更新を検討します。

- リリース済み仕様の意味を訂正する
- 承認済みの公開契約や利用方法を変更する
- ドキュメントサイトの公開URLや参照方法を互換性なく変更する

コミットの`docs`種別だけでPATCH更新を決定しません。

## バージョンの正本

各リポジトリのGitタグとGitHub Releaseをバージョンの正本とします。

- タグ形式は`vMAJOR.MINOR.PATCH`
- 正式なタグは`main`のリリースコミットへ付ける
- `develop`のコミットへ正式なバージョンタグを付けない
- `package.json`、module定義などへ、実行時に不要なプロダクトバージョンを重複して持たせない
- アプリケーションでバージョン表示が必要になった場合だけ、manifestとの同期方法を別途設計する
- `devbox.json`と`devbox.lock`にはプロダクトバージョンを記録しない

## リリース手順

1. 対象リポジトリの直近バージョン以降の変更を確認する
2. 公開契約への影響から次のバージョンを決める
3. `develop → main`のリリースPRを通常のmerge commitでマージする
4. `main`のリリースコミットへバージョンタグを付ける
5. 同じタグからGitHub Releaseを作成する

実環境へのデプロイがあるリポジトリでは、既存の検証・承認・デプロイ手順も満たします。

## リリースノート

GitHub Release本文をリリースノートの正本とし、日本語で次を記載します。

- 変更概要
- 利用者または外部契約への影響
- 破壊的変更
- 必要な移行・適用順序
- 関連するIssue、PR、他リポジトリのRelease

手動管理の`CHANGELOG.md`は当面必須としません。複数リポジトリへ影響する場合は、バージョン番号をそろえる代わりに関連PRとReleaseを相互リンクします。
