# Source of Truth Discovery

## 目的と適用条件

Memoriaの設計・調査・実装・レビューなど、依頼の判断に**最新の設計・規約・実装の根拠が必要なとき**に使用します。特に作業の開始・再開、対象領域の変更、既存仕様との照合、Repository横断の調査、正本間の不整合確認に適用します。単に正本の所在を尋ねられた場合にも、必要な範囲の読み取りで対応します。

本Skillは、既存の正本への到達・実際の取得・照合・引き渡しを再現可能にする**作業手順**です。新しい正本、設計上の優先順位、操作権限、独立した工程ゲートを定義しません。取得すべき文書をすべて毎回読むことや、新しい調査記録ファイルを一律に作ることも要求しません。

## 正本と責務境界

- [Context map](../../content/context/index.mdx)：Task別の読み取り順序・横断影響・情報の優先順位と参照経路の正本。
- [ドキュメント管理方針](../../content/documentation-policy.mdx)：設計情報の所有先・成果物の責務と記載範囲。
- [AI支援開発](../../content/ai-development.mdx)：最新状態の確認、判断と合意、検証結果と未確認事項の区別、書き込み権限。
- 各Repositoryの最新`AGENTS.md`、該当Owner Document、schema・設定・code・test・CI：所有する内容の現在の正本。
- 関連Issue・PR：現在のTask固有の要求・合意・進捗と変更差分。設計文書や実装契約の代わりにはしない。

**Task Context Resolution**（[Skill](../task-context-resolution/SKILL.md)）はGoal・Scope・対象Repository・現在のTask状態・操作許可を整理する。本Skillはその入力をもとに**どの正本が必要かを発見し、取得結果と根拠を整理する**。**Branch Management**（[Skill](../branch-management/SKILL.md)）は作業ブランチを判断する。具体的なコード構造・原因の深掘りはCodebase Investigation等の後続作業、設計の採否や修正方針の決定は人間との対話を含む設計作業に委ねる。

Skill内へContext mapのOwner Document一覧や優先順位を複製しません。関連規約が変更されてもGitHub上の最新正本を読み直します。**本Skillを使うだけではGitHub writeは許可されません**。

## 入力

- 最新のユーザー指示と合意済みGoal・Scope・不変条件・確認したい論点。
- 対象Repository、Issue・PR・branch（分かる範囲）。不明な値を推測しない。
- 照合すべき領域（Domain / Screen / System、横断規則、実装契約など）と、検証に必要な具体性。

Task Contextが未整理であればTask Context Resolutionを適用します。調査が読み取り専用の場合は、その範囲で進め、branchやPRを作りません。

## 実行手順

### 1. 参照経路と所有先を特定する

1. `memoria-design`の最新`AGENTS.md`・[Context map](../../content/context/index.mdx)を入口として、依頼に該当するタスク別読み取り順序を選ぶ。必要な場合はProduct VisionやFirst Releaseなどの上位前提も参照する。
2. 対象Domain・画面・システム・操作種別に対して、どのOwner Documentが意図する振る舞い・規約を所有するかを[ドキュメント管理方針](../../content/documentation-policy.mdx)とContext mapで確認する。
3. 実装・schema・test・CIの検証が必要なときは、対象Repositoryの最新`AGENTS.md`から実装規約と所有する実行可能な契約へ到達する。複数Repositoryにまたがる場合は所有先と検証対象を分離する。
4. 認証・認可、Privacy、Transaction、冪等性、削除、Accessibility、Responsive、テスト、運用等の横断影響を評価し、**影響のある領域だけ**関連正本を追加する。単に記載されているという理由で全文取得を強制しない。

### 2. GitHubの最新内容を実際に取得する

1. 設計・実装・レビューの判断に必要な文書・ファイルの本文と対象branch・PRの最新状態をGitHubから取得する。ファイルの場所が不明なときは一覧・検索で候補を絞り、必要な本文だけ取得する。
2. 一覧に存在すること、過去に取得したこと、会話やIssueに要約があることを、今回本文を取得した証拠として扱わない。**発見済み／本文確認済み／未確認**を区別する。
3. 読み取りに失敗した場合は、代替の許可済みreadや対象の絞り込みを検討する。取得できない項目と、そのため確定できない判断を明示する。同じ失敗操作を無制限に繰り返さない。
4. 作業中に対象branch・Scopeや正本が変わったときは、影響する範囲を最新状態で再照合する。同じ情報を形式的に何度も取得しない。

### 3. 設計・規約・実装の一致と差異を整理する

1. 設計書に書かれた**意図する振る舞い**と、所有Repositoryのschema・設定・code・testが示す**実際の振る舞い・実行可能な契約**を区別する。Issue・PRはTask固有情報であり、これらを無条件に上書きしない。
2. 同じ内容について複数の正本候補がある場合は、所有責務とContext mapの情報優先順位を確認する。設計と実装の不一致は、どちらか一方が自動的に正しいと断定せず、差異と影響を提示する。
3. 仕様変更・設計修正・実装修正の選択に重要な判断が必要なら、**本Skillだけで採否を決めない**。合意が必要な論点を後続の設計・実装判断へ渡す。未確認を「一致した」とは報告しない。
4. 変更前後の実装契約や視覚・操作上の振る舞いが重要な場合は、比較基準として確認すべき正本と実装・Story・testを特定する。具体的な回帰検証は対応する実装・レビュー作業が所有する。

### 4. 発見結果を引き渡す

作業規模と論点に応じ、**必要な項目だけ**以下の軽量な結果を会話や作業報告にまとめます。固定JSON Schemaや新しい永続台帳は作りません。

| 項目 | 内容 |
| --- | --- |
| 対象と目的 | 今回のScope、確認したい振る舞い・契約 |
| 参照経路と所有先 | Context mapから到達したDomain / Screen / Systemの正本とRepository |
| 本文確認済み | 実際に取得したRepository / path / branchと、判断に関わる内容 |
| 発見のみ・未確認 | 候補は特定したが本文未取得、取得失敗、影響未確定の対象 |
| 一致・不整合 | intended behaviorとactual behavior、複数正本、Issue・PRとの照合結果。未照合なら未確認 |
| 追加確認・要合意 | 残る参照対象、採否判断が必要な論点、後続作業と停止条件 |

根拠へのリンクを必要な範囲で残し、今回取得していない資料を確認済みと書かない。長期的な合意や進捗の反映先は既存のOwner Document・Issue・PR規約に従います。

## 完了条件

- 対象Taskに必要な正本の所有先・参照経路が示され、判断に必要な本文を実際に取得したか、取得できなかった範囲が明示されている。
- 設計の意図、実装の実態、Issue・PRのTask情報と、未確認の項目を混同していない。
- 不整合や重要な未合意判断を独断で修正せず、後続作業へ必要な根拠と不足情報を渡している。
- Context map・他Skillの責務や操作権限を変更せず、読み取り依頼のみからGitHub writeを行っていない。
