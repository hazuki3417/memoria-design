# ブランチ運用規約

## 目的

Memoriaでは、個人開発・小規模プロダクトに適した簡易Git Flowを採用します。4リポジトリは独立して管理しますが、ブランチの意味、PRの向き、リリース判断を統一します。

コミットメッセージは[コミットメッセージ規約](./commit-message)、正式リリースの番号とタグは[バージョニング規約](./versioning)を正本とします。

ステージング・テスト専用ブランチは設けません。環境を追加する必要が生じた場合は、ブランチではなくGitHub Environmentsやデプロイ設定による分離を検討します。

## 長期ブランチ

| ブランチ | 役割 | 直接push | 通常の変更元 |
| --- | --- | --- | --- |
| `main` | 本番リリース可能な安定版 | 禁止 | `develop`からのリリースPR |
| `develop` | 次回リリースへ向けた日常開発の統合先 | 禁止 | 作業ブランチからのPR |

`main`は本番環境そのものではなく、本番へリリース可能であり、本番へ反映されたコードを追跡する安定ブランチです。実際に本番で稼働している版は、デプロイ履歴やリリースタグで確認します。

各リポジトリの既定ブランチは`develop`とします。

## 作業ブランチ

通常の作業ブランチは、最新の`develop`から作成します。

| 接頭辞 | 用途 |
| --- | --- |
| `feature/*` | 新機能 |
| `fix/*` | 通常の不具合修正 |
| `docs/*` | ドキュメント |
| `refactor/*` | 挙動を変えない内部改善 |
| `chore/*` | 設定、依存関係、保守作業 |
| `hotfix/*` | 本番向け緊急修正 |

ブランチ名は作業内容が分かる短いkebab-caseとします。人間による手動開発とChatGPTによる支援のどちらでも同じ規則を適用し、作業者や利用ツールをブランチ名へ含めることは必須にしません。

例:

- `feature/image-search`
- `fix/upload-timeout`
- `docs/branch-strategy`
- `refactor/graphql-resolver`
- `chore/update-dependencies`
- `hotfix/authentication-failure`

Issue番号を使用する場合は`feature/123-image-search`のように接頭辞の直後へ含めます。意味のない連番、個人名だけの名前、`work`や`temp`など目的が判断できない名前は使用しません。

## 作業コミット

作業branch内のcommit数と粒度は固定しません。変更内容や利用するGitHub連携の手順に応じて複数commitを作成でき、PR作成前に一つへまとめる必要はありません。

commit数を減らすことだけを目的としたsquash、rebase、履歴の書き換えは行いません。手動で作成するcommit messageは[コミットメッセージ規約](./commit-message)に従います。

## PRの状態

PRは原則として、レビューを依頼できる通常のPRとして作成します。Draft PRを既定にしません。

- 受け入れ条件と必要な実装・設計を確認してから通常のPRを作成する
- ChatGPT経由で作成する場合も、Draftの明示的な指示がなければ通常のPRとする
- ChatGPT経由の成果物はChatGPT上でbuild・testせず、PR作成後にGitHub Actionsで検証する
- 設計相談、途中経過の共有、依存PRの待機など、未完成であることを明示する必要がある場合だけDraftを使用する
- Draftを使用する場合は、残作業、確認したい事項、Readyへ変更する条件をPR本文へ記載する
- 通常PRの作成後に新しい不足が判明した場合は、影響を明示し、必要ならDraftへ戻すか作業を分ける
- 設計更新と受け入れ条件の確認を省略せず、test・buildはGitHub Actionsの必須checkで確認する

## マージ方針

PRは原則として通常のmerge commitでマージします。これにより、作業ブランチのcommit履歴と、PR単位の統合点を維持します。

- `feature/*`などから`develop`へのPRは通常マージする
- `develop`から`main`へのリリースPRも通常マージする
- `hotfix/*`から`main`へのPRも通常マージする
- squash mergeとrebase mergeは、履歴を変更する明確な理由と人間の合意がある場合だけ使用する
- マージ済み作業ブランチはGitHubの自動削除設定、または人間の確認後に削除する
- `main`と`develop`は削除対象にしない

## 派生元ブランチの取り込み

作業中に派生元ブランチが更新された場合は、原則としてrebaseで取り込みます。

```sh
git fetch origin
git rebase origin/develop
git push --force-with-lease
```

`hotfix/*`の派生元は`main`であるため、`origin/main`へrebaseします。

- `develop`を作業ブランチへmergeすることは原則として避ける
- rebaseは本人だけが利用している作業ブランチで行う
- 他の開発者が利用している共有作業ブランチでは、履歴を書き換える前に合意する
- rebase後のpushには`--force`ではなく`--force-with-lease`を使用する
- `main`と`develop`はrebaseまたはforce pushしない
- conflictは内容を理解して解消し、解消後に必要な検証を再実行する

## 通常開発

1. 最新の`develop`から作業ブランチを作成する。
2. 人間がローカルで実装・検証するか、ChatGPTの支援で変更を作成する。ChatGPT上では成果物を検証しない。
3. 受け入れ条件と変更内容を確認し、作業ブランチから`develop`へ通常のPRを作成する。
4. GitHub Actionsの結果、差分、受け入れ条件を確認する。
5. 人間の承認後にPRをマージする。
6. マージ済みの作業ブランチを削除する。

通常の機能・修正PRを`main`へ直接作成しません。

## リリース

1. `develop`がリリース候補として検証済みであることを確認する。
2. `develop`から`main`へのリリースPRを作成する。
3. 変更内容、関連PR、互換性、migration、デプロイ、rollback方法を確認する。
4. CI成功と人間の承認後にマージする。
5. 本番デプロイの成否を確認する。
6. バージョニング規約に従い、`main`のリリースコミットへ`vMAJOR.MINOR.PATCH`形式のタグを付ける。
7. 同じタグから日本語のGitHub Releaseを作成する。

`main`へのマージと本番デプロイを自動連携する場合でも、実際の稼働版はデプロイ履歴で確認します。

## 緊急修正

本番障害など、通常の`develop`経由では間に合わない場合に限り`hotfix/*`を使用します。

1. 最新の`main`から`hotfix/*`を作成する。
2. 必要最小限の修正と検証を行う。
3. `main`へのPRを作成し、人間が承認する。
4. 本番反映後、同じ修正を`develop`へPRで同期する。
5. `main`と`develop`の両方へ反映されたことを完了条件とする。

## `master`の廃止

新たに`master`を作成しません。既存の`master`が見つかった場合は、削除前に次を行います。

1. `main`とのcommit差分を確認する。
2. `master`だけにある変更をPRで`main`へ統合する。
3. 既定ブランチ、CI、デプロイ、README、外部連携の参照を`main`へ変更する。
4. 未完了PRや必要なタグが残っていないことを確認する。
5. 人間の明示的な承認後に`master`を削除する。

履歴を失う可能性があるため、差分未確認の削除やforce pushは行いません。

## リポジトリ横断変更

複数リポジトリへ変更が必要な場合も、リポジトリごとに作業ブランチとPRを作成します。各PRに次を記載します。

- 関連する他リポジトリのPR
- 契約の所有リポジトリ
- マージ順序
- デプロイおよびmigrationの順序
- 後方互換性
- rollback方法

各リポジトリの`develop`へ互換性を保って統合し、リリース時に必要な組み合わせと順序を人間が確認します。

## 保護規則

GitHub上では、少なくとも`main`と`develop`に次の保護を設定します。

- 直接pushを禁止する
- PR経由の変更を必須にする
- 必須CIの成功を要求する
- unresolved conversationがないことを要求する
- force pushと削除を禁止する
- `main`のマージは人間の明示的な承認を必須にする

個人開発でGitHub上の独立したreview approvalを必須にできない場合でも、PR差分とCI結果を人間が確認した記録を残します。

## インフラストラクチャの追加規則

`memoria-IaC`では、`main`へのマージだけで無条件に本番適用しません。

- PRでは`cdk synth`と必要な`cdk diff`を確認する
- 本番deployは対象環境を確認し、人間が明示的に承認する
- `cdk destroy`は通常のCI・リリースフローから除外する
- stateful resourceの置換・削除にはbackup、migration、rollback計画を必要とする
