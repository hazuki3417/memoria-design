# Media Update

## 概要

登録済みMediaの編集可能な情報を更新するScreenです。

Media Browserで1件または複数のMediaを明示選択して開始し、Media Uploadと共通する編集Interactionを利用します。ただし、登録済みMediaのOriginal fileを置き換える機能ではないため、file選択、drag and drop、Upload、Upload進捗、Upload retry、画像Processing状態等のfile登録に固有な要素は提供しません。

Initial ReleaseではTag編集を対象とします。Group分類は本Screenの対象外です。Media UpdateはMedia自身の編集に責務を限定し、Media ↔ Group relationの操作はMedia Browser / Media Detailへ集約します。

## 目的

登録済みMediaについて、Media Browser上で複雑な編集UIを展開せず、1件または明示選択した複数MediaのTagをまとまった編集作業として確認・変更できるようにします。

Media UploadとMedia UpdateでTag編集のInteractionを不必要に別実装へ分岐させず、Media登録前後で共通化できる編集UI・validation・未保存状態の扱いを共有できる構造を前提とします。

## 開始点 / Scope

Media Browserの選択状態から「編集」を開始し、Userが明示選択したMediaだけを対象として本Screenへ遷移します。

query結果全件、未取得Media、同じTag filterへ一致するMedia等を暗黙に編集対象へ含めません。

Personalでは現在Personal contextで選択したMedia、Communityでは現在Community contextで選択したMediaを引き継ぎます。Screenを開いたことでApplication contextを切り替えません。

1件だけを選択して開始することも、複数件を選択して開始することもできます。

## 編集対象

Initial Releaseで編集する情報は現在scopeのTag relationです。

- Personal contextではPersonal Tagだけを扱う
- Community contextでは現在CommunityのCommunity Tagだけを扱う
- 既存Tagの付与・解除を行える
- 未登録Tag名を入力した場合の作成・付与は[Media Tag](/media/tag)のsemanticsに従う
- Tag入力を確定しただけでは保存せず、Screen内の未保存状態として保持する
- 保存前の変更はキャンセルできる

Original file、Uploader、Upload日時、Custodian、共有先、Processing状態は本Screenで変更しません。

Groupへの追加・除外は本Screenの対象外です。複数MediaへのGroup追加はMedia Browser、1 Mediaの現在のdirect Group所属の確認・修正はMedia Detailを使用します。

## Media Uploadとの関係

Media UploadとMedia Updateは、Mediaを新規登録するか既存Mediaを更新するかというライフサイクルは異なりますが、Mediaへ設定する情報を編集するCapabilityは共通です。登録・更新の違いを理由にMedia設定UIを分岐させず、同じ設定UIを両Screenから利用します。

Media Upload固有:

- file追加・削除
- file previewとfile validation
- Upload開始
- Upload進捗・成功・失敗
- Upload retry
- Media登録後のProcessing状態

Media Update固有:

- 登録済みMediaの取得
- 現在保存されているTag relationの初期表示
- 保存時の現在状態・認可の再検証
- 更新結果のMedia単位での表示

共通化対象:

- Mediaの識別に必要なpreview
- Tag入力
- 既存Tag候補
- 未保存Tagの追加・解除
- 複数Mediaへの共通Tag編集
- Media単位のTag編集
- validationと未保存変更の表示

共通化はScreen全体を同一Componentへ統合することを意味しません。file登録や既存Media取得、登録・保存結果などライフサイクル固有の処理は各Screenが担当し、その前後で利用するMedia設定UIは同一のComponent / state / pure logicを利用する構造を基本とします。UploadとUpdateのUIを意図的に似せるのではなく、設定対象と編集Capabilityが同じである結果として同じUIになります。

## 複数Mediaの編集

複数Mediaを編集する場合、選択Mediaへ共通する変更とMedia単位の変更を同じ作業内で行えるようにします。

共通編集では、明示選択したMediaへ同じTagを追加または解除できます。共通編集の結果を、各Mediaが同一のTag集合を持つよう強制する「全置換」として扱いません。Userが指定した追加・解除だけを各Mediaへ適用し、指定していない既存Tag relationは維持します。

Media単位の編集では対象Mediaの現在Tagを確認し、そのMediaだけの追加・解除を行えます。

同じTagに対して共通編集とMedia単位編集が競合する場合、保存前の最終編集状態から各Mediaへ適用する差分を明確に導出し、Userの意図しない二重適用を行いません。

## 保存

保存Actionを実行した時点で、対象Mediaごとに現在scope、Mediaの存在・可視性、Membership / role、Tag relation等を再検証します。

複数Mediaの更新は一つのUser意図として開始できますが、全Mediaを1つのatomic transactionとして扱いません。

- Mediaごとに成功・失敗を識別する
- 1件の失敗を理由に成功済みMediaをrollbackしない
- 成功したMediaは保存済み状態へ更新する
- 失敗したMediaは未保存の変更内容と失敗理由を識別できる状態で維持する
- retry可能な失敗では失敗対象だけを再試行できる
- 認可喪失やMedia利用不能等、同じ入力の再送では成立しない場合は単純retryを提示しない

未登録Tagの作成とMediaへの付与はdomain上別の結果です。Tag作成に成功してrelation追加に失敗した場合、そのMediaのTag変更を成功として表示しません。

## 状態

### Loading

編集対象Mediaと現在scopeのTag relationを取得しています。取得完了前に空の編集状態を表示して既存Tagが存在しないように見せません。

### Editing

対象Mediaと現在保存されているTagを表示し、未保存の追加・解除を編集できます。

変更がない場合は不要な保存requestを実行しません。

### Saving

保存対象と未保存変更を維持し、同じ変更を重複送信しないよう保存Actionを制御します。

### Saved

対象となった変更がすべて保存済みであることを確認できます。元のMedia Browserへ戻る導線を提供します。

### Partial failure

複数Mediaの一部だけ保存できた状態です。成功済みMediaを未保存へ戻さず、失敗Mediaと理由を識別し、可能な場合は失敗対象だけ再試行できます。

### Load failure

編集対象を取得できない場合はEditingと混同せず、再試行または元のMedia Browserへ戻れるようにします。

### Target unavailable

Screen表示中にMedia削除、共有解除、Membership喪失等で対象Mediaが現在contextから編集不能になった場合、そのMediaへの変更を成功として扱いません。

複数Mediaのうち一部だけ利用不能になった場合、他Mediaまで編集不能にはしません。

## 未保存変更とNavigation

未保存変更がある状態でScreenを離れる操作では、変更が破棄されることをUserが理解できるようにします。

保存またはキャンセル後は、可能な限り編集開始元のMedia Browser contextへ戻ります。開始元のTag filter、読み込み済みCollection、scroll位置等の復元はMedia BrowserのNavigation contractに従います。

Application contextが利用不能になった場合は、Application IAに従う安全なdestinationへ移動します。

## Responsive対応

Wide / Mediumでは複数Mediaのpreviewと編集状態を比較しながら、共通Tag編集とMedia単位編集へ到達できる構成を基本とします。

Compactでは全Mediaを同時に並べることを要求せず、現在編集しているMedia、対象件数、共通変更、保存状態を見失わないpresentationへ適応します。

viewportによって編集semanticsや保存対象を変えません。

## UI具体化

Media UploadのVisual Prototypeで検証したTag編集Interactionを基礎とし、file Uploadに関する領域を除外した構成から具体化します。

画面では少なくとも次を確認できるようにします。

- 編集対象Mediaと件数
- Mediaを識別するpreview
- 共通Tag編集
- Media単位のTag編集
- 未保存変更
- 保存Action
- 保存中状態
- 成功・部分失敗・失敗理由
- キャンセル / 元画面へ戻るAction

Original file名をMediaの主要な識別情報として新たに要求しません。Media Browser / Detailと同様、visual contentを主要な識別情報とします。

Upload用のdrop zone、file picker、file validation、Upload progress、Processing progress、Upload retry等は表示しません。

## 制約

- Media UpdateはOriginal fileの置換機能ではない
- Upload済みfileを再送しない
- Group分類を本Screenへ含めない
- Tag編集でCustodian、共有範囲、閲覧権限を変更しない
- query結果全件を暗黙の編集対象にしない
- bulk保存を全件atomic transactionとして扱わない
- UI上のAction availabilityをAPI側認可の代替にしない
- Media Uploadとの共通化を理由にUpload固有stateを本Screenへ持ち込まない

## 後続設計

次はVisual PrototypeでMedia Uploadとの共通Component境界、複数Media編集時の共通Tag操作と個別Tag操作のpresentation、部分失敗時の表示を検証します。

Group操作は本Screenへ追加せず、Media Browser / Media DetailのGroup分類Interactionを正本とします。
