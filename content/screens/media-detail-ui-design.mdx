# Media Detail：UI Design

## 概要・適用範囲

[Media Browser / Detail画面仕様](/screens/media-browser-detail)で定める情報・操作・状態・権限・結果に対して、Media Detailの既存UIおよびVisual Prototypeから得られた具体的な表示・操作条件を整理します。採用したMedia DetailのUI構成と、リファクタリングで維持する表示・操作を扱います。

画面の業務上の意味は[Media Browser / Detail](/screens/media-browser-detail)、Domain・共有権限は対応するDomain設計、共通ModalのFocusや閉じ方は[Overlay Pattern](/design-system/patterns/overlay-temporary-surface)が所有します。**本書はComponent分割やProp構造を規範化しません。** 実装内だけで確認されていた数値・見た目は、合意済みの画面仕様と衝突しない限り、リファクタリング前後で維持する現行UIの比較基準として記録します。未接続のMockを製品仕様へ昇格させません。

## UI構成・情報の優先順位

### ViewerとDialogの構成

- Media DetailはMedia BrowserとGroup Browserの双方から開く共通のフルスクリーンDialogを基本とし、選択中Media、順序付きMedia Collection、Context（Personal / Community）を利用します。呼び出し元の選択中Group、検索条件、スクロール、Pane幅等はDetailの開閉によって初期化しません。
- 画像を主領域に配置し、Mediaのアスペクト比を保ちながら利用可能な領域へ表示します。ViewerのHeader / Footer、Info Panel、各種編集DialogおよびModalの上下関係は既存Media Browserを回帰比較基準とします。Fullscreen ViewerはMantine標準Portalで描画し、Application Shell固有のPortal targetを要求しません。透過背景・FullscreenとNested Modalの重なり順はOverlay側の責務として保持します。
- 選択Mediaの前後移動は利用元Collectionの順序に従い、前後に対象がない方向の操作を提供しません。取得済み範囲外へ移動する場合は[画面仕様](/screens/media-browser-detail)に定める追加取得に従います。移動時はViewportを初期化し、方向を示すtransitionを維持します。
- Mediaの画像が表示できない場合もViewer全体が消えず、プレビュー失敗の代替表示と操作への到達性を維持します。縦長／横長、画像番号、Compactの配置差分は検証対象です。
- Media Detailが閉じても呼び出し元に戻れます。削除確認など別のDialogはViewerの上に重ねて扱い、確認をキャンセルした場合はDetailを維持します。Dialogのタイトル、入力内容、Actionが閉じる途中で別の操作へ入れ替わる表示は許容しません。

### 画像操作とZoom

- Wide / Mediumでは前後移動、Zoom In / Out、100% Reset、回転、情報Panelの開閉を提供します。ViewerのIcon-only操作には識別できるAccessible Nameを付与します。Compactは主要な閲覧・前後移動・終了・情報確認とProduct Actionを優先し、精密なZoom／回転UIは必須としません。
- Zoomの範囲は**50〜300%**です。割合（%）を表示し、候補選択・数値入力・段階操作で設定可能とします。入力途中の空文字、範囲外入力、確定操作、外側へのFocus移動と表示の同期は挙動を区別して検証します。入力を受け取るUIと実際の画像変形の責務は混同しません。
- 回転・Zoom変更と選択Mediaの変更を区別し、Mediaの前後移動で適切にViewportをリセットします。回転リセット時の不要な逆方向アニメーションは発生させません。既存のslide / fade、余白と操作位置を、表示領域別に比較します。

### Info Panelの視覚構成

- Wide等ではViewer側面に情報Panelを配置し、Compactでは画像の下側へ展開する構成です。既存UIの横幅**340px**、Compactの縦方向展開、**0.3秒**のtransition、スクロール、Panel境界と余白はリファクタリング時の比較対象です。ユーザー設定に基づく初期開閉、画面幅変更後の維持条件は[画面仕様](/screens/media-browser-detail#ui具体化)に従います。
- 表示順序は **基本情報とOriginal Download → Groups → Tags → 共有先Community（Personalの場合）／管理情報（Communityの場合）→ 独立したMedia削除Action** とします。情報が増えてもPanel本文がスクロール可能で、Media削除Actionは下部の独立したDanger Actionとして維持します。
- 基本情報はファイルサイズ、画像サイズ、アップロード日時、Uploaderを順に示します。旧Prototypeでこの情報に固定サンプル値を使用していたことは実データ契約を意味しません。実際のMediaデータへの接続はAPI / 画面仕様に従います。
- Original DownloadはViewer FooterのPrimary Actionではなく、ファイル情報に近接するlabel付きの控えめなActionです。可能・権限不足・処理中の3状態を区別し、利用できない場合は同じ位置で無効化と理由説明を提示します。理由はButtonからアクセシブルに関連付け、hoverだけに依存させません。
- Groups / Tags / Communityは視覚的に同じSection階層を持ち、必要な区切り線、Section内のPadding、見出しと件数、操作入口と値の一覧を表示します。Section間のDividerと、同一Section内の区切り線を区別します。ライト／ダークテーマに適応し、固定色に依存しません。
- Groups / Tagsの値は長い名称でも折り返し、Badgeの表現は既存Groupが `outline`、Tagが `light` の比較基準です。分類Sectionの下にある区切り線は親のInfo Panelが表示します。

## 表示状態と表現

利用可能なDownload、権限不足、Original処理中や画像表示失敗は「UI構成・情報の優先順位」のViewerとInfo Panelで定める表示に従います。Groups / Tags / Communityの正常な0件・初期件数・超過件数や展開状態は以下の節で具体化します。Loading・Error・保存結果不明等の成立条件は[画面仕様](/screens/media-browser-detail)を正本とし、表示条件を推測して追加しません。

### Groups / Tags / Communityの展開

- GroupsとTagsは**6件まで**、Personalの共有先Communityは**3件まで**を初期表示とします。0件ではGroup / Tagを「未設定」、共有先を「未共有」と表示し、利用可能な編集・共有操作は維持します。
- 超過分だけをCollapseで開閉し、閉じた状態では「ほかN件を表示」、展開時には「折りたたむ」を中央付近の操作として表示します。Chevron方向と `aria-expanded` を状態に一致させ、既存の**200ms** transitionを維持します。通常件数では展開Actionを表示しません。
- 長いCommunity名がある場合も、対象Communityの「共有解除」Actionが狭められず、両方を識別・操作できます。Communityの行高は既存の**32px以上**を比較基準とし、必要な余白を設けます。Communityごとの共有解除は展開中も維持します。
- Personalでは共有先の各Community行に個別の「共有解除」を提供します。共有ActionはSection見出し側、共有解除Actionは各行に置き、隣接による誤操作を避けるDividerと余白を設けます。Community contextではPersonal向け共有Actionではなく「管理」「Community管理」を表示します。

## Interaction・Feedback

### 編集・共有・削除Dialog

- Groups / Tags編集は、それぞれ選択中の集合をDraftとして表示し、追加／除外を行い、保存確定またはキャンセルします。呼び出し元で保持したDraftと保存済み値を混同せず、キャンセルで保存しません。再度開く場合の選択値は現在の保存済み状態に一致させます。
- 共有先Communityの追加は未共有候補から**1 Community**を選択します。候補なし、未選択、選択済みの各状態を区別し、未選択では確定できません。複数Communityを1操作で編集するGroupsと同種のMultiSelectへ置換しません。
- 共有解除は対象Community名を明示する確認Dialogから行い、そのCommunityの共有関係のみを解除します。破壊的な確定Actionは危険操作として明瞭に区別し、キャンセルでは変更しません。共有先を削除するとMedia本体や他のCommunityの関係が消えるという説明にはしません。
- 単一Media削除は「Mediaを削除」とし、ファイル名・ラベル等の入力を要求せず、復元できないことを伝えて明示的に確認します。キャンセルではMediaを変更せず、確定時には呼び出し元の削除処理へ委譲します。
- これらのDialogは既存のタイトル、説明、入力候補、操作順序、Keyboard / Focus、Responsive、Viewerとの重なり順を維持します。実際の保存完了通知や結果不明時の復旧は、Mock上の操作結果ではなく[画面仕様](/screens/media-browser-detail)とBackend契約に従います。

## Responsive・入力方式

ViewerのWide / Medium / Compactでの操作Capabilityと表示領域の使い分け、Info Panelの横方向／縦方向の展開、各DialogのKeyboard / Focus・Modal重なり順は、上記「UI構成・情報の優先順位」「Interaction・Feedback」の各節を適用します。幅の区分による維持対象のUser Goalと操作条件は[画面仕様](/screens/media-browser-detail#responsive対応)を正本とします。

## 設計判断・制約

### 表示・操作の依存境界

UIのDraft、Viewerの選択、画像操作、情報Sectionの展開、共有・分類の実Mutationは独立した責務として整理できます。ただし、`detailValues`、`setDetail`、`onClose` 等の実装API名やHook所有関係をDesignの永続的なインターフェース仕様にはしません。React内部責務を分離する際も、上記の見た目、Action、状態、Responsiveを失わせないことが前提です。

## Fullscreen Viewer HostとResponsive Layoutの責務分離（2026-10-29、A案合意）

### 採用方針

Media Detail本体は標準Task Modalの`Body / Divider / Footer`構成に置き換えず、画像閲覧を主目的とする**専用Fullscreen Viewer**を維持する。内部では**Fullscreen Viewer Host**（Overlayの表示・Portal・Focus・Dismiss）と**Responsive Layout**（PreviewとInfo Panelの配置・領域配分）を独立した責務として設計する。共通Modalのために既存の画像操作、情報、状態、表示領域、Layoutを簡略化しない。編集・共有・削除確認は共通Task ModalをViewerより上位に表示する。

### ViewportごとのLayout Contract

- **Wide / Medium**: Viewerを主領域とし、Info Panelは開いている場合に右側へ並べる。既存のPanel幅340px、開閉アニメーション0.3秒、境界線、画像のアスペクト比維持、Header / Footerの操作位置を回帰比較基準とする。Panelを閉じたときは画像領域が残り幅を利用できる。
- **Compact**: Previewの下へInfo Panelを縦方向に展開する。画像閲覧・前後移動・終了・情報確認を維持し、Panelの内部スクロールと操作可能性を保つ。既存のBottom領域、開閉状態および詳細操作の優先順位を維持する。Panelの高さ制約・スクロール所有の詳細は実装前にViewportとlong contentで検証する。
- すべてのサイズで選択Mediaの切替えによって**Fullscreen Hostを不必要に再生成しない**。URLで選択されたMedia Identityと、Preview/InfoPanelの個別表示状態を整合させる。Zoom・回転・前後移動アニメーションの既存仕様とFocus / Scroll Contractを維持する。

### 非同期表示と操作の責務

- **Controller**: URL / History、選択Media ID、ID順序Snapshot、詳細取得、署名URL、画像・Processing状態、PollingとRetryを所有する。Viewer HostやLayoutがGraphQL・Routerを直接操作する形にはしない。
- **Viewer Host**: 一つのFullscreen Overlayに責任を持ち、Modal Portal、Focus、Escape / close、Overlay上への編集・確認Modalの重なり順を保証する。
- **Responsive Layout**: PreviewとInfo Panelの位置・領域を決める。Mediaの取得成功/失敗等のビジネス状態を推測せず、Controller/Presenterから渡されたViewModelを各表示領域へ配置する。
- **Preview**: 初回詳細取得中、Processing、画像読込中、表示可能、処理失敗、画像取得/Decode失敗、Polling停止、対象不在等を独立したPreview状態として描画する。画像取得失敗は手動再試行のみ。詳細未取得時に一覧サムネイルを「詳細画像の取得成功」と誤認させない。
- **Info Panel**: 初回詳細取得中はSkeleton等で未確定情報を示し、PreviewがLoading中でも独立して取得済み情報を表示する。Group / Tag / Communityの「未設定」「未共有」は**0件が確定した場合のみ**使用し、Loading / ErrorをEmptyと混同しない。既存のMetadata / Groups / Tags / Community / Deleteの配置と個別の閲覧・編集Actionを保持する。
- 前後移動時は選択IDに属するPreview/Infoの内容を一致させ、前のMediaの古い情報やErrorを次のMediaの情報として残さない。Previewだけの失敗で利用可能なInfo/編集Actionを不必要に失わせず、詳細の必須情報が失敗した場合は未確認のActionを有効化しない。

### 未確定事項と実装Gate

この合意は**Host / Layout分離という構造の採用**であり、DOM構造や新Component名・props形状・Breakpoint・Compact Panelの最大高さ・Skeletonの具体表示などを確定するものではない。これらは既存のVisual/Behavioral/Responsive contractに照らして詳細設計・検証する。

既存の媒体取得・URL/History・Processing Polling設計は[Media Browser / Detail](/screens/media-browser-detail)、[Media Detailテスト設計](/system/web/media-detail-test-design)およびWebの`docs/media-detail-controller-design.md`（実装設計ブランチ）に従う。既存のMediaDetailViewer/Preview/InfoPanelを比較基準とし、Component化前後でWide / Medium / Compact、Panel開閉、画像の前後移動、Zoom/回転、Nested Modal、Loading/Error、Keyboard/Focus、内部スクロールの回帰を検証する。追加の仕様判断はユーザー合意後に正本へ反映する。

### 標準Portal移行（2026-10-29 合意）

Media Detail用の専用 `#application-modal-root` は廃止し、Mantineの標準Portalへ統一します。専用のrootなしでもFullscreenと透明背景はMantineが提供するModal props / stylesで表現できます。既存の閲覧レイアウト・情報Panel・開閉・Nested Overlay・Focus / Keyboardの契約は不変とし、VRTおよびInteractionによって検証します。固有のPortal targetを再導入する場合は必要な理由と検証結果を明示し、再合意します。
