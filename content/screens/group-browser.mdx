# Group一覧・詳細

## 概要

PersonalまたはCommunity contextで、現在scopeのMedia Groupを検索・閲覧し、Groupを手がかりに目的のMediaを素早く発見し、必要に応じてGroupの分類関係を確認する画面です。

> 実装状況: 既存のmemoria-webにはGroup名検索、flatなGroup一覧、選択したGroupのMedia表示があります。本仕様で定義するPersonal / Community scope、DAG relation、Community roleによる管理権限には差分があります。

## 目的

Userがfolder treeやDAG全体を理解することを要求されず、現在scopeのGroupを名前から発見し、Groupを選択すると同じ画面の中で分類されたMediaへ直接到達でき、必要に応じて関連Groupも確認できるようにします。Group詳細画面への段階的な遷移を主要導線にしません。

PersonalとCommunityで同じGroup interaction modelを利用し、Application contextによって対象scopeと管理権限だけを切り替えます。

## 表示情報

### Group discovery

現在scopeに存在するGroupをflatな一覧として提示します。

Group BrowserはApplication Navigationによって現在のページがGroupsであることを識別できるため、Group discovery領域の先頭でページタイトルとして「Groups」や「グループ」を反復表示しません。

検索Inputと作成Actionのように同じ行で一つの操作領域を構成するinput / interaction controlは、control heightを揃えて視覚的な一体感を保ちます。同一対象への関連する編集Actionは、Userが別々の概念として選択する必要がない限り入口を不必要に分割せず、まとまりのある編集導線として提示します。ページタイトルはcontent領域へ原則として重複表示せず、設定画面のように多数の項目を構造化する場合や、情報を独立したblockとして区切るため見出し自体が情報構造を担う場合には必要に応じて表示します。

Group discovery itemではGroup名を必須のidentityとして表示し、視覚的な手掛かりとしてそのGroupへ直接分類されているMediaのthumbnail previewを表示します。previewにはdirect Mediaを作成日時の新しい順に最大4件使用し、descendant GroupのMediaは含めません。これはGroup自身へ直接分類されているMediaのpreviewであり、Group選択後に表示する「Group自身 + すべてのdescendants」のaggregate Media Collectionのpreviewとは扱いません。

previewは2 x 2の4つのPreview Cellを基本単位とします。各Cellはdirect Mediaのthumbnailを表示するMedia Cell、またはMediaではなくGroupそのものを表すGroup Cellとして扱います。direct Mediaが4件未満の場合は不足分をGroup Cellとし、Mediaが存在しないことを示すplaceholderとしては扱いません。これによりdirect Mediaが0件でもGroup item自体のvisual identityを成立させ、descendant Group由来のMediaだけがaggregate Media Collectionに存在する場合にも、Group discoveryのpreviewと選択後Collectionを同一のMedia集合であるかのように表現しません。

direct Mediaが4件までは作成日時の新しい順にMedia Cellとして表示し、5件以上存在する場合も具体的な残件数は表示せず、4番目のMedia Cellへ非数値のcontinuation cueを重ねてpreviewがさらに存在することだけを示します。このcueはaggregate Media総件数を表しません。 Group CellはGroupが存在することを示す装飾表現とし、内部ではaggregate Mediaのthumbnailをvisual素材として最大3件重ねて表示できます。Group Cell内部のthumbnail自体には、そのCellへMediaが分類されていることを示すデータ上の意味を持たせません。複数のGroup Cellが存在する場合はGroup Cellの出現順にaggregate Media previewを3件ずつ順番に消費し、1つ目は1〜3件目、2つ目は4〜6件目、以降も同様に割り当てます。Media Cellですでに使用したdirect Mediaとの重複を除外するための特別な処理は行いません。thumbnail画像だけを取得・表示できなかった場合も、その補助情報の失敗によってGroup item全体を取得失敗として扱わず、該当CellをGroup Cell相当の表示へfallbackしてGroup discoveryを継続します。Media Cell、Group CellのどちらもMediaへのclick targetやMedia Detailを開く操作対象にはせず、Group discovery item全体としてGroupを選択するための補助的なvisual informationとします。

**Mediaが関連付いていないGroupの表示**: Group自身のdirect Mediaが0件で、descendant Groupを含むaggregate Mediaも0件であることが確定している場合、Group discovery itemのpreviewは、背景色だけの空Cellや輪郭だけの枠を並べるのではなく、Mediaを持たないGroupだと利用者が認識できる専用の視覚表現とします。Group名・Group item全体の選択操作・2 x 2のpreview領域という基本構成は維持します。具体的な図像、配置、色、文字の有無はVisual Reviewで確定し、Storybook MDXに記録します。

**direct Mediaが0件でもaggregate Mediaがある場合**: このGroup自身にはdirect Mediaがないことと、子孫Group経由のMediaがあることを混同しません。従来のGroup Cellにaggregate Media画像を装飾素材として用いることは可能ですが、direct Mediaのthumbnailであるかのように表現しません。上記の「Mediaが関連付いていないGroup」の専用表現は、aggregate Mediaも0件と確定した場合に適用します。

**未取得・画像取得失敗との区別**: Groupのdirect / aggregate Mediaが未取得の状態、読み込み中、取得失敗、Mediaは存在するがthumbnailのみ取得できない状態を、正常な0件と推定しません。件数や関連有無を判定するデータが不足する場合は、一時表示・fallbackでGroup item自体を維持しますが、「Mediaがない」と断定する専用表現には切り替えません。いずれの状態でも補助的previewの欠落だけでGroup名やGroup選択の機能を失わせません。

Group itemにはMedia件数、relation情報、Group管理Actionを標準表示しません。現在選択中のGroupが検索結果内に存在する場合はselected stateを視覚的に表現しますが、Group item自体を選択状態のSource of Truthにはしません。Group discoveryの通常一覧および検索結果に件数は表示しません。取得済みGroup数・検索条件に一致するGroup総数・読み込み進捗数値のいずれも一覧操作パネルには設けません。

一覧はDAG上のroot Groupだけに限定しません。所属先Groupの有無にかかわらず、現在scopeに存在するすべてのGroupを検索・発見できるようにします。

検索していない通常状態ではGroup名順を標準の並び順とします。

### 選択したGroup

Groupを選択した状態では、Mediaを主要contentとして扱います。HeaderではGroup identityと操作領域を分け、Group名、および現在利用可能なGroup管理Actionと選択を閉じるActionへ到達できるようにします。Personal / Communityで同じ基本layoutを使用し、contextごとに別のHeader構造を作りません。権限がないGroup管理Actionは非表示とし、非表示Actionのための透明なplaceholderや空き領域を予約しません。表示対象Actionが0件から複数件まで変化しても成立するlayoutとします。

少なくとも次を確認できるようにします。

- Group名
- このGroupが所属するGroup
- このGroupに所属するGroup
- このGroup自身およびすべてのdescendant Groupへ分類されているMediaを重複排除したCollection

Groupには一意なrootやpathが存在しないため、folder breadcrumbを現在位置やGroup identityとして表示することを前提にしません。

Group間relationのDAG構造例は[Media Group - Group同士の関係](/media/group#group同士の関係)を参照します。このScreenではDAG全体をgraphとして表示することを要求せず、選択Groupを中心に直接relationを確認します。

### Group metadata

選択中Groupのrelation情報はMediaより低い優先度の補助情報として扱い、このGroupのdirect parentsとdirect childrenだけを確認できるようにします。descendant全体はaggregate Media Collectionの成立条件には利用しますが、metadataとして再帰的なDAGを展開しません。

metadataに表示するparent / child GroupはGroup Navigationの入口にせず、選択対象を切り替えるclickableなGroup一覧として扱いません。別Groupを探索・選択する責務はGroup discoveryが担います。relation metadataは現在Groupの構造を理解するための情報に限定し、DAG traversal UIへ発展させません。

Visual presentationでは、この補助情報の見出しを「このGroupとの関係」とし、選択中Groupを基準とする情報であることを明示します。relation方向のラベルは、直訳した日本語がかえって意味を曖昧にすることを避けるため `Parents` / `Children` を使用します。UI copyは日本語への機械的な統一を目的とせず、日本語話者にとって一般的で理解しやすい英単語・カタカナ語の方が概念を簡潔かつ正確に伝えられる場合は、それらを使用できます。

relation metadata自体をinline編集UIにはしません。relationを変更する場合はHeaderのRelations Actionからrelation編集Dialogへ進み、閲覧と編集の責務を分離します。

direct parents / direct childrenはそれぞれ最大10件のため、metadata表示ではPaginationや追加読み込みを提供せず全件を確認できるようにします。0件の場合は正常なEmpty stateとして該当relationがないことを明示します。

MediaがRelay Connectionによる無限ローディングであるため、metadataをMedia Collectionの物理的な末尾へ配置することは要求しません。Mediaより低い情報優先度を維持したうえで、固定領域、折りたたみ等の具体的presentationはUI具体化・Visual Reviewで決定します。

## 操作

### Groupを検索する

Userは現在scopeのGroupをGroup名のfree textで検索できます。

検索はGroup DAGの特定階層やrootだけを対象にせず、現在scopeのGroup全体を対象とします。検索結果からGroupを選択すると、同じGroups画面でそのGroupのMediaを確認できます。

Group検索状態と現在のGroup選択状態は独立して扱います。Group Aを選択した後に検索条件を変更し、Group Aが現在の検索結果から外れても、選択中GroupとそのMedia表示を解除しません。検索結果から別のGroup Bを選択した時点で選択対象をBへ切り替え、検索を解除してAが再び一覧へ現れた場合はAが選択中であればその状態を通常どおり表現します。

Group検索の取得・追加取得に失敗しても、既に成立している選択中GroupとそのMedia Collectionを破棄しません。検索領域で失敗を示して再試行できるようにします。Group選択を解除するのは、明示的に選択を閉じた場合、別Groupを選択した場合、選択中Groupの削除・利用不能化等、選択状態そのものに作用する出来事を基本とします。

検索のmatching algorithmやAPI pagination方式等の実装契約は本Screen Specificationでは固定しません。

### Groupを選択する

一覧または検索結果からGroupを選択すると、同じGroups画面内でそのGroupのMediaを優先して確認でき、必要に応じて所属関係も確認できます。

Group選択はGroups画面内でMediaの探索対象を切り替える操作として扱います。選択したGroup自身への直接分類に加え、すべてのdescendant Groupへ分類されているMediaを再帰的に含め、複数のGroupやDAG上の複数経路から到達する同一Mediaは1件として重複排除します。Mediaは標準のMedia Browserと同様に作成日時の降順で提示します。選択状態は画面内で保持し、Groupを切り替えるたびにURLやbrowser historyを更新しません。

選択GroupのMedia Collectionには追加の検索・Filterを提供しません。Groupを選択すること自体をMedia集合を発見・絞り込む主要なInteractionとし、選択後に恒常的な追加検索・Filterが必要になる場合は、機能を重ねて補う前にGroup構造・分類方法・Group BrowserのDiscovery UXが適切かを見直します。Mediaそのものを検索・Tag等で絞り込んで発見する責務はMedia Browserが担います。

Media CollectionはRelay Connectionによる無限ローディングとし、選択中GroupのHeaderやMedia表示領域にaggregate Mediaの総件数・取得済み件数を表示しません。無限ローディングのLoading / Error / Retry / Empty / 終端の状態は、件数を表示せずに区別します。

### Groupを作成する

Personal contextではUser本人がGroupを作成できます。

Community contextではAdministratorだけがGroupを作成できます。Memberには分類体系を変更する作成Actionを提供しません。

Group作成Dialogでは必須の名称に加え、任意でParents / Childrenのrelationを指定できます。MediaやParent / ChildがないGroupも正常に作成できます。作成をキャンセルした場合は入力内容を破棄し、作成処理を実行しません。

**G-12：Group作成のAtomic保存**: 作成ActionではGroup名および任意のdirect Parents / Childrenの希望状態をまとめてBackendへ送り、Group本体の作成と指定したrelationの登録を**1つの業務操作・同一Transaction**として扱います。Backendは作成権限、名前の制約・重複、同一scope、対象Group存在、DAG制約等を検証し、希望する状態すべてを登録できる場合のみCommitします。関係の1件でも登録できない場合はGroup本体の作成も含めてRollbackし、途中まで作成されたGroupやrelationを残しません。Parent / Child未指定の場合は名前だけでGroupを作成できます。作成・relation登録は操作ごとに段階的に成功通知せず、**作成結果が確定した時点で成功または失敗を一貫してFeedback**します。確定した失敗では作成Dialogと入力Draftを維持し、原因を理解して修正・再実行できるようにします。通信断・Timeout等で成否を確定できない場合は、単純な失敗と断定せず、重複作成を防ぐためServerの確定状態を確認してから復旧を判断します。Group作成の冪等性や不確定結果の照会方式はAPI実装設計で定めます。

### Groupを編集する

Personal contextではUser本人、Community contextではAdministratorが、選択中Groupの名前とGroup間relationを1つの編集Dialogで変更できます。名前変更とrelation管理は同じGroup自身に対する編集として扱い、別々のDialogや編集画面へ分割しません。

編集DialogではGroup名と、選択中Groupを基準とするParents / Childrenの双方を扱います。Group名はDialog上部で編集し、relationは方向の異なる情報としてParents / Childrenを区別して表示します。WideではParents / Childrenを左右に配置でき、Compact / Mediumでは同じ配置を強制しません。

Dialog内の名前変更、relationの追加・解除は同じDraftとして保持し、個々の変更を即時反映せず、保存Actionでまとめて反映します。Group discovery側の検索条件変更やGroup一覧の追加読み込みによって、編集Dialogで保持しているDraftを失いません。保存せず編集Dialogを終了した場合は、未保存のDraftを破棄し、保存Mutationを実行しません。**現段階では未保存変更の有無にかかわらず破棄確認を挟みません。** キャンセルと、共通Overlayの振る舞いによりDialogが終了する操作は、終了時の未保存Draftの扱いを同じにし、Group固有のEscape / outside click例外を追加しません。Dialogの終了を許可する入力手段やFocus・Overlay動作は共通Patternと既存のVisual / Behavioral Contractに従います。保存処理中の重複操作やDraft変更は「操作処理中・競合」の制約に従います。

この破棄確認省略は、Frontendのテスト設計・実装を進めるために現時点の状態分岐を限定する**暫定判断**です。破棄確認を要する利用者負担の閾値、明示Cancelと偶発的Dismissの扱い、確認を追加する判断基準が十分に定義されたわけではありません。利用実態・誤操作・再入力負担等の根拠と横断Patternとの整合性を別Issueで検討し、必要に応じて本仕様を再評価します。

**G-15の取得前提（現在のInitial Release方針）**: 編集開始前に、対象Groupの確定済みdirect Parents / Childrenと、scope内のrelation候補一覧および各方向の追加可否を取得します。候補APIのページが複数になる場合も編集開始前に必要なページをすべて取得し、取得成功を編集開始の条件とします。候補の初回・途中ページ取得が失敗した場合は編集Dialogを開始せず、選択中Groupの閲覧状態を維持したまま、編集を開始できない理由と再試行Actionを提示します。Loading / Errorは「候補0件」と区別します。編集開始後の候補検索、選択・解除は取得済み情報を用いてFrontend内で行い、検索・選択のたびにBackendへアクセスしません。保存するまでGroup relationは変更されません。候補情報の鮮度は保存時にBackendで再検証します。このInitial Release方針では編集開始後の候補追加取得は提供しません。作成前のGroupにはIDがないため、作成Dialogにおける候補可否の事前判定は別途API契約・設計上の検討対象とします。

relation先は同一scopeのGroupから名前で検索できます。検索していない状態でもscope内Groupを通常の名前順で発見できるようにします。検索結果には既にrelationがあるGroupも表示し、現在のrelation状態を識別できるようにします。Group自体を候補から隠すことで制約を表現せず、parent / childそれぞれの追加Actionについて利用可否を示します。自己参照、既存relation、循環、深度、直接relation数上限等により追加できない方向はActionをdisabledにし、touch / keyboardを含めて理由を確認できるようにします。同じGroupを同一Draft内でParentとChildの両方には指定できず、反対方向ですでに指定されている候補はdisabledとして残し、その理由を候補内で示します。relation selectorでは選択済みGroupを個別に解除できる一方、誤操作による一括解除を避けるため全件を一度にクリアするActionは提供しません。

Parents / Childrenはそれぞれ直接10件までとし、relation表示領域では全件を確認できるようにします。選択済みGroupの表示順は追加した順や検索による一時的な候補順ではなく、共通UIルールに従ってTagとして表示するGroup名文字列の昇順に正規化します。DetailのParents / Childrenを複数Tagで表示する場合も同じ順序を適用します。 relation selectorは未選択時から、Pillをおおむね4行見渡せる固定表示領域を確保し、選択数の増減によって周辺レイアウトを変動させません。4行は表示領域の高さを定めるための目安であり、Group件数やGroup名の長さから高さを算出しません。選択済みGroupが表示領域に収まらない場合も、selector内部のスクロール等により全件を確認・解除できるようにします。relation候補は編集Dialogを開く前に全ページの取得を完了するため、Dialog内ではFrontendに取得済みの候補を名前で絞り込み、選択・解除できます。Dialog内の検索・選択でBackendへの取得やMutationを実行せず、候補の追加読み込み状態も設けません。候補の事前取得に失敗した場合は編集開始前の画面で理由と再試行を示し、Groupの閲覧状態を維持します。

**G-16の保存契約**: 保存Actionでは、Frontendは選択中Groupの希望するGroup名・direct Parent Group ID集合・direct Child Group ID集合という**最終状態**をBackendへ送ります。FrontendはrelationのADD / REMOVE Command列を構築してAPIへ渡さず、Backendが最新の保存済み状態との差分を算出します。関係の選択・解除中にMutationは送信しません。保存時はBackendでscope・存在・権限・DAG制約と同時編集による競合を再検証し、他Userの変更を無条件に黙って上書きしません。競合検知の具体的なAPI方式（version等）はBackend実装設計で定めます。

Group編集の保存は**Atomic Update（全件成功または全件失敗）**とし、Group名とdirect Parent / Childの希望状態を同一保存単位として扱います。希望状態全体が成立する場合だけ確定し、1件でも成立しない場合は今回の変更全体を確定しません。例として保存済みParentが{1}で希望が{1,2,3}の場合、2を追加できても3を追加できなければ保存失敗となり、Parentは{1}のままです。成立しなかった対象・理由を伝え、Dialogと入力Draftを維持して利用者が修正・再保存できるようにします。通信断などで成否を確認できない場合は失敗・未保存と断定せず、Serverの確定状態を確認してから再試行・表示を判断します。

保存成功時、renameはGroup identity、Media relation、他Groupとの関係を維持したまま名称へ反映します。relation変更によってdescendant集合が変化し得る場合は、最新relationに基づくaggregate Media CollectionをBackendから再取得します。

relation変更が成立して選択中Groupのdescendant集合が変化し得る場合、現在表示しているaggregate Media Collectionとの差分をClient側で再構築しません。成立した最新relationを基準とする新しいCollectionとしてServerから取得し直し、Media一覧のスクロール位置は先頭へリセットします。

Groupにparent / child relationが0件の状態も正常として扱います。

編集Dialogの責務はGroupの変更Draftを編集し、保存または破棄することです。通常の確定Actionは保存とキャンセルに限定します。Group削除は編集内容の保存Actionとして扱わず、編集Dialogには別の削除Taskへ進む入口だけを提示します。編集Dialogでは明示的なキャンセルActionへ終了操作を集約し、同じ意味の右上close Actionを重複して提示しません。削除へ進む場合は現在の編集Draftを保持したまま削除Confirmation Dialogを上位に提示し、削除をキャンセルした場合は保持した編集Dialogへ戻ります。

### Groupを削除する

Personal contextではUser本人、Community contextではAdministratorがGroupを削除できます。

削除Confirmation DialogはGroup削除の影響を理解し、実行または中止する判断だけを責務とします。編集用Fieldや保存Actionは配置しません。対象Group名を示し、対象GroupによるMedia分類とparent / child relationが削除される一方、Media本体と他Group本体は削除されないことを理解できるようにします。Group名の再入力は要求しません。

削除によってDAGが途切れても、Systemは他Group間のrelationを自動生成して再接続しません。削除結果が確定するまでは重複実行を防ぎます。成功したGroupが現在選択中であれば選択を解除し、aggregate Media Collectionを破棄してGroups画面の未選択状態へ戻り、成功Feedbackを示します。失敗した場合は成立済みの選択中GroupとMedia表示を不必要に破棄せず、失敗理由に応じたFeedbackを示します。

**G-17：削除結果と一覧取得を独立して扱う**: Group削除Mutationの確定結果と、その後のGroup一覧の再取得結果は別の処理・別の状態として扱います。削除が確定成功した場合は削除成功として選択状態を整理し成功Feedbackを示します。後続の一覧再取得が失敗しても、削除成功を取り消したり削除失敗として通知したりしません。一覧取得の失敗は通常のGroup discoveryのError / Retry規則に委ね、**「削除は成功したが一覧更新に失敗した」という組合せ専用の通知・画面状態は設けません**。削除が確定失敗した場合は削除処理の失敗として扱い、既存の選択状態・編集Draftを不必要に失わせません。通信断等で削除結果が不明な場合は成功・失敗を断定せず、Server側の確定状態を確認して復旧を判断します。削除確定前は同一操作の重複実行やConfirmation Dialogの終了によって結果と画面状態の対応が曖昧になることを防ぎます。

削除成功Feedbackは削除処理の責務、一覧Errorと再試行はGroup discoveryの責務です。作成・編集を含む他のMutationでも、Mutationが確定成功した後のQuery失敗をMutation失敗へ変換しないことを基本とし、処理間の依存や例外がある場合は該当画面仕様で明示します。

**表示同期の実装方式は操作結果から独立**: 削除Mutationの成功後に一覧表示を最新化する方法として、Apollo Clientのnormalized cache更新、Queryの再取得、cache invalidation等を選択できます。キャッシュ更新による再描画を用いる場合も、一覧表示の同期が削除Mutationの成功条件になるわけではありません。具体的なCache Policy、Connectionのedge除去・件数管理、複数scope・検索・Paginationへの反映、一時的なstale表示、必要な再取得はFrontend実装設計で判断します。**Mutation成功後のQueryを必ず実行することも、キャッシュ更新だけで一覧が正しく同期されることも、この画面仕様では仮定しません。**

### 選択中Groupの操作

選択中GroupのHeaderから、現在利用可能なGroup管理Actionとして編集と削除へ到達できるようにします。renameとGroup間relation管理は同じGroup自身に対する編集であるため入口を不必要に分割せず、Headerの三点メニューでは「編集」へ集約します。編集DialogではGroup名とParents / Childrenのrelationを扱います。削除はGroup管理の一部として編集Dialogから到達できるようにし、Headerに独立した削除Actionを重複して設けません。通常の編集操作とは区別して提示し、実行時はConfirmation Dialogで確認します。選択を閉じるActionはGroup管理権限とは独立した画面操作として常に利用でき、実行するとGroup選択を解除して未選択状態へ戻ります。Group選択はURLやbrowser historyの正本ではないため、選択を閉じてもNavigation historyを変更しません。

PersonalではUser本人にGroup管理Actionを提供し、CommunityではAdministratorに提供します。Community Member等、Group管理Capabilityを持たないUserには管理Actionをdisabled表示するのではなく非表示とします。権限による表示数の差を吸収するための透明なdummy Actionやplaceholderは使用しません。Capability自体は存在するものの現在状態・constraintによって一時的に実行できないActionの表現は、各Actionの状態設計に従います。

**テスト設計・実装のための暫定判断（G-18）**: Group構造管理の作成・編集・削除・relation変更Actionは、Personal本人またはCommunity Administratorに提供し、Community Memberには非表示とします。権限が確定していない間は、管理Actionの実行を許可しません。権限が確認できた後、管理Capabilityがあるが詳細取得・保存処理中など現在の状態によって実行できない場合は、Action固有のdisabled / Loading等の状態を使用します。権限情報の取得失敗はMemberであると確定したことを意味せず、閲覧・分類等の別Capabilityを不必要に失わせず、必要な再取得・復旧を可能にします。認可は実行時にServerでも再検証します。

これはGroup Browserのテスト可能な期待結果を確定するための**暫定的な画面固有ルール**であり、非表示とdisabledを使い分ける横断基準が確立されたことを意味しません。Media DetailのOriginal downloadは、Personal / Communityの双方でAction自体を配置し、Custody・role・処理状態等により非活性化して理由を表示する別の設計です。複数条件によるAction availability、Actionの発見性、レイアウト安定性、権限変更時の表示についての横断的な判断基準は別Issueで引き続き検討します。

### Media分類

AdministratorとMemberを含む現在scopeで分類権限を持つUserは、既存Groupを使ってMediaを分類できます。

Initial Releaseでは[Media Browser / Detail](/screens/media-browser-detail)のMedia Detailを、Mediaを既存Groupへ追加・除外する主要な入口とします。

Group Browserでは選択したGroup自身およびすべてのdescendant Groupへ分類済みのMediaを重複排除して確認し、aggregate Media Collectionのthumbnailを選択すると[Media Browser / Detail](/screens/media-browser-detail)を正本とする共通のMedia Detailを開きます。Group discovery item内のpreview thumbnailはGroup選択のための補助情報でありMedia Detailへの入口にしませんが、Group選択後のaggregate Media Collectionに表示するMedia thumbnailはMedia Detailへの明示的な入口として扱います。

Group Browserから開いたMedia Detailでも、Media Browserから開いた場合と同じMedia Detail Capability一式を提供します。利用元ScreenがGroup Browserであることを理由にProduct Actionを追加・削除せず、現在のApplication context、対象Mediaの状態・Custody、Membership / role等からAction availabilityを一貫して導出します。共有、Original download、削除、Group分類編集等、Media Detailが現在条件で提供するActionは共通仕様に従います。

Media Detail内の前後移動は、Detailを開いた時点の選択中Groupのaggregate Media Collectionを利用元Collectionとして、その作成日時降順の順序を使用します。移動先がまだ取得されていない場合もMedia Detail共通仕様に従ってRelay Connectionから必要な範囲を追加取得します。Detailを閉じた場合は同じ選択中Groupへ戻り、Group選択、取得済みaggregate Media Collection、可能な範囲のscroll位置を維持し、可能であれば起点thumbnailへfocusを戻します。Detail表示中にGroup relation変更等によってaggregate Collection自体が更新された場合は、古いCollectionを復帰の正本として固定せず、Group Browserの最新Collection状態を優先します。

一方、Mediaの複数選択やMedia集合に対するbulk Actionは提供しません。Group BrowserはMediaをGroup起点で発見・閲覧できるようにしつつ、画面自身が提供する管理操作はGroupの作成・rename・relation管理・削除等のGroup操作に限定します。Mediaを複数選択して分類・共有・削除等を行う操作は、Mediaを主体とするMedia Browserの責務とします。複数Mediaの一括分類はMedia Browserで明示選択したMedia集合から実行します。

## 状態

### Groupあり

現在scopeのGroupを発見・選択できます。Groupを選択すると、同じ画面でそのGroupのMediaを優先して確認し、relationも参照できます。

管理権限を持つUserだけがGroup構造を変更するActionを利用できます。

### Empty

現在scopeにGroupが1件も存在しないことが確定した場合、Group discoveryの一覧領域に、Media BrowserのEmpty状態と同様に**空状態を説明する表示**を設けます。単に一覧Itemや枠を表示しない状態で終わらせず、「まだGroupがありません」等の状態見出しと、Groupを作成・利用し始めるための説明を提示します。読み込み中、取得失敗、検索結果0件とは区別します。

Group作成権限があるPersonal User / Community Administratorには、Empty表示から「Groupを作成」Actionへ到達できるようにします。このActionは通常のGroup作成Dialogを開き、別の作成方式を導入しません。Community Memberには作成Actionや管理権限があると誤認させる操作を表示せず、Groupがまだ存在しないことだけを適切に案内します。通常の操作パネルにある作成ActionとEmpty内の作成導線は同じ目的・処理へ接続します。

Mediaが0件のGroupも正常なGroupとして一覧・検索対象に含めます。Groupが存在する場合に、Mediaがないことだけを理由に一覧全体のEmptyへ切り替えません。一覧Item内のpreviewが空である場合の扱いは「Group discovery」の専用表現に従います。

選択中Groupのaggregate Mediaが0件の場合はMedia表示領域を空白のままにせず、現在のGroupに表示対象Mediaがないことを明示します。同様にdirect parentまたはdirect childが0件の場合も、relation情報の領域で該当relationがないことを明示します。これらは正常に取得できた0件状態として、読み込み中・取得失敗と区別します。

**G-05〜G-07の表示・Responsive Contract**: aggregate Mediaが正常に0件であることが確定した場合、Wide / Compactの双方に同等の「Mediaがありません」という見出しと、「このGroupまたはその下位Groupに分類されたMediaはありません。」という補足説明を示します。幅に合わせた折り返し・余白の差は許容しますが、Compactだからといって説明内容やMedia Emptyの意味を省きません。Parents / Childrenのdirect relationはWide / Compactの双方で確認でき、方向別に0件の場合は「なし」等の正常なEmpty表示を示します。Compactでもrelation領域そのものを削除しません。Media・Parents・Childrenがすべて0件でもGroupのidentity、選択状態、権限に応じた管理Action、選択解除の機能を維持し、Group本体の不存在や異常状態とは扱いません。

**取得状態との区別**: selected Group詳細またはaggregate MediaがLoading・取得失敗・未取得である場合、取得済み件数が0、またはデータが未定義であるという理由だけで「Mediaがありません」と断定しません。確定したaggregate Media総件数と現在取得済みMedia数を区別し、Mediaが存在するが先頭ページ未取得の状態も正常0件として扱いません。Parents / Childrenについても未取得・取得失敗を確定0件と混同しません。G-05〜G-07のInteraction TestではMedia0／Parents0／Children0の各組合せ、片方向だけ0、Compact / Wide、Loading / Errorから正常データへの回復を検証します。

### 検索結果なし

現在scopeにGroupは存在するが、確定したGroup名検索条件に一致するGroupが0件の場合は、Media BrowserのFilter結果0件と同様に、Group自体が存在しないEmpty状態とは異なる案内を一覧領域に表示します。「一致するGroupがありません」等の見出し、現在の検索条件を変更できる説明、および「検索を解除」Actionを提供します。作成を検索結果0件からの主要な解消Actionとはせず、検索条件の見直し・解除を優先します。

検索解除は入力中の検索文字列と確定済みの検索条件を解除し、現在scopeの通常のGroup一覧へ戻します。検索結果0件でも既存の選択中GroupとそのMedia Collectionを解除・破棄しません。検索解除後に選択中Groupが一覧へ再び現れた場合は、その選択状態を通常どおり表示します。

Empty／検索結果なしのどちらも、見出し、補足説明、必要に応じたIconとActionを組み合わせた案内を一覧内容領域に配置し、件数表示を除く検索・作成操作パネルやCompact / WideにおけるGroup選択・復帰の機能を失わせません。具体的な余白、Icon、色、Responsiveの配置はMedia Browserとの視覚的一貫性を確認するVisual ReviewとStorybook MDXで確定します。

### データ取得中・読み込み失敗・再試行

Group discoveryの一覧、選択中Groupの詳細・aggregate Media Collection、Group間relation候補は、それぞれ独立した取得対象として扱います。 Group間relation候補は編集開始前に全件取得するため、編集開始後の候補fetchMoreはInitial Releaseの画面状態として扱いません。取得対象と失敗した操作を利用者へ区別して示し、無関係な領域に存在する取得済みデータや操作状態を失わせません。取得結果がまだ確定していない状態を、Group・Media・relationが正常に0件であるEmptyと表示しません。

| 取得状態・失敗箇所 | 表示・保持する状態 | 復旧Action |
| --- | --- | --- |
| Group一覧の初回取得中 | Group discovery領域でLoadingを示し、Groupが0件と断定しない。既存の選択中詳細がある場合は維持する | 結果確定を待つ |
| Group一覧の初回取得失敗 | 一覧領域に取得失敗を示す。Emptyや検索結果なしを表示しない | 現在scope・確定した検索条件の一覧取得を再試行 |
| 一覧の再取得・検索失敗（以前の一覧・選択中Groupがある） | 以前に取得済みの一覧と選択中Group・Media Collectionを利用可能な範囲で維持し、一覧領域で取得失敗を示す。以前の一覧は新しい検索条件の取得結果であるかのように表示しない | 失敗した一覧取得を同じ確定条件で再試行 |
| 一覧の追加取得失敗 | 取得済みGroupを残し、追加取得分が欠けていることを示す。既存選択を解除しない | 同じ検索条件・未取得範囲の追加取得を再試行 |
| 選択中Groupの詳細を初回取得中 | Groupのidentityと選択状態を維持し、詳細・aggregate Media領域でLoadingを示す。未取得のMediaを0件として扱わない | 結果確定を待つ |
| 選択中Groupの詳細取得・再取得失敗 | 選択Group自体を保持し、取得済みの詳細・Mediaがある場合は閲覧を続けられるようにする。詳細領域に失敗を示し、利用不能と断定しない | 当該Groupの詳細を再取得 |
| aggregate Mediaの追加取得失敗 | 取得済みMediaと選択中Groupを維持し、続きの取得失敗をMedia領域に示す | 同じCollection条件で未取得の続きを再試行 |
| relation候補の初回・事前全件取得失敗 | 編集開始を許可せず、選択中Groupの閲覧状態を維持し、正常0件と区別して失敗理由を示す | 編集開始に必要な候補情報の取得を再試行 |

再試行は、失敗した取得対象と条件を利用者が認識できるActionとして提供し、再試行中は同じ要求の意図しない重複実行を防ぎます。再試行が成功したら当該エラー表示を解消し、最新の取得結果へ反映します。再試行も失敗した場合は、保持可能な既存データと再試行可能性を維持します。無期限の自動再試行や、別条件への黙示的な切り替えを復旧手段の前提にしません。取得済みデータがない場合は失敗した領域にErrorを示し、既存データがある場合はその閲覧を妨げない位置にErrorと再試行を提示します。

一時的な通信失敗、権限・Membershipの変更、対象Groupの不存在・利用不能は意味が異なります。**Groupが存在しないと確定できない通信エラーだけでは選択を解除しません。** 対象の削除・利用不能を確定できた場合は次節の選択解除とFeedbackへ移り、Application context自体の利用不能はNavigationの規則に従います。GraphQL / HTTPの具体的error codeと判定方法はAPI契約・Frontend接続の実装設計で確認し、本画面仕様だけで存在しない判定能力を仮定しません。

初回取得・再取得・追加取得・正常な0件・失敗・再試行成功・再試行再失敗、およびGroup選択中に別領域の取得が失敗した状態を、それぞれテストで再現・検証できる状態として扱います。

### 選択中Groupが利用不能になった

自分で選択中Groupを削除した場合、またはrefetch・Action結果等によって選択中Groupが削除済み・利用不能であることをWebが認識した場合は、Group選択を解除し、そのGroupを基準とするaggregate Media Collectionを破棄してGroups画面の未選択状態へ戻します。Group一覧も認識できている最新状態へ更新します。

自分で削除した場合は削除成功としてFeedbackし、別User等による外部変更を後から認識した場合はGroupが利用できなくなったことをFeedbackします。別Userによる削除・変更をリアルタイムに検知することは要求せず、Webが変更を認識するまでは既に取得済みの表示が一時的に残ることを許容します。

Group単体の利用不能とApplication context自体の利用不能を区別します。Community Membership喪失等によって現在Community contextを利用できなくなった場合はGroups画面の未選択状態へ留まらず、[Application Information Architecture](/system/application-information-architecture)に従って利用可能な安全なApplication destinationへ移動します。

### 権限変更

CommunityでAdministratorからMemberへroleが変更された場合、Group閲覧と既存Groupを使ったMedia分類Capabilityは維持し、Group作成・rename・削除・Group間relation管理を継続実行させません。 管理権限の喪失が確定した場合はGroup管理Actionを非表示へ切り替え、未完了の管理操作を成功として通知しません。編集Dialog内の管理Actionが実行できなくなった場合は、操作を継続できない理由を利用者に伝え、失敗・未保存の状態を成功済みと誤認させません。実行中のMutationの実際の結果はServerの認可・確定結果に基づいて判断します。

Membership自体を失った場合はCommunity Groupを継続表示せず、[Application Information Architecture](/system/application-information-architecture)に従って利用可能な安全なApplication destinationへ移動します。

### 操作処理中・競合

作成、rename、relation変更、削除の結果が確定するまで、同じ操作の意図しない重複実行を防ぎます。relation保存中は保存Actionの再実行とDraftの追加変更を一時的に停止し、どのDraftを保存しているかを曖昧にしません。即時反映型のInteractionを採用する別Actionでも、処理中lock、debounce、throttle等をActionの性質に応じて用い、意図しない短時間の重複実行を許可しません。

操作直前からGroup名、relation、role等が変更されて要求を成立できなくなった場合は現在状態を再評価し、成立しなかった操作と理由をUserが理解できるようにします。

## Navigation

Group Browserは[Application Information Architecture](/system/application-information-architecture)で定義するPersonal / Community contextのGroups領域です。

Personalから開いた場合はPersonal Groupだけ、Communityから開いた場合は現在CommunityのGroupだけを扱います。Groupを選択してもApplication contextは変更しません。

Group一覧と選択中GroupのMediaは同じGroups画面・同じ基本URLで扱い、Groupごとの専用詳細URLへの遷移を主要導線にしません。Personalの基本URLは`/groups`、Communityの基本URLは`/communities/[communityId]/groups`とします。選択中GroupはGroups画面内で保持し、`groupId`等のquery parameterを選択状態の正本にはしません。reloadやGroups画面への再入場ではGroup未選択の状態から開始します。Group選択の履歴をbrowser historyへ積まず、GroupsというNavigation destinationの内部でMediaを探索するInteractionとして扱います。split view等のpresentationはルーティング詳細設計・Visual Reviewで決定します。Compact / Medium / WideのいずれでもGroup選択からMediaへの到達を優先します。

## 制約

- GroupはfolderではなくDAGとしてrelationを持つ分類概念です。
- Group discoveryはflatな一覧を基本とし、DAG全体のgraph visualizationを主要Interactionにしません。
- Groupに一意なrootやbreadcrumb pathを仮定しません。
- Group名は1〜100文字とします。文字数はUTF-8 byte数ではなく、Userが1文字として認識するUnicode grapheme cluster単位で数えます。
- Group名は**元の入力をtrimする前に**Unicode制御文字（`Cc`。改行・タブ・NUL等）と行・段落区切り（`Zl` / `Zp`）を検証し、先頭・末尾を含めて1文字でも存在すれば無効とします。禁止文字を黙って除去・変換せず、作成・編集とも理由を示します。禁止文字がない場合のみ前後のUnicode whitespaceをtrimし、1〜100書記素などの名前制約を適用します。Backendも同一方針で検証します。`Cf`は一律禁止せず、追加制約は用途別に別Issueで検討します。共通の定義は[Unicode単一行入力ガイドライン](/guidelines/unicode-single-line-input)を参照します。
- Group名は同一scope内で重複できません。
- Personal Groupと各Community Groupは独立したscopeです。
- CommunityではAdministratorだけがGroup構造を管理し、Memberは既存Groupを利用したMedia分類だけを行えます。
- UI上のAction availabilityをAPI側の認可・DAG constraint検証の代替にしません。
- Groupのdomain semanticsは[Media Group](/media/group)、Community固有の認可は[Community権限](/community/authorization)を正本とします。
- TagはInitial Release対象ですが、本Screen SpecificationでGroupと同一Interactionを仮定しません。

## Responsive対応

表示領域や入力方式が変わっても、Groupの一覧、名前検索、Group選択、relationの確認、および権限のあるGroup管理Capabilityを維持します。

WideではGroup discoveryと選択中Groupを同時に確認できる構成を基本とし、選択中GroupではMediaを主領域、関連Groupを補助情報として扱います。Mediaの閲覧を優先し、関連Groupには「このGroupの所属先」と「このGroupに所属するGroup」を区別して表示します。relation編集DialogではWide時に選択中Groupを中心としてparents / childrenを左右に配置する構成を基本とします。

Compact等、Group discoveryと選択中Groupを同時表示するとMedia閲覧を阻害する表示領域では、両者を無理に並べずGroups画面内で表示面を切り替えます。Group選択後は選択中GroupのMediaを優先し、Group discoveryへ戻れる明確な操作を提供します。この切り替えはGroups領域内のInteraction stateであり、Groupごとの専用URLや別のGroup Detail destinationへのNavigationとは扱いません。

Mediumを含む具体的なlayout、2-pane表示から切り替え表示へ移行するbreakpoint、カラム幅等は、実装時の利用可能領域とVisual Reviewで確認して決定します。Compact / Medium / Wideという区分だけを理由に固定layoutを割り当てず、表示領域が変わってもGroup discoveryからMediaへ速やかに到達できるCapabilityを維持します。

Group名検索、Group選択、管理Action、relation情報の確認をhoverだけに依存させず、touchとkeyboardでも主要Capabilityへ到達できるようにします。

### G-20：表示面の切り替え・Keyboard・Focus Contract

Group Browserの一覧・Detailは同じ画面内のInteraction Stateです。CompactでGroupをKeyboardまたはTouch等から選択し、Group一覧の表示面が非表示・Unmountされるときは、選択GroupのDetail側へFocusを移し、見出しまたはDetail内でTaskを開始できる最初の適切な操作をFocus先にします。単に古いGroup ItemへFocusを残したり、Document Bodyへ意図せず戻したりしません。Focus移動は切り替え後に目的Elementが利用可能になった時点で行い、Keyboard / 支援技術でも遷移先を認識できるようにします。Touch利用者へ不必要なKeyboard操作を強制しません。

Compactの「一覧に戻る」または同等のActionでは、戻り先のGroup discoveryを表示し、元のGroup Itemが引き続き存在し利用可能ならそこへFocusを戻します。Groupが削除済み、検索結果から消失、現在のCollectionで未取得などにより起点が利用できなければ、検索Inputなど現在のGroup discoveryで安定して操作を再開できるFocus先を選びます。**Focus復帰のためだけに検索条件を解除したり、別Groupを暗黙に選択したり、無条件の全件取得を行いません。**

Wide / Compactの切替境界を跨ぐViewport変更時も、現在選択中のGroup、取得済みMedia・relation、成立している編集Draft、Dialogの開閉と操作可能なCapabilityを不必要に失わせません。非表示・UnmountされたElementにFocusが取り残される場合は、現在表示されている相当するActionまたは適切な安定したFocus先へ移動します。特定のBreakpointを本ルールで新たに固定せず、Mediumを含むLayoutとVisual Contractは実装・Visual Reviewで確認します。Focus遷移による画面内Stateの変更をURL / browser historyの変更として扱いません。

Group Item・Media Item・検索Form・関係Disclosure・管理ActionはKeyboardでも利用でき、Tab順、Enter / Spaceによる起動、Escapeによる一時Surfaceの終了をそれぞれ標準のComponent semanticsおよび[Overlay / Temporary Surface](/design-system/patterns/overlay-temporary-surface)に従って提供します。Modal内のFocus containmentと終了後のFocus復帰、Destructive Confirmationで削除Actionへ勝手に初期Focusしない原則を維持します。削除成功などで起点GroupやTriggerが消滅した場合は、閉じた後にGroup一覧の検索欄等の利用可能な安定した位置を選びます。処理中の終了可否はG-17の操作結果確定Contractに従います。

### G-20：テストと視覚的回帰の保証

StorybookのWide / Compactだけで完了と扱わず、Mediumを含むResponsive、Group選択・一覧復帰・Viewport変更のFocusと状態維持、Keyboardの検索・選択・Detail/Relation操作、DialogのCancel・Confirm・Focus復帰、権限差、正常Empty・Loading・Error・Retryをリスクに応じて再現します。G-05〜G-07で合意したCompactでのParents / ChildrenおよびMedia Emptyの同等情報も検証対象です。

単独Componentの表示・操作とFocusはStorybook Interaction Test、画面とAPI接続・非同期Mutation / Queryの状態連携は必要なIntegration Test、表示とBreakpointの回帰はVRT、検出可能なアクセシビリティ違反はAccessibility検査で責務を分けます。テストの階層は[Frontend Testing](/system/web/frontend-testing)に従い、Story / VRT / Interaction / Accessibilityのいずれか1種類で別の保証を代替しません。既存のVisual PrototypeとWeb本体のVisual / Behavior / Responsive Contractを維持し、変更の前後比較を実施します。

## Media / Group一覧の操作パネル配置規則

MediaとGroupの一覧は、操作パネルをコンテンツの上に配置し、開始位置と余白を揃えます。検索・フィルターは左、追加Actionおよび画面固有Actionは右に配置し、コンテンツとの境界にDividerを設けます。通常のMedia / Group一覧では件数を表示せず、件数表示用の予約領域や独立した行も設けません。Compactでは既存Actionの利用可能性を維持して必要に応じたResponsive配置を許容します。

共通化するのは視覚的な配置ルールであり、操作パネルの実装Componentは共通化しません。MediaのTag検索・選択モード、Groupの入力時検索など既存の画面固有Capabilityと操作タイミングは維持します。

### 検索確定とRelay Connectionのページング

MediaとGroupの検索Inputのplaceholderはそれぞれ「Tagを検索」「Groupを検索」とする。両方に「検索」ボタンを配置し、入力途中のdraft条件と確定済みの検索条件を分離する。検索ボタンまたは検索formのEnterによって条件を確定し、該当Connectionを先頭ページから取得する。コンテンツ領域のスクロールによって同じ確定条件で次ページを取得する。条件を変更して再検索した場合は旧cursorを流用しない。Groupの検索実行・再取得は選択中GroupとそのMedia表示を解除しない。通常一覧・検索結果および選択中GroupのMedia一覧では取得済み件数・総件数を表示しない。

現時点のVisual Prototypeと本体WebのモックではRelay/APIは接続せず、Groupは確定条件によるローカル絞り込み、MediaはTag metadataを持たないため検索条件の確定のみを表現する。実データの絞り込み・先頭ページ取得・スクロール追加取得はBackend接続時に実装する。MediaとGroupの操作パネルは共通Component化せず、視覚的配置規則のみ共有する。

### Group作成導線のモック実装

Group一覧の「Groupを作成」Actionは作成Dialogを開く。Dialogでは必須のGroup名（最大100文字）と任意のParents / Childrenを設定できる。キャンセルは変更を破棄し、作成Actionで登録を確定したときのみDialogを閉じ、一覧へ新規Groupを追加し成功Notificationを表示する。新規GroupのMedia件数は0件とする。現時点のWeb実装とVisual Prototypeでは画面内stateによるモック登録であり、Backend永続化やGraphQL mutationの成功を意味しない。

### Group Detailの関係セクション開閉

「このGroupとの関係」は可変幅Paneでも文言とChevronが離れないよう、左側に隣接配置する。閉時は右向き、開時は下向きとし、アイコンの回転と内容の開閉はそれぞれ200msでアニメーションする。配置の横断ルールは `content/guidelines/disclosure-controls.mdx` を正本とする。
