# Collection Discovery

## Purpose

Search、Filter、Sort、Pagination / Infinite Loadingを、Collectionから目的の対象を発見するための共通概念として整理します。すべてのCollectionへ同じControl一式を追加するPatternではありません。

## Search

SearchはUserが既知または言語化可能な識別情報から対象を探す必要がある場合に提供します。検索対象とmatching semanticsは各Screen / Domain Contractを正本とします。

Media Browserのようにfree text searchを提供しないScreenへ、共通Patternを理由にSearchを追加しません。

## Filter

Filterは現在Collectionのscopeを保ったまま条件で集合を絞り込みます。適用中のFilterを認識・解除できる必要があります。結果0件はCollection自体のEmptyと区別します。

複数条件のAND / OR、Tag semantics等はDomain / Screen Contractを正本とし、Design Systemで統一しません。

## Sort

Sortは比較・発見にUser controlが必要な場合だけ提供します。既定順がProduct semanticsとして十分なCollectionへsort UIを追加しません。

Sort key、direction、single / multi-columnはScreen Contractで定義します。Membersの単一column sortとMediaの固定作成日時降順を同じUI ruleへ統合しません。

## State / URL

共有・復元・BackでのTask継続に意味がある条件はURL state候補ですが、すべてをURL化しません。Navigation / WayfindingのDeep Link原則に従います。

Selection中に条件変更が対象集合の意味を変える場合はSelection / Bulk Action Patternに従います。

## Pagination / Infinite Loading

Memoria Webでは追加読み込みが必要なCollection全般に**Infinite Loadingを標準**として採用します。Media一覧に限らず適用しますが、すべてのCollectionへ機械的に強制するものではありません。Task、Collectionの規模・順序、Accessibility、API contract等に明確な理由がある場合は、Load Moreやページ番号Paginationを例外として個別に検討し、Screen Specificationへ理由とBehaviorを記録します。ページ番号方式を標準として提供しません。単にUIの好みだけで方式を変えません。

取得が正常に完了し、現在条件に一致するItemが0件の場合は、空白のままにせずデータがないことを明示します。初期Empty、検索・Filter結果0件、Relation等の部分Collectionが0件である正常結果を、Loadingや取得失敗と区別します。具体的な文言やEmpty State ComponentはScreen / Patternに従います。

追加取得中、終端、追加取得失敗を区別します。失敗時は表示済みItem、成立済みSelection、検索・Filter条件、スクロール位置を可能な限り維持してRetryを提供します。検索・Filter・Sort変更時は新しい条件のCollectionを取得し直しますが、明示選択済みItemを意図せず解除せず、未取得Itemを暗黙に選択しません。条件そのものが変化した場合は新しいCollectionの先頭から探索を開始でき、旧Collectionのスクロール位置維持を必須としません。一時的な追加取得失敗や条件不変のRefreshで既存Collectionを不必要に初期化しません。

Viewport到達だけに依存せず、Keyboardや支援技術からも追加取得と状態を利用できるようにします。Responsive環境でも主要なCollection閲覧・追加取得Capabilityを維持します。

**Collection発見・閲覧のための通常一覧、検索結果、Filter結果では件数を表示しません。** この規則はMedia Browser・Group Browser・Group選択後のaggregate Media Collectionに適用し、取得済み件数、全件数、`取得済み件数 / 総件数` の進捗数値を通常の一覧操作パネルやHeaderに配置しません。無限ローディングでは、先頭取得中・追加取得中・追加取得失敗とRetry・正常0件・終端を適切に表現します。終端に必ず文言を表示することは要求しません。

**件数が利用者の判断に必要な独立した用途は引き続き表示します。** 具体的には明示選択数、Actionの対象件数・成功/失敗件数、relation等の選択上限と現在の選択数、容量・登録件数等の利用統計、個別Sectionの展開対象数などです。用途ごとに何の集合を数えるかをDomain / Screen Specificationに明記し、総件数と取得済み件数を取り違えません。通常一覧での数字表示を復活させる場合は、当該画面の利用者価値と件数の意味について別途設計合意を必要とします。Infinite LoadingやRelay Connection採用を件数表示の根拠にしません。

Collectionに基づくDetailの前後Navigationでは、取得済みItem集合をCollection全体の境界として扱いません。現在のCollection条件と順序で移動先が存在する場合は必要に応じて追加取得して継続し、失敗しても成立済みのDetailや一覧状態・現在位置を破棄せずRetryできるようにします。

Relay Connection、cursor、fetch size、cache policy、virtualization等の実装方式は[Web実装規約](/system/web/implementation-conventions)および対象Screen / GraphQL契約で扱います。

## No Results

Search / Filter結果0件では適用条件を維持し、変更・解除へ到達できるようにします。新規作成を常に主要復旧Actionにはしません。

## Responsive

Compactでも現在条件と解除方法を理解できる必要があります。ControlをMenu / Popover等へProgressive Disclosureしても条件そのものを不可視にしません。

## Constraints

- Search / Filter / SortをCollectionの標準三点セットにしない。
- Search algorithmをUI Patternから推測しない。
- 固定Product orderへ不要なsort UIを追加しない。
- Filter結果0件をEmpty collectionと同一視しない。
- Infinite Loadingを追加読み込みが必要なCollectionの標準とし、例外はTask・Accessibility・API等の理由とともにScreenで明示する。
