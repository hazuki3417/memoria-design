# Action

## Purpose

Userが現在のTaskで実行できるActionの意味、優先順位、対象との関係を一貫して理解できるようにします。

Action DesignはButtonの見た目を分類するComponent catalogではありません。Product上のAction RoleとPlacementを定義し、Button、ActionIcon、Menu等の具体的なpresentationはTaskとUI Contextに応じて選択します。

## When to Use

Page、Form、Dialog、Collection、Selection、Object、Media等に対してUserが明示的なActionを実行できるUIへ適用します。同格のChoiceへ、Primaryを一つにするためだけの恣意的な優先順位は付けません。

## Action Role

### Primary Action

現在のAction ContextでTaskを前進または完了させる推奨Actionです。推奨Actionが存在する場合、一つのAction ContextにPrimary Actionは原則一つとします。一画面に一つという意味ではなく、Page、Form、Selection等の独立したAction ContextはそれぞれPrimaryを持てます。

通常のPrimary Actionは[Color System](/design-system#color-system)のEffective Accentを利用します。

### Secondary Action

Primaryを補助する、Taskを戻す、または現在のTaskを確定せず終了する等、Primaryと同等の視覚的強度を必要としないActionです。

### Quiet Action

利用可能である必要はあるものの、通常時に強い注意を要求しない補助Actionです。Toolbar、Viewer等でProgressive DisclosureやContextual Actionと組み合わせます。

### Danger Action

削除、破棄等の損失または破壊的なConsequenceを持つActionです。DangerはPrimary / Secondaryとは独立したSemanticで、PrimaryかつDangerも成立します。Context Accentでは上書きせずDanger Semantic Colorを使用します。Confirmation / Undoの必要性は[Content Design](/design-system/content-design)に従います。

## Visual Hierarchyの判断原則（Issue #244）

Action RoleはUserに推奨する操作とその補助関係を表し、Visual Hierarchyはその関係を認識できる強度で表現します。**既存ScreenのButton variantを規範として逆算しません。** Role、Danger Semantic、Presentationを別々に判断し、具体的なMantine variantの標準対応はFrontend実装契約で定義します。

### RoleからPresentationへの判断

1. **Action ContextとTaskを特定する**: Page、Form、Dialog、Selection等、どのTaskに対する操作かを明確にする。
2. **推奨Actionの有無を判断する**: 明確な推奨操作がある場合にPrimaryを割り当てる。推奨操作がない場合はPrimaryを作らず、同格Choiceに恣意的な優劣を付けない。
3. **補助関係を整理する**: Primaryと対になる取消・戻る等はSecondary、通常時に目立たせる必要がない補助操作はQuietとする。Roleは色やButton variantから決めない。
4. **Dangerを独立に判定する**: 削除・破棄等のConsequenceを確認し、必要なActionへDanger Semanticを組み合わせる。Dangerだけを理由にPrimaryへ昇格させない。
5. **Contextに応じて視覚的強度を選ぶ**: Primaryは同じAction Context内で最も明確な視覚的強調を基本とし、通常はEffective Accentを用いる。SecondaryはPrimaryより控えめに、Quietは通常時の視覚的主張を抑える。各Roleを特定の塗り・輪郭・variant名へ固定しない。

### DangerとVisual Hierarchy

Primary + Dangerは、操作の結果を十分に認識できる**強い表現を基本**とし、Danger Semantic Colorと明確なlabelを利用します。ただし、不可逆性、誤操作の可能性、周囲の情報密度、確認段階、操作の頻度を踏まえ、強調の程度をContextごとに調整します。強い赤い塗りをあらゆるContextで必須とはしません。Secondary / Quiet + Dangerでは補助的なHierarchyを維持しつつ、破壊的な意味が伝わる表現を選びます。

Dangerの強調だけで誤操作対策を完結させません。操作結果を明示するlabel、対象と影響の説明、必要に応じたConfirmation / Undo等は既存のContent DesignおよびScreen Contractに従います。Dangerを単なる赤色のvariantとして扱わず、色以外の情報も併用します。

### 仮想ケースによる検証

| 仮想Context | RoleとSemantic | Presentation判断 |
| --- | --- | --- |
| 新規作成・編集Form | 保存・作成 = Primary、キャンセル = Secondary | 確定操作を明確に強調し、キャンセルはそれより控えめにする |
| 削除確認Dialog | 削除確定 = Primary + Danger、キャンセル = Secondary | Dangerと結果を明示する。強調度は不可逆性・誤操作リスク・確認段階に応じて調整する |
| 同格の追加方法の選択 | 明確な推奨がなければPrimaryなし | 同格の選択肢を同等の強度で提示し、恣意的なPrimaryを作らない |
| Collectionの補助Toolbar | 編集・整理等 = SecondaryまたはQuiet、削除 = 必要に応じてDangerを併用 | 主TaskがなければPrimaryを強制しない。操作の発見性とContent Firstを両立する |

これらは原則の検証用ケースであり、既存画面の現状を承認・変更するものではありません。Roleが同じでもAction Contextが異なればpresentationは変わり得ます。同じContext内では優先度の違いが理解できる一貫したHierarchyを保ちます。

### 実装との境界

- Design SystemはRole、Semantic、視覚的な強弱、例外の判断基準を正本とします。
- Mantineの `filled` / `default` / `light` / `subtle` / `outline` 等への具体的なmapping、Theme設定、Component propsはFrontend実装契約で決めます。
- LabelとIconの選択は本Patternの「ButtonへのIcon併用判断」に従い、Icon有無をRoleの代用にしません。
- 既存Screen / Visual Prototypeはこの文書更新で変更しません。確定した原則に対する既存実装の監査と修正は別途扱い、既存Visual / Behavior contractを確認してから変更します。

## Placement

Actionは固定座標ではなく、Action対象との関係が理解できる場所へ配置します。

- **Page Action**: Page全体に作用する。Page introduction / header付近を標準的な候補とするが固定位置とはせず、主要Contentを妨げない発見可能な場所を選ぶ。
- **Form Action**: Form全体の変更確定・破棄等をFormとの関係が理解できる領域へ配置する。長いFormでは主要Actionへの到達性を維持する。
- **Dialog Action**: Dialog全体の確定・キャンセルActionは原則Action areaへ集約し、本文へ同じ確定Actionを重複させない。
- **Collection / Selection Action**: 選択集合へのActionは選択状態・対象数との関係が理解できる領域へ配置する。
- **Contextual Action**: 特定Object / SectionへのActionは対象の近くへ配置し、低頻度Actionは必要に応じてProgressive Disclosureする。
- **Media Overlay Action**: Mediaへの操作はMediaとの空間的関係を維持し、Media Firstを阻害しない強度と配置にする。

局所Actionを発見性だけを理由にPage Actionへ昇格させません。Empty State等で同じPage ActionをよりContextualに提示する場合は不要な重複を避けます。

## Action Group

横方向ではPrimary Actionを進行方向の終端側へ配置します。LTRの現在のMemoria UIでは通常右側です。Primaryと直接対になるSecondaryはその手前へ配置します。

Navigation、Flow離脱、補助Action等で意味が異なる場合は必要に応じて別Groupとして空間的に分離します。これはPrimaryを画面右端へ固定する規則ではなく、Group自体のalignmentはTaskとContainerに応じて決定します。同じPattern内では順序を理由なく変更しません。

## Responsive Behavior

Compact等でAction Groupを縦方向へStackする場合、Primary Actionを原則先頭、Secondaryをその後に配置します。Responsive後もHierarchy、主要Taskへの到達性、十分な操作対象を維持します。

戻る / 次へ等のNavigation Pairのように空間的関係自体がInteraction理解に重要な場合は、機械的にPrimary-firstへ変換せずPattern / Screen Contractで定義します。

狭い領域へ無理に横並びにしてlabelを切り詰めるよりStack、Grouping、Menu等へ適応します。ただしPrimaryをスペース不足だけを理由にMenuへ隠しません。

## Presentation

Main Taskではなく、発見性を下げてもTask達成を妨げず、開いた後も対象との関係を理解できるActionはMenu等へProgressive Disclosureできます。

IconだけでActionを十分理解できるContextではActionIconを利用できます。Close、Previous / Next、Zoom等が代表例です。重要なProduct ActionやIconだけでは結果を判断しにくいActionはlabel付きを基本とし、ActionIconにはaccessible nameを提供します。

IconはAction理解を補助する場合に利用し、Decorationとして機械的に追加しません。Iconの有無でHierarchyを表現しません。

## Label

Action labelは[Content Design](/design-system/content-design)を正本とします。UI ContextからActionが一意に理解できる場合は、OK、保存、次へ、戻る、キャンセル等の必要十分な抽象度を利用できます。Contextだけでは結果や対象を安全に判断できない場合は必要な対象またはActionをlabelへ含めます。

## State

Disabledは現在実行できないことを表しますが、理由を説明する仕組みとは扱いません。Userが解決可能なConstraintをContextから理解できない場合は適切な情報から理由を理解できるようにします。

Action受付後に同じActionの重複実行を防ぐ必要がある場合、実行可能な状態のまま放置しません。Loading / Processingの具体presentationは対象Taskの非同期BehaviorとScreen Contractが確定した時点で設計し、本Patternでは固定しません。

## Visual Foundation

Button height、padding、radius、Typography、hover、pressed、focus、disabled appearance、Icon spacing等はMantineへ委譲します。

Mantineのfilled / default / light / subtle / outline等をProduct上のAction Roleとして再定義しません。具体的なComponent / variant mappingはFrontend実装契約として決定し、Mantine標準でProduct Contractを満たせない場合だけMemoria固有ruleを追加します。

## Accessibility

- Keyboardで主要Actionへ到達・実行できる。
- Focusを視認できる。
- Touchでも十分な操作対象を確保する。
- Icon-only Actionにaccessible nameを提供する。
- Danger、Disabled、Selected等をColorだけに依存して伝えない。
- Visual orderと意味的な操作順序を不必要に乖離させない。
- Responsive後も主要Actionへ到達できる。

標準HTMLとMantineのaccessible primitiveを優先します。

### ButtonのLabel・Icon選択判断（Issue #166の再設計）

**明確なテキストlabelを操作の意味伝達の基本**とします。ただし、**label-onlyをすべてのContextでの標準Presentationとはしません**。label-onlyとIcon + labelは、Action Context、Interaction Pattern、操作の理解・識別・発見性を踏まえて選択します。既存Screenの採用例を判断根拠にはしません。

- **Label-only**: テキストだけで操作が明確に理解でき、Iconによる実質的な理解・識別・発見性の改善が見込めない場合に選択します。Iconを一律に付与して装飾やVisual Hierarchyの代用にしません。
- **Icon + label**: 複数Actionの素早い識別、操作対象・方向・種類の理解、Toolbar等での発見性に具体的な利点がある場合に選択します。Iconの意味がlabelと矛盾せず、視覚的なノイズや認知負荷を増やさないことを確認します。Iconがlabelの代わりに操作結果を説明する前提にはしません。
- **Icon-only**: Iconと周辺Contextによって意味が十分理解できる、慣習的で高頻度な補助操作等に限定して検討します。低頻度、結果が曖昧、破壊的、重要な確定操作では特に慎重に判断します。accessible name、Keyboard操作、Focus表示、十分なTouch Targetを必須とし、Tooltipだけに意味の理解を依存させません。
- **Roleとは独立**: Primary / Secondary / Quiet / DangerだけでIcon有無を決めません。Dangerには明確なlabelと結果・対象の説明を優先し、Iconの有無を危険性の唯一の手掛かりにしません。
- **Responsive**: 幅不足のみを理由にlabelを取り除きません。Stack、Grouping、配置変更、適切なMenu等を先に検討し、主要Actionの発見性を維持します。
- **Pattern内の一貫性**: 同じInteraction Pattern・同じ種類のActionには、利用者の期待が揃うPresentationを適用します。異なるContextでの機械的な統一は要求しません。

#### ToolbarでのLabel・Icon判断（Issue #245）

Toolbarでは**Hybrid（Label-only / Icon + label / Icon-onlyの混在）を許容**します。ただし、Toolbarであることや省スペースだけを理由にIcon-onlyを標準化しません。操作の意味の明確さ、発見性・識別性、空間効率の順に評価し、同じInteraction Pattern内で合理的な一貫性を保ちます。

1. **Icon-onlyで結果を予測できるか**: Iconと対象・周辺Contextだけで操作結果が十分に明確な場合に限り検討する。複数の意味に解釈できる場合はlabelを維持する。
2. **Icon併用の価値があるか**: labelが必要な操作では、Iconが識別速度、操作対象・方向の理解、発見性を実質的に改善するならIcon + label、改善しないならlabel-onlyを選ぶ。
3. **重要性とリスクを評価する**: 破壊的・不可逆・低頻度・重要な確定操作はIcon-onlyの許容基準を厳しくし、結果・対象が伝わるlabelを優先する。
4. **Toolbar全体で検証する**: Grouping、順序、Visual Hierarchy、Presentation混在の理由を確認する。同種のActionは合理的な理由なく異なる表現にしない。

| 仮想Action | 判断の方向性 |
| --- | --- |
| Viewerの閉じる・Zoom | 慣習とContextで結果が明確ならIcon-onlyを許容 |
| 編集 | Iconだけで編集対象が不明確ならlabelを維持 |
| 共有・Groupへ追加 | 操作の対象・結果を明示するlabelを維持し、Iconの識別上の価値を評価 |
| 削除 | 破壊的な結果を説明するlabelを優先し、Icon-onlyは慎重に判断 |

Hybridは無秩序な混在を意味しません。Accessible Name、Keyboard、Focus、Touch Targetの要件はPresentationによらず満たし、Icon-onlyのTooltipだけに意味の理解を依存させません。幅不足時はlabelの削除よりもStack、Grouping、適切なMenu等を先に検討します。既存画面の採用例は本判断の根拠とせず、実装変更は別途扱います。

#### 仮想Contextでの判断例

| Context | 評価の方向性 |
| --- | --- |
| 保存・キャンセルのForm | 明確なlabel-onlyで十分かを評価。Iconの一律付与は不要 |
| 複数操作が並ぶToolbar | Icon + labelによる識別速度・発見性の改善を評価。Toolbarという理由だけで必須化しない |
| Viewerの閉じる・Zoom | 慣習とContextが明確ならIcon-onlyを検討。Accessible Name等は必須 |
| 削除確認Dialog | 対象と結果を説明するlabelを優先。DangerであることのみでIconを追加しない |
| 同格Choice | 操作の識別を補助するIcon + label等を検討し、Iconの有無で恣意的な優先順位を作らない |

この判断基準は一般的なUI/UX原則から設計した規範です。既存Screen / Visual Prototypeのlabel、Icon、layout、behaviorは本変更で修正しません。既存実装との差分監査・修正は別途判断します。

## Constraints

- 一画面にPrimary Actionを一つだけと解釈しない。
- 同格のChoiceへPrimaryを一つにするためだけの優先順位を付けない。
- Primaryを常に画面右端へ配置する規則と解釈しない。
- Dangerを単に赤いButtonのVisual variantとして扱わない。
- Mantine variant名をProduct上のRoleとして仕様化しない。
- Loading / Processingの具体表現をAPI・非同期Behaviorの設計前に固定しない。


## LabelとIconの選択判断（Media First / Trustworthy）

ActionのPresentationはIconの省スペース性だけで決めず、Userが操作対象・結果・影響を予測できることを優先します。MemoriaのPersonal / Trustworthy / Calm / EnduringおよびMedia Firstに従い、重要なProduct ActionやIconだけでは意味が曖昧になるActionは、短く明確なテキストlabelを基本とします。見出しに隣接するContextual Actionは小さなQuiet / Subtle presentationによりContentの視覚的優先度を維持できます。Iconは理解を補助する場合のみ併用し、Decorationや一律のIcon化を目的にしません。

Close、Previous / Next、Zoom、回転、情報Panel開閉等、周囲のContextで意味が十分明確なViewer補助ActionにはIcon-onlyを採用できます。ただしaccessible name、Keyboard / Touchからの到達性、十分な操作対象を必須とし、Hover tooltipのみを意味の伝達手段にしません。特に共有・共有解除等のアクセス範囲を変えるActionは「+」「×」「ゴミ箱」だけで表現せず、関係の変更とMedia自体の削除を区別できるlabelを用います。狭い画面でも主要Actionの意味を失わせるIcon-onlyへの機械的置換を行わず、配置・Stack・Menu等をTaskに応じて調整します。
