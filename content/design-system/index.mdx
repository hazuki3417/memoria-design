# Design System

Memoria Design Systemは、実際のScreen設計から確認された再利用可能なUI/UX上の解決方法を段階的に定義します。

実装Foundation、Design Systemの成長方針、UX Principles等の全体方針は[Frontend UI設計・開発方針](/system/frontend-ui-development)を正本とします。

## Design Direction

MemoriaのVisual DesignとInteraction Designは、Product Visionで定義する「現実のCommunityで生まれたMediaを一緒に見て、整理し、残していく場所」と、Content First / Media Firstを基礎に、次の方向性を共通の判断軸とします。

### Product Character

Memoriaは **Personal / Trustworthy / Calm / Enduring** なProductとして設計します。

個人や身近な人たちとの思い出を、安心して一緒に見て、整理し、時間をかけて残していける、静かで信頼できる場所を目指します。公開SNSのようにAttentionや反応を競う場所、汎用Storageや業務用Media管理Toolのような無機質な作業空間、過去を懐かしむことだけに特化したRetro / Nostalgicな体験には寄せません。

### Emotional Goal

利用者がMemoriaを使うときの感情的なGoalを **Reassured / Familiar / Unhurried / Attached** とします。

- **Reassured**: 大切なMediaを安心して置き、共有範囲や重要な操作の結果を予測できる。
- **Familiar**: 無機質なStorageではなく、自分や身近な人たちの場所だと感じられる。
- **Unhurried**: 新着消費や反応を急かされず、自分たちのペースでMediaを見て整理できる。
- **Attached**: UI自体への装飾的な愛着を作るのではなく、蓄積されたMediaとCommunityへの愛着が時間とともに育つことを支える。

### Visual Personality

Visual Designは次を基準とします。

- **Neutral foundation + Emerald identity**: 基本UIはNeutralで落ち着かせ、Emerald GreenをMemoriaのIdentityを表す主要な色の方向性とする。画面全体をGreenで染めず、Mediaを主役にしたまま必要な場所でIdentityを与える。具体的なpalette、shade、semantic tokenはColor Systemで別途定義する。
- **Neutral temperature**: 冷たく無機質なCoolさにも、NostalgicなWarmさにも振り切らない。Emeraldが持つ自然な生命感と親しみを加えながら、全体はNeutralに保つ。
- **Clean / Refined / Slightly Sharp**: 親しみや安心感を保ちながら、輪郭はすっきりと洗練し、ややSharpで現代的な印象とする。過度なroundnessや「かわいさ」を目的とした造形へ寄せない。
- **Content-led**: 視覚的な主役はUserのMediaとDataとし、UI自体が競合しない。装飾を減らすこと自体を目的とするMinimalismにはしない。
- **Purposeful Visuals / Meaningful Decoration**: Icon、Shadow、Color、Motion等は、理解、情報階層、操作性、状態変化、親しみ、質感、Brand Identityを伝える意味がある場合に利用する。単なる賑やかしとして追加しない。
- **Quiet by Default, Expressive with Purpose**: 通常時は静かにContentを支える。一方、選択、重要なAction、状態変化、Warning、Error等、利用者の注意や理解が必要な場面では目的を持って明確に表現する。

### Interaction Philosophy

意味のあるUser Actionには、Systemが入力を認識したこと、処理中であること、または結果として何が変化したかを、利用者が知覚できるFeedbackとして返します。

Interactionは必要に応じて **Action → Acknowledgement → Progress / Transition → Result** のlifecycleで捉えます。すべてのActionに各段階を個別表示することは要求せず、即時に完了する選択であればSelected stateへの変化だけで成立します。Upload等の時間を要する処理では、受付、進行、処理状態、完了または失敗をTaskに必要な粒度で追跡できるようにします。

Animationは装飾やModernさ自体を目的とせず、状態遷移、空間的な関係、操作への応答を理解しやすくするFeedback手段として利用します。Animation以外にもpressed / selected state、Progress、Notification、Inline Feedback等、そのInteractionに適した表現を選択します。

このInteraction Philosophyは[Frontend UI設計・開発方針](/system/frontend-ui-development)の **Immediate Feedback** を具体化するDesign Directionであり、Feedback Patternの具体的なsurface選択は[Feedback](/design-system/patterns/feedback)に従います。

## UX設計・レビュー

- [Content Design](/design-system/content-design): UI上の言葉をインターフェースとして設計し、情報選択、Voice & Tone、Content Role、共通Pattern、AI Reviewの基準を定義します。
- [UX設計・レビュー基準](/design-system/ux-review): 画面の導線、入力、Feedback、復旧、一貫性、Accessibilityを共通の観点で評価します。AIによる設計・レビュー時にも参照します。

## Patterns

- [Editable Form](/design-system/patterns/editable-form): 既存データを編集し、有効な変更が存在する場合に変更を確定するための共通Pattern。
- [Creation Dialog](/design-system/patterns/creation-dialog): Application contextを維持したまま、限定的な新規作成Taskを完了するための共通Pattern。
- [Feedback](/design-system/patterns/feedback): 操作結果や問題を、利用者が理解・解決できる場所に応じて提示するための共通Pattern。

## 共通ドロップダウンメニューのデザイン方針（Visual Review中）

- アカウントメニューやContext Switcherなど、同種のリスト型ドロップダウンには一貫したデザインを適用する。
- GitHubのサイト上のメニューを参考に、控えめな境界線と影、コンパクトな余白、hover・focus時の明瞭な背景表示、必要に応じた項目グループの区切りを用いる。GitHubの実装や寸法をそのまま仕様とはしない。
- keyboard操作、focusの視認性、touch操作のしやすさを維持する。コンパクト化によって操作対象が小さくなりすぎないよう確認する。
- 現段階ではStorybookでのVisual Review対象とし、細部の寸法・配色は承認後に共通実装へ反映する。

## 表示テーマとContext Accent（Visual Review中）

- 表示モードは「システム」「ライト」「ダーク」の3種類とし、システム選択時はOSの表示設定に追従する。ユーザーの選択として扱い、Contextを切り替えても表示モードを維持する。
- Context Accent Colorは、現在のContextを視覚的に識別するための補助的なpresentationとする。ヘッダー、選択中Navigation、Context Switcherのindicator等、Context識別に必要な場所へ限定して使用し、一般的なAction / status / text colorのsemantic roleとして使用しない。
- 色だけをContext識別手段にせず、Context名や選択状態等の非色情報を併用する。
- Accent ColorはLight / Darkで共通の値を使用する。ThemeごとにAccentを再割当せず、Themeによって見え方の強さが異なることは許容する。
- Accent Colorを文字色として使用することは前提にしない。将来Accentを背景としてforegroundを重ねる場合、そのforegroundの可読性は別途保証する。
- Accentと隣接Surfaceの識別が難しい場合は境界表現で補償する。境界の具体的な色差アルゴリズム・閾値はFrontend実装とVisual Reviewで決定し、Accent自体をThemeごとに変更して解決しない。
- Community AccentはCommunityのbranding / domain identityではなく、UserごとのContext presentation設定とする。同じCommunityでもUserごとに異なる色を使用できる。
- Community参加時にUser向けの初期Accentをランダム生成する。同一Userが現在所属する他CommunityのAccentと完全一致する値は避けるが、類似色まで自動的に排除することは要求しない。
- 初期Accent生成では極端な明度を避ける。具体的な生成範囲・乱数方式はFrontend / API / Data実装契約で決定する。
- Community AccentはUserが後からColor Pickerで任意の `#RRGGBB` 値へ変更できる。手動選択では明度による制限を設けず、見分けにくい組み合わせはUser自身が変更できる。
- Community Accentの変更は[Community Settings](/screens/community-settings)から行い、選択時に即時保存・即時反映する。保存失敗時は保存済みの色へ戻し、再試行可能なFeedbackを提示する。
- Context Switcherでは各ContextのAccent indicatorを表示し、切替前にもContext名と色を併用して識別できるようにする。
- Community Accentの具体的な永続化model / API contractは後続のBackend設計で確定する。Presentation設定であることを理由にCommunity entityのbranding fieldとして扱わない。
- Personal AccentはUserごとのpresentation preferenceとし、[User Settings](/screens/user-settings)から任意の `#RRGGBB` へ変更できる。初期値は固定default Accentとし、Communityのようなランダム生成・重複回避は行わない。変更は即時保存・即時反映し、失敗時は保存済み値へ戻す。
