# Design System

Memoria Design Systemは、実際のScreen設計から確認された再利用可能なUI/UX上の解決方法を段階的に定義します。

実装Foundation、Design Systemの成長方針、UX Principles等の全体方針は[Frontend UI設計・開発方針](/system/frontend-ui-development)を正本とします。

## Design Direction

MemoriaのVisual DesignとInteraction Designは、Product Visionで定義する「現実のCommunityで生まれたMediaを一緒に見て、整理し、残していく場所」と、Content First / Media Firstを基礎に、次の方向性を共通の判断軸とします。

### Product Character

Memoriaは **Personal / Trustworthy / Calm / Enduring** なProductとして設計します。

個人や身近な人たちとの思い出を、安心して一緒に見て、整理し、時間をかけて残していける、静かで信頼できる場所を目指します。公開SNSのようにAttentionや反応を競う場所、汎用Storageや業務用Media管理Toolのような無機質な作業空間、過去を懐かしむことだけに特化したRetro / Nostalgicな体験には寄せません。

### Emotional Goal

利用者がMemoriaを使うときの感情的なGoalを **Reassured / Familiar / Unhurried / Attached** とします。

- **Reassured**: 大切なMediaを安心して置き、共有範囲や重要な操作の結果を予測できる。
- **Familiar**: 無機質なStorageではなく、自分や身近な人たちの場所だと感じられる。
- **Unhurried**: 新着消費や反応を急かされず、自分たちのペースでMediaを見て整理できる。
- **Attached**: UI自体への装飾的な愛着を作るのではなく、蓄積されたMediaとCommunityへの愛着が時間とともに育つことを支える。

### Visual Personality

Visual Designは次を基準とします。

- **Neutral foundation + Emerald identity**: 基本UIはNear-neutralでわずかにCoolなGrayを基調として落ち着かせ、Emerald GreenをMemoriaのBrand Identityを表す主要な色の方向性とする。画面全体をGreenで染めず、Mediaを主役にしたまま必要な場所でIdentityを与える。EmeraldはContextが独自のAccentを持たない場合のdefault Accentでもあり、具体的なpalette、shade、semantic tokenはColor Systemで定義する。
- **Neutral temperature**: 冷たく無機質なCoolさにも、NostalgicなWarmさにも振り切らない。Emeraldが持つ自然な生命感と親しみを加えながら、全体はNeutralに保つ。
- **Clean / Refined / Slightly Sharp**: 親しみや安心感を保ちながら、輪郭はすっきりと洗練し、ややSharpで現代的な印象とする。過度なroundnessや「かわいさ」を目的とした造形へ寄せない。
- **Content-led**: 視覚的な主役はUserのMediaとDataとし、UI自体が競合しない。装飾を減らすこと自体を目的とするMinimalismにはしない。
- **Purposeful Visuals / Meaningful Decoration**: Icon、Shadow、Color、Motion等は、理解、情報階層、操作性、状態変化、親しみ、質感、Brand Identityを伝える意味がある場合に利用する。単なる賑やかしとして追加しない。
- **Quiet by Default, Expressive with Purpose**: 通常時は静かにContentを支える。一方、選択、重要なAction、状態変化、Warning、Error等、利用者の注意や理解が必要な場面では目的を持って明確に表現する。

### Interaction Philosophy

意味のあるUser Actionには、Systemが入力を認識したこと、処理中であること、または結果として何が変化したかを、利用者が知覚できるFeedbackとして返します。

Interactionは必要に応じて **Action → Acknowledgement → Progress / Transition → Result** のlifecycleで捉えます。すべてのActionに各段階を個別表示することは要求せず、即時に完了する選択であればSelected stateへの変化だけで成立します。Upload等の時間を要する処理では、受付、進行、処理状態、完了または失敗をTaskに必要な粒度で追跡できるようにします。

Animationは装飾やModernさ自体を目的とせず、状態遷移、空間的な関係、操作への応答を理解しやすくするFeedback手段として利用します。Animation以外にもpressed / selected state、Progress、Notification、Inline Feedback等、そのInteractionに適した表現を選択します。

このInteraction Philosophyは[Frontend UI設計・開発方針](/system/frontend-ui-development)の **Immediate Feedback** を具体化するDesign Directionであり、Feedback Patternの具体的なsurface選択は[Feedback](/design-system/patterns/feedback)に従います。


## Foundationの利用方針

Memoriaは、Visual Designの基礎となるscaleや一般的なComponent behaviorを独自に再設計することを目的とせず、MantineをDesign Systemの実装Foundationとして可能な限りそのまま利用します。

Typography、Spacing、Radius、Border、Shadow、Iconography等の一般的なVisual Foundationについて、Product固有のDesign Contractが確認されていない段階でMemoria独自のToken、scale、Primitiveを網羅的に定義しません。Mantineの標準的なDesign Systemで要求を満たせる場合は、そのTheme、scale、Component behavior、AccessibilityをFoundationとして採用します。実際のScreen設計・実装・Visual Reviewを通して繰り返し必要となる意味や、Mantineでは表現できないProduct固有の要求が確認された場合に限り、Memoria固有のSemantic Token、Pattern、Component contractへ昇格します。

Color SystemのようにProduct IdentityやContext固有の意味を持つ領域、Responsive behaviorやMedia固有LayoutのようにScreen / ProductのGoalから決まる領域は、この委譲によってMantineへ仕様判断そのものを移す対象ではありません。MemoriaはProduct固有の意味とContractを定義し、その実現手段としてMantineを利用します。

この方針はMantineの既定値を無条件に仕様化することを意味しません。既存実装上の局所的な指定や慣習も、それだけを理由にDesign Systemへ昇格させません。Product要件、Screen Contract、Accessibility、再利用される意味を基準に、追加設計の必要性を判断します。

### Typography

TypographyはMantineのTypography SystemをFoundationとして利用します。Font family、Font size scale、Line height、Font weight、Heading scale等について、現段階ではMemoria独自のscaleやSemantic Typography Tokenを網羅的に定義しません。

Mantineの `Title`、`Text`、size、weight等の標準的な仕組みを基本とし、Page Title、Section Heading、Metadata等にMemoria固有の一貫した意味や表現が必要であることが実画面から確認された場合に、そのRoleとContractを追加します。具体的なpx値や既存画面の局所指定を、Visual ReviewやProduct上の必要性なしにDesign Systemへ固定しません。


### Spacing / Layout / Responsive

SpacingはMantineのSpacing scaleをFoundationとして利用し、Product固有の必要性が確認されていない段階でMemoria独自のSpacing scaleを定義しません。

Responsive breakpointは[Frontend UI設計・開発方針](/system/frontend-ui-development)に従い、原則としてMantine標準Breakpointを利用します。Breakpointは「いつLayoutを変えるか」を表すFoundation上の境界であり、各Screenで「何をどのように変えるか」というResponsive behaviorとは分離して扱います。Responsive behaviorはScreenの主要Goal、情報優先度、Interactionに基づいてScreen Contractとして設計します。

Content WidthはBreakpointとは別のLayout constraintとして扱います。既存実装に存在する `max-width` 等の具体値は、狭いViewportへ追従するResponsiveな実装であっても、その数値のDesign上の根拠がSource of Truthから確認できない場合、それだけを理由に共通Layout Tokenへ昇格させません。

Content Widthの具体値はScreenの目的、Contentの性質、Media First、可読性、操作性等から決定し、必要に応じてVisual Reviewで妥当性を確認します。複数Screenで同じ意味を持つLayout constraintが繰り返し確認された場合に、共通のLayout ContractやTokenへの昇格を検討します。

## Color System

Color Systemは、具体的な色をComponentへ直接割り当てるのではなく、Memoriaが色の意味と解決規則を定義し、実際のColor resolutionとMantine Componentへの適用は可能な限りMantineが提供するTheme / Colorの概念・機能・仕組みに委譲します。Mantineで表現できる責務を再実装する独自Color Engineは設けません。

### Semantic Color

基本的なSemantic Roleを次のように扱います。

- **Neutral**: Background、Surface、Text、Border、Disabled等の通常UI。Near-neutralでわずかにCoolなGrayを基調とし、冷たく無機質なBlue Grayや黄みの強いWarm Grayには寄せない。
- **Accent**: 現在のContextにおける主要なInteractive emphasis。具体色を固定せず、Context-awareに解決する。
- **Success**: 成功、完了、正常なPositive state。
- **Info**: 中立的な情報、Processing等のInformative state。
- **Warning**: 注意、確認を要する状態。
- **Danger**: Error、失敗、破壊的Action。

Success / Info / Warning / Dangerは状態の意味を表すSemantic Colorであり、Context Accentによって上書きしません。また、状態や意味をColorだけで伝えず、Icon、Label、Text、形状等、そのUIに適切な非色情報を併用します。

### Brand ColorとAccent Color

**Memoria Brand Color** と **Accent Color** は別の概念として扱います。

Memoria Brand ColorはProduct Identityを表す **Emerald Green** とします。Emeraldの方向性は **Balanced / Slightly Deep / Clear** とし、落ち着きと信頼感を持ちながら、古さや重さを感じさせない色を目指します。具体的なpaletteとshadeはVisual Reviewを通して確定します。

Accent Colorは現在のContextにおけるInteractive emphasisを表すSemantic Roleです。Effective Accentは次の規則で解決します。

```text
effectiveAccent = contextAccent ?? memoriaEmerald
```

Context Accentが存在する場合、通常のInteractive UIではContext AccentがMemoria Emeraldに代わってAccentとして機能します。Context Accentが存在しない場合はMemoria Emeraldをdefault Accentとして使用します。これにより、Brand IdentityとしてのEmeraldを維持しながら、一つのContext内で複数のAccentが競合することを避けます。

Primary Action、Selected / Active / Focus等、Mantine標準ComponentのどのstateにAccentを適用するかは、Memoria側でComponentごとのColor ruleを重複定義せず、原則としてMantineのThemeとComponent behaviorへ委譲します。Media固有表現等、Mantineの標準的な仕組みではDesign Contractを満たせない場合のみ、該当するPattern / Componentで追加の規則を定義します。

### Context AccentとColor Resolution

Context AccentはCommunityのbranding / domain identityではなく、UserごとのContext presentation設定です。同じCommunityでもUserごとに異なる色を使用できます。

Userが設定・保存するContext Accentのraw valueと、UIで利用するEffective Accentの表現は分離します。任意の `#RRGGBB` を直接すべてのComponent stateへ適用することを前提とせず、Mantineが提供するColor / Theme機構を利用して、必要なpalette、shade、variant、foreground等へ解決します。

Color resolutionの具体的なAPI、palette生成方法、shade選択、contrast補償等は、利用するMantine versionの標準機能を確認した上でFrontend実装契約として決定します。Memoria独自のColor resolutionを追加する場合は、Mantineでは満たせないDesign Contractが明確な場合に限定します。

Light / Dark Themeでは同じ保存済みContext AccentをSourceとして扱いますが、Accessibilityと各Theme上での視認性を保つため、UIへ適用されるshadeやforeground等のResolved Colorまで同一であることは要求しません。

## UX設計・レビュー

- [Content Design](/design-system/content-design): UI上の言葉をインターフェースとして設計し、情報選択、Voice & Tone、Content Role、共通Pattern、AI Reviewの基準を定義します。
- [UX設計・レビュー基準](/design-system/ux-review): 画面の導線、入力、Feedback、復旧、一貫性、Accessibilityを共通の観点で評価します。AIによる設計・レビュー時にも参照します。

## Patterns

- [Action](/design-system/patterns/action): Actionの優先順位、対象との関係、配置、Responsive presentationを定義する共通Pattern。
- [Form Control](/design-system/patterns/form-control): Field semantics、Validation、Control選択、Commit、Layout、Accessibilityを定義する共通Pattern。
- [Navigation / Wayfinding](/design-system/patterns/navigation-wayfinding): Navigation hierarchy、現在地、移動semantics、Responsive capabilityを定義する共通Pattern。
- [Overlay / Temporary Surface](/design-system/patterns/overlay-temporary-surface): Dialog、Drawer、Popover、Menu、Tooltip等のSurface選択、Dismiss、Focus、Responsive behaviorを定義する共通Pattern。
- [Content Presentation](/design-system/patterns/content-presentation): List、Table、Card、Metadata等のpresentation選択と情報階層を定義する共通Pattern。
- [Media Presentation](/design-system/patterns/media-presentation): Media Firstに基づくBrowser、Preview、Detail、Metadataの共通Contract。
- [Selection / Bulk Action](/design-system/patterns/selection-bulk-action): 複数選択のscope、bulk Action、部分成功、Responsive behaviorを定義する共通Pattern。
- [Collection Discovery](/design-system/patterns/collection-discovery): Search、Filter、Sort、Pagination / Infinite Loadingの選択原則を定義する共通Pattern。
- [Empty / Zero State](/design-system/patterns/empty-zero-state): Initial Empty、No Results、Relation Empty、Error等の意味的な区別を定義する共通Pattern。
- [State Representation](/design-system/patterns/state-representation): Status、Role、Permission、Selection等を必要な強さで表現する共通Pattern。
- [Page Structure](/design-system/patterns/page-structure): Page Identity、Page Action、Primary Content等の意味的なPage構造を定義する共通Pattern。
- [File Input](/design-system/patterns/file-input): File picker、Drag & Drop、選択済みfile、事前Validationの共通Contract。
- [Editable Form](/design-system/patterns/editable-form): 既存データを編集し、有効な変更が存在する場合に変更を確定するための共通Pattern。
- [Creation Dialog](/design-system/patterns/creation-dialog): Application contextを維持したまま、限定的な新規作成Taskを完了するための共通Pattern。
- [Feedback](/design-system/patterns/feedback): 操作結果や問題を、利用者が理解・解決できる場所に応じて提示するための共通Pattern。

## 共通ドロップダウンメニューのデザイン方針（Visual Review中）

- アカウントメニューやContext Switcherなど、同種のリスト型ドロップダウンには一貫したデザインを適用する。
- GitHubのサイト上のメニューを参考に、控えめな境界線と影、コンパクトな余白、hover・focus時の明瞭な背景表示、必要に応じた項目グループの区切りを用いる。GitHubの実装や寸法をそのまま仕様とはしない。
- keyboard操作、focusの視認性、touch操作のしやすさを維持する。コンパクト化によって操作対象が小さくなりすぎないよう確認する。
- 現段階ではStorybookでのVisual Review対象とし、細部の寸法・配色は承認後に共通実装へ反映する。

## 表示テーマとContext Accent（Visual Review中）

- 表示モードは「システム」「ライト」「ダーク」の3種類とし、システム選択時はOSの表示設定に追従する。ユーザーの選択として扱い、Contextを切り替えても表示モードを維持する。
- Context Accentは[Color System](#color-system)で定義するAccentのContext-specificなSourceとする。Context Accentが存在する場合はMemoria Emeraldに代わってEffective Accentとして解決し、存在しない場合はMemoria Emeraldへfallbackする。
- 色だけをContext識別手段にせず、Context名や選択状態等の非色情報を併用する。
- Community AccentはCommunityのbranding / domain identityではなく、UserごとのContext presentation設定とする。同じCommunityでもUserごとに異なる色を使用できる。
- Community参加時にUser向けの初期Accentをランダム生成する。同一Userが現在所属する他CommunityのAccentと完全一致する値は避けるが、類似色まで自動的に排除することは要求しない。
- 初期Accent生成では極端な明度を避ける。具体的な生成範囲・乱数方式はFrontend / API / Data実装契約で決定する。
- Community AccentはUserが後からColor Pickerで任意の `#RRGGBB` 値へ変更できる。保存値を直接Component colorとして利用せず、Color SystemのColor resolutionを通してEffective Accentへ解決する。
- Community Accentの変更は[Community Settings](/screens/community-settings)から行い、選択時に即時保存・即時反映する。保存失敗時は保存済みの色へ戻し、再試行可能なFeedbackを提示する。
- Context Switcherでは各ContextのAccent indicatorを表示し、切替前にもContext名と色を併用して識別できるようにする。
- Community Accentの具体的な永続化model / API contractは後続のBackend設計で確定する。Presentation設定であることを理由にCommunity entityのbranding fieldとして扱わない。
- Personal AccentはUserごとのpresentation preferenceとし、[User Settings](/screens/user-settings)から任意の `#RRGGBB` へ変更できる。初期値はMemoria EmeraldをSourceとするdefault Accentとし、Communityのようなランダム生成・重複回避は行わない。変更は即時保存・即時反映し、失敗時は保存済み値へ戻す。
