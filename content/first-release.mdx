# 初回Releaseの範囲と成功条件

## 目的

初回Releaseでは、静止画像を個人およびCommunityで安全に閲覧・共有し、GroupとTagを使って整理できる状態を実現します。将来のProduct全体が静止画像と動画を扱うことと、初回Releaseで提供する対象は区別します。

本ページを初回Releaseの範囲、優先順位、成功条件の正本とします。要求や詳細設計で未確定の事項は対応するIssueで判断し、推測によって確定済み仕様へ含めません。

## 対象利用者と利用場面

対象は、自分の画像を保存・整理するUserと、家族や部活動などの閉じたCommunityで画像を共有する参加者・Administratorです。Userは個人管理画像をCommunityへ共有する方法と、Community管理画像として直接Uploadする方法を利用します。

## 初回Releaseに含める機能

| 領域 | 必須範囲 | 設計上の留意点 |
| --- | --- | --- |
| 認証・User | Login、nickname登録・変更、Logout、session失効、account削除 | Auth0とMemoriaの責務を分離し、個人情報を最小化する |
| 静止画像 | Upload、一覧表示、詳細表示、削除 | 動画や画像以外のファイルは含めない |
| 表示用画像 | アスペクト比を維持した複数幅のWebP Variant | 一覧と詳細で同じVariantを利用し、原本より拡大しない |
| 非同期処理 | 原本保存、Media/Custody登録、Processing Job、Transactional Outbox、Redis Streams、Worker | 冪等性、失敗、再試行、削除との競合を扱う |
| Community | Community、参加者、Administrator、Invitationと参加状況に応じた閲覧 | Community外のUserは閲覧不可。Initial Releaseでは有効なInvitationのacceptでMembershipを直接成立させ、User起点Join Requestは将来機能とする |
| 管理と共有 | User管理、Community管理、個人管理画像のCommunity共有、Communityへの直接Upload | UploaderとCustodianを分離し、参加中のUploader本人に削除・Original downloadを認める |
| Group | Groupの作成・編集・削除と画像の整理 | 閲覧権限を制御しない。Group関係はDAGとし、複数親を許可して自己参照・循環を禁止する |
| Tag | Tagの作成・編集・削除、画像への付与・解除、Tagによる絞り込み | 管理範囲、編集権限、条件の詳細は要求・詳細設計で決定する |
| アクセス制御 | User、Community参加者、Administrator、Custodian、Uploaderに応じた認可 | 原本アクセスはUser Custodian、Community Administrator、参加中の該当Uploaderに制限する |
| 実行基盤 | EC2 + Docker、Deploy、秘密情報管理、Backup、復旧、監視 | 予算に応じて構成し、PostgreSQL/Redisの配置は運用設計で確定する |
| 品質管理 | 各RepositoryのGitHub Actions quality gateと人間によるReview | ChatGPTの実行環境ではbuild、test、静的解析、構文検証を行わない |

Media削除とUser account削除は初回Releaseの必須機能です。管理主体の委譲と独立した原本download画面は初回Releaseの必須機能とはしません。それらを提供する場合は既存の不変条件と認可設計に従います。

## 初回Releaseに含めない機能

- 動画、PDF、文書、音声単体など静止画像以外の登録
- 課金、料金体系、請求処理、自動Tag付け
- profile画像、複数認証方法のaccount統合、公開用account ID：[#51](https://github.com/hazuki3417/memoria-design/issues/51)・[#52](https://github.com/hazuki3417/memoria-design/issues/52)・[#53](https://github.com/hazuki3417/memoria-design/issues/53)
- メール通知・push通知：[通知機能 #47](https://github.com/hazuki3417/memoria-design/issues/47)
- Media管理主体の委譲：[委譲機能 #48](https://github.com/hazuki3417/memoria-design/issues/48)
- 利用価値を実現するために必須ではない一括操作や高度な検索
- ごみ箱、削除済み画像の復元、アーカイブ
- BrowserからS3への直接Upload
- ECS/Fargateへの移行、Multi-Region構成、24時間の常時対応体制。ProductionのPostgreSQL / Redis HAはBaselineとし、可能なら複数Failure Domain / 3 AZへ分散する
- 既存本番dataや無停止運用を前提とする高度な段階的DB移行

DB schemaの初期化と安全なmigration実行は初回Releaseで必要です。既存本番dataの保持、無停止切替、旧versionとの後方互換が実際に必要な場合は、その条件に応じて段階的移行を追加します。

## End-to-Endの成功条件

### 個人管理画像

1. Userがログインし、自分の画像をUploadできる。
2. 処理完了後、画像を一覧および詳細画面で閲覧できる。
3. 画像をGroupで整理し、Tagを付与・解除し、Tagで絞り込める。
4. 画像を削除すると、一覧・詳細画面や関連付けから安全に除去される。

### Communityへの共有

1. Userが自分の管理する画像を所属Communityへ共有できる。
2. Community参加者は共有された画像を閲覧できる。
3. Community外のUserは閲覧できず、一般参加者は原本を取得できない。
4. 共有解除、参加資格の喪失、権限変更後は、新しい閲覧許可を発行しない。

### Communityへの直接Upload

1. 所属するUserがCommunityへ静止画像をUploadできる。
2. 操作したUserはUploaderとして記録され、CommunityがCustodianになる。
3. Community Administratorは管理権限に基づいて操作できる。
4. Community参加中のUploader本人は、自分がUploadしたMediaを削除し、Originalをdownloadできる。
5. 退会・除外・User削除後はUploader本人の権限を失効させる。

### 異常系と運用

- 未認証、権限不足、対象消失、画像処理中、処理失敗を利用者が識別できる。
- 非同期処理は重複実行、再試行、削除との競合で不整合な権限や派生物を残さない。
- 原本と表示用画像は非公開Storageで管理し、認可された経路からだけ配信する。
- EC2 + Dockerで安全にDeployでき、Backup、復旧、監視の担当と手順が明確である。
- Web、API、IaC、設計Repositoryのquality gate結果と人間のReviewに基づいて公開可否を判断する。

性能、容量、可用性、RPO/RTO、Backup保持期間、観測項目は[非機能要件](/system/cross-cutting/non-functional-requirements)を正本とします。Security・Privacyの詳細は専用の要求Issueで確定します。

## 設計状況と残る設計事項

Initial ReleaseのProduct / Domain設計は、UserとCommunityの主要領域について確定済みです。Application UIについても、[Application Information Architecture](/system/application-information-architecture)と[Screen Specification](/screens)で主要Flowを定義し、Media Browser / Detail、Media Sharing、Group BrowserとMedia ↔ Group分類Interactionまで横断設計済みです。Media Uploadの詳細InteractionとTagの基礎設計・具体的Interactionは未確定です。

今後の設計では、確定済み領域を再度一括設計するのではなく、残る未確定事項と実装契約を必要な順に具体化します。

## 設計と実装の優先順位

1. Tagの基礎設計とPersonal / Communityにおける権限・分類・絞り込みInteractionを具体化する。
2. 静止画像Upload、Variant、非同期処理、失敗・再試行をMedia UIと整合する形で具体化する。
3. 確定したProduct / Domain / Screen仕様を入力として、GraphQL等のAPI実装契約を具体化する.
4. account削除等で必要なSecurity詳細とAuth0強制再認証方式を、関連実装へ着手する前に確定する。
5. memoria-webではApplication IAとDesign System PatternをStorybook上の実行可能UIへ落とし込み、Visual Reviewを経てApplicationへ実装する。
6. EC2 + Dockerの運用、Deploy、Backup、復旧を確定し、Repositoryごとの実装Issueとquality gate・結合確認へ接続する。

Product / Domain設計ではUserが達成する目的、Systemが保証する結果、不変条件を定義し、Screen SpecificationではそれをUserが理解・操作するInformation / Action / State / Navigationへ具体化します。GraphQL等のAPI契約はこれらの確定仕様を実装へ接続する契約として定義し、画面都合だけでProduct / Domain ruleを決定しません。

すべての要求を一括で確定してから実装することは前提にしません。依存する判断が確定した領域から、[アジャイル開発とイテレーション運用](/development-process)に従って小さな単位で進めます。

## Release後に検証する仮説

利用者が個人または所属Communityの画像を見つけ、閲覧し、GroupとTagで整理し、認可された相手と共有できれば、初回Releaseの中心的な価値を提供できます。Upload・画像処理の成功と失敗、認可拒否、主要操作の完了状況を観測し、実際の利用状況から次の優先順位を判断します。
