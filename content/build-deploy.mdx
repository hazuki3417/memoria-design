# ビルド・デプロイ


## 概要


| 対象 | 基準 |
| --- | --- |
| 本番リリース | `main`の正式Release |
| 日常開発 | `develop` |
| 検証環境 | 専用branchを作らずdeploy設定・GitHub Environments・AWS側で分離 |

branchはcodeの統合段階、environmentは実行先です。作業branchを通常のmerge commitで`develop`へ統合し、結合確認後に`develop`から`main`へRelease PRを作成します。`main`の対象commitへSemantic VersioningのtagとGitHub Releaseを作成します。各リポジトリは独立versionで、pre-releaseは使用しません。

AWSはOIDCと短期credentialを優先し、IaCはsynth・diffでIAM拡大、resource置換、data削除を確認します。DB・storage変更はbackup、migration、rollbackまたはroll-forwardを事前に決めます。

## Containerのbuildと実行基盤

初期はEC2上でDocker containerを実行します。APIとMedia Workerは用途別のimageとしてbuildし、Outbox Publisherは必要に応じてAPI imageを共有します。API、Publisher、Workerは独立したprocessとして起動し、将来的にECS/Fargateへ移行できる境界を維持します。

local開発、CI、EC2上の構成は、同じDockerfile、lock file、Docker Compose構成を正本とします。環境差分が必要な場合は共通の`compose.yaml`に開発用またはCI用の差分を重ね、各環境で異なるservice構成を手作業で複製しません。

## BuildKitとimageの再利用

build commandは環境ごとに実行し、BuildKitのlayer cacheで実際の再buildを抑えます。CIではimageをbuildする段階とcontainerを起動する段階を分け、build済みimageの起動時には`docker compose up --no-build`を使用できます。

GHCR上の共通base imageは標準構成に含めません。Media Workerのnative依存が増え、build時間や転送量が実際の問題になった場合に限り、base imageの公開範囲、更新手順、cache効果を確認して検討します。

CIはLinux runner上で必要なruntimeをsetupし、local環境保護を目的とするDevboxの導入を必須にしません。CIの検証項目と実行段階は[テスト設計](/test-design)を参照してください。

## Deploy、migration、rollback

GitHub ActionsでbuildしたDocker imageをcommit SHAまたはdigestで識別し、同じartifactをdeployへ再利用します。latestを本番の識別子にしません。AWS接続はOIDC、EC2への操作はSSMを標準とし、長期Access KeyとSSH公開を前提にしません。

PostgreSQL migrationは専用の一時containerでdeploy全体につき一度だけ実行し、成功後にApplicationを更新します。process起動ごとの自動migrationは行いません。複数EC2がある場合だけ1台ずつrolling deployします。

production deployは人間の承認を必要とし、environmentごとの同時実行を防ぎます。rollbackは互換性を維持した以前のimmutable imageへの再deployを基本とします。詳細は[EC2・Docker運用基盤](/system/infrastructure/ec2-runtime-operations)と[DB schema migration](/system/data/schema-migration)を参照してください。
