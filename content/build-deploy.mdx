# ビルド・デプロイ


## 概要


| 対象 | 基準 |
| --- | --- |
| 本番リリース | `main`の正式Release |
| 日常開発 | `develop` |
| 検証環境 | 専用branchを作らずdeploy設定・GitHub Environments・AWS側で分離 |

branchはcodeの統合段階、environmentは実行先です。作業branchを通常のmerge commitで`develop`へ統合し、結合確認後に`develop`から`main`へRelease PRを作成します。`main`の対象commitへSemantic VersioningのtagとGitHub Releaseを作成します。各リポジトリは独立versionで、pre-releaseは使用しません。

AWSはOIDCと短期credentialを優先し、Terraformのformat・validateで静的検証を行い、対象環境のplanでIAM拡大、Resource置換、Data削除を確認します。State BackendとLockの設定を確認してからCloudに適用します。DB・Storage変更はBackup、Migration、RollbackまたはRoll-forwardを事前に決めます。

## Containerのbuildと実行基盤

初期はEC2上でDocker containerを実行します。APIとMedia Workerは用途別のimageとしてbuildし、Outbox Publisherは必要に応じてAPI imageを共有します。API、Publisher、Workerは独立したprocessとして起動し、将来的にECS/Fargateへ移行できる境界を維持します。

local開発、CI、EC2上の構成は、同じDockerfile、lock file、Docker Compose構成を正本とします。同じ責務の実行構成は必要な環境差分を重ね、手作業で複製しません。一方、ローカル常駐サービスと検証・開発支援タスクは用途が異なるため、[ローカル開発環境](/local-development)で定める `docker-compose.yml` と `docker-compose.integration.yml` に分離します。クラウド実行環境のComposeはmemoria-IaCが所有し、Web/APIのDockerfile・実行契約を利用します。

## Development用Container Registry

AWS Development用のApplication Runtime Imageは **GitHub Container Registry（GHCR）のPrivate Package** に格納します。`memoria-web`の1 imageと、`memoria-api`のAPI / Media Worker / Media Storage Cleanup / Outbox Publisher / Migrationの5 imageを、それぞれ所有するRepositoryのGitHub Actionsから発行します。

- `develop`への統合後Commitに対して各Repositoryの発行条件となるCIが成功した場合のみ、`GITHUB_TOKEN`で同Commit SHAのImageをPushします。Pull RequestではPackageを発行しません。発行Jobのみ`packages: write`権限を持ち、Development EC2やProductionの自動Deployは行いません。
- ImageのRepository名は `ghcr.io/hazuki3417/memoria-web` と `ghcr.io/hazuki3417/memoria-{api,media-worker,media-storage-cleanup,outbox-publisher,migration}` を基本とします。TagのCommit SHAは追跡用、**EC2での選択と固定は発行済みのManifest Digest（`@sha256:...`）**で行います。BuildされたImageとDeployされたImageのDigestを追跡可能にします。
- Private Packageの可視性、Source RepositoryからのActions Access、Pull可能なGitHub IdentityとToken権限は初回Publish時に確認します。EC2では管理者が必要時に読み取り権限のGitHub Credentialで認証し、Digest固定のImageを手動Pullします。TokenをEC2の恒久設定、Compose環境変数、Git、Docker Imageに配置しません。AWS Instance RoleはGHCR Private Packageの認証手段とはなりません。
- 起動とMigrationは従来どおり`memoria-IaC`の手動Scriptが担当します。AWS ECRはDevelopmentの標準Registryには採用せず、将来のAWS Runtime形態や運用コストが変化した場合に再評価します。既存のBundle Export/ImportはオフラインFallbackとして保持します。
- GitHub PackagesのStorage・転送の課金、Retentionとアクセス制御は実運用で確認します。GHCR採用はProduction Release Artifactの発行タイミング・Retention・CD方式まで決めるものではありません。

## BuildKitとimageの再利用

build commandは環境ごとに実行し、BuildKitのlayer cacheで実際の再buildを抑えます。CIではimageをbuildする段階とcontainerを起動する段階を分け、build済みimageの起動時には`docker compose up --no-build`を使用できます。

GHCR上の共通base imageは標準構成に含めません。Media Workerのnative依存が増え、build時間や転送量が実際の問題になった場合に限り、base imageの公開範囲、更新手順、cache効果を確認して検討します。

CIはLinux runner上で必要なruntimeをsetupし、local環境保護を目的とするDevboxの導入を必須にしません。CIの検証項目と実行段階は[テスト設計](/test-design)を参照してください。

## Deploy、migration、rollback

GitHub ActionsでbuildしたDocker imageをcommit SHAまたはdigestで識別し、同じartifactをdeployへ再利用します。latestを本番の識別子にしません。AWS接続はOIDC、EC2への操作はSSMを標準とし、長期Access KeyとSSH公開を前提にしません。

PostgreSQL migrationは専用の一時containerでdeploy全体につき一度だけ実行し、成功後にApplicationを更新します。process起動ごとの自動migrationは行いません。複数EC2がある場合だけ1台ずつrolling deployします。

production deployは人間の承認を必要とし、environmentごとの同時実行を防ぎます。rollbackは互換性を維持した以前のimmutable imageへの再deployを基本とします。詳細は[EC2・Docker運用基盤](/system/infrastructure/ec2-runtime-operations)と[DB schema migration](/system/data/schema-migration)を参照してください。
