# 設計書テンプレート

## 目的

Product domainごとの設計書について、ページの責務、必須の章立て、記載粒度、表記を統一します。テンプレートは記載漏れと形式の揺れを防ぐ基準であり、不要な空見出しや意味のないページを増やすものではありません。

## 共通の書式

- ページ先頭は、単独で対象と内容を識別できるH1見出しにする。
- H1の直後に「概要」を置き、対象範囲、所有者、目的を記載する。
- 実装との差分がある場合は、概要直下に「実装状況」の引用ブロックを記載する。
- 同じ情報を別domainやContextへ複製せず、正本へlinkする。
- 未決定事項と初回Release対象外は、決定済み仕様と分けて関連Issueへlinkする。
- 共通規約は横断設計へ集約し、domain固有ページでは適用関係と例外だけを記載する。
- 名称は同じ概念に対して統一し、表の列順、章立て、粒度をページ種別ごとに揃える。
- 実装に必要な制約、境界条件、失敗時処理を省略せず、不要な詳細は機械的に追加しない。

## Domain概要

推奨fileはindex.mdxです。

1. 概要: domainの目的、対象範囲、実装との差分。
2. 主要概念: entity、actor、重要な用語。
3. 制約と責務境界: 所有する情報と他domainへの依存。
4. 設計書の読み取り順序: 個別ページへのlink。
5. 初回Release対象外: 対象外の機能と追跡Issue。

## ユースケース

推奨fileはuse-cases.mdxです。

1. 概要: 対象actorと操作範囲。
2. Actor: 必要な場合は役割を表で示す。
3. ユースケース: 操作ごとに前提条件、実行主体、処理結果、境界条件を記載する。
4. 対象外: 提供しない操作と理由、必要な場合は関連Issue。

各操作には一つの見出しを設け、正常系だけでなく拒否条件と他domainへの影響を明示します。

## 認証・認可

推奨fileはauthorization.mdxです。認証と認可をまとめる必要があるdomainではauthentication-authorization.mdxを使用できます。

1. 概要: 認証・認可の対象と責務境界。
2. 主体と役割: actor、role、必要な前提条件。
3. 操作と権限: 操作、許可主体、条件、禁止事項。
4. 権限失効: 退会、削除、session失効などの影響。
5. エラーと境界条件: 未認証、権限不足、対象消失、競合。

## 論理データモデル

推奨fileはdata-model.mdxです。

1. 概要: domainが所有する概念と目的。
2. Entityと関連: entity、関連、多重度、状態。
3. 不変条件: 排他性、一意性、必須条件、状態遷移。
4. 他domainとの境界: 所有者と正本へのlink。

物理型、index、SQL固有の制約は物理データモデルへ分離します。

## 物理データモデル

推奨fileはphysical-data-model.mdxです。

1. 概要: 対象domain、所有table、実装との差分。
2. 共通規約: [物理データモデル共通規約](/system/data/physical-model-conventions)への参照とdomain固有の例外。
3. 全体ER: 関連が複数ある場合にdiagramを示す。
4. 所有table: tableごとにcolumn、型、制約、意味を記載する。
5. index・一意制約: 該当tableの直下で検索条件と重複防止を説明する。
6. 削除規則: FK動作、物理削除、保持対象、例外を説明する。
7. 他domainとの境界: 外部参照と設計の正本を示す。

column表は「列 / 型 / 制約 / 意味」の4列に統一します。共通のID型や時刻型をdomainごとに再定義せず、共通規約へlinkします。

## レコードパターン

推奨fileはrecord-patterns.mdxです。

1. 概要: 検証する操作と対象範囲。
2. 代表的な正常パターン: 操作前後のrecordと結果。
3. 禁止・境界パターン: 制約違反、重複、競合。
4. 非影響範囲: 変更してはいけない他domain・他record。

## 整合性とTransaction

推奨fileはconsistency-transactions.mdxです。

1. 概要: 不変条件とTransactionの対象。
2. Transaction境界: 何を同じ処理単位で確定するか。
3. 競合制御: lock順序、条件付き更新、重複request。
4. 外部I/Oと失敗時処理: 冪等性、再試行、復旧、運用。
5. 他domainとの境界: 所有者と正本へのlink。

## 設計判断

推奨fileはdesign-decisions.mdxです。

1. 概要: 何についての判断を記録するか。
2. 採用した判断: 判断ごとに決定、意図、制約を記載する。
3. 採用しない方式: 不採用理由と必要な将来Issue。
4. 他domainへの影響: 別domainの正本へのlink。

一覧表だけで判断を終えず、後から判断理由を再確認できる粒度で背景とtrade-offを残します。
