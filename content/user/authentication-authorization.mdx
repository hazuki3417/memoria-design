# Userの認証と認可

## 概要

> 実装状況: Access Token検証の基盤は存在します。Memoria User解決、User登録・Profile更新・削除は再実装中です。

Auth0とMemoriaの責務、User固有の認証主体解決、再認証、復帰先を定義します。全domain共通の認証、認可、個人情報、秘密情報の扱いは[認証・認可・Privacy共通方針](/system/cross-cutting/authentication-authorization-privacy)を参照します。

## 主体と役割

| 主体 | 役割 |
| --- | --- |
| User | Auth0で認証し、Memoria Userとして操作する |
| Auth0 | password、外部identity、認証sessionを管理する |
| Memoria | issuer・subjectと内部Userの対応、nickname、User状態を管理する |
| 各Memoria domain | Membership、Administrator、Media権限を管理する |

## 操作と権限

| 操作 | 許可主体・条件 | 禁止事項 |
| --- | --- | --- |
| User登録 | Auth0で認証済みで、issuer・subjectに対応するUserが存在しない主体 | 同じissuer・subjectの重複登録 |
| 通常操作 | issuer・subjectに対応するACTIVE User | DELETING User、登録未確定Userによる操作 |
| nickname変更 | ACTIVE User本人 | 他Userのnickname変更 |
| account削除確定 | ACTIVE User本人。最終確定前にAuth0で再認証する | 再認証失敗・取消し・期限切れ時の削除開始 |

Access Tokenの検証とMemoria Userの解決は分離します。APIの認証境界はAccess Tokenを検証してissuer・subjectから認証主体を確定し、各Use Caseが必要なUser状態を解決します。User登録はUserが未登録であることを要求し、通常操作は対応するUserがACTIVEであることを要求します。Clientからissuer・subjectを受け取って操作主体を指定させません。

## 権限失効

LogoutではMemoriaとAuth0のsessionを終了します。session失効時は再Loginし、User状態と現在のCommunity権限を再評価します。UserがDELETINGへ遷移した時点でLoginと新しい操作を拒否し、cleanup完了後はMemoria Userを物理削除します。

Login・登録後の復帰先はallowlistに一致する内部相対URLだけを受け付け、Uploadや削除操作を自動再開しません。

## 取得する認証情報

Auth0からはissuer、subjectと登録画面のnickname初期値に使う表示名だけを利用します。表示名が取得できない場合も、issuer・subjectが正常に確定していればnicknameの手入力による登録を許可します。表示名の取得失敗を認証失敗とは扱いません。一方、issuer・subjectを確定できない場合は登録を許可せず、再Loginを案内します。emailとprofile画像は要求・保存せず、issuer・subjectを画面や通常logへ出力しません。

## GraphQLでの登録状態の解決

認証済み主体の現在Userを取得する`me` QueryはUser自体をnullableとします。Access Tokenが有効でissuer・subjectに対応するUserが存在しない場合は`null`を返し、登録前の正常状態として扱います。ACTIVE Userが存在する場合はUserを返し、DELETING Userは通常操作と同様に拒否します。

Userのfieldを登録状態のためにnullableにはせず、Userが存在する場合のProfileや識別子は各fieldの業務上のnullabilityに従います。

## 認証主体の解決

issuerとsubjectの組は1件のUserにだけ対応します。同じemailや表示名を根拠に統合しません。一致するUserがない場合は登録画面へ遷移し、複数件に一致する不整合は認証失敗として運用対応します。

## 再認証

account削除の最終確定前はAuth0再認証を必須とします。失敗・取消し・期限切れの場合は削除Jobを開始せず、MediaとCommunityの個別確認も省略しません。

再認証は確認済みの削除計画に対する本人確認として扱います。再認証後にCommunityの扱い等の削除計画を変更した場合は、その再認証結果を最終確定に利用せず、変更後の削除計画についてReviewと再認証をやり直します。

強制再認証とcallbackはBFFが担当します。成功後、BFFは認証済みAccess Tokenと対象ReviewをAPIへ渡し、APIは認証主体とReview ownerを照合して短期の再認証状態をServer-sideで保持します。Browserへ再認証証明を公開せず、最終削除Mutationにも証明値を渡しません。

再認証状態は対象Reviewにだけ有効です。期限切れ、Reviewの変更・再生成、削除確定成功後には再利用できません。callback成功だけでは削除を開始せず、Memoria上の最終確定Actionを別途必須とします。Account deletion専用のAuth0 Authorization requestでは `prompt=login` と `max_age=0` を指定し、通常Login routeとは分離します。通常Sessionが新しいことだけを再認証成立の根拠にしません。callback stateは対象ReviewへServer-sideでbindingし、任意の外部return URLを受け付けません。

API側の再認証bindingは再認証成立時から10分間だけ有効とし、単回使用とします。期限切れ、Review変更・再生成、削除確定成功時に無効化します。bindingの永続化媒体は実装上のtransaction・複数instance・障害時挙動を満たすServer-side storeを使用し、Browser Cookieやlocal storageを正本にしません。具体的なtable/cache選択はImplementation Detailです。

## エラーと境界条件

| 状況 | 扱い |
| --- | --- |
| 期限切れ・不正なtoken | 認証を拒否する |
| issuer・subjectに一致するUserなし | 登録画面へ案内する |
| DELETING User | Loginと操作を拒否する |
| account削除時の再認証失敗 | 削除Jobを開始しない |
| 外部URLへの復帰要求 | 拒否する |
