# Media処理と派生物

> 全体の責務分担、failure path、シーケンス図、採用理由は[Media登録・非同期処理アーキテクチャ](/media/upload-processing-architecture)を参照してください。

## 概要

> 実装状況: 幅別Variant生成、Processing Job、Outbox、Media Workerを実装中です。各処理の接続は進んでいますが、ビルド・統合検証は未完了です。

Originalは利用者がアップロードした画像・動画そのものです。表示用の派生物を生成してもOriginalを変更せず、管理主体や公開範囲を保存パスへ含めません。PDF、Office文書、音声単体は対象外です。

## 保存する情報

| 情報 | 責務 | 保持 |
| --- | --- | --- |
| Original | 利用者がアップロードした元データ | Object Storageへ永続化 |
| Media Variant | 表示に適した派生ファイル | Object StorageとDBへ永続化 |
| Processing Job | 生成処理の状態と再実行の管理 | DBへ永続化 |
| 処理中間データ | decode・resize・encodeの一時データ | Worker内のみ。永続化しない |

Mediaは画像と動画を共通に表す概念です。Image・Videoが種別固有の属性を持ち、Media Variantは種別に応じた派生物を表します。

## 画像のVariant

- Originalのアスペクト比を維持したWebPを生成します。
- Originalは変更せず、VariantからEXIF、GPS、撮影日時、撮影端末などのmetadataを除去します。
- 画像の向きは表示に必要な範囲で補正し、metadata自体を業務dataとして抽出・保存しません。
- Initial ReleaseのVariant width baselineは320、640、960、1280、1920pxです。候補幅は表示contractの一部として扱い、単なるruntime tuningで暗黙変更しません。将来変更する場合はMedia配信・Frontendの`srcset` / `sizes`との整合を確認します。encode品質等の処理parameterは実装・運用計測に基づき調整できます。
- Originalを超える幅への拡大は行いません。候補幅の間に収まるOriginalには、Originalと同じ幅のVariantを追加できます。
- 一覧用thumbnailと詳細用previewを別々の保存資源として定義しません。画面の表示目的に応じて同じVariant集合から選択します。
- 一覧では`object-fit: cover`、詳細表示では`object-fit: contain`など、切り抜きの違いは表示側で表現します。
- Browserは`srcset`と`sizes`を使用して画面サイズ・device pixel ratioに適したVariantを選択します。
- 透かしは要件に含めません。必要性が合意されるまでは生成処理へ追加しません。

| Originalの幅 | 生成幅の例 |
| --- | --- |
| 200px | 200px |
| 800px | 320px、640px、800px |
| 2400px | 320px、640px、960px、1280px、1920px |

Initial ReleaseでUploadを受け付けるOriginal形式は**JPEG、PNG、WebP**です。**HEIC / HEIFは初回リリースの受理対象から延期**し、対応可否を別課題で管理します。AVIFもInitial Releaseの入力形式には含めません。

拡張子やClient申告MIME / HTTP Content-Typeを形式判定の正本にしません。Server側で実fileのsignature / containerを解析し、許可形式として識別でき、かつ画像としてdecode可能であることを受理条件とします。受理したOriginalは無加工で保持し、表示用には他形式と同じWebP Variant集合を生成します。

file extensionやClient申告MIMEはClient側の早期Feedbackや補助情報に利用できますが、それらと実file内容が一致しないことだけを理由に拒否しません。実内容が許可形式として正常なら受理でき、反対にextensionや申告MIMEが許可形式を示していても実内容が未許可形式・不正container・decode不能なら拒否します。

Mediaへ保存する`mime_type`はClient申告値ではなくServerが実内容を検証して確定したcanonical MIMEとします。Original file nameはUserが選択した元file名として保持し、実形式に合わせる目的でextensionを書き換えません。将来HEIC / HEIFを導入する場合、Product上の受理形式とcontainer / profileから確定するcanonical MIMEの識別を分離します。

### canonical MIMEの確定・保存契約（Usageとの共通境界）

- **Upload Serverの必須責務**: Client申告のMIME、HTTP Content-Type、file extensionに依存せず、受信したOriginalの実byte列からsignature / containerを解析し、対応形式であることとdecode可能性を検証した上で、検証結果に対応するcanonical MIMEを確定する。Client申告値をそのまま `media.mime_type` へ保存してはならない。
- **保存の必須条件**: Originalの永続登録時には、検証済みcanonical MIMEを `media.media.mime_type` へ、Original実byte数を `media.media.file_size` へ保存する。Media / Custody / Processing Job等の登録transactionが成功した時点で両値が確定していることを保証する。未検証・未確定・未対応・decode不能なOriginalは登録成功にしてはならない。Variant Processingの成功を待ってcanonical MIMEを確定する実装にはしない。
- **責務の所在**: canonical MIMEの検証・確定はUpload側の責務である。Usage側で実ファイルを再取得・再検証したり、拡張子・申告MIMEで推測・補正したりしない。Upload実装では必ず検証結果をMedia登録へ受け渡し、DB保存まで結線する（将来のUpload実装で省略しない）。
- **形式分類**: Usageは保存済み `media.mime_type`（canonical MIME）から `OriginalImageFormat` へ導出する。初回リリースの新規受理形式は `JPEG` / `PNG` / `WEBP` に限り、互換性のため `HEIF` がenumに存在する場合でもUpload受理を意味しない。専用のcanonical formatカラムは追加しない。JPEGは `image/jpeg`、PNGは `image/png`、WebPは `image/webp`、将来HEIF familyを受理する際は実内容検証で確認したcanonical MIMEを `HEIF` に集約し、具体的なMIME集合をUploadの形式検証で確定させる。Usage独自に受理対象を増やさない。
- **未知・不整合データ**: 登録済みACTIVE OriginalにUsage分類不能なMIMEがある場合は、黙って除外、0件扱い、拡張子へのfallbackを行わない。総計とformat別内訳の一致を保てない集計結果を成功として返さず、データ不整合として検知・調査できるようにする。将来の受理形式追加時にはUploadのcanonical MIME契約・Usage分類・GraphQL enumを整合させる。
- **境界の確認**: Upload実装時のレビューでは「実byte検証 → canonical MIMEの確定 → DB保存」および「未検証Originalの登録拒否」を必須確認項目とする。Backendの自動テスト導入は全体のテスト方針が定まるまで本変更の必須条件としない。


Originalの向き、透過情報、decode可能性、file signature、画素数などを静止画像処理で検証します。変換できない形式を正常完了として扱いません。Upload受付時に確定できる不正入力と、受付後の非同期処理でのみ判明する処理失敗は区別します。

Initial Releaseでは1 Originalあたりのfile size上限を128 MiBとします。この値はProduct上限であり、Client、GraphQL/API、HTTP server、reverse proxy等の実装上限は128 MiBの有効な画像を拒否しないよう整合させます。file sizeだけではdecode後のresource使用量を制限できないため、画像安全上限を独立して適用します。Initial Releaseでは1画像あたりの総pixel数を100 megapixels（100,000,000 pixels）以下とします。width / heightはそれぞれ32,768 pixels以下とします。総pixel数上限とは独立して適用し、総pixel数が100 MP以下でも極端に縦長・横長な画像は拒否します。

## EXIF OrientationとVariant幅の整合

JPEGのEXIF Orientation（1〜8）を表示用pixelへ反映してからWebP Variantを生成します。Original byte列とEXIF自体は改変しません。90度・270度回転の場合は**補正後の幅**をVariant生成幅の基準とします。

- publicationではGeneratorから補正後の幅・高さを渡し、保存済みOriginal寸法と同値または縦横反転であることを照合します。
- 320 / 640 / 960 / 1280 / 1920pxのうち補正後の幅以下の候補を生成し、1920px以下なら補正後Original幅も含めます。拡大はしません。
- terminal Jobのcleanupは縦横入替時に生成し得る幅も候補とし、公開中のStorage keyを除外します。

## 処理単位

1 request・1 Processing Jobは1 Mediaを扱います。画面で複数選択できてもAPI requestとJobはMedia単位に分離し、失敗とretryの影響を限定します。Upload Batchが必要になった場合も画面の集約概念として扱い、個別Jobの独立性を維持します。

Processing Jobのretryはfailure種別で分けます。一時的なI/Oや実行基盤の障害等、同じ入力で回復可能なfailureはSystemが同じJobを自動retryします。decode不能・破損等、同じOriginalでは回復しないfailureは自動retryしません。retry可能なfailureもruntimeで定めた上限へ到達した場合はterminalなFAILEDとして確定します。

Initial ReleaseではterminalなProcessing failureに対するUser向け手動retryを提供しません。運用上のreprocessではterminal Jobの完了後に新しいProcessing Jobを作成し、同じOriginalから派生物を再生成します。Media登録済みである以上、Processing failureだけを理由にMediaをMedia Browserから除外せず、表示用Variantを利用できない状態として扱います。

## 動画と容量情報

Video Variantの形式・生成条件は動画ユースケースの具体化後に決定します。画像専用の前提をMedia全体へ固定しません。

容量把握にはOriginalの`media.file_size`とVariantの`size_bytes`を使用できます。ただし課金、料金表、Billing Usageは要求として確定していないため構築しません。

## Processing状態同期の横断設計案（Issue #339）

> 設計レビュー中。合意済み原則と提案値を区別する。実装・API契約の変更は未着手。

### 合意済みの原則

- Media Upload・Media Browser・Media Detailなど、非同期画像Processing状態を表示する各Featureで**共通の集約Polling**を利用する。MediaごとのPolling timerを作らない。
- BackendをProcessing状態の正本として、**Media単位**で結果を同期する。Apollo Cacheを共有し、Contextや独立StoreへBackend状態を複製しない。
- Media UpdateのTag保存・HTTP Upload転送進捗は今回の監視対象外。UI表現（Badge、Loader、Thumbnail）は画面別に維持する。
- SSE/WebSocketは今回導入しない。将来の通知要件が具体化した際に再検討する。
- PROCESSING / READY / FAILEDを区別する。FAILEDでもMedia登録は維持し、User向け手動reprocessを新設しない。

### API契約案（人間の最終承認待ち）

現状は `media(id)` とRelay Connection `mediaList` で状態・Variantを取得できる。一括状態照会は未提供。新しいGraphQL Queryで `scope` と重複除去した `mediaIds` を受け取り、各Media IDの `PROCESSING/READY/FAILED` を軽量に返す案とする。結果は必ず現在のScopeで認可し、削除・不存在・アクセス不能をProcessing失敗へ偽装しない。応答Schema、不可視項目の扱い、件数上限は要合意。監視Queryは署名付きVariant URLを発行せず、READY検知時に対象Mediaの既存Queryを認可付きで再取得する。READYでもVariant取得・画像読込の成否は別に扱う。

### Client Coordinator案

- Consumerは `(Scope, Media ID)` を登録・解除し、重複登録を集約する。参照がなくなった対象を監視から外す。Scope変更・User変更で古い応答を適用しない。
- Processing対象ゼロ件では通信しない。Scope別・上限付きBatchで同時に照会し、前Tickと重複送信しない。Timerは共有し、通信数をMedia件数へ直接比例させない。上限を超える場合のBatchの分割・公平性は負荷試験で決定する。
- Browserは取得済みRelay ConnectionのProcessing対象だけを登録し、処理完了時に対象MediaのApollo正規化Cacheへ反映。Connection全体を定期refetchせず、追加読み込み済み項目・Tag filter・Selection・Scrollを保つ。
- UploadはHTTP 201 ReceiptのMedia IDをfile行と関連付けて登録し、結果不明な送信を推測でProcessingへ移さない。READY/FAILEDをfile行へ反映する。
- DetailはDialog表示中・対象MediaがPROCESSINGのときだけ登録。既存Detail個別Pollingの停止・再開・3回失敗ルールと統合時の振る舞いを明示して整合させる。
- Processing監視は署名付きVariant URLの更新と別責務。Browserの現行12分URL再取得が追加読込済みページを失う挙動は別途回帰検討する。Apollo Cacheの `__typename/id` 正規化とQuery field整合も実装前に検証する。

### 監視ライフサイクル案

| 条件 | 動作 |
| --- | --- |
| PROCESSINGを登録 | 初回確認して共有Pollingを開始 |
| READY | 対象Media詳細・Variant再取得が成功したら表示を更新し、Processing監視から解除 |
| FAILED | 対象Mediaだけ終端失敗を反映し監視解除、登録Mediaは残す |
| 監視対象0件・Document非表示 | 定期監視を止める |
| 可視復帰 | 現在登録されているMediaを直ちに再確認 |
| Scope/User変更 | 旧登録と古いQuery応答を無効化 |
| 通信障害 | Backend状態は推測で変えず、再試行可能なエラーとして扱う |
| 認可喪失・削除 | FAILEDに変換せず、アクセス不能を別状態として処理 |
| Variant取得・画像読込失敗 | READYと画像表示失敗を分離し、既存の明示再試行方針と整合させる |

**確定済みの横断監視規則（2026-10-27合意）**:

- **Polling間隔は10秒**。監視対象がある場合、集約Coordinatorがこの間隔で状態確認する。Mediaごとに個別Timerを持たない。
- **Polling通信が3回連続して失敗したら自動監視を停止し、明示的な手動再開を必要とする**。通信失敗をProcessingのFAILEDとして扱わず、未確認の結果をREADYと推測しない。成功した状態照会による失敗カウントのリセットを前提とする。具体的なBatch間の失敗カウント境界と再開UIは後続設計で定義する。
- **Documentが非表示の間はPolling停止**。可視状態への復帰時には監視対象の状態を**即時再確認**する。ただし通信失敗3回で停止済みの場合に、可視復帰だけで手動再開条件を解除しない。復帰時確認と自動停止条件の優先関係はこの規則に従う。
- 停止中も最後に確認したProcessing状態を成功へ推測変更しない。

**引き続き未決定**: Batch件数上限、Batch単位・Scope単位の失敗カウント境界、複数Tab集約、画面ごとの手動再開UI、再取得失敗と画像読込失敗の区別。

### 実装仕様レベルの詳細設計（Issue #339、未合意箇所は提案）

この節はVisual Prototype以外の実装・テストを見積もれるようにする詳細仕様案である。既存の合意（集約Polling、10秒、連続3回停止・手動再開、非表示停止・復帰即時確認）は確定とし、以下の**提案**は最終レビューまで仕様変更として確定しない。

#### APIの具体的な提案契約

```graphql
enum MediaProcessingLookupStatus { FOUND UNAVAILABLE }
type MediaProcessingLookupItem {
  mediaId: ID!
  lookupStatus: MediaProcessingLookupStatus!
  processingStatus: ProcessingStatus
}
extend type Query {
  mediaProcessingStates(scope: ScopeInput!, mediaIds: [ID!]!): [MediaProcessingLookupItem!]!
}
```

- `FOUND`なら `processingStatus` は必須、`UNAVAILABLE`なら `null`。GraphQL SDLで条件付きnon-nullは表現できないためResolverとテストで保証する。存在しない・削除済み・権限なしは同一の `UNAVAILABLE` として扱い、存在有無を開示しない。Scope自身へのアクセス権なしは既存ScopeのGraphQL認可Error契約に従って**Query全体を拒否**する。
- 入力Media IDは必須、空配列は空結果、重複IDは `VALIDATION`。一度のQueryは**最大100 ID（提案）**。順序は入力順、入力1件につき出力1件。混在する `FOUND` と `UNAVAILABLE` は部分結果として返す。構文不正なID・上限超過はQuery全体を `VALIDATION` とする。
- Mediaの有効性・可視性はMedia Listと同じActor/Scope認可を毎回適用する。独立した安全でないID-only SELECTを作らない。User/Community別の認可をClient cacheの状態だけで判断しない。
- 一括照会はProcessing Statusのみ返し、Variant/URLを署名しない。処理状態はDB確定済みのJob/Variantの読取Projectionに揃え、`READY`返却時点で公開済みVariantを後続Media Queryが読めることを同一DBの確定順序で保証する。
- `media(id)` は既存GraphQL Queryとして存在するが、Scope別の可視性とVariant返却保証は実装で再検証する。複数READYのVariant詳細取得を最初からN個の同時Requestで行わず、既存GraphQL Documentでalias/Batch化できるかを検証し、必要なら**別途**軽量の認可付き `mediaByIds` をAPI設計に追加する（未決定）。GraphQL Queryは必要なVariantだけ選択し、失効したURLを再利用しない。

#### Coordinatorの状態とAPI（Web設計案）

単一Apollo Client単位の `MediaProcessingMonitor` をApplication Provider境界へ配置する案。Webが直接Redis/Jobを読むことは禁止。Consumerの登録単位は `scopeKey + mediaId` で、`scopeKey` は`PERSONAL`または `COMMUNITY:<communityId>` を正規化した値。同一Mediaを複数Consumerが使う場合も参照登録は区別し、通信だけ集約する。

```ts
type MediaProcessingMonitorState =
  | { kind: "active" }
  | { kind: "paused-hidden" }
  | { kind: "stopped-network-error" }
  | { kind: "idle" }

type WatchToken = {
  scopeKey: string
  mediaId: string
  consumerId: string
}
// 概念Interface。実装時にHook/Provider名を確定する。
interface ProcessingMonitor {
  watch(token: WatchToken): () => void
  retry(scopeKey?: string): void
}
```

- `watch`は登録解除関数を返し、StrictModeのmount/unmount、Dialog切替、Context切替に対して冪等に解除。Backend `PROCESSING`の対象のみ登録し、READY/FAILED/UNAVAILABLEなら登録を終了する。
- 複数Scopeで同じMediaが見えてもリクエストは**Scope単位で認可**する。単一Timerを用い、TickでScope別Batchを作成する。これは「1 Mediaにつき1 Request」を防ぐものであり、Scope数やBatch分割まで常に1 Requestと保証するものではない。
- 初回watch時は速やかに照会し、その後は直近の開始時点から最短10秒後に定期照会する。新規watch追加は実行中Batchに割り込ませず次Tickへ含める。複数同時watchの初回照会は同一microtask/短い集約窓でcoalesceする（集約窓の数値は実装詳細）。
- 通信中の同じ `scope + batch` は再送せず、前Tickが終わらない場合次Tickをskipする。失敗時も固定10秒間隔を基準とし、再開を無限に積み上げない。
- 登録更新ごとにGenerationを保持し、通信完了時点で `scopeKey`・登録所有者・Generationを再検証。古いresponseはCacheへ書かない。logout時はCoordinatorと認証依存Cacheを破棄する既存のsign-out契約に従う。
- Document非表示時はTimer停止、実行中Responseは条件確認して扱う。可視復帰時の即時照会は、既存通信処理と多重化せず一度だけ要求。ネットワーク障害による停止中は復帰イベントで自動再開しない。
- **提案**: 失敗回数はScopeごとの「Polling cycle」単位で管理し、1cycleで複数Batchがあればいずれかの通信失敗時に1回失敗、全Batch成功時にゼロへ戻す。部分成功Batchは成功したMediaへ反映してよいが、失敗Batchの対象を成功扱いしない。3cycle連続で失敗したScopeだけ停止し、他Scopeは継続。manual retryは対象Scopeのfailure countを初期化して即時再確認し、その後定期Pollingを再開。未認証や権限失効などの非一時エラーは3回の通信失敗としてretryし続けず、Auth/Scopeの既存回復画面に引き渡す。
- **提案**: 100 IDずつに分割し、Scope内の各Batchを順次照会。負荷試験で必要なら並列数を制限しつつ変更。100ID超の対象も取りこぼさず毎cycleですべて巡回する。複数タブの通信共有はInitial Release対象外（タブごとに可視時のみ監視）とし、タブ間の状態は次回Queryで最終的に一致させる。

#### Apollo Cache・Variant取得の状態整合

- Apollo Clientのデフォルト `Media: { keyFields: ["id"] }` 相当の正規化が実際に成立するか、generated Queryが `__typename` を含むか確認する。`processing.status` の更新はMedia IDで `cache.modify` /Fragment等を通して既存Mediaへ紐づける。`MediaProcessing`が埋め込み型でも親Mediaから安全に書換え可能なQuery/Fragmentを用いる。
- Pollingで `READY` を受信しても、Variant詳細Queryに失敗した場合はVariant表示を成功扱いしない。`processing.status` のサーバー確定値は保持し、Thumbnail取得エラーを独立して表示・明示Retryする。Media Detailで合意済みの画像読み込みエラー手動Retryと同じ原則を適用。
- Backend Processing結果とVariant詳細更新は同一Mediaについて単調な進行を原則とし、遅延したPROCESSINGの応答でREADY/FAILEDを上書きしない。運用reprocess等で終端後の再処理が起きうる場合は、Job revision/versionを持つAPIが必要か別途確認して確定する。
- `mediaList`のRelay `edges/cursor/pageInfo`は状態監視によって書換えない。Tag filter・Scope切替時は既存Connectionを保ったまま監視集合だけ更新する。
- 署名付きVariant URL（現行15分期限、Webの12分更新）は独立して更新する。従来の先頭page `refetch` によりfetchMore分が消える問題はProcessing監視導入時に修正するか、別Issueとして切り分ける必要がある。新規Pollingがこの既存回帰を増幅しないことをAcceptanceに含める。

#### Feature別の接続

| Feature | Watchの開始 | 終了 | 結果反映とRetry |
| --- | --- | --- | --- |
| Media Upload | HTTP 201成功後の `mediaId` が取得できた行 | 画面離脱・当該行除去・終端 | 個別行のProcessing/READY/FAILED Badgeと集計。失敗はMedia Browserへ誘導、重複Uploadしない |
| Media Browser | 現在読み込み済みのConnectionのPROCESSING Node | Scope/Filter変更・一覧離脱・終端 | READYは当該タイルのVariant再取得、FAILEDは失敗Placeholder。追加ページ/選択/スクロール保持 |
| Media Detail | Dialog Openかつ対象がPROCESSING | Dialog Close・対象変更・終端 | Viewer・情報パネルのLoading/Failureへ反映。停止時はDialog内Retry |
| Group Browser等 | Media NodeのProcessing表示が存在する場合のみ | ConsumerのUnmount・終端 | Browserと同じ原則。現行実装の該当箇所を実装着手前に網羅確認 |

停止・手動再開の共通Statusは監視Coordinatorが保持するが、**UIの表示場所や文言はVisual Prototypeの範囲**。現行Visual/Behavior Contractを暗黙に改変しない。既存Detail固有の3回停止・Dialog内再開仕様は横断停止と同じ意味に揃え、画面間で異なる監視Timerを作らない。

#### 失敗種別の優先順位

1. 認証不可/Scope非許可: 当該Scopeの監視を無効化し、既存のAuth/Permission UIへ。Processing FAILEDとは区別。
2. 監視Queryの一時通信障害: 対象Scopeの連続失敗を加算。3回で停止し明示再開。各Mediaの直前確認済み状態は維持。
3. `UNAVAILABLE`: 当該IDの監視解除。存在・権限の詳細をUIに漏らさない。
4. `FAILED`: terminal Processing FailureとしてBadge/Placeholderに反映。User向けProcessing retryは設けない。
5. `READY` + Variant取得エラー: Processingの完了と画像表示可能性を分離。再試行はVariant取得だけを対象とし、Mediaを再Uploadしない。
6. `READY` + 画像読み込みエラー: Image elementの明示再試行。Processing監視は再開しない。
7. API結果の欠損/重複/未知Status: プロトコルエラーとして当該cycle失敗、無条件成功扱いせずTelemetryへ記録。

#### テスト仕様

- Backend: 不正/重複/101 IDs、空ID集合、単一Scope外Media、削除済み、共有権限失効、混在Found/Unavailable、Job自動Retry中のPROCESSING、完了直後のVariant公開可否、負荷試験100ID。
- Web単体: StrictMode登録解除、1 Mediaの3 Consumer登録、異なるScopeの同一ID、追加Media・Filter切替、古いResponse排除、複数Batch、未表示時にRequestしない、復帰時に即時1回、停止中の復帰では再開しない、cycle3失敗→手動再開。
- 結合: Upload HTTP 201→Media ID関連付け→Browserの同一MediaをREADY反映、FAILEDは登録維持、Detail Dialogの開閉・切替、signed URL有効期限、Variant取得失敗→手動再試行、画像Load失敗→手動再試行。
- 回帰: Relay追加読込済みpage維持・選択数/ID不変・Scroll/Filter維持、Responsive/UI表示差分、操作のKeyboard到達性。Visual Prototypeは変更せず、実装段階で既存Prototypeを比較基準として利用する。

#### 最終レビューの判断一覧

1. **API**: 上記 `mediaProcessingStates` のSchema、不可視時 `UNAVAILABLE` とScope単位Errorの区別、最大100 ID、重複ID拒否。
2. **Coordinator**: Scope単位の連続失敗カウンタ（3 cycle）、Batchの100件分割、複数Tabの集約なし。
3. **データ整合**: READY後Variant再取得のAPI効率と、reprocess時のrevisionの必要性。
4. **既存UIとの境界**: 各Featureでの手動再開UI配置とBrowserの12分URL更新で追加ページを失う現行挙動の改善範囲。**Visual Prototypeを変更して確定しない。**
