# Media処理と派生物

> 全体の責務分担、failure path、シーケンス図、採用理由は[Media登録・非同期処理アーキテクチャ](/media/upload-processing-architecture)を参照してください。

## 概要

> 実装状況: 現在は画像用のthumbnail・previewを扱っています。共通の幅別Variant、Processing Job、Outboxによる非同期処理への統一は未実装です。

Originalは利用者がアップロードした画像・動画そのものです。表示用の派生物を生成してもOriginalを変更せず、管理主体や公開範囲を保存パスへ含めません。PDF、Office文書、音声単体は対象外です。

## 保存する情報

| 情報 | 責務 | 保持 |
| --- | --- | --- |
| Original | 利用者がアップロードした元データ | Object Storageへ永続化 |
| Media Variant | 表示に適した派生ファイル | Object StorageとDBへ永続化 |
| Processing Job | 生成処理の状態と再実行の管理 | DBへ永続化 |
| 処理中間データ | decode・resize・encodeの一時データ | Worker内のみ。永続化しない |

Mediaは画像と動画を共通に表す概念です。Image・Videoが種別固有の属性を持ち、Media Variantは種別に応じた派生物を表します。

## 画像のVariant

- Originalのアスペクト比を維持したWebPを生成します。
- Originalは変更せず、VariantからEXIF、GPS、撮影日時、撮影端末などのmetadataを除去します。
- 画像の向きは表示に必要な範囲で補正し、metadata自体を業務dataとして抽出・保存しません。
- Initial ReleaseのVariant width baselineは320、640、960、1280、1920pxです。候補幅は表示contractの一部として扱い、単なるruntime tuningで暗黙変更しません。将来変更する場合はMedia配信・Frontendの`srcset` / `sizes`との整合を確認します。encode品質等の処理parameterは実装・運用計測に基づき調整できます。
- Originalを超える幅への拡大は行いません。候補幅の間に収まるOriginalには、Originalと同じ幅のVariantを追加できます。
- 一覧用thumbnailと詳細用previewを別々の保存資源として定義しません。画面の表示目的に応じて同じVariant集合から選択します。
- 一覧では`object-fit: cover`、詳細表示では`object-fit: contain`など、切り抜きの違いは表示側で表現します。
- Browserは`srcset`と`sizes`を使用して画面サイズ・device pixel ratioに適したVariantを選択します。
- 透かしは要件に含めません。必要性が合意されるまでは生成処理へ追加しません。

| Originalの幅 | 生成幅の例 |
| --- | --- |
| 200px | 200px |
| 800px | 320px、640px、800px |
| 2400px | 320px、640px、960px、1280px、1920px |

Initial ReleaseでUploadを受け付けるOriginal形式はJPEG、PNG、WebP、HEIC / HEIFとします。AVIFはInitial Releaseの入力形式には含めません。

拡張子やClient申告MIME / HTTP Content-Typeを形式判定の正本にしません。Server側で実fileのsignature / containerを解析し、許可形式として識別でき、かつ画像としてdecode可能であることを受理条件とします。HEIC / HEIFを含めOriginalは無加工で保持し、表示用には他形式と同じWebP Variant集合を生成します。

file extensionやClient申告MIMEはClient側の早期Feedbackや補助情報に利用できますが、それらと実file内容が一致しないことだけを理由に拒否しません。実内容が許可形式として正常なら受理でき、反対にextensionや申告MIMEが許可形式を示していても実内容が未許可形式・不正container・decode不能なら拒否します。

Mediaへ保存する`mime_type`はClient申告値ではなくServerが実内容を検証して確定したcanonical MIMEとします。Original file nameはUserが選択した元file名として保持し、実形式に合わせる目的でextensionを書き換えません。HEIC / HEIFというProduct上の入力形式と、container / profileから確定するcanonical MIMEの技術的識別は分離します。

Originalの向き、透過情報、decode可能性、file signature、画素数などを静止画像処理で検証します。変換できない形式を正常完了として扱いません。Upload受付時に確定できる不正入力と、受付後の非同期処理でのみ判明する処理失敗は区別します。

Initial Releaseでは1 Originalあたりのfile size上限を128 MiBとします。この値はProduct上限であり、Client、GraphQL/API、HTTP server、reverse proxy等の実装上限は128 MiBの有効な画像を拒否しないよう整合させます。file sizeだけではdecode後のresource使用量を制限できないため、画像安全上限を独立して適用します。Initial Releaseでは1画像あたりの総pixel数を100 megapixels（100,000,000 pixels）以下とします。width / heightはそれぞれ32,768 pixels以下とします。総pixel数上限とは独立して適用し、総pixel数が100 MP以下でも極端に縦長・横長な画像は拒否します。

## 処理単位

1 request・1 Processing Jobは1 Mediaを扱います。画面で複数選択できてもAPI requestとJobはMedia単位に分離し、失敗とretryの影響を限定します。Upload Batchが必要になった場合も画面の集約概念として扱い、個別Jobの独立性を維持します。

Processing Jobのretryはfailure種別で分けます。一時的なI/Oや実行基盤の障害等、同じ入力で回復可能なfailureはSystemが同じJobを自動retryします。decode不能・破損等、同じOriginalでは回復しないfailureは自動retryしません。retry可能なfailureもruntimeで定めた上限へ到達した場合はterminalなFAILEDとして確定します。

Initial ReleaseではterminalなProcessing failureに対するUser向け手動retryを提供しません。運用上のreprocessではterminal Jobの完了後に新しいProcessing Jobを作成し、同じOriginalから派生物を再生成します。Media登録済みである以上、Processing failureだけを理由にMediaをMedia Browserから除外せず、表示用Variantを利用できない状態として扱います。

## 動画と容量情報

Video Variantの形式・生成条件は動画ユースケースの具体化後に決定します。画像専用の前提をMedia全体へ固定しません。

容量把握にはOriginalの`media.file_size`とVariantの`size_bytes`を使用できます。ただし課金、料金表、Billing Usageは要求として確定していないため構築しません。
