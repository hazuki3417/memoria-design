# Mediaレコードパターン

## 概要

> 実装状況: このページのMedia、Custody、Access、Event tableは未実装です。Image Groupの一部だけが対応します。

具体的なIDとレコードを使用し、操作前後に存在すべきデータを定義します。例ではUserを`U1`・`U2`、Communityを`C1`・`C2`、Mediaを`M1`、Groupを`G1`・`G2`と表記します。

## Imageをuploadする

入力:

- Uploader: U1
- Media: M1
- file: `family.jpg`、image/jpeg、4 MiB、1920×1080

作成するレコード:

| table | key | 主な値 |
| --- | --- | --- |
| media | M1 | IMAGE、family.jpg、ACTIVE、uploaded_by=U1 |
| media_images | M1 | width=1920、height=1080 |
| media_custodies | M1 | user_id=U1、community_id=NULL |
| media_events | E1 | UPLOADED、actor=U1、to_user=U1 |
| media_processing_jobs | J1 | media_id=M1、status=PENDING |
| outbox_events | O1 | aggregate_id=M1、job_id=J1、未送信 |

作成しないレコード:

- media_videos
- media_community_accesses
- media_group_media

U1は著作権者ではなくUploaderと初期Custodianです。

Worker完了後は`media_variants`へ320、640、960、1280、1920pxのWebPを記録し、`media_processing_jobs(J1)`をCOMPLETEDへ更新します。重複配送時は同じ幅のVariantを追加作成しません。

## CommunityへImageを直接uploadする

UploaderがU1、投稿先がC1の場合、`media.uploaded_by_user_id=U1`、`media_custodies.community_id=C1`、`media_custodies.user_id=NULL`とします。U1の投稿履歴とC1の管理責任は別々に保持します。

C1参加者はVariantを閲覧できます。Original downloadと削除はC1のCommunity Administrator、およびC1へ参加中のUploader U1に許可します。U1が退会した場合、`media.uploaded_by_user_id=U1`が残っていてもMembershipがないため、閲覧・Original download・削除を拒否します。U1がUser削除され`uploaded_by_user_id=NULL`になった場合は「削除済みUser」と表示し、MediaはC1に残します。

## User管理Mediaを複数Communityへ共有する

操作前:

| table | key | 値 |
| --- | --- | --- |
| media_custodies | M1 | user_id=U1 |
| community_memberships | C1-U1、C2-U1 | U1が両Communityへ参加 |

C1、C2へ共有した後:

| table | key | 値 |
| --- | --- | --- |
| media_community_accesses | M1-C1 | created_by=U1 |
| media_community_accesses | M1-C2 | created_by=U1 |
| media_events | E2 | ACCESS_ADDED、target=C1 |
| media_events | E3 | ACCESS_ADDED、target=C2 |

`media_custodies(M1)`は変更しません。C1とC2の間に関係を作らず、Media本体も複製しません。

## 共有を一つだけ解除する

M1-C1を解除します。

- `media_community_accesses(M1,C1)`だけを削除
- M1-C2は維持
- CustodyとObject Storageは変更しない
- ACCESS_REMOVED eventを追加

## Communityを作成して招待する

| table | key | 主な値 |
| --- | --- | --- |
| communities | C1 | name=家族 |
| community_memberships | C1-U1 | U1が参加 |
| community_administrators | C1-U1 | U1がAdministrator |
| community_invitations | I1 | community_id=C1、token_hash=HASH1、expires_at=発行から7日後 |

U2がI1から申請すると`community_join_requests(R1)`を`status=PENDING`で登録します。U1または他のAdministratorが承認すると、同じTransactionで`community_memberships(C1,U2)`を作成し、R1を`APPROVED`へ更新します。拒否や本人取消しの後は、同じCommunity・Userで新しい申請行を作成できます。

## User退会時に共有とCommunity分類を解除する

U1がM1をC1とC2へ共有し、C1のGroup G1とTag T1へ関連付けている場合、C1からの退会時に次を同じTransactionで処理します。

- `community_administrators(C1,U1)`が存在すれば、別Administratorが残ることを確認して削除
- `community_memberships(C1,U1)`を削除
- `media_community_accesses(M1,C1)`を削除
- M1とC1のG1・T1の関連だけを削除
- `media_community_accesses(M1,C2)`、M1本体、Custody、G1・T1本体を維持

U1がUploaderでCustodianがC1である別Mediaは削除しません。

## Community削除の登録パターン

C1にCommunity CustodyのMediaが残っている場合、Community削除を拒否します。対象Mediaが0件であれば、C1のMembership、Administrator、招待、参加申請、Community Group・Tag、M1-C1共有を削除します。User管理M1、M1-C2共有、C2側の分類は変更しません。

## UserからUserへ委譲する

管理主体の委譲は将来機能であり、以下の委譲パターンは初回Release対象外です。

操作前:

- Custody: M1→U1
- Access: M1→C1、M1→C2

同一DB transactionで次を行います。

1. M1のCustody行を`FOR UPDATE`でlock
2. M1のAccessを全削除
3. CustodyをU2へ更新
4. CUSTODIAN_CHANGED eventを追加

操作後:

| table | 状態 |
| --- | --- |
| media_custodies | M1→U2 |
| media_community_accesses | M1の行は0件 |
| media_events | from_user=U1、to_user=U2 |
| media.uploaded_by_user_id | U1のまま |

## UserからCommunityへ委譲する

M1をU1からC1へ委譲します。

- 既存Accessを全削除
- Custodyを`user_id=NULL、community_id=C1`へ更新
- CUSTODIAN_CHANGED eventへfrom_user=U1、to_community=C1を記録

C1参加者はCustodyとMembershipにより閲覧します。M1-C1というAccess行は作りません。

## CommunityからUserへ委譲する

M1をC1からU2へ委譲します。

- CustodyをU2へ更新
- Accessは0件のまま
- Eventへfrom_community=C1、to_user=U2を記録

U2が必要なCommunityへ改めて共有します。

## 禁止するCustodyパターン

| user_id | community_id | 判定 |
| --- | --- | --- |
| U1 | NULL | 許可 |
| NULL | C1 | 許可 |
| NULL | NULL | CHECK違反 |
| U1 | C1 | CHECK違反 |

同じMediaへCustodyを2行登録することはmedia_id PKで禁止します。

## Media Group

### 単純構造

- G1: U1 scope、「旅行」
- M1、M2をG1へ追加

`media_group_media`:

| media_group_id | media_id |
| --- | --- |
| G1 | M1 |
| G1 | M2 |

### 木構造

Groupは「旅行」→「日本」→「東京・京都」と「旅行」→「海外」です。

`media_group_relations`:

| parent | child |
| --- | --- |
| 旅行 | 日本 |
| 日本 | 東京 |
| 日本 | 京都 |
| 旅行 | 海外 |

### DAG

「沖縄」は「旅行」と「夏」の両方を親に持ちます。

| parent | child |
| --- | --- |
| 旅行 | 沖縄 |
| 夏 | 沖縄 |

`沖縄→旅行`または`沖縄→夏`の追加は循環になるため拒否します。異なるUser・Community scope間の親子関係も拒否します。

## User削除

U1がM1・M2・M3を管理している場合:

| Media | 選択 | 結果 |
| --- | --- | --- |
| M1 | U2へ委譲 | CustodyをU2へ変更、Access解除 |
| M2 | C1へ委譲 | CustodyをC1へ変更、Access解除 |
| M3 | 削除 | DELETINGへ変更しstorage削除を開始 |

U1 CustodyのMediaが0件になり、U1が管理するCommunityの委譲または削除も解決した後だけUserを削除します。UploaderとEvent actorのU1参照はON DELETE SET NULLになります。

## Media削除

削除要求時:

- media.statusをDELETINGへ更新
- 原本・preview・thumbnail・動画派生物ごとにstorage operationを作成
- 新しい閲覧・更新・共有・委譲を拒否

storage削除完了後のDB transaction:

- Group関連、Access、Custody、subtype、Mediaを削除
- DELETED eventを追加
- Eventと完了済みstorage operationは保持期間に従って削除

Media本体を復元するレコードやarchive pathは作りません。
