# テスト設計

## 概要

> 実装状況: 各repositoryにテスト基盤はありますが、すべての層・主要結合scenarioを網羅しているわけではありません。

成果物のbuild、test、静的解析、性能検証はGitHub Actionsを正本とします。人間は必要に応じてローカル開発環境で再現できますが、ChatGPTの実行環境では成果物を検証せず、PR作成後のquality gateへ委譲します。

| 対象 | 主な検証 |
| --- | --- |
| Web | 表示、操作、loading、empty、error、accessibility |
| API domain・service | ユースケース、認可、境界値、状態遷移 |
| Repository | SQL、制約、transaction、対象外dataへの非影響 |
| GraphQL | schema、resolver、error、生成互換性 |
| 非同期処理 | Outbox commit、Redis配送、重複配送、Worker retry、pending recovery |
| Media配信 | Variant生成、Original認可、Community権限、署名期限 |
| IaC | unit test、synth、diff、IAM、resource置換 |
| 結合 | Web・API・認証・DB・storageの主要scenario |

RepositoryのInsert・Update・Deleteでは、操作対象に加えて対象外dataを用意し、操作後の全体を比較します。件数だけでなく、対象外dataが変化していないこと、constraint違反時に部分更新が残らないことを確認します。

Mediaの委譲、公開解除、User削除、物理削除は複数resourceの整合性を重点確認します。PRには検証対象、GitHub Actionsの結果、必要な手動確認、riskを記録します。ChatGPT上でbuild・testを実行していないことは未実施理由や失敗として記載しません。

## 全Repository共通：Quality Gateの一時停止・再開

この運用方針は `memoria-design`、`memoria-web`、`memoria-api`、`memoria-IaC` と今後追加するRepositoryに適用します。個別RepositoryのWorkflow設定はこの方針に従い、Repository固有の検査内容・トリガー・手動実行方法は各Repositoryで定義します。

- **一時停止はWorkflowファイルを削除せず、PR・Push・schedule等の自動実行トリガーを無効化する**方法を原則とします。停止のために検査Jobを削除したり、常時成功するダミーCheckへ置き換えたりしません。
- 原則として`workflow_dispatch`による手動検証を維持します。手動実行まで停止する必要がある場合は、理由、対象範囲、再開条件を明記した例外として扱います。
- 停止理由、開始時点、対象Repository・Workflow、再開条件、停止中のPR確認方法をIssue等に記録します。未実行の検査を成功扱いせず、未検証範囲を明示して人間が統合可否を判断します。
- 再開時は自動トリガーを復元し、現行実装・依存関係に対する実際の検査成功を確認します。手動Selective実行の部分成功を標準Quality Gate全体の成功と混同しません。
- Branch ProtectionやRequired Checksの利用可否に依存しない運用とします。利用できる場合も、停止中のWorkflowを必須Checkとして要求しないよう整合を確認します。
- トリガーの無効化・復元はGitHub Actionsで有効な構文を使用し、意図しないイベントでの実行がないことを確認します。
- **変更ファイルに基づく検査選択は別の設計事項**です。Webの詳細なpath-to-group matrixを他Repositoryへ無条件に流用しません。Repositoryごとの依存関係と品質保証を踏まえて決定します。

既にWorkflowファイルを削除して一時停止しているRepositoryについては、過去の措置を直ちに復元することは要求しません。次回のQuality Gate再設計・再導入時からこの原則を適用します。実装や再有効化は別途合意して進めます。

## Frontend Component・Visual Regression・E2Eのテスト設計

Frontendのテスト階層、Interaction Test、Storybook、Integrationの責務・選択基準は[Frontendテスト戦略](/system/web/frontend-testing)を正本とする。以下は横断的な検証環境・VRT・E2E・Quality Gateの原則を扱う。

### 責務と検証境界

- Component化は再利用性のみを目的とせず、表示とUI操作をアプリケーション固有の処理から分離し、テスト容易性を高めるためにも行います。利用箇所が1つでも独立して検証する価値があればComponent化できます。
- Componentは表示、UI状態の表現、UI操作とイベント通知を担当します。API通信、業務処理、アプリケーション全体の状態更新は外側が担当し、propsとイベント等の明確な契約で接続します。
- StorybookはComponentの状態と操作を再現する検証環境です。実在する重要な状態をStoryで表現し、全Componentに固定数のStoryを要求しません。
- Component内で完結する操作・イベントはStorybook Interaction Test、表示の視覚的回帰はStorybookを対象とするVRT、分離したロジックはUnit Test、Web・API・DBをまたぐ主要フローはE2Eで検証します。不要な重複は避けます。
- Visual Prototypeは原則Component VRTの対象外ですが、既存の表示・操作・レスポンシブ仕様の維持義務は変わりません。

### VRT

- 原則として `src/components/**` のStoryを対象とし、`src/prototypes/**` は対象外とします。ディレクトリを基本条件にStoryメタデータで理由付きの除外やViewport省略を指定できます。抽出異常による対象0件を成功扱いしません。
- Desktop 1440px、Mobile 375pxを標準とし、レスポンシブ検証の価値が重複する場合のみ理由を明示して片方を省略できます。
- Baseline画像はGitで管理し、期待画像の変更は意図したUI変更としてレビューします。通常の比較実行でBaselineを自動更新しません。
- Chromium、OS、フォント、Device Scale Factor等を固定したLinuxコンテナ等の共通環境でBaselineを生成・比較します。フォント・画像待機、アニメーション・時刻・乱数・外部データの安定化を行います。
- 差分は原則失敗とし、閾値の安易な拡大で隠しません。失敗時はExpected・Actual・DiffをArtifactとして確認できるようにします。
- Component、共通スタイル、Storybook設定の変更など、影響があるPRでVRTを実行します。Prototypeのみ・文書のみの変更は原則不要です。影響不明なら省略せず実行します。Story単位の選択最適化は検証漏れがないと確認できてから導入します。

### VRT Baselineのライフサイクルと実行タイミング（2026-10-22合意）

VRTは**承認済みBaselineを比較の正本として扱う通常実行**と、**Baselineの生成・更新・承認**を別工程とする。通常比較が差分を自動承認したり、Baselineを上書きして成功扱いしたりしてはならない。

1. **対象選定**: テストマトリクスから視覚的な検証価値がある状態・Viewportを特定し、Storyの`vrt`タグで対象を明示する。対象0件を成功扱いしない。
2. **初回登録**: 再現可能な共通撮影環境でBaselineを生成する。生成直後の比較成功だけを根拠に採用せず、採用済み画面設計・既存UIとのVisual / Responsive比較とレビューを経てGitへ登録する。
3. **通常比較**: UIに影響する変更時は、Gitに登録されたBaselineと現在の画面を比較する。意図しない差分、Baseline欠落、撮影失敗を検出し、成功へ読み替えない。
4. **意図した変更**: 差分の原因を確認し、製品UI変更の合意を設計の正本へ反映してから必要なBaselineだけを明示更新する。更新画像をPRでレビューし、更新後の通常比較を再実行する。
5. **実行環境**: Baseline生成と比較でChromium・Playwright・OS・フォント・Device Scale Factor・Viewport・Locale等を統一し、非同期描画・画像・フォント・アニメーション・時間・乱数・外部データを安定化する。環境が一致しない比較は信頼できる回帰判定としない。
6. **結果の扱い**: 差分時にExpected / Actual / Diffおよび実行ログを確認できる状態にし、失敗を閾値の拡大や自動更新で覆い隠さない。生成・比較・レビュー・実行成功は異なる状態として記録する。

**実行タイミング**: 初回導入または新規VRT対象追加ではBaseline作成・承認後に比較する。通常のUI変更PRでは原則として比較のみを実行し、意図したUI変更ではレビューを経てBaselineを更新する。ロジックのみの変更はUI影響で比較要否を判断する。CIへの自動組み込み・Quality Gate化は別途設計・合意する。

**段階導入**: Phase 1は少数Storyでローカルの生成・比較・更新・レポート確認と撮影環境の再現性を確立する。Phase 2でPR上の差分・Baseline承認運用を整え、Phase 3でUI影響のあるPRに対する自動比較を導入する。Phase 1の完了前に後続Phaseが導入済みと扱わない。

### E2E

- 実Frontend・API・テスト専用DBを接続した隔離環境で、責務をまたぐ主要ユーザーフローを検証します。制御不能な外部サービス境界のみ必要に応じてMock/Stubします。
- テストケース間のデータ独立性を確保し、Fixture・Factory・API等で前提データを準備します。後片付けまたは環境リセットで再実行可能にし、並列実行時の衝突を防ぎます。
- 認証済み状態の再利用を可能にし、認証自体のE2Eは別に設けます。
- 通常PRでフルE2Eを一律には実行しません。主要機能・認証・権限変更時は影響するシナリオ、リリース前は主要フローのフルE2E、手動時は指定したシナリオ群を実行します。依存関係を考慮し、影響不明なら安全側で実行します。

### Quality Gateとの関係

- Standardの軽量検査と、変更の影響により必要となる条件付きVRT・E2Eを区別します。条件付き検査が必要な変更では、未実行を成功とみなしません。
- 検査選択はファイルパスだけでなく依存関係を考慮し、差分取得失敗や判定不能時には必要な検査を省略しません。実行・省略・失敗を明確に表示します。
- WebとAPIにまたがる変更のE2E起動、実行環境、CI構成、Storybookテスト実装方式、VRTメタデータ形式、Baseline環境の具体的なバージョンは詳細設計で定義します。

## Backend CI

`memoria-api`のquality gateでは、変更内容と対象repositoryの実装状況に応じて、次の検証を実行します。

- `gofmt`、`go vet`、`staticcheck`によるformatと静的解析
- unit test、Domain・Use Case test、Repository・integration test
- GraphQL schema・operationの整合性とGraphQL integration test
- PostgreSQL migrationとschemaの検証
- 並行処理を扱う箇所のrace test
- k6による主要GraphQL Query・Mutationの性能regression検知
- OpenTelemetryのtrace伝播と非同期処理境界のintegration test

service構成にはlocal開発と共通のDocker Composeを使用し、CI固有の設定だけを差分として重ねます。ただし、test runnerまで一律にcontainer化することは前提にしません。project固有imageのbuildが通常のfeedbackを遅くする場合は、固定versionのCI runner/toolchainからtestを直接実行し、PostgreSQLなど既製imageで再現できる依存serviceだけをcontainerとして分離します。k6など既製imageをそのまま利用できるtest toolもcontainer利用の対象にできます。image自体の検証が目的の場合はbuildを実行します。

imageのbuild、依存serviceの起動、migration・seed、test、性能検証、log・artifactの収集を分けます。障害解析に必要なlogを回収した後、CI専用のcontainerとvolumeを片付けます。

開発環境でJaegerなどの可視化UIを使用する場合でも、通常のPRではCollectorや必要な出力確認だけを使用し、CIの実行時間とresource消費を抑えます。

## Frontend CI

`memoria-web`のquality gateは、次の責務を分けて検証します。

| 検証 | 目的 |
| --- | --- |
| TypeScript | 型の整合性 |
| Biome | lintとformat |
| Vitest | UI logicとunit test |
| Storybook | componentの表示・操作・accessibility |
| GraphQL codegen・operation検証 | API schemaとFrontend契約の整合性 |
| Next.js build | production向けのbuild可否 |
| Playwright | 実browserでの主要E2E scenario |

ESLintは既存のBiomeと重複するため前提にしません。PlaywrightやVisual Regressionは対象scenarioと費用対効果に応じて導入し、すべての変更へ一律に要求しません。

## k6による性能regression

k6は大規模な負荷試験だけではなく、変更による性能劣化を検出するためにも使用します。実行時間と負荷はbranch運用と実行段階に合わせて分けます。

| 実行段階 | 検証内容 |
| --- | --- |
| `develop`向けPR | 主要なGraphQL Query・Mutationを少数のvirtual userと短い固定scenarioで実行し、thresholdでregressionを検知する |
| `develop`への統合後・`main`向けRelease PR | PRより長いscenarioで、統合後の主要な操作と負荷傾向を確認する |
| 夜間実行・Release前 | 必要に応じてstress、soak、spike testを実行する |

対象scenario、実行時間、virtual user数、thresholdはIssueと対象repositoryの実行可能なCI設定で具体化します。k6は性能劣化の発生を検知し、[OpenTelemetry](/system/cross-cutting/observability)は同期・非同期処理のどこで遅延が生じたかを追跡します。

## 非機能要件の検証

応答時間、一覧件数、file size、非同期処理、認可、削除、backup、復旧、監視の初期目標と受け入れ条件は[非機能要件](/system/cross-cutting/non-functional-requirements)を正本とします。

通常のPRでは変更に対応する境界値test、認可test、冪等性test、構成検査を優先します。k6による性能測定、復旧演習、障害注入は初回Release前または対象基盤の変更時に実施し、すべてのPRで長時間の運用試験を必須にしません。

## Behavior、Contract、不変条件

testは実装詳細やmethod呼び出し回数ではなく、期待する振る舞い、公開契約、認可、状態遷移、不変条件、境界値、失敗時の整合性を確認します。Domainはunit test、Use Caseは振る舞い中心のunit test、Repositoryは実PostgreSQL、Redis処理は実Redis、GraphQLはAPI integration testで検証します。

Frontendは既存のVitest、Testing Library、Storybook、必要なPlaywrightを使用します。mockは外部境界に限定し、内部構造を過度に固定しません。table-driven testは同一Behaviorの入力variationに使い、異なる業務scenarioを一つのtableへ混在させません。

### Integration testの依存境界

integration testでは、プロジェクト内で管理する永続化基盤は可能な限りproductionと同種の実serviceを使用します。PostgreSQLは通常の開発用databaseと共有せず、test専用containerとvolumeを使用し、productionと同じmigrationからschemaを構築します。接続先など環境ごとに変動する値は環境変数や設定で切り替え、testのためだけにApplicationやDomainへ分岐を持ち込みません。

Auth0、外部storageなどプロジェクト外のserviceはApplicationから見た境界を交換可能にし、integration testではmockまたはlocalな代替実装をcomposition rootで注入します。例えば認証はAuth0 SDK自体を各testからmockするのではなく、検証済みidentityをApplicationへ渡す認証境界を差し替えます。storageもServiceやResolverが特定vendorのclientへ直接依存することを避け、必要な契約を境界として定義します。

この差し替えはproductionとtestで業務logicを分岐させるためではなく、外部serviceとの通信境界を隔離するために使用します。HTTP、GraphQL、Service、Repositoryなど検証対象の内部経路は可能な限りproductionと同じ実装を通します。外部service固有のintegrationが必要な場合は、そのserviceとの契約を検証するtestとして別途扱います。

coverageは不足を見つける補助指標であり、数値だけを品質目標にしません。人間はtestが仕様を表現し、失敗・境界・securityを含み、実装を壊したときに検出できるかをReviewします。

## Architectureと生成物の機械検査

DomainからInfrastructure、Transport、gqlgen、pgx、Redis、Zap、OpenTelemetryへの禁止依存や、ApplicationへのGraphQL生成型の流入は、重要なimport ruleに絞ってCIで検査します。巨大な専用Architecture frameworkは初期前提にしません。

Backendはgofmt、go vet、staticcheck、必要最小限のlint、unit・integration test、生成物同期、buildを対象にします。Frontendは既存のBiome、TypeScript、Vitest、GraphQL codegen、Storybook、Next buildを対象とし、ESLint・Prettierを重複導入しません。migration、image起動、Repository横断E2Eは段階と必要性に応じて追加します。
