# Communityの整合性とTransaction

## 概要

> 実装状況: Community関連のDB定義は一部存在しますが、本ページで定義するCommunity機能と整合性制約は未実装です。

Community作成、招待、参加、Membership role、退会・除外、削除に関するdomain固有のTransaction境界と競合制御を定義します。共通のlock順序、状態再確認、外部I/Oの扱いは[Transaction・競合制御の共通方針](/system/cross-cutting/transactions-consistency)を参照します。

## Transaction境界

| 操作 | 同じTransactionで確定する内容 |
| --- | --- |
| Community作成 | Community、作成Userの`admin` Membership、User × Community Settings（初期Accent）登録 |
| 招待URL再発行 | 既存URL無効化、新規URL登録 |
| Invitation accept | URL有効性、Community存在、Membership不存在、`member` Membership、User × Community Settings（初期Accent）作成 |
| User起点参加申請（将来） | Community存在、Membership不存在、重複申請確認、申請登録 |
| User起点申請承認（将来） | `admin`権限、申請状態、User存在確認、`member` Membership作成、申請確定 |
| User起点申請拒否・取消し（将来） | 操作者権限、PENDING確認、状態更新 |
| Role変更 | Membership確認、Community lock、`admin`数の再確認、role更新 |
| 退会・除外 | 最終Administrator確認、User管理Mediaの共有解除、Community分類関連削除、Membership削除（従属SettingsをCASCADE削除） |
| 共有追加・解除 | Membership・Custody確認、Access追加・削除、Community分類関連削除、Event記録 |
| Community削除受付 | Community lock、`ACTIVE`・削除権限・対象Community管理Mediaの再確認、Communityを`DELETING`へ遷移、関連情報の削除・無効化、Community管理Mediaの削除対象確定 |
| Community削除完了 | Community管理MediaとCustody参照がすべて解消済みであることを確認し、Communityを物理削除 |

## 競合制御

Community lifecycleとAdministrator不変条件の直列化点は`community.communities`行とします。Role変更、退会、除外、User削除によるMembership削除、通常Community削除、Community Custodyへの直接UploadはCommunity行を`SELECT ... FOR UPDATE`でlockし、その後にMembership、Administrator数、Community存在、Custody等を最新状態で再確認します。

Invitation acceptは再利用可能なInvitationによる複数Userの同時参加を不必要に直列化しないため、Community行を共通mutexとしてlockしません。Invitation行をlockして有効性を再確認し、User lifecycle、Community存在、Membership不存在を確認した上でMembership PK / UNIQUEと組み合わせて重複参加を防ぎます。

User起点Join Requestの状態遷移は対象Request行を直列化点としてlockし、PENDING等の現在状態を再確認します。承認のようにAdministrator権限やMembership作成を伴う操作では、必要なCommunity / Membership lockを共通順序で追加します。

## Administrator不在の防止

Administrator権限は`community_memberships.role = 'admin'`で表現します。Role変更、退会、除外、User削除ではCommunity行を`SELECT ... FOR UPDATE`でlockし、変更後の`admin` Membership数を再確認します。最後のAdministratorを失う操作はrollbackします。Administrator専用tableとの二重管理は行いません。

## 招待URLの一意性とAccept

Communityごとに`revoked_at IS NULL`を条件とするpartial unique indexで招待URLを1件に制限します。期限切れURLは再発行Transactionで無効化してから新規行を追加し、現在時刻に依存するpartial indexは作成しません。

Initial ReleaseのInvitation acceptでは、Invitationをlockして期限・無効化状態を再確認し、Membership不存在を確認した上で`community_memberships(role='member')`と初期Accentを持つ`community_user_settings`作成を同じTransactionで確定します。Invitation自体に使用済み状態は持たせず、有効期間内は複数Userが同じURLを利用できます。Invitation acceptのためにJoin Requestを作成しません。

## User起点Join Requestの競合

User起点Join RequestはInvitation acceptとは独立した将来機能です。申請、承認、拒否、取消し、User削除では申請行と必要なCommunity・User行をlockします。状態が`PENDING`であることを再確認し、先にcommitした操作だけを有効とします。

## 共有解除と分類情報

退会・除外・Community削除時は、共有関係と対象CommunityのGroup・Tag関連を同じTransactionで整理します。User管理Media本体、他Community共有、他Community分類を変更しません。

## 退会・除外のatomic cleanup

Initial Releaseでは、退会・除外に伴うMembership削除、対象Userが管理するMediaの当該Community Access削除、当該Community scopeのGroup・Tag関連削除を一つのDB transactionで確定します。cleanupだけを非同期化して、Membership消失後に共有・分類relationが残る中間状態は導入しません。

処理ではCommunityをlockして最終Administrator条件とMembershipを再確認した後、共有・分類relationを削除し、最後にMembershipを削除してcommitします。途中で失敗した場合は全体をrollbackします。

将来relation件数の増大によりtransaction規模が問題になる場合は、cleanupのみを単純に非同期化せず、論理的な離脱状態とdurable cleanup Jobを含むLifecycleとして別途設計します。Initial Releaseではその中間状態を導入しません。

## Community削除のcleanup

Initial Releaseの通常Community削除では、Community管理Mediaが存在していても削除を受け付けます。Community行をlockして削除権限と最新のCommunity管理Media集合を再確認し、確認済みの削除意図に対する対象を確定します。

削除受付TransactionでCommunityを`ACTIVE`から`DELETING`へ遷移し、Membership、Invitation、Join Request、当該CommunityへのUser管理Media Access、Community scopeのGroup / Tagとそれらの従属relationを整合した状態で削除または無効化し、Community管理Mediaを削除Lifecycleへ移行させます。`DELETING` Communityは通常の閲覧・参加・更新・Upload対象にせず、復元して`ACTIVE`へ戻しません。User管理Media本体、User scopeの分類、他Communityへの共有は変更しません。

Community管理MediaのObject Storage上のOriginal・Variant等の外部I/OはCommunity削除受付のDB transactionへ含めません。Media domainの削除Lifecycleとdurable cleanup Jobへ委ねます。`media_custodies.community_id`の`ON DELETE RESTRICT`を安全装置として維持し、Community管理MediaとCustody参照が残る間はCommunity recordを物理削除しません。すべての対象Mediaが物理削除され参照が解消した後、削除完了Transactionで`DELETING` Communityを物理削除します。cleanup失敗時はCommunityを`DELETING`のまま保持し、Media domainの再試行・運用再開に従います。

Account削除時にCommunity削除を選択する場合も同じCommunity / Media cleanup原則を使用しますが、User account削除を含む全体Flowの確認・再認証はAccount Deletion Flowの責務として分離します。

## Community削除とUpload

Community削除とCommunityへの直接Uploadは同じCommunity行をlockします。後続TransactionはCommunity存在とCommunity lifecycleを再評価し、削除対象確定後のCommunityへのUploadや、同時UploadによるCommunity管理Mediaの削除対象漏れを防ぎます。

## 外部I/Oと失敗時処理

Community domainの通常操作はDB内で完結させ、Object Storageなどの外部I/OをCommunityのTransactionへ含めません。Media file削除、派生物、Outbox、Processing Jobなどの外部I/Oを伴う処理はMedia domainへ委ねます。

retry可能な操作では、lock後に現在状態を再確認し、重複requestによってMembership、Invitation、共有関係を重複作成しないよう[冪等性と再試行](/system/api/idempotency)に従います。Community削除やUser削除に伴うcleanupでは[削除・Lifecycle共通方針](/system/cross-cutting/deletion-lifecycle)を適用します。

## 他domainとの境界

Community domainはMembership、role、Invitation、User起点Join RequestとCommunity削除時のCommunity側整合性を保証します。Object Storage、Media削除、Custody、共有、Outbox、Processing JobのTransactionは[Mediaの整合性とTransaction](/media/consistency-transactions)を正本とし、User削除受付とUser状態は[Userの整合性とTransaction](/user/consistency-transactions)を正本とします。

## エラーと境界条件

| 状況 | 扱い |
| --- | --- |
| 未認証UserによるCommunity操作 | 認証が必要 |
| Community外Userによる詳細取得 | 情報を公開しない |
| 招待tokenが無効・期限切れ | Invitation acceptを拒否 |
| 参加済みUserによるInvitation accept | Membershipを重複作成せず、既存Membershipを参加済みの成功結果として扱う |
| User起点Join Requestの重複（将来） | 既存PENDING申請を維持し重複登録しない |
| 最後のAdministratorの退会・降格・除外 | 拒否 |
| Community管理Mediaが残るCommunity削除 | 対象Mediaを削除対象として確定し、Community削除を継続 |
| Membershipを失ったUploaderの操作 | 拒否 |
| 同時Invitation accept | lock・一意制約・idempotencyによりMembershipを重複作成しない |
| User削除とInvitation acceptの競合 | 削除済みUserの参加を禁止 |

## Invitation管理API・競合・障害Contract（Issue #238）

### 公開操作の意味論（GraphQL schema namingはAPI設計時に整合）

| 操作 | 入力 | 成功時の結果 | 必須の制約 |
| --- | --- | --- | --- |
| Invitation状態取得 | communityId | status、expiresAt、Invitation ID、Administratorには有効なURL | MemberにはURL・token・暗号文を返さない。閲覧不可Communityは404相当 |
| Invitation発行 | communityId、idempotencyKey | 新規Invitation ID、URL、expiresAt | 現在有効なInvitationがないことを再検証。再送時は同じ結果を返すか状態確認へ誘導 |
| Invitation無効化 | communityId、expectedInvitationId、idempotencyKey | 無効化後の状態 | 対象が変わっていれば競合。別Invitationを無効化しない |
| Invitation再発行 | communityId、expectedInvitationId、idempotencyKey | 新規Invitation ID、URL、expiresAt | 旧Invitation失効と新規作成を単一Transactionで確定 |
| Invitation accept | token | Membership参加済み結果 | hash照合、期限・失効・Community状態・MembershipをTransaction内で再検証 |

- 取得・発行・無効化・再発行は操作時点のACTIVE User、ACTIVE Community、現在のadmin MembershipをServerで検証する。Memberの状態取得ではInvitationの存在・期限を示す範囲もCommunity Settings仕様に従い、secretを含めない。操作権限がない既存Memberには403相当、Communityの存在を公開できないUserには404相当を返す。
- 発行・無効化・再発行は対象Community / Invitationを適切にlockして状態を再確認する。Confirmation画面の状態は排他lockとみなさない。expectedInvitationIdが現行対象と一致しない場合は競合結果を返し、別URLへの暗黙の読み替えを禁止する。
- idempotencyKeyは操作主体・Community・operation・request payloadにscopeを限定し、同じkeyで異なるpayloadを受け付けない。重複送信は新しいInvitationを増やさない。保持期間・応答再生時のsecret取り扱いは[冪等性と再試行](/system/api/idempotency)と整合させる。secretを平文でidempotency recordへ保存しない。
- 暗号化は新規InvitationをDBへcommitする前に完了させ、token_hash・暗号文・key ID・nonce・期限を同一Transactionで永続化する。暗号化失敗時はInvitationを発行しない。外部KMS I/OをDB lock中に行わないよう準備し、commit直前の状態再検証を維持する。
- URL再表示は現在のInvitationの有効性とadmin権限を確認した上で復号する。失効・期限切れ・権限変更との競合時は再検証してsecretを返さない。KMS失敗時はURLを返さず、現在のInvitationを勝手に再発行・失効させない。
- 結果不明のmutationではClientはまず状態を再取得する。再発行の無条件再送は禁止する。通信切断・commit済み応答消失・同時Administrator操作を区別できるよう、現在のInvitation IDと有効期限を取得可能にする。
- API responseのURLには`Cache-Control: no-store`相当を適用し、CDN・shared cache・SSR state・analytics・error reporting・traceへtokenを含めない。URL表示はAdministratorの明示的な管理画面に限定し、role喪失時はClient stateからsecretを破棄する。

### 検証シナリオ

1. 発行直後と再訪時に同じ有効URLを表示でき、token_hashによるacceptが成立する。
2. Member・退会者・削除中Community・非所属Userにsecretが返らない。
3. 同時発行・同時再発行・Confirmation中の別操作で有効Invitationが複数成立せず、誤ったURLを失効させない。
4. mutationの応答消失・重複idempotencyKey・異なるpayloadでのkey再利用が安全に扱われる。
5. 期限到来・失効・role喪失とURL再表示の競合で利用可能と誤表示しない。
6. nonce再利用がなく、AAD改ざん・ciphertext改ざん・key不一致・鍵喪失時に秘密情報を返さない。
7. rotation中の再表示・accept・並行更新が安全で、旧鍵廃止前に残存暗号文を検査する。
8. log、audit、trace、analytics、browser cache、GraphQL errorにtoken・暗号文・復号鍵が漏れない。
