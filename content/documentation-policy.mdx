# ドキュメント管理方針

## 目的

設計書をMemoriaの最新設計を理解するための正本として保ちます。読者が時系列や資料間の優先順位を解釈しなくても、現在採用する設計へ到達できる状態にします。

## 設計書に書く内容

- 採用する要求、構造、振る舞い
- 設計の思想と意図
- 制約と境界
- 採用しない機能・方式と理由
- 実装可能なschemaを所有するrepository
- 設計と実装の差分

変更履歴、過去の設計、移行済み資料、日付ごとの状態は記載しません。変更経緯はGitのcommit、PR、Issueで確認します。

## 設計の詳細度

設計書は概要説明だけで完了とせず、実装に必要な判断を開発者が推測しなくてよい詳細度まで具体化します。すべての機能で同じ種類の資料を機械的に作るのではなく、対象の複雑さとriskに応じて必要な設計を選びます。

### 概要設計

- 目的、Actor、ユースケース
- 用語と責務境界
- 主要な概念と関係
- 設計思想、制約、非対応理由
- repository間の契約

### 詳細設計

実装へ影響する場合は、次を設計します。

- 論理ERと物理ER
- table・column・型・PK・FK・unique・CHECK・index・削除規則
- GraphQLの型、input、payload、pagination、error、transaction境界
- Object Storageのpath、派生file、lifecycle、認可
- 正常・禁止・境界となる具体的なデータパターン
- 操作前後のレコード変化と対象外レコードへの非影響
- 同時実行、lock、冪等性、retry、補償処理
- DBと外部serviceをまたぐ整合性
- 失敗時の状態、復旧方法、test観点

設計の完了はページ数ではなく、実装時に重要な仕様判断が残っていないことを基準にします。未決定事項が実装を左右する場合は、設計を完了扱いにしません。

### データパターン

抽象的なER図だけでは、排他制約、複合key、DAG、委譲、削除などの振る舞いを十分に確認できません。代表IDを使った具体的なレコード例を併記し、次を明確にします。

- 操作前に存在するレコード
- 作成・更新・削除するレコード
- 変更してはいけないレコード
- constraintで拒否するパターン
- transaction完了後に成立する不変条件

## 情報の移行と削除

draw.io、SVG、旧MDXなどから正本を移行するときは、概要だけでなく属性、関連、多重度、constraint、データパターン、操作順序、例外、意図、非対応理由まで確認します。情報が別形式に存在することを理由に削除せず、必要情報が現在の構成へ完全に統合されたことを確認してから削除します。

変更履歴として残す必要はありませんが、最新設計へ未統合の情報を失ってはいけません。内容が競合する場合は、人間が採否を判断してから正本を更新します。

## 実装との差分

設計書は実装に合わせて古い設計へ戻さず、合意された最新設計を本文に記載します。実装との差分がある場合は、対象ページの`## 概要`直下へ次の形式で簡潔に記載します。

> 実装状況: 現在の実装はImage中心です。Mediaと動画処理は設計との差分があります。

差分には、未実装、部分実装、実装が設計と異なる事実だけを記載します。経緯や変更履歴は書きません。

## 構成

人間が「プロダクト → 用語・ユースケース → システム全体 → 詳細設計 → 開発・運用」の順に理解できるようにします。Nextraの順序は各階層の`_meta.js`を正本とし、タイトルに「将来」「過去」「履歴」「初期」「現行調査」などの時間を表す分類を付けません。

## Product domainごとの設計書構成

独立したProduct domainは`content/<domain>/`へ配置し、Media、Community、Userを同じ階層で管理します。主要domainでは次の読み取り順序と設計粒度を共通化します。

| 設計観点 | 推奨file | 記載内容 |
| --- | --- | --- |
| 概要 | `index.mdx` | 目的、対象範囲、主要概念、入口 |
| ユースケース | `use-cases.mdx` | Actor、操作、前提条件、結果 |
| 権限 | `authorization.mdx` | 役割、認可条件、権限失効。必要な場合のみ作成 |
| 論理データモデル | `data-model.mdx` | entity、関連、多重度、domain境界 |
| 物理データモデル | `physical-data-model.mdx` | table、column、PK、FK、constraint、index |
| レコードパターン | `record-patterns.mdx` | 操作前後のdata、禁止状態、非影響範囲 |
| 整合性とTransaction | `consistency-transactions.mdx` | Transaction境界、lock、競合、失敗時処理 |
| 設計判断 | `design-decisions.mdx` | 決定、意図、制約、不採用理由 |

`_meta.js`で上記の順序を明示します。各ページの章立て、必須項目、表形式、記載粒度は[設計書テンプレート](/design-document-templates)を正本とします。複雑さに応じて権限、ライフサイクルなど必要なページを追加し、空のテンプレートを機械的に作りません。

物理データモデルで複数domainに共通するID、日時、命名、constraint、index、削除方針は[物理データモデル共通規約](/system/data/physical-model-conventions)に集約します。各domainには適用関係、固有のtable定義、例外だけを記載し、共通ルールを繰り返し定義しません。

## 正本の所有とdomain横断参照

各設計情報は、それを所有するdomainのページを正本とします。Community、Membership、Administrator、招待URL、参加申請のtable・状態遷移・Transactionは`content/community/`に置きます。Media、Custody、共有関係、Variant、Processing Job、Object Storageの設計は`content/media/`または対応するsystem設計に置きます。

domainをまたぐ操作は、自domainで成立させる不変条件と依存先へのlinkを記載します。別domainのtable定義、権限表、詳細なTransactionを本文へ複製しません。設計変更時は所有元を先に更新し、依存するdomainでは責務境界と参照先を同期します。

User、Media、Communityは独立domainとして同じ構成と所有境界を適用します。将来Group、Tagなどが独立した設計領域になった場合も同じ規則に従います。

## Nextraのファイル構成

Nextra 4とNext.js App Routerを使用し、責務を次のように分けます。

| パス | 責務 |
| --- | --- |
| `content/` | MDX本文と階層ごとの`_meta.js` |
| `app/` | root layoutとMDX catch-all route |
| `mdx-components.js` | Nextra themeのMDX component |
| `next.config.mjs` | Nextraを組み込むNext.js設定 |

本文とサイドメニューは`content/`を正本とし、Pages Router用の`pages/`、`theme.config.jsx`、JSON形式の`_meta.json`は使用しません。

## 正本の境界

設計、用語、横断判断は`memoria-design`を正本とします。GraphQL・SQL schema、生成設定、package設定、command、repository固有の実装規則は所有する実装repositoryを正本とします。

設計本文と図はMDX＋Mermaidを使用します。draw.ioで検討しても、採用する情報はMDX＋Mermaidへ反映します。理由・制約・非対応理由は関連する設計本文に置き、別の履歴資料やADRへ分離しません。

ページ移動時は`_meta.js`、README、AGENTS、Context、内部linkを同じPRで更新します。secret、本番識別子、個人情報は記載しません。

## Issueと設計書の整合性

Issueには対象作業の目的、受け入れ条件、進捗、後続課題を記録し、設計書には長期的に有効な最新の方針だけを記載します。Issueの一覧、日付ごとの進捗、完了率、棚卸し履歴を設計書やContextへ複製しません。

設計書の移動、repository構成の変更、責務の変更があった場合は、関連Issueの資料path、対象repository、command、親子関係も確認します。定期的な確認手順は[アジャイル開発とイテレーション運用](/development-process#issueの定期棚卸し)、タスク時の読み取り順は[Context map](/context#issueを定期的に棚卸しする)を正本とします。
