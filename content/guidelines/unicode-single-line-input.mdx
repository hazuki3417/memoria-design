# 単一行テキスト入力のUnicode Validation

## 対象と目的

本ガイドラインは、MemoriaがUserに編集・入力させる**単一行の短いテキスト値**（Group名などの名称、Tag名、Community名、単一行検索条件等）について、制御文字に関する共通の入力規則を定めます。具体的な文字数上限、重複制約、trim・検索の意味は各Domain / Screen Specificationを正本とします。

複数行の本文、外部サービスから受領する原文、ファイルのオリジナル名、Secret / Password等の入力は、単一行名称と同じ規則を無条件で適用せず、該当Domainの必要性と既存契約を確認して個別に判断します。個別Fieldの棚卸しと適用状況はIssue #296で追跡します。

## 合意済み共通規則

- Unicode General Category **`Cc`（Control）** は単一行入力の元の入力文字列に1文字でも含まれれば拒否します。LF（`U+000A`）、CR（`U+000D`）、TAB（`U+0009`）、NUL（`U+0000`）、ESC（`U+001B`）等を含みます。
- Unicode General Category **`Zl`（Line Separator）** と **`Zp`（Paragraph Separator）** も拒否します。これらは`Cc`に含まれないため別途検証します。
- **検証順序**：元の入力を対象に上記の禁止文字を判定し、禁止文字が存在する場合は、trimや正規化に先立って入力無効とします。これにより、先頭や末尾に貼り付けたTAB・改行がtrimにより黙って消されて受理されることを防ぎます。禁止文字が存在しない場合に、Field固有のtrim・長さ・重複等の規則を適用します。
- 禁止文字をサイレントに削除・別文字へ置換して保存しません。利用者が問題を修正できる理由を表示し、保存失敗時に入力Draftを可能な限り保持します。
- Frontendの早期検証だけでは不十分であり、**Backendは保存／検索等のAPI境界で用途に応じた最終検証**を行います。Frontend / BackendでUnicode判定が一致するようにテストします。
- Unicode General Category **`Cf`（Format）** は**一律禁止しません**。双方向制御文字・zero-width文字など要注意のものがある一方、ZWJやZWNJは絵文字や言語表現に必要になる場合があります。どの`Cf`を許容・制限するかは用途別に評価し、現段階では全面禁止・全面安全のいずれも仮定しません。
- 通常の内部空白、結合文字、適法な絵文字を`Cc` / `Zl` / `Zp`と混同して禁止しません。書記素数による文字数上限を持つFieldは、そのDomainで書記素境界を定義します。

## 実装・テスト観点

- paste、IME・composition、keyboard入力、支援技術、GraphQL/APIの直接呼出しなど入力経路が異なっても同じ入力規則になること。
- 禁止文字が先頭・末尾・内部にある場合を検証すること。特にtrimで消えるTAB、LF、CRを明示的にテストすること。
- `Cc`、`Zl`、`Zp`の拒否に加え、内部の通常空白や絵文字ZWJ列を不当に拒否しないこと。
- 現行画面の入力Field・保存済み値・外部取得文字列との互換性を確認し、既存のVisual / Behavioral Contractを維持すること。
- 識別文字列のなりすまし、双方向制御、不可視文字等の`Cf` / その他のUnicodeカテゴリに関する追加の制約は別途検討すること。
