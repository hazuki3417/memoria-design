# 人間中心のAI支援開発ガイド

## 目的

Memoriaの開発主体は人間です。人間がローカル開発環境で設計・実装・検証する手動開発を基本とし、ChatGPTとGitHub連携は、調査、要件整理、設計検討、変更案の作成、レビューなどを支援するために利用します。

手動開発とAI支援を利用した開発は、どちらも正式な開発経路として扱います。AIは自律的な開発主体や意思決定者ではなく、人間の判断と作業を補助する立場です。どちらの経路でも、同じ設計規約、レビュー基準、テスト、CI、承認手順を適用します。

Codex CLI、IDE拡張、Codex Cloudは前提にしません。各リポジトリは独立したGit履歴とリリース単位を維持し、複数リポジトリを一つのGitリポジトリへ統合しません。

## 開発モデル

| 項目 | 人間による手動開発 | ChatGPTによる支援 |
| --- | --- | --- |
| 位置付け | 基本となる開発主体 | 人間の開発作業を支援 |
| 主な作業場所 | Windows、WSL2、Devboxを用いたローカル環境 | ChatGPTとGitHub連携 |
| 主な用途 | 設計、実装、ローカル検証、デバッグ | 調査、要件整理、設計案、変更案、PR・レビュー支援 |
| 実行時の検証 | ローカル検証とGitHub Actions | GitHub Actions。必要に応じて人間がローカルで再現 |
| 最終判断 | 人間 | 提案と報告に限定 |
| マージ・リリース | 人間の確認と承認が必須 | 明示的な依頼を受けた操作のみ |

AIが作成した変更も、人間が作成した変更と同じ品質基準を満たす必要があります。反対に、AI向けに整備するCIや手順は、人間のローカル開発でも再利用できる形にします。

## 専門的なFeedback

ChatGPTは人間の指示へ受動的に同意するだけでなく、Senior Engineerの観点から意思決定の質を高めるFeedbackを行います。人間が最終判断者であることは、技術的な懸念や異論を提示しない理由にはなりません。

提案、要求、設計、実装方針を確認するときは、必要に応じて次を明示します。

- 妥当な点と、その判断が成立する前提
- Architecture、保守性、security、data整合性、運用、費用、開発速度へのrisk
- 小規模な現在に対する過剰設計と、将来拡張だけを理由にした複雑化
- 既存の要求、設計、実装、開発方針との矛盾
- 可逆性が低い判断と、先に検証すべき仮説
- 代替案、そのtrade-off、推奨案
- 事実、推測、未確認事項の区別

懸念がない場合も、どの前提で妥当と判断したかを簡潔に伝えます。重大なriskがある場合は作業後に付記せず、変更前に指摘します。人間がtrade-offを理解したうえで別案を選択した場合は、その決定と理由を尊重し、設計へ記録します。

## 対話と意思決定

人間とChatGPTの対話は、単発の回答を返すだけでなく、要求と設計の不確実性を減らし、判断を正本へ残すために行います。

### ChatGPTのスタンス

- 人間の目的と背景を理解し、表面的な指示だけを機械的に処理しない
- 決定権を奪わず、専門的な評価、異論、代替案、推奨を積極的に示す
- 合意を急ぐために懸念を省略せず、重要度と影響を簡潔に説明する
- 過去の合意を尊重しつつ、新しい事実で前提が崩れた場合は再検討を提案する
- 不明点を勝手に仕様化せず、影響が大きい選択は人間へ確認する
- 小さく可逆な判断は合理的な仮定を明示して進め、結果を報告する
- 作業の実施、PR作成、Merge、Releaseなど、許可の範囲を推測で拡張しない

### 対話の進め方

複数の論点がある場合は番号を付け、依存関係の強い順に一つずつ扱います。一度にすべてへ回答を求めず、現在扱う論点、推奨案、理由、主なtrade-offを示します。

各回答を受けた後は、少なくとも次を整理します。

- 合意した内容
- 判断の理由と成立する前提
- 影響を受ける要求、設計、repository
- 制限事項と採用しない案
- 新たに生じた論点
- Issueまたは設計書へ反映すべき内容

人間の回答が推奨案と異なる場合も、直ちに否定せず、riskを再評価します。許容可能なtrade-offであれば決定を尊重し、重大な矛盾、安全性、data欠損、将来の移行困難がある場合は具体的な根拠を示して再確認します。

### 表現と記録

- 合意済み、提案、未決定、実装状況を混在させない
- 推奨案には理由と不利益も併記する
- 専門用語を使う場合は、判断に必要な意味を説明する
- 長い論点は表、状態遷移、Mermaidなど、関係を確認しやすい形にする
- 対話中の一時的な説明を設計書へそのまま複製せず、合意した最新状態へ整理する
- 長期的な判断は設計書、Task固有の受け入れ条件と進捗はIssue、変更と検証結果はPRへ記録する

## リポジトリと責務

| リポジトリ | 責務 | 主な契約 |
| --- | --- | --- |
| `memoria-web` | Web UI、認証済み画面、GraphQLクライアント | GraphQL schema、ユーザー向け用語 |
| `memoria-api` | GraphQL API、ドメインロジック、永続化、オブジェクトストレージ | GraphQL schema、DB/storage contract |

## ローカル開発環境

人間の主要な開発環境として、Windows、WSL2、Devboxを使用します。各リポジトリを同じ親ディレクトリへ個別にcloneします。

```text
memoria/
├── memoria-api/
├── memoria-web/
├── memoria-design/
└── memoria-IaC/
```

Git管理はリポジトリごとに独立させます。開発者は対象リポジトリのREADMEと`AGENTS.md`を確認し、Devbox内で実装、生成、静的検査、テスト、ビルドを行います。

複数リポジトリに変更が必要な場合も、リポジトリごとにブランチ、コミット、PRを分けます。ブランチの役割、起点、PRの向きは[ブランチ運用規約](/branch-strategy)に従います。

## 情報の優先順位

人間とAIが判断に利用する情報は次の順に扱います。

1. 現在のタスクで合意した要件
2. 対象リポジトリの`AGENTS.md`
3. このリポジトリにあるプロダクト設計と用語集
4. 対象リポジトリのREADME、実装、テスト
5. IssueおよびPRに残されたタスク固有の判断

設計資料と実装が一致しない場合は差異を報告し、推測で片方を正しいものとして更新しません。タスク別の読み取り順序と正本への参照は[Context map](/context)に従います。Contextには設計内容を複製せず、参照先とタスク固有の制約を記載します。

## 開発プロセス

Memoriaは[アジャイル開発とイテレーション運用](/development-process)に従います。要求、設計、実装、検証を反復し、IssueをProduct Backlogとして扱います。初回Release前でも検証可能な小さなIncrementを`develop`へ継続的に統合します。

大規模機能は、利用者価値または独立して検証できる振る舞いを基準にPhaseへ分割します。各Phase内で必要な要求確認、設計、実装、検証を行い、工程別のPhaseへ戻しません。人間による手動開発とChatGPTによる支援のどちらも、同じイテレーションGoal、受け入れ条件、Definition of Doneに従います。

## 標準ワークフロー

1. 人間が目的、受け入れ条件、優先順位、変更可能範囲を決定する。
2. Issueへ要件を記録し、必要ならリポジトリ別のサブタスクへ分割する。
3. 人間が手動で作業するか、ChatGPTの支援を利用するかをタスクに応じて選択する。
4. 実装前に影響範囲、リスク、検証方法を確認する。
5. ローカル環境で実装した場合は、生成、静的検査、テスト、ビルドを実行する。
6. 最新の`develop`からリポジトリごとの作業ブランチを作成し、受け入れ条件と必要な検証を満たしてから`develop`をbaseとする通常のPRを作る。関連PRと適用順序を相互リンクする。
7. GitHub Actionsで、開発経路に依存しない共通の検証を実行する。
8. 人間がdiff、検証結果、設計との整合性をレビューする。
9. 人間の明示的な承認後に`develop`へマージする。リリース時は`develop`から`main`へのPRを別途作成する。
10. 長期的に有効な設計判断をこのリポジトリへ反映する。

ChatGPTへ実装支援を依頼する場合も、作業内容、変更対象、検証結果をPRへ明示します。ChatGPT経由でPR操作やマージを行う場合は、対象と操作内容について人間の明示的な指示を必要とします。

ChatGPT経由のPRは通常のPRとして作成し、Draftは人間が明示的に指示した場合だけ使用します。Draftを使用する場合は、未完了事項とReadyへ変更する条件をPR本文へ記載します。

## GitHub機能の採用基準

ChatGPTによる支援では、GitHub Pluginで一連の運用を継続できる機能だけを標準ワークフローへ採用します。一部の操作だけがPluginに提供されていても、作成、更新、完了、解除など、運用に必要なライフサイクルを扱えない機能は採用しません。

- GitHub Pluginで利用可能と確認できたIssue、PR、コメント、ラベルなどを使用する
- Pluginが対応していない操作を通常運用として`gh`、GitHub Web UI、独自MCPで補完しない
- GitHub Projectsは、Pluginで継続的に管理できないため使用しない
- MilestonesはIssueへの割り当てだけでは運用せず、作成、更新、終了、解除を含む管理がPluginで完結するまで使用しない
- 全体の進捗は親Issue、領域別の作業は子Issue、完了条件はチェックリスト、作業状態はIssueのOpen／Closedで管理する
- 日程が必要な場合は親Issueまたは対象Issueへ目標日と前提条件を記載する
- Pluginの機能が拡張された場合は、運用全体が完結することを確認してから採用を再検討する

この基準は、手動操作を技術的に禁止するものではありません。人間が例外的な保守操作を行っても、それをChatGPT支援の標準ワークフローにはしません。利用できないGitHub機能に合わせて独自の仕組みを増やすより、IssueとPRを正本として単純な運用を維持します。

## Issue・依頼の最小要素

IssueまたはChatGPTへの依頼には、少なくとも以下を含めます。

- 達成したい結果
- 対象リポジトリ
- 受け入れ条件
- 変更してよい範囲
- 実行すべき検証
- 互換性、セキュリティ、データ移行上の制約

例:

```text
memoria-webで画像一覧の空状態を実装する。
既存のMantineとi18nのパターンを使い、API契約は変更しない。
Storybookと単体テストを追加し、TypeScript、Biome、Vitest、Next buildを通す。
実装前に影響範囲と検証計画を確認する。
```

## リポジトリ横断変更

GraphQL schema、認証、ファイル保存、インフラ、ユーザー向け用語の変更は横断変更になりやすいため、次を明示します。

- 契約の所有リポジトリ
- 影響を受けるリポジトリ
- 後方互換性
- PRのマージ順序
- deployおよびmigrationの順序
- rollback方法

GraphQL契約は原則として`memoria-api`で先に定義し、互換期間を設けて`memoria-web`を追随させます。破壊的変更を単独PRで行いません。

## 権限と安全境界

次の操作は、人間が対象と内容を確認し、明示的に許可した場合に限ります。

- 本番・ステージング環境へのdeployまたはdestroy
- DB migration、データ削除、バックアップ復元
- シークレットや認証情報の作成・変更・表示
- IAM権限の拡大
- 外部サービスへのメッセージ送信
- 既定ブランチへの直接push
- 失敗したテストの削除やsnapshotの無検証更新

AIは許可の範囲を推測で拡張しません。人間による手動操作でも、レビュー、バックアップ、ロールバックなど各リポジトリの安全手順に従います。

## 完了条件

変更は以下を満たしたときに完了候補となります。

- 受け入れ条件を満たしている
- 対象リポジトリの`AGENTS.md`に記載された検証が成功している
- 生成元と生成物が同期している
- テストが追加または更新されている
- セキュリティ、互換性、migrationへの影響が説明されている
- 横断変更では関連PRと適用順序が記載されている
- 必要な設計資料が更新されている
- 人間がdiffと検証結果を確認し、承認している

## 導入後の改善候補

初期監査では、次を独立したIssueとして扱う価値があります。

- `memoria-api`のDevbox（Go 1.24）とGitHub Actions（Go 1.22）の統一
- `memoria-web`へのCI追加（Biome、TypeScript、Vitest、Next build）
- `memoria-design`のパッケージマネージャーとlockfileの統一
- `memoria-IaC`のルートと`src/`に分散したNodeパッケージ構成の整理
- 各リポジトリのbranch protectionと必須チェックの設定
