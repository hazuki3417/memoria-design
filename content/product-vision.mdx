# プロダクトビジョン・設計原則

## この文書の位置づけ

Memoriaが何のために存在し、どのような価値を守るかを示す、個別のRelease計画・Domain設計・画面仕様・技術選択より上位の判断指針です。個別仕様の詳細や法的な権利関係をこの文書だけで確定しません。

この文書では、合意済みの方針と、今後のレビューで判断する候補を区別します。未確定事項を確定済みのプロダクト信念として扱いません。

## 存在意義と目指す体験

Memoriaは、家族やサークルなど、現実のCommunityで生まれた写真や動画を、その集まりの人たちが一緒に見て、整理し、残していける場所を目指します。個人が持つファイルを一時的に見せ合うだけでなく、Communityの中で思い出が積み重なっていくアルバムのような体験を中心に据えます。

その原点は、初期draw.ioに記された**「Communityは外部には閉じ、内部では開く」「Mediaは博物館の展示物に近い」**という考え方です。これをプロダクトの中心的な方針とします。

## プロダクトの中心となる思想

### 現実の集まりに近いCommunity

Communityは、家族やサークルなど、現実世界で一緒に時間を過ごす人たちの集まりに近いものです。外部からは閉じられた空間とし、参加する人たちが安心してMediaを共有できる場所にします。

### 外部には閉じ、内部では開く

CommunityにMediaを公開することは、そのCommunityの参加者に見せることを意味します。Community内では参加者全員が等しく閲覧でき、一部の参加者だけが閲覧できるMediaや、参加者ごとの細かな閲覧権限は設けません。

「等しく閲覧できる」は閲覧範囲の原則であり、削除やOriginal downloadなどの操作権限まで全員同一にする意味ではありません。操作権限はCommunity権限設計で定義します。

### Mediaは博物館の展示物に近い

Communityに置かれたMediaは、Uploader個人の手元だけで管理するファイルではなく、その集まりの人たちが一緒に眺め、整理し、残していくものとして扱います。誰かがCommunityを離れても、その人が残したMediaまで自動的に失われることはありません。

この比喩は、閲覧体験と継続的な管理についての思想です。著作権や法的所有権を定義するものではありません。

### 個人の場所とCommunityの場所を分ける

Community全員には見せたくないMediaは、個人の領域で管理します。個人管理MediaをCommunityへ共有する場合は、そのCommunityの参加者全員が閲覧できるものとして扱い、Media自体の管理主体は個人のままとします。

## 現行仕様への反映と初期案との違い

上記の思想を実現するため、Communityへ直接UploadしたMediaはCommunityをCustodianとし、Uploaderは別に記録します。これは内部設計上「Communityの共有資産」と説明できるものですが、**「共有資産」はプロダクトの理念そのものではなく、思想をデータモデルとライフサイクルへ落とし込むための用語**です。

初期draw.ioにはCommunityのネストやprivate/publicの2値による公開範囲の案もありますが、現在はCommunity同士をネストせず、MembershipとCustody・共有関係で閲覧範囲を表現します。Community Groupは分類専用であり、閲覧権限を分割しません。初期案の具体的な構造を現在の仕様として復活させるものではありません。

初期資料：[draw.io SVG（履歴上の原本）](https://github.com/hazuki3417/memoria-design/blob/eb215f4291d4cb28fac3e9a55716f5d96b0af21f/pages/_drawio/modeling.drawio.svg)。

## 設計へ落とし込む原則

| 原則 | 設計・実装時の判断 |
| --- | --- |
| 管理主体とUploaderを分離する | Mediaは常に1 Userまたは1 CommunityをCustodianとし、Uploaderは別に記録する |
| 管理責任と閲覧権限を分離する | Community参加資格を基準に共有Mediaの閲覧を認可し、Uploaderとの個別関係だけで判断しない |
| Communityの継続性を守る | Uploaderが退会・Account削除してもCommunity管理Mediaを自動削除しない |
| 個人の管理責任を尊重する | User管理MediaのCommunity共有はCustodyの変更ではない |
| 閉じた共有空間を守る | Community外Userには内部Mediaを公開せず、Membershipとroleに応じて操作を認可する |
| 整理と管理権限を混同しない | Group・Tagによる分類はMediaのCustody・閲覧権限を変更しない |

具体的な操作権限、削除条件、共有解除、データモデルはMedia・Community・Userの各Domain設計を正本とします。

## 設計判断への適用

新機能や仕様変更では、最初に「誰のMediaか」「誰が閲覧できるか」「Uploaderや参加者が離れた後に何が残るか」を確認します。個人の利便性とCommunityの継続性が衝突する場合は、現在のCustodianと共有範囲を明確にしたうえで、暗黙の移管・削除を避ける設計を検討します。合意済みの信念と衝突する変更は、個別実装で例外化せず、Product上の判断としてレビューします。

## 全体レビューで確定する事項

以下は現時点で新たなプロダクト信念としては未確定です。既存のDomain仕様を変更する意図はありません。

1. Communityの継続性と、Uploader本人による削除権限が衝突する場合の長期的な優先順位。初回Releaseでは参加中のUploader本人にCommunity管理Mediaの削除権限があります。
2. Community管理Mediaを長期に継承する際のAdministrator交代・Community消滅へのProduct上の期待。初回ReleaseのCommunity削除条件は既存仕様を維持します。
3. Communityの共有体験と、個人のプライバシー・削除希望が衝突する場面での原則。法的な権利・義務は別途検討が必要です。
4. 将来の動画・通知・公開共有などで、閉じたCommunityという境界をどこまで維持するか。
5. 「博物館の展示物」という比喩を、将来の継承・公開・削除機能の具体的な判断にどこまで適用するか。
