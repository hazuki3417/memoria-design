# DB設計プロセス（試行用 v0.1）

> [作業プロセス定義テンプレート](/context/workflow-process-template) v0.2と[共通実行ルール](/context/workflow-execution-rules) v0.3に基づく草案です。既存の開発・GitHub運用規約を置き換えません。DB実装やMigrationの実行は対象外です。

## 1. 基本情報

- **識別子**：database-schema-design
- **名称**：DB設計
- **版**：試行用 v0.1
- **状態**：草案
- **適用する共通実行ルール**：作業プロセスの共通実行ルール v0.3

## 2. 目的と適用範囲

### 目的

合意された要求と既存の設計・実装を照合し、DBのtable、column、constraint、index、relation、変更影響を設計書として具体化することです。

### 適用条件

DB設計の新規作成または変更が明示的に依頼された場合に適用します。

### 対象範囲

指定されたdomainの論理・物理データモデル、関連するユースケース、Transaction、既存schema、データ移行上の設計上の懸念です。

### 対象外

DB migrationの作成・実行、実装コードの変更、本番DBの操作、PRのマージ、Release。別途依頼・承認が必要です。

## 3. 開始条件

| 必須入力 | 内容 | 不足時の対応 |
| --- | --- | --- |
| 対象 | domain・機能・変更要求 | 一意に定まらなければ確認 |
| 参照先 | 設計・実装repositoryとbranch / commit | 正本の最新状態を確認し記録 |
| 設計目的 | 解決する問題、期待する振る舞い | 判断に影響する曖昧さは確認 |
| 許可範囲 | 調査のみ・設計案作成・設計書更新 | 不明な変更操作は実施しない |

開始前に[Context map](/context)、[ドキュメント管理方針](/documentation-policy)、[物理データモデル共通規約](/system/data/physical-model-conventions)、関連するdomain設計と既存schemaを確認します。

## 4. 作業対象と網羅性

- **対象を列挙する単位**：要求・業務操作、entity / table、column、constraint、index、FK、影響を受ける既存処理。
- **対象の探索方法**：Context mapのDB・対象domainの参照経路から開始し、関連ユースケース、論理・物理モデル、Transaction、既存schema、migration履歴を確認する。
- **対象に含める条件**：要求を成立させるための保存・参照・更新・削除・競合制御に直接影響するもの。
- **対象から除外する条件**：変更要求と依存関係のないもの。除外理由を記録する。
- **探索完了の確認**：要求と業務操作ごとに、必要なtable・制約・関連処理への対応を照合し、未処理の参照先がないことを確認する。
- **探索できなかった範囲**：資料名・原因・影響を記録し、必須範囲が未確認なら完了としない。

探索完了は未知の関連対象が存在しないことの保証ではありません。

## 5. 参照情報

| 情報 | 情報源 | 探索範囲 | 取得完了条件 |
| --- | --- | --- | --- |
| 要求・設計判断 | 合意済み要求、対象Issue、domainのユースケース | 対象操作と関連する状態 | 対象要求と根拠を特定 |
| 論理・物理モデル | 対象domainの正本 | 対象entityと関係 | 参照版を記録 |
| 共通DB規約 | 物理データモデル共通規約 | ID、型、命名、制約、削除 | 適用規約を特定 |
| Transaction | 共通方針とdomain固有の正本 | 書き込み・競合・削除 | 関連する制約を特定 |
| 既存実装 | 所有repositoryのschema、migration、test | 影響するtableと処理 | 現行schema・履歴・版を記録 |
| 横断的な影響 | API、非同期処理、認可、運用の正本 | 対象変更が影響する範囲 | 採用・除外理由を記録 |

資料の不存在、取得失敗、内容不足を区別します。設計と実装が異なる場合は差異を報告し、勝手に一方へ合わせません。

## 6. 作業工程

### 工程01：対象と開始条件の確定

- **種類**：固定
- **必須区分**：必須
- **実行条件**：依頼を受領した
- **先行工程**：なし
- **入力・参照情報**：依頼、Issue、参照先、変更許可
- **実行内容**：目的・対象・対象外・参照先・許可範囲を確定する
- **判断基準**：依頼と既存の正本
- **許可される裁量**：なし
- **承認条件**：不明な範囲変更は人間へ確認
- **成果物**：対象と開始条件の記録
- **完了条件**：必要な項目が一意に記録される
- **確認する証拠**：依頼とGitHubの最新状態
- **失敗時の対応**：不足を確認し、中断する
- **次工程への移行条件**：工程01完了

### 工程02：資料探索と現状の確認

- **種類**：固定
- **必須区分**：必須
- **実行条件**：工程01完了
- **先行工程**：工程01
- **入力・参照情報**：対象、Context map、既存schema
- **実行内容**：関連する正本・schema・migration履歴を探索し、対象と採用・除外理由を記録する
- **判断基準**：第4・5章
- **許可される裁量**：なし
- **承認条件**：対象範囲の拡大は確認
- **成果物**：参照一覧、現状と差分
- **完了条件**：必須資料の取得・版確認と探索先の採用・除外理由の記録が終わる
- **確認する証拠**：パス、commit、schema、migration
- **失敗時の対応**：必須資料を確認できなければ中断
- **次工程への移行条件**：工程02完了

### 工程03：要求と変更影響の整理

- **種類**：裁量
- **必須区分**：必須
- **実行条件**：工程02完了
- **先行工程**：工程02
- **入力・参照情報**：要求、現状、関連する正本
- **実行内容**：要求をtable・column・relation・constraint・indexへ対応付け、影響する既存操作とデータを列挙する
- **判断基準**：要求と既存の設計・実装
- **許可される裁量**：要求を満たす候補案の列挙と比較。要求の変更は禁止
- **承認条件**：新しい仕様判断が必要なら工程05へ進む前に確認
- **成果物**：要求対応表、影響一覧、未決定事項
- **完了条件**：全要求に対応先または未決定理由がある
- **確認する証拠**：要求・schemaとの対応関係
- **失敗時の対応**：重要な判断が不足すれば中断
- **次工程への移行条件**：工程03完了

### 工程04：DB設計案の作成

- **種類**：裁量
- **必須区分**：必須
- **実行条件**：工程03完了
- **先行工程**：工程03
- **入力・参照情報**：要求対応表、現行モデル、共通規約
- **実行内容**：論理・物理モデルの変更案、制約、index、移行上の注意点、代替案と懸念を記述する
- **判断基準**：既存規約、要求、不変条件
- **許可される裁量**：規約と要求を満たす複数案の検討。破壊的変更の採否は不可
- **承認条件**：重要な設計変更は工程05で確認
- **成果物**：設計案と比較根拠
- **完了条件**：対象要素の変更前後と理由、影響が記載される
- **確認する証拠**：現行設計と提案差分
- **失敗時の対応**：未決定事項を明示して中断または確認
- **次工程への移行条件**：工程04完了

### 工程05：重要な設計判断の承認

- **種類**：承認
- **必須区分**：必須
- **実行条件**：工程04完了
- **先行工程**：工程04
- **入力・参照情報**：設計案、代替案、互換性と移行の影響
- **実行内容**：仕様変更、破壊的変更、データ移行上の判断について承認を得る。重要な判断がない場合も「追加承認不要」の根拠を記録する
- **判断基準**：人間の明示的な合意と既存の許可範囲
- **許可される裁量**：なし
- **承認条件**：重要な設計判断は明示的な合意が必要。PR merge・本番操作は別途許可
- **成果物**：承認対象と合意内容、または承認不要の根拠
- **完了条件**：必要な判断の承認状況が確定する
- **確認する証拠**：人間の回答、Issue・PR
- **失敗時の対応**：承認待ち・否認なら中断
- **次工程への移行条件**：必要な承認が取得済み

### 工程06：許可された設計書の更新

- **種類**：固定
- **必須区分**：必須
- **実行条件**：工程05完了、設計書変更の許可がある
- **先行工程**：工程05
- **入力・参照情報**：承認済み設計案、対象ファイル
- **実行内容**：許可範囲の設計書を更新する。調査・設計案のみの依頼なら変更不要の分岐として記録する
- **判断基準**：合意済み設計案と文書管理方針
- **許可される裁量**：表現の調整のみ。仕様変更は不可
- **承認条件**：許可範囲外の変更は再確認
- **成果物**：変更差分または変更不要の記録
- **完了条件**：変更を実施してGitHubから反映を再取得、または変更不要の根拠を記録
- **確認する証拠**：変更先の最新内容、commit
- **失敗時の対応**：結果不明なら再実行せず状態確認
- **次工程への移行条件**：工程06完了

### 工程07：設計内容と影響の検証

- **種類**：固定
- **必須区分**：必須
- **実行条件**：工程06完了
- **先行工程**：工程06
- **入力・参照情報**：要求対応表、変更後設計、関連規約
- **実行内容**：要求、型・制約・FK・index、既存データ互換性、Transaction、関連設計との整合を確認する。実装変更やmigration実行は行わない
- **判断基準**：要求、共通規約、対象domainの不変条件
- **許可される裁量**：なし
- **承認条件**：検証で新たな仕様判断が生じた場合は再確認
- **成果物**：項目別の判定と根拠、未解決事項
- **完了条件**：全検証項目に判定・根拠があり、未確認範囲が明示される
- **確認する証拠**：設計差分、関連正本、必要なGitHub Actions
- **失敗時の対応**：不一致は記録し、無断で設計を変更しない
- **次工程への移行条件**：工程07完了

### 工程08：結果の報告

- **種類**：固定
- **必須区分**：必須
- **実行条件**：工程07完了
- **先行工程**：工程07
- **入力・参照情報**：全工程の実行記録
- **実行内容**：設計内容、差分、検証結果、未決定事項、実装・移行の残作業を報告する
- **判断基準**：記録済みの証拠
- **許可される裁量**：なし
- **承認条件**：Issue作成・PR merge・本番操作は別途許可
- **成果物**：最終報告
- **完了条件**：実行状態、成果物、検証結果、残課題を区別して報告
- **確認する証拠**：全工程の記録と最新のGitHub状態
- **失敗時の対応**：必須工程が未完了なら共通ルールの中断時報告に切り替える
- **次工程への移行条件**：終了

## 7. 工程間の関係

- **基本的な実行順序**：01 → 02 → 03 → 04 → 05 → 06 → 07 → 08
- **並行実行**：なし
- **繰り返し処理**：新たな要求・重大な不整合が発覚した場合は影響を受ける工程に戻る。無制限に繰り返さず、判断不能なら中断する。

| 分岐条件 | 実行する工程 | 実行しない工程 |
| --- | --- | --- |
| 設計書更新が許可された | 工程06で更新・反映確認 | なし |
| 調査・設計案のみ | 工程06で変更不要の根拠を記録 | 更新操作 |
| 重要な設計判断がない | 工程05で承認不要の根拠を記録 | 承認要求 |
| 重要な設計判断がある | 工程05で承認を得る | 承認前の更新 |

## 8. 判断と承認

- **AIが判断できる事項**：関連資料の探索、要求と既存schemaの対応付け、規約内の候補案の作成、検証結果の記録。
- **人間の承認が必要な事項**：重要な設計判断、仕様変更、破壊的変更、合意していない移行方針、許可範囲外のGitHub変更。
- **判断不能な場合**：不足と影響を記録し、中断時報告を行う。

## 9. 中断と再開

- **中断条件**：必須資料の不足、重要な判断の未承認、実行手段の不足。
- **再開条件**：不足の解消、必要な承認の取得。
- **再開時の確認**：GitHubの最新の設計書・schema・PR状態を確認する。
- **再実行**：入力や正本が変わり完了済み工程の結果が無効になった場合だけ、理由を記録して再実施する。
- **重複防止**：対象パス・commit・変更差分を確認し、同じ変更を繰り返さない。

## 10. 作業全体の完了条件

1. 工程01〜08の必須工程が証拠により完了している。
2. 対象要求とtable・column・制約・関連処理の対応が記録されている。
3. 必要な承認が取得され、許可された設計書更新がGitHubで確認できる。設計案のみなら更新不要の根拠がある。
4. 既存schemaとの差異、データ移行・互換性への影響、未解決事項が報告されている。
5. DB実装・migration・本番反映の完了と混同していない。

## 11. 実行結果の記録

- **共通記録への追加項目**：要求とDB要素の対応、参照commit、設計差分、互換性・移行の影響、承認、検証結果。
- **成果物・記録の保存先**：依頼で指定されたIssue・PR・設計書。保存操作は許可範囲を確認する。
- **未解決事項の管理方法**：判断と根拠を記録し、必要ならIssue化を提案する。Issue作成は許可を確認する。

## 12. 固有の制約

- 設計書は意図した仕様、実行可能schemaは現状の実装を表す。差異を機械的に解消しない。
- 既存データを破壊する移行・本番DB操作を設計作業に混在させない。
- 重要な設計判断は人間と合意してから反映する。
- 人間によるレビューを省略しない。

## 定義を有効化する前の確認

この文書は試行用の草案です。既存schemaを含む具体的な小規模変更に適用し、探索・承認・設計書更新・検証の条件が実際に機能することを確認してから有効化を検討します。
