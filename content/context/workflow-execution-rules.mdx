# 作業プロセスの共通実行ルール（設計案 v0.3）

> 本文は試行用の設計案です。既存の開発規約やGitHub運用規約を置き換えるものではありません。実運用へ組み込む前に、既存の正本との整合性を確認します。

## 目的と適用範囲

定義済みの作業プロセスをAIが実行する際、参照、工程、判断、例外、完了確認を一貫して扱うための共通動作を規定します。成果物そのものの正確性を保証するものではなく、人間によるレビューを前提とします。

## 作業の開始

1. 指定された作業に対応するプロセス定義を取得し、名称・版・適用範囲を確認します。
2. 必須入力と開始条件を照合します。
3. 定義が見つからない、一意に特定できない、または必須条件が不足する場合は、推測で開始せず確認します。
4. 作業対象の最新状態と、既存の正本が定める適用規約を確認します。

## 情報の参照

1. プロセスで定義された情報源・探索範囲・取得完了条件に従います。
2. 参照した資料の識別子、リポジトリ・ブランチ、可能な場合はコミット、取得時点、取得結果を記録します。
3. 「資料が存在しない」「取得に失敗した」「取得したが内容が不足する」を区別します。
4. 作業範囲と判断基準を変えない補助的な調査・関連資料の追加参照は許可します。
5. 未取得の資料を参照済みとして扱いません。必須資料の不足は定義された例外処理に従います。

## 工程の実行

**自律実行の原則**：一度の作業指示を受けたら、定義された工程のうちAIの権限と利用可能な情報・手段で実行できるものを、工程の完了条件まで連続して実行します。ユーザーとの対話へ戻るのは、実際に判断・承認が必要な地点、必要な情報・実行手段が不足して継続できない地点、または定義された完了地点に限ります。工程の途中結果や作業量を理由に、実行可能な後続工程を残して回答を終了しません。


- **固定工程**：定義された順序・処理・条件を守ります。必須工程の省略や独自の完了判定を禁止します。
- **裁量工程**：目的・制約・判断権限の範囲で方法を選べます。目的、作業範囲、完了条件を変更してはなりません。
- **承認工程**：承認対象と操作範囲を提示し、必要な承認を得るまで対象操作を実行しません。

工程の順序変更は、プロセス定義で許可されている場合だけ行います。工程の開始条件と先行工程の完了を確認してから着手します。

## 対象の網羅性と工程の終了判定

- 複数対象を扱う工程では、開始時に対象を識別子付きで列挙し、追加・除外とその理由を記録する。工程ごとに対象総数、処理済み数、未処理数を照合する。
- 各対象の判定には根拠または判定できない理由を対応付ける。「調査したが証拠が不足する未確認」と「調査・判定自体をしていない未処理」を区別する。未確認は根拠付きの判定結果になり得るが、未処理は工程完了の根拠にならない。
- 工程完了前に対象一覧と結果一覧を突合し、対象の追加・除外を反映した総数と判定済み数が一致することを確認する。件数一致だけで十分とはせず、識別子の欠落・重複と必須確認項目の未処理も確認する。
- 最終回答前には必須工程・条件付き工程の分岐・未処理対象・承認待ち操作を再点検する。未処理が残り実行可能なら作業を継続し、途中結果を最終回答に置き換えない。
- 大量の対象は処理単位に分割してよいが、分割は承認待ちや中断の理由にならない。単位ごとの処理済み識別子・判定・根拠・残件を引き継ぎ、次の単位を自律的に処理する。会話をまたぐ再開が必要なら既存の実行記録方針に従い追跡先を判断し、未確認の永続化やバックグラウンド継続を約束しない。
- 情報・実行手段の不足などで実際に続行不能になった場合のみ、未処理対象と停止理由、再開条件を明記して定義済みの中断・判定不能処理に移る。回答の作成や処理量そのものを停止理由にしない。

## 判断の制御

1. 判断基準と権限はプロセス定義に従います。
2. 未定義の判定基準、例外、作業範囲の拡張を独自に追加しません。
3. 判断不能な事項は根拠とともに記録し、定義された承認・中断処理に従います。
4. 作業中の個別合意を、正式な改訂なしに恒久的な共通ルールへ転用しません。
5. 既存の正本や現在の明示的な依頼との矛盾を見つけた場合は、勝手に優先順位を作らず既存の情報優先順位と承認手順に従います。

## 実行状態の管理

作業全体と各工程の状態を別々に記録します。状態は次の5種類とします。

| 状態 | 意味 | 移行条件 |
| --- | --- | --- |
| 未着手 | 開始していない | 初期状態。開始条件が満たされれば実行中へ移行します |
| 実行中 | 着手済みで処理を継続している | 完了条件を満たせば完了、継続できなければ中断、結果が確定できなければ判定不能へ移行します |
| 完了 | 定義された完了条件を証拠で確認した | 原則として終了状態。再検証が必要になった場合は理由を記録し、最新状態を確認してから再実行します |
| 中断 | 必要な入力、承認、情報、実行手段が不足し、処理を継続できない | 再開条件を満たし、最新状態を確認した場合に実行中へ移行します |
| 判定不能 | 実行結果や変更先の状態を確認できず、完了・未完了を確定できない | 状態確認により実行中・完了・中断のいずれかへ移行します。未確認の変更操作を繰り返しません |

- 状態を変更するときは、理由、時点、根拠、残作業を記録します。
- 必須工程が未着手・実行中・中断・判定不能の場合、作業全体を完了にしてはなりません。
- 条件付き工程を実行しない場合は、適用条件に該当しなかった根拠を記録します。「実行しない」という分岐結果を、工程の実行完了と混同しません。
- 作業の実行状態と成果物の評価結果は別々に記録します。問題の検出や不合格という評価結果だけで、作業の実行状態を中断や未完了へ変更しません。
- 状態を確定できない場合は、完了を推測せず判定不能として扱います。

## 会話への報告と作業状態の一致

- **中間報告**：作業途中の確認結果を共有しても、それだけで実行状態は変わらない。実作業を続ける場合は実行中として報告し、そのまま後続工程を実行する。中間報告を作業終了の代わりにしない。
- **回答を終了するとき**：作業全体の現在状態を冒頭または結論に明示する。未完了の必須工程がある場合は、単に「継続中」「引き続き対応する」と記載して回答を終えない。
- **中断報告**：必要な入力・承認・情報・実行手段の不足などにより実際に継続できない場合は、冒頭で「中断報告」と明記し、完了工程・未完了工程・中断理由・再開条件・ユーザーに必要な操作の有無を示す。報告すること自体や作業量の多さを中断理由にしない。正当な中断理由なく実作業が終了した場合も未完了の事実を隠さず、停止理由を確認できなければその旨を報告する。
- **判定不能報告**：実行結果を確定できない場合は冒頭で明記し、確認済み事項と未確認事項、次に必要な読み取り確認を示す。
- **承認待ち**：承認が必要な工程へ到達する前に、承認なしで完了できる先行工程をすべて実施する。承認を待つ操作と未承認の範囲、判断材料、推奨案、承認後の再開地点を明記し、対話へ戻る。承認待ちは正常な停止地点だが作業全体の完了ではなく、単なる継続中とも表現しない。承認が不要な独立工程は、依存関係と定義された順序が許す範囲で先に実施する。
- **完了報告**：定義された完了条件を証拠で満たした場合だけ使用する。工程の一部完了と作業全体の完了を区別する。
- **終了前の確認**：最後の回答が中間・中断・判定不能・承認待ち・完了のどれに当たるかを確認し、本文と実際の処理状態を一致させる。実作業を継続しないまま「継続中」とだけ記載して最終回答を終えない。回答の終了は中断を許可する条件ではない。

## 次の対応とユーザーの判断を支援する報告

- 完了・中断・判定不能・承認待ちの報告では、確認できた根拠に基づき、次の対応とその推奨理由を示す。次の対応が存在しない場合はその旨を示す。
- ユーザーの判断が必要な場合は、判断対象、実行可能な選択肢、推奨案と理由、各選択がもたらす主な影響を簡潔に示し、何について回答してほしいかを明確にする。
- 既存の権限・承認規約で実行できる作業に、不要な承認を求めない。ユーザーの追加判断が不要な場合は、必要に応じてその旨を明記する。
- 推奨案は判断材料であり、仕様・優先順位・変更操作の承認を代替しない。承認が必要な操作は、対象と内容を明示して合意を得る。
- 中断や判定不能を解消できる手段が確認できていない場合は、実行できると断言せず、未確認事項と確認方法を示す。

## 失敗・中断・再開

1. 失敗時は工程に定義された再試行条件・上限・代替手段に従います。
2. 変更操作の結果が不明な場合、再実行よりも変更先の読み取り確認を優先します。
3. 中断時は完了工程、未完了工程、中断理由、再開条件を記録します。
4. 再開時は現在の情報源と変更先の最新状態を確認し、重複した変更操作を防ぎます。
5. 状態を確定できない場合は判定不能として報告し、推測で継続しません。

## 中断時・判定不能時の報告

中断・判定不能のときは、通常の完了報告とは区別して、その時点の状態と確認済みの結果を報告できます。

- 冒頭に中断時または判定不能時の報告であることを明記します。
- 完了済み工程と証拠、未完了工程、未取得・未確認の範囲を区別します。
- 暫定的な結果には確認できた範囲と制約を明示し、全体の結論として扱いません。
- 中断理由、再開条件、次に必要な確認を記録します。
- この報告は工程外の状態通知であり、個別プロセスの通常報告工程や作業全体の完了条件を満たしたことにはなりません。

## 完了判定

完了報告の前に、必須工程、条件付き工程の分岐理由、参照情報の取得条件、工程ごとの証拠、成果物、未解決事項を照合します。変更を伴う場合は変更先を再取得して反映を確認します。条件を満たさない場合、作業全体を完了と報告しません。

## 試行・評価の終了管理

共通ルールや個別プロセスの妥当性を検証する試行は、実案件の作業完了条件とは別に、評価対象、比較観点、試行の上限または停止条件、未検証範囲、終了判断を開始前に定めます。検証目的で新しい実案件を際限なく追加しません。試行の終了は、正式運用の承認や成果物の正確性の保証を意味しません。

## 実行用テンプレートの利用

- 個別プロセスを新規に定義・有効化するときは、工程の実施結果、証拠、未処理対象、分岐・承認、完了条件を確認できる実行用テンプレートを同時に設計し、定義文書内または明示した参照先に配置する。依頼文のテンプレートや単なる使用例を代用しない。
- 実行時には該当する実行用テンプレートを基準に記録し、対象・工程・必須項目の欠落がないか終了前に照合する。テンプレートの記入だけで完了とみなさず、各工程の証拠と完了条件を確認する。
- プロセスの工程・分岐・承認・完了条件を変更するときは、実行用テンプレートへの影響を確認し、必要な修正を同時に行う。書式が既存の正本と矛盾する場合は正本に従い、差異を解消する。
- 実行用テンプレートは作業記録の書式であり、実行ごとの記録をGitへ保存する新たな義務や、既存の承認条件の緩和を意味しない。

## 実行記録

少なくとも、使用した定義と版、対象、参照情報と取得状況、工程ごとの状態・状態変更の理由・証拠、条件付き工程の実施または不実施の根拠、判断と承認、成果物とその評価結果、未完了・判定不能事項、作業全体の終了状態を把握し、必要な情報を報告します。

- **基本の報告先**：作業を指示した会話への回答です。完了・中断・判定不能のいずれでも、確認できた結果、未確認事項、参照した定義と版、対象、重要な判断、変更先や検証結果を簡潔に報告します。
- **Gitで管理しないもの**：実行ごとの報告専用ファイルは原則として作成・コミットしません。設計書や実装などの成果物、長期的な設計判断は、それぞれ既存の正本へ反映します。
- **Issueの併用**：複数工程にわたる継続作業、承認待ち、中断・再開、会話をまたぐ引き継ぎなどが必要な場合は、AIがIssue管理の必要性を判断してユーザーに作成を確認します。既存Issueが適切なら新規作成せず再利用します。ユーザーから明示的にIssue利用を指示された場合はその指示と既存の権限・運用規約に従います。
- **Issueを利用する場合**：開始時に目的、対象、定義と版、完了条件を明示し、重要な進捗・判断・中断・再開・結果をコメントで追跡します。すべての細かな操作を記録する必要はありません。完了条件を確認してからクローズし、未完了事項は区別します。会話への報告も省略しません。
- **再現性と追跡**：必要に応じて参照したリポジトリ・ブランチ・コミット、実行条件、PRやIssueへのリンクを記載します。Issueや回答だけで実行環境の完全な再現を保証するものではありません。
- **例外**：法令・監査・既存の正本・明示的な依頼で保存が必要な場合は、その要件を優先します。個別プロセスでは追加の報告項目とIssue利用の判断基準を定義できますが、報告ファイルの恒常的なコミットを標準にはしません。

## 変更管理

共通ルールおよび個別プロセスの恒久的な変更には明示的な合意を必要とします。実行時の例外を自動的に規則へ昇格させません。GitHubの操作権限、ブランチ、PR、品質確認については既存の正本を優先して参照します。
