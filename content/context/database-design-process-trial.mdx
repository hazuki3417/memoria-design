# DB設計プロセスの試行記録：Image Variant

> 試行用v0.1の工程を、既存のImage Variant物理モデルと実行可能SQLの比較に適用しました。新しいDB要件や変更指示を仮定しません。

## 対象・参照

- 対象：`media.image_variants`の一意性、派生物の保存先、再処理時の公開切替
- 設計：`memoria-design` の `docs/workflow-execution-state-and-coverage`、`content/media/physical-data-model.mdx`
- 共通規約：`content/system/data/physical-model-conventions.mdx`
- 実装SQL：`memoria-api` の `develop`、`schemas/postgres/migrations/00001_initial.sql`
- 対象外：実行中DBの状態、全migration履歴、GraphQL・Worker実装、実際のmigration実行、他テーブルの網羅的な設計検証

## 確認した内容

| 観点 | 設計書 | SQL定義 | 判定 |
| --- | --- | --- | --- |
| Variant識別 | `id`をPKとする | `id varchar(26) PRIMARY KEY` | 一致 |
| 元画像の参照 | `image_media_id`が`images(media_id)`を参照 | 同じFKとON DELETE CASCADE | 一致 |
| 幅ごとの一意性 | `(image_media_id, format, width)`がUNIQUE | `image_variants_identity_unique` | 一致 |
| 保存先の一意性 | `storage_key`がUNIQUE | `image_variants_storage_key_unique` | 一致 |
| 再処理時の切替 | 旧Variantを提供しながら新Objectを生成し、DB参照を一括更新 | SQL上は既存行の更新を妨げない | SQLとの明確な矛盾なし。Workerの振る舞いは未確認 |

## 試行で判明した課題

1. 既存設計を維持するケースでは工程05・06を「追加承認不要」「変更不要」として実行できる。
2. 設計書とSQLが一致していても、Worker実装の公開切替が設計どおりであることは証明できない。
3. 新規要求に基づく実際のDB変更では、承認・設計書更新・変更後の検証を別途試す必要がある。
4. 参照したファイルの版だけでなく、repositoryのcommitも実行記録へ残す運用が必要である。

## 次の検証候補

合意済みの小規模なDB変更要求を対象に、変更案の承認から設計書反映までを試す。現時点では変更要求を仮定してDBの設計・実装を変更しない。
