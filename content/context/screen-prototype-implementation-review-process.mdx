## 2. 目的と適用範囲

### 目的
画面詳細仕様、Storybook等のVisual Prototype、memoria-web本体実装について、表示、操作、状態、画面遷移、レスポンシブ動作の一致・差異・不足・検証不能を根拠付きで明らかにし、対象を漏れなく確認したか判定する。**差異の修正と整合性確認は別工程**とする。

### 適用条件
指定した画面群の三者比較を依頼されたとき。開始対象の指定はドメイン、画面、機能、Storyのいずれでもよいが、指定の粒度をそのまま確認完了の単位とはみなさない。

### 対象範囲
- `memoria-design` の対象画面仕様、関連するUI/UX・ナビゲーション・デザインシステムの規定
- `memoria-web` のVisual Prototype、Story、画面・機能・共通Component、route、状態と操作
- 同じWeb画面での利用元別の動作、画面間の接続、Personal/Communityなどの表示条件
- API応答を前提とする画面表示・失敗・復帰の**Web側表現**（必要ならモック・既存実装を確認）

### 対象外
- Backendの設計、実装、APIの実動作、DB、非同期処理の正しさの検証
- GraphQL契約やBackendの変更、Web実装・Prototype・画面仕様の修正そのもの
- リリース、マージ、本番操作

## 4. 作業対象と網羅性

**二層構成を試行する。** ドメイン等は対象を列挙・管理する範囲とし、実際の確認単位は「画面またはまとまった機能と、その状態・操作・利用元との接続」とする。Storyの粒度は統一されていないため、Story数を作業数・網羅率に使わない。作業単位は事前に固定せず、成果物の対応関係を調べて、各単位の内部で確認を完結できるよう分割する。

1. 指定範囲に関係する画面仕様の一覧を作る。仕様の画面・状態・操作・表示条件・遷移・共通機能への参照を識別子付きで抽出する。
2. StorybookのStory一覧と、それぞれが表現する画面・状態・表示幅・操作を調べる。Story未定義の仕様も残す。
3. Webのroute、feature、component、画面間接続を逆方向から探索する。仕様やStoryに存在しない実装も対象候補にする。
4. 仕様→Story→本体、Story→仕様→本体、本体→仕様→Storyの**三方向**から突合する。
5. 共通機能には「共通機能自体の確認先」を一つ割り当て、利用元ごとに異なる入力・権限・前後移動・復帰・状態保持などは**各利用元の接続項目**として割り当てる。
6. 複数ドメインにまたがる項目は主担当単位と他の利用元を記録する。未割当、重複、境界未確定の項目がないか照合する。
7. 除外する項目は根拠と理由を記録する。探索できない範囲は「未探索／取得不能」として明示し、網羅性を保証したことにしない。

**単位の成立条件**：各確認項目が一意の主担当単位に属し、接続項目には利用元と接続先が付され、当該単位の確認が他単位の完了待ちにならないこと。成立しなければ単位を組み直す。無理に細分化しない。

### 二段階で確認範囲を確定する（P2→P3）

確認項目の詳細調査に先立ち、まず**対象索引**を作る。対象索引は確認結果の台帳とは別物であり、対象の取りこぼしを防ぐための軽量な一覧とする。

| 対象索引の種類 | 1行の単位 | 必須の記録 |
| --- | --- | --- |
| 画面仕様 | 対象画面の節またはまとまった規定 | 仕様ファイル・節、適用条件、対応する確認単位 |
| Story | Story export | Story名、対象画面・状態・表示幅、対応する確認単位 |
| 本体Web | route・feature・操作入口・主要状態分岐 | パスと識別子、利用元・条件、対応する確認単位 |
| 境界 | 画面間遷移・共通機能の利用元・状態の引継ぎ | 利用元→接続先、保持・変更される状態、対応する確認単位 |

- 索引ではすべての振る舞いを細かく記述しない。1行に複数の異なる確認内容が含まれてもよいが、**詳細化したときにどの確認項目へ分かれたか**を追跡できるよう索引IDを付ける。
- 最初に仕様・Story・実装・境界の**四方向**で候補を探索し、索引の各行に担当確認単位を割り当てる。対象外とした行には理由を残す。関連先が見つからない行も削除しない。
- すべての索引行に「確認項目ID群」または「対象外の理由」を対応付ける。逆に、すべての確認項目IDは少なくとも1つの索引IDに結び付ける。これを索引と台帳の**相互照合**とする。
- 索引の一覧が一通りそろうまでは、確認単位の詳細調査を完了としない。ただし、索引を作りながら明白な差異を発見した場合は先に記録してよい。
- 対象探索の途中で新しい要素を発見した場合は索引へ追加し、関係する単位の割当と完了判定を更新する。索引の固定を理由に新たな対象を無視しない。

### 対象索引の完了判定（見出しの列挙だけでは不可）

索引作成を「見出し・Story・主要ファイルを列挙した」段階で終了しない。次の条件をすべて満たす必要がある。

1. 画面仕様の各節を読み、**段落・箇条書き内の独立した条件、操作、成功・失敗、状態遷移、表示条件**を索引から確認項目へ展開できる状態にする。章・節の見出し数は網羅率の分母にしない。
2. Storyをexport単位で全件列挙し、各Storyが再現できる状態・利用元・表示幅を実装から確認する。Storyがない条件を索引に残す。
3. Web側のroute、操作入口、state、分岐、主要共通Componentを逆探索し、対応する索引・確認項目へ割り当てる。関数名から振る舞いを推定せず、実際のstate変更と描画を確認する。
4. 画面間接続を、利用元の入口、渡すCollection・Context、接続先の機能、戻り先と状態保持に分けて確認する。接続の一部だけが存在する場合も未確認範囲を残す。
5. 索引の全行を確認項目IDへ対応付けるか、根拠付き対象外とする。確認項目側からも索引へ逆参照し、未割当・重複の有無を検査する。

**見出し列挙済み／主要構造探索済み／規定抽出済み／相互照合済み**を別の進捗として記録する。索引の行数だけから対象網羅率を算出しない。

### 確認単位ごとの独立完了

各単位について、(1)担当する索引行が確定、(2)その行から派生する確認項目をすべて記録、(3)全項目を判定または理由付き未確認として整理、(4)境界の接続項目に利用元・接続先・状態引継ぎが明示、(5)当該単位の未処理がゼロ、を満たした場合に**その単位の確認作業完了**とする。

共通機能そのものの整合性を他単位が担当する場合、利用元の単位はその結果を待たず、**利用元側の接続が検証済みか／未確認か**を独立して判定できる。ただし、共通機能が未確認なら全体の整合性を合格としない。関連単位の結果が変わった場合は影響する接続項目のみ再確認する。

索引の作成が未完了の段階で個別単位を「完了」と報告しない。必要なら「抽出済み項目の調査完了」と表現する。

### 候補を確認可能な項目にする基準

仕様の長い段落から抽出した候補は、まだ確認項目ではない。**同じ操作でも条件によって期待結果が変わる場合は分割**する。特に以下を点検する。

- PersonalとCommunity、AdministratorとMember、操作可能／不可、権限失効
- 通常／Empty／検索0件／取得失敗／操作中／部分成功／競合
- Wide／Medium／Compact、mouse／touch／keyboard
- 共通機能の一般的な操作と、利用元のCollection・前後移動・復帰
- 初回表示、検索条件変更、再取得、画面再入場、Dialogを閉じる操作

**1確認項目の完了条件**は、前提条件、操作または表示対象、期待結果、PrototypeとWebの観測結果、判定と証拠が揃っていること。複数条件を1行で管理する場合は条件別の判定を残し、どれか未確認なら行全体を「一致」としない。

確認項目を無制限に細分化しない。**期待結果と判定が同じ条件**は一つにまとめてよい。細分化の目的は件数を増やすことではなく、異なる結果を一つの判定で隠さないことである。

### 調査の終了と整合性の合格を分離する

- **探索途中**：仕様・Story・Web・境界の索引に未探索範囲がある。
- **列挙完了**：索引の全対象と確認項目が相互照合済みで、対象外理由を含め未割当がない。
- **調査完了（未確認あり）**：列挙した項目をすべて調査し、実表示・操作等の未確認を理由付きで残した状態。
- **調査完了（未確認なし）**：必要な確認方法を実施し、未確認・未処理がない。
- **整合性合格**：調査完了（未確認なし）に加え、差異・未実装・仕様不足・矛盾が残っていない。

試行のため一部の項目だけを抽出した場合は、どれほど詳細に調べても「対象全体の調査完了」と呼ばない。改善作業では各反復で**発見した問題→変更した手順→同じ対象での再確認→残件**を記録する。変更後の手順を再試行していない場合は有効性を未検証とする。

### 確認項目台帳（P2〜P7で共通利用）

三方向探索の結果は、Story数やファイル数ではなく**仕様上の表示・状態・操作・遷移・利用条件**を基礎とする確認項目として記録する。仕様に存在しないStory・本体の要素も独立項目として追加する。識別子は実行中に安定させ、途中で分割・統合した場合は元の識別子との対応を残す。

| 必須項目 | 記録する内容 |
| --- | --- |
| 確認項目ID・確認範囲 | 固有ID、ドメイン／画面／機能、Personal/Community、権限、表示幅などの条件 |
| 確認する内容 | 表示・文言・状態・操作・遷移・復帰など、期待される一つの振る舞い |
| 画面仕様の根拠 | 仕様ファイルと節・行。仕様にない場合は「規定なし」と明記 |
| Prototypeの根拠 | Story名、Component、該当箇所。Storyがない場合も記録 |
| 本体Webの根拠 | route、feature、Component、該当箇所。見つからない場合は探索範囲を記録 |
| 担当単位・境界 | 主担当単位、共通機能の確認先、利用元→接続先、他単位との関係 |
| 確認方法 | 静的照合／実表示／操作試験と、実行環境・入力条件 |
| 判定と根拠 | 一致／差異／未実装／仕様不足・矛盾／未確認／未処理、期待結果と観測結果 |
| 残件 | 未確認理由、次の確認手段、必要なら修正候補・追跡先 |

**項目分割の基準**：異なる表示条件・操作結果・利用元によって判定が変わるものは分割する。1つのStoryが複数項目に対応してもよいし、複数Storyが同一項目を検証してもよい。共通Componentの一般的な表示・操作は主担当単位で検証し、利用元から渡される対象集合、権限、画面復帰などは利用元別の項目にする。対象を重複検証しないことより、接続の漏れを防ぐことを優先する。

### 網羅性を確認する方法

1. **仕様起点**：対象仕様の各表示情報・操作・状態・Navigation・制約・Responsiveの記述を台帳の項目IDへ対応付ける。対象外は理由を付ける。
2. **Story起点**：各Storyがどの項目を表現するか記録する。Storyだけの表示・操作は新規項目にする。Storyがない条件を「仕様なし」と混同しない。
3. **実装起点**：Personal/Community両方のroute、画面内の分岐、共通Component、操作入口を項目へ対応付ける。仕様・Storyにない実装も追加する。
4. **境界起点**：画面間遷移、共通機能の利用元、表示幅、権限・Contextの組合せを確認し、少なくとも関連する項目IDと主担当単位を付す。
5. 台帳に割り当てられない仕様・Story・本体要素を**未割当一覧**として残し、解消または理由付きで対象外とする。単位間で同じ項目を扱う場合は主担当を一つにし、接続側の固有項目は別IDにする。

台帳を作っただけでは網羅性が証明されたことにはならない。**探索対象の一覧、台帳への対応、未割当の有無**を突き合わせて初めてP7を判定する。

### P4・P5の確認方法
GitHub上の静的調査で確認できる内容と、Storybook・本体の実表示や操作が必要な内容を区別する。実行環境やブラウザー検証手段がない場合、実表示を確認したと主張しない。静的に一致して見えても、見た目・動作の一致が未検証なら「未確認」とする。共通Componentを参照している事実だけで画面全体の整合性を合格としない。

### 確認の実施可能性

確認方法を次のように区別する。**静的調査で確定できる事項**（Storyの定義、route、操作入口の有無、コード上の分岐等）は根拠付きで判定してよい。一方、表示位置、重なり、Responsiveの実際の見え方、ユーザー操作後の結果など、実行しなければ確定できない事項は静的なコード類似だけで「一致」にしない。

実行環境を利用できる場合は、対象条件ごとにStorybookと本体の表示・操作を検証する。実行環境が利用できない場合は確認項目を削除せず、必要な実行条件と未確認理由を記録する。Backendを起動・検証する必要があるケースは、Web側のモック等で再現できる範囲だけを扱い、Backend自体の検証に踏み込まない。

### P6の判定
- **一致**：対象条件で仕様・Prototype・本体が整合すると確認できた。
- **差異**：三者の少なくとも一つに矛盾があり、根拠を示せる。
- **未実装**：仕様に要求があり、対応するPrototypeまたは本体の機能が存在しないと調査範囲内で確認できた。存在を断定できない場合は未確認。
- **仕様不足・矛盾**：正本だけでは期待結果を定められない、または規定同士が矛盾する。
- **未確認**：調査は行ったが証拠・実行手段が不足し判定できない。
- **未処理**：調査自体が未実施。工程完了として扱わない。

結果には、画面／状態／操作／利用元、関連ファイル・行やStory名、期待・観測・確認方法、重要度の根拠、後続の修正候補を対応付ける。重要度や修正先の判断が必要なら提案に留める。

## 7. 工程間の関係

基本順序は P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8。P4・P5は確認単位ごとに繰り返してよい。確認途中で新たな画面・接続を発見した場合はP2/P3へ戻り、割当と総数を更新してから続行する。単位分割の都合だけで対象を除外しない。調査不能項目は理由を記録し、調査可能な残項目は続ける。

## 8. 判断と承認

AIは資料探索、確認単位の暫定分割、事実の比較、根拠付き分類、修正候補の提示まで行える。**仕様の変更、Prototypeや本体の振る舞い変更、正式な作業単位の採用、修正の優先順位決定**など重要な判断は人間の合意を必要とする。作業単位の割当は試行中の調査上の整理であり、恒久的な粒度の決定ではない。確認結果が不十分でも勝手に仕様を補わない。

## 9. 中断と再開

必須の資料・権限・調査手段が不足し続行できない場合は中断する。結果不明のGitHub変更操作は再実行せず読み取り確認する。再開時は最新のIssue、branch、仕様、Story、実装を取得し、前回の識別子・処理済み項目・未処理項目と照合する。変更があった項目だけ再判定し、完了済みの結果を無条件に再利用しない。

## 10. 作業全体の完了条件

### 完了判定を二段階に分ける

**第1段階：対象の列挙が完了したか**。画面仕様の対象節、Story、Personal/Communityのrouteと実装、共通機能と利用元接続を台帳に対応付け、未割当をゼロにする。未探索や取得不能がある場合は範囲と影響を明記し、「列挙完了」としない。

**第2段階：列挙した確認項目の調査が完了したか**。全項目に根拠付きの判定を記録し、「未処理」をゼロにする。実表示・操作の未確認は「未確認」として残せるが、未確認が残る場合は**三者の整合性が確認済みとは報告しない**。確認作業が完了していても、整合性の合格とは異なる。

### 作業全体の条件

- P1〜P8の必要工程を実施し、全項目に判定または根拠付きの未確認がある。未処理はゼロ。
- 仕様・Story・本体・境界からの四方向探索と対象索引、共通機能と利用元の接続、単位間の未割当・重複を確認済み。
- 未確認・仕様不足・差異・未実装が残っていても、**確認作業は完了し得る**。成果物の整合性が合格したこととは区別する。
- 必須資料の未取得などで対象を列挙できなければ完了とせず中断・判定不能を報告する。
- 修正・再検証は後続の別作業とし、今回の完了条件に混在させない。

## 11. 実行結果の記録

原則として会話で、対象範囲、参照branch・時点、確認単位と割当、件数、項目別判定、証拠、未確認、修正候補、検証方法の限界を報告する。複数回にまたがる場合や未解決の課題を追跡する必要がある場合は既存Issueを検索し、Issueの新規作成はユーザーへ確認する。既存Issueを利用する場合は対象、版、判定、残件、再開地点を記録する。仕様変更の正本は画面仕様、Webの変更はmemoria-webとし、調査記録だけを理由に本体を変更しない。

## 12. 固有の制約

- Backendを調査・変更しない。API応答条件はWeb側表示の入力条件としてのみ扱う。
- Storyを一律の作業単位にしない。Storyの粒度に規則があると仮定しない。
- 画面・機能・ドメインの境界をまたぐ操作を、別の単位が確認すると推測して省略しない。
- 既存Prototypeや本体の表示・操作を、比較のために簡略化・置換しない。
- 画面仕様、Prototype、本体のいずれも、他を自動的に上書きする根拠にしない。

## プロセス専用の依頼文

**簡易版**

> 画面仕様・Visual Prototype・本体Web実装の整合性確認プロセス（v0.4草案）で、［対象ドメインまたは画面群］を確認してください。Backendは対象外とし、差異の修正は行わず、確認結果と未確認事項を報告してください。

**詳細版**

> 画面仕様・Visual Prototype・本体Web実装の整合性確認プロセス（v0.4草案）を、対象［ドメイン／画面／機能／Story］、参照branch［指定またはdevelop］で実施してください。画面仕様・Story・本体・境界の対象索引を作り、確認項目と相互照合し、共通機能と利用元ごとの接続を確認してください。表示、状態、操作、Responsive、遷移を根拠付きで分類し、未処理ゼロと未確認の区別を報告してください。Backend検証と修正は対象外です。

## 試行で判明した改善理由（2026-10-09）

Media Browserは状態・操作・Personal/Community・CompactなどでStoryを分割している一方、Group BrowserはWide/Compactの2 Storyであり、Story数を分母にすると確認漏れを検出できない。Group BrowserはPersonalとCommunityの両routeから利用され、Group内Mediaから共通Media Detailを開く接続は画面仕様にあるが、確認した本体・Prototypeコードではその操作入口を確認できなかった。これらの境界を記録できるよう、v0.2で**確認項目台帳、四方向（仕様・Story・実装・境界）の照合、二段階の完了判定**を追加した。

この調査は静的な確認に限定され、画面の実表示・操作、全状態・全操作の網羅的な検証は未実施。差異の修正は行わない。試行記録は[PR #214](https://github.com/hazuki3417/memoria-design/pull/214)のコメントを参照。

## v0.3での改善理由

[Media / Groupの部分試行台帳](/context/screen-prototype-web-review-trial-ledger)では13項目を抽出できたが、仕様の全節・全Story・本体の全入口を列挙したわけではなく、各単位の独立完了や未割当ゼロを証明できなかった。台帳だけを直接増やすと、項目を細分化するほど全体の見通しが悪くなるため、v0.3では**軽量な対象索引→確認項目への詳細化→相互照合**の二段階方式を導入した。

## v0.4での改善理由

[Group Browser対象索引の試行](/context/group-browser-review-index)で、仕様の26見出し、2 Story、主要構造と代表的な接続を索引化した。しかし、見出しの下には多数の独立した条件・操作があり、これだけでは網羅性を証明できなかった。また、実装の`openDetail`はGroupの選択を表し、名前からMedia Detailへの接続と誤認する危険があった。このためv0.4では**見出し列挙と規定抽出を別工程として判定する基準**と、state・描画による実装の意味の確認を追加した。

## v0.5での改善理由

Group Browserの仕様本文から56件の中間粒度の確認候補を抽出した。見出しより細かくできた一方、Community role、部分成功、Responsive等の条件が一候補に残るため、候補の件数だけでは独立した判定を保証できない。v0.5では**条件別の分割基準、1項目の判定条件、調査完了と整合性合格の段階的区別、反復の再検証**を明文化した。試行候補は[Group Browser対象索引](/context/group-browser-review-index)に記録する。

## 試行する場合の評価計画

Media BrowserとGroup Browserを最初の試行例とし、Storyの粒度差、Groupから共通Media Detailへの接続、Personal/Communityの違いを評価する。必要ならCommunity関連画面を追加する。評価項目は (1) 対象の未割当・重複、(2) 単位内での確認完結性、(3) 共通機能と利用元接続の漏れ、(4) 未確認と未処理の区別、(5) 実行時間・再開可能性。各例で三方向の探索と境界の照合を終えた時点で評価を一区切りとし、問題が見つかれば該当工程を修正する。**試行終了は正式採用を意味しない**。実行手段がなく画面の実表示を検証できない範囲は評価の限界として残す。
