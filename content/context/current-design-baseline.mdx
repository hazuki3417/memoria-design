# Current design baseline

## 位置づけ

このページはMemoriaの**現行設計を読むための入口**です。詳細仕様を複製せず、現在有効なSource of Truthとその優先関係を示します。

過去の過去の作業記録、PR、設計統合作業の状態は現行仕様そのものではありません。設計判断の経緯を確認する場合は、各文書の「設計判断・理由」、ADR、またはhistorical traceabilityを参照します。

## Source of Truthの読み方

同じ事項について複数文書に記述がある場合は、次の順で具体的な正本を優先します。

1. 対象Domain / System領域の詳細設計（use case、authorization、data model、physical model、consistency、API contract等）
2. 横断的なApplication / Implementation contract
3. Initial Release scope、NFR、Security等の横断Requirement
4. ADR / design decision（判断理由と再検討条件）
5. traceability文書（設計判断・旧仕様の解消経緯を追跡する履歴）

実行可能Schema、migration、generated code、runtime configuration等について設計文書が実装Repositoryを正本として明示している場合は、そのRepositoryの最新状態を併せて確認します。

## 現行の主要正本

- `/first-release` — Initial Releaseの機能範囲
- `/system/application-detailed-design-baseline` — Application / Domain横断contract
- `/system/implementation-cross-cutting-baseline` — 実装横断contract
- `/system/api/graphql` — GraphQLのsemantic contract
- `/system/api/schema-ownership` — GraphQL SDL / generated artifactの所有境界
- `/system/api/http-media-upload` — Media Upload HTTP contract
- `/system/application-implementation-boundaries` — Backend Application / Adapter / Worker境界
- `/system/runtime-process-model` — Backend runtime process responsibility
- `/system/implementation-test-matrix` — Backend実装のtest contract
- `/system/data/physical-model-conventions` と各Domainの `physical-data-model` — Persistence contract
- User / Community / Media各領域のuse case、authorization、data model、consistency / transaction文書
- `/screens` — Screen Specification
- `/system/infrastructure` — Infrastructure設計。Backend API設計から推測して上書きしない

## 現行の横断原則

PostgreSQLをdurable application truthとし、Redis Streamsはdelivery / triggerとして扱います。DB更新と非同期配送はTransactional Outbox等のdurable stateで接続し、Redis配送完了を通常のAPI成功条件にしません。

Application / DomainはTransportやInfrastructureの型へ依存しません。Public API、Worker、Query Service、Repository、Transactionの責務境界は各Backend正本に従います。

Initial Releaseで提供しないことと、将来拡張可能なDomain / Persistence境界を維持することは分離します。未提供であることだけを理由に、合意済みの将来境界を削除しません。

## Screen Specificationの責務境界

Screen Specificationは、利用者が確認するInformation、実行するAction、区別すべきState、Navigation上の意味、制約、Responsiveで維持するCapabilityを正本とします。

具体的なlayout、visual design、Component構成、および `Dialog` / `Drawer` / `Modal` / `Page` / `Sidebar` / `split view` 等のpresentationは、presentation自体がProduct要件である場合を除いてUI具体化側で決定します。既存実装やDesign System Patternの存在だけをProduct仕様へ昇格させません。

## 設計判断と履歴の保持

設計変更時は、現行contractだけでなく「なぜその判断をしたか」「何を採用しなかったか」「どの条件で再検討するか」を失わないよう、対象正本のDecision節またはADRへ残します。

`design-decision-traceability` は、横断レビューで行った設計判断と旧仕様の解消経緯を追跡する履歴資料です。現在の仕様を決める文書ではなく、現行仕様は上記の各正本から読み取ります。

## 実装時の原則

既存仕様・実装を推測せず、対象GitHub repositoryの最新状態を確認します。設計と実装が異なる場合は設計を勝手に実装へ合わせず差分を確認します。新しい重要な設計判断が必要な場合は合意後に正本へ反映します。

本当に未解決の事項だけをIssueまたは明示的なOpen Items文書で追跡し、解消済みTODOや過去の作業順序を現行仕様として残しません。
