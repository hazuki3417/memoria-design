## 試行時の確認単位（暫定）

| 単位ID | 確認する内容 | 境界 |
| --- | --- | --- |
| M-B | Media Browserの一覧・検索／Tag絞り込み・状態・複数選択 | Personal/Communityで異なるAction、Detailを開く入口 |
| M-D | 共通Media Detailの表示・操作・前後移動・分類Action | 利用元のCollectionと復帰先は各利用元で確認 |
| G-B | Group Browserの一覧・選択・検索・管理・状態 | Personal/Communityの権限と表示、選択中GroupのMedia表示 |
| G-M | Groupから共通Media Detailへの接続 | Groupのaggregate Media Collection、前後移動、閉じた後の選択・scroll・focusの復帰 |

M-Dを共通機能の主担当、G-MをGroup利用元固有の接続項目とする。**M-Dを確認しただけでG-Mを確認済みとしない。** 分割が妥当かどうかも試行評価の対象であり、恒久的な開発単位の決定ではない。

### 未列挙・未処理の範囲

上表は境界と台帳運用の試行用に抽出した項目であり、仕様のすべての記述を項目化したものではない。少なくとも以下は**未処理**であり、項目数・網羅率・全体完了を主張しない。

- Media Browser / Detail：情報Panel、Group分類の細部、Tag、processing failure、Media利用不能、権限失効、Original download、Context別Action、全Responsive、Dialog layering、各操作の失敗と再試行
- Personal / Community Media：Upload、共有・共有解除、削除、Membership / Custodyに応じたAction、状態・遷移
- Group Browser：DAG relation、編集・削除・作成の制約、検索結果なし、Empty、読み込み失敗、選択中Group利用不能、競合・部分成功、管理権限、全Responsive、Collection再取得
- Storyと実装からの全要素逆探索、全共通Componentの参照探索、実表示・操作・focus・アクセシビリティ・画面幅別比較

## v0.2の評価

| 評価観点 | 結果 | 根拠 |
| --- | --- | --- |
| 単位間の未割当を発見できるか | **一部有効** | M-DとG-Mを分け、Groupからの接続項目を明示できた。ただし全項目を列挙していないため未割当ゼロは未証明 |
| Story粒度の差を吸収できるか | **有効** | Mediaは状態・操作別、GroupはWide/Compact。Story数ではなく項目IDで扱えた |
| Communityの確認漏れを防げるか | **一部有効** | Group StoryにCommunity専用例がなくても本体routeからGB-02を抽出できた |
| 各単位で独立に完了できるか | **未証明** | 共通Detailと利用元接続の責務は分離できるが、実表示・全操作の確認が残る |
| 完了判定が誤解を招かないか | **有効** | 「抽出した項目を静的に調査」と「全対象の列挙完了」を分離できた |
| 台帳の維持負担 | **要改善** | 1行に条件・証拠・結果をまとめると複数条件の判定が混ざりやすい。規模が増えた場合は代表項目と条件別結果の分割を検討 |

### 次の改善候補

1. **一覧の網羅性と個別項目の深さを区別する**：最初に仕様節・Story・route・接続の索引を完成させ、詳細判定を小分けに進める方式を試す。
2. **条件ごとの判定を分ける**：Personal/Community、権限、表示幅、成功/失敗で期待結果が異なる場合、項目IDを分割または条件別の結果を記録する。
3. **共通機能の確認先を固定しすぎない**：M-Dは暫定主担当。将来別の利用元が増えた場合は利用元接続項目を追加し、共通機能自体の確認を重複させない。
4. **実行可能な試験を別途実施する**：静的に存在する操作入口だけでvisual / behavioral regressionがないと判断しない。

**結論**：v0.2の確認単位・台帳は境界の欠落を発見する用途に使えるが、今回の部分試行で「単位内で完結し、単位間の漏れがない」とはまだ証明できない。正式採用・画面実装の変更は行わない。
