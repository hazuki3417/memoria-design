# Context map

## 目的

Context mapは、開発者とChatGPTがタスクに必要な正本へ到達するための索引です。設計書の内容をAI向けに複製するものではありません。

人間がサイト全体を読む場合は、Homeとドキュメント管理方針が示す「プロダクト概要 → 用語・ユースケース → 全体構成 → 詳細設計 → 開発・運用」の順序を使用します。Context mapのタスク別順序は、特定作業の調査を効率化するためのものであり、人間向けのナビゲーション構成を置き換えません。

## 情報の優先順位

1. 現在のIssueまたは会話で人間が合意した要件
2. 承認済みの最新設計書
3. 所有リポジトリにある実行可能なschema・設定・実装・テスト
4. 対象リポジトリの`AGENTS.md`とREADME
5. 過去のIssue・PR
6. AIが生成した要約

上位と下位が矛盾する場合は差異を報告し、人間の判断を求めます。

## ChatGPT作業時の共通制約

ChatGPTは成果物のbuild、test、静的解析、構文検証を自身の実行環境で行いません。変更内容と設計の整合性を確認してPRを作成し、実行による検証をGitHub Actionsへ委譲します。依存関係の導入や代替検証commandの探索を作業条件にしません。

作業branchのcommit数と粒度は固定せず、複数commitを許容します。一つのcommitへまとめるためだけの操作は不要です。詳細は[AI支援開発](/ai-development)と[ブランチ運用](/branch-strategy)を参照してください。

6. synth・diffとresource置換、IAM、データ保持への影響

### Mediaの非同期処理・派生物

1. [Media処理と派生物](/media/processing)でOriginal、Variant、Processing Jobの責務を確認する
2. [非同期Media処理](/system/api/asynchronous-processing)と[Transactional Outbox](/system/api/transactional-outbox)でAPI・Publisher・Workerの境界を確認する
3. [冪等性](/system/api/idempotency)でrequestの再送とJobの重複実行対策を確認する
4. [Mediaストレージ](/system/data/storage)と[Media表示と配信](/system/web/media-delivery)で保存path、配信、表示用Variantを確認する
5. Originalのupload経路はFrontendからAPIを経由してObject Storageへ保存し、S3への直接uploadは将来的な最適化候補として扱う
6. Communityへ直接投稿したUploaderの削除・Original download権限は[Community権限](/community/authorization)を正本とし、Community参加中に限る

### 非機能要件・運用設計

1. [非機能要件](/system/cross-cutting/non-functional-requirements)で初期目標、測定方法、見直し条件を確認する
2. [ログ・可観測性](/system/cross-cutting/observability)でlog、trace、Media Eventの目的と保持期間を確認する
3. [Mediaストレージ](/system/data/storage)で容量、認可、署名期限、物理削除、backupとの関係を確認する
4. [非同期Media処理](/system/api/asynchronous-processing)、[Transactional Outbox](/system/api/transactional-outbox)、[冪等性](/system/api/idempotency)で遅延、retry、障害時の扱いを確認する
5. [IaC設計](/system/infrastructure)と[テスト設計](/test-design)で初期EC2構成、RPO・RTO、監視、検証方法を確認する
6. Release範囲、動画固有条件、Security・Privacyの詳細が未確定の場合は、関連Issueの合意前に数値や機能を追加しない

### CI・性能検証

1. [テスト設計](/test-design)で対象repositoryのquality gateと実行段階を確認する
2. [ビルド・デプロイ](/build-deploy)でDocker Compose、BuildKit cache、CI環境の責務を確認する
3. `memoria-api`ではGoの静的解析、Domain・Repository・GraphQL・migration・race・traceの検証を変更内容に応じて選択する
4. `memoria-web`ではTypeScript、Biome、Vitest、Storybook、GraphQL codegen、Next.js build、必要なPlaywrightを確認する
5. k6のscenarioとthresholdをIssueおよび対象repositoryのCI設定で確認し、PR・統合後・夜間実行の負荷を区別する
6. 性能劣化の調査では[ログ・可観測性](/system/cross-cutting/observability)のtrace伝播を確認する
7. ChatGPT上では上記の検証を実行せず、PR作成後のGitHub Actionsで結果を確認する

### リポジトリ横断変更

1. 契約を所有するリポジトリを決める
2. 影響する全リポジトリの`AGENTS.md`を読む
3. [ローカル開発環境](/local-development)に従って必要なサービスを起動する
4. 後方互換性、PRのマージ順序、deploy・migration順序を決める
5. リポジトリごとに作業ブランチとPRを分ける
6. 関連PRを相互リンクする

### イテレーションまたは大規模機能を計画する

1. [アジャイル開発とイテレーション運用](/development-process)を確認する
2. 固定期間を設けず、Goal、対象Issue、対象外、開始時の前提をイテレーションIssueへ記載する
3. Issueの目的、受け入れ条件、依存関係、検証方法が着手可能な状態か確認する
4. 一つのGoalとして完了・検証できない機能は、利用者価値または検証可能な境界でPhaseへ分割する
5. 各Phaseの開始条件、完了条件、契約、互換性、migration、無効化方法を定義する
6. Layer別・工程別のPhase、長期branch、巨大PRだけで進めない
7. 中断時は完了・未完了、branch、検証、risk、次の一手をCheckpointとして記録する
8. 再開時は最新の`develop`、Issue・PR、設計、依存関係を再確認する
9. 未完了項目は完了扱いにせず、影響を再評価してBacklogへ戻す
10. Reviewと振り返りをイテレーションIssueへ記録し、3イテレーション完了後に運用を見直す

### 対話によって要求・設計を決定する

1. [AI支援開発の対話と意思決定](/ai-development#対話と意思決定)を確認する
2. 目的、背景、既存の合意、今回決める範囲を確認する
3. 論点へ番号を付け、依存関係の強い順に一つずつ扱う
4. 各論点で推奨案、理由、risk、trade-off、代替案を示す
5. 回答後に合意、前提、影響範囲、制限、未決定事項を要約する
6. 新しい回答が既存設計と矛盾する場合は、自動で上書きせず人間へ確認する
7. 合意した最新状態を設計書、Taskの進捗をIssueへ反映する

### 要求・設計方針を検討する

1. 人間が達成したい結果と、その背景を確認する
2. [AI支援開発の専門的なFeedback](/ai-development#専門的なfeedback)に従う
3. 提案の妥当性、成立条件、risk、既存方針との矛盾を評価する
4. 過剰設計、不可逆な判断、security・data・運用上の問題を先に指摘する
5. 代替案とtrade-offを示し、推奨案を明確にする
6. 事実、推測、未確認事項を区別し、人間の判断が必要な点を質問する
7. 合意した判断、意図、制限事項、非対応理由を正本へ反映する

### GitHubでタスクと進捗を管理する

1. [AI支援開発のGitHub機能の採用基準](/ai-development#github機能の採用基準)を確認する
2. GitHub Pluginで作成から完了まで扱える機能だけを選ぶ
3. 全体目標を親Issue、独立した作業単位を子Issueとして作成する
4. 各Issueへ目的、対象、成果物、受け入れ条件、関連資料を記載する
5. 親Issueのチェックリストと各IssueのOpen／Closedで進捗を管理する
6. PRのマージ前に受け入れ条件とチェック項目を実績に基づいて更新し、完了した項目だけをチェック済みにする
7. 未完了項目は理由と後続Issueを記載し、マージ後にIssueのOpen／Closedが実態と一致することを確認する
8. GitHub ProjectsとMilestonesは使用せず、日程が必要な場合はIssue本文へ記載する
9. PRは通常の状態で作成し、人間が明示した場合だけDraftとする
10. Pluginで扱えない操作を`gh`やWeb UIで補完する前提の運用を作らない

### Issueを定期的に棚卸しする

1. [アジャイル開発とイテレーション運用](/development-process#issueの定期棚卸し)で実施契機と完了判断を確認する
2. `memoria-design`のOpen Issueと親Issue、および関連する`memoria-web`、`memoria-api`、`memoria-IaC`の子Issue・PRを確認する
3. 各Issueの受け入れ条件を最新の`develop`、PRの差分、GitHub Actionsの実行結果と照合する
4. 完了を確認できた項目だけチェックし、未確認・失敗・対象外は事実と後続Issueを明記する
5. 親子Issueの参照、Open／Closed、優先順位、依存関係、設計書pathを同期する
6. 受け入れ条件を満たしたIssueはCloseし、残件があるIssueはOpenを維持する
7. 人間が一部未完了のまま先行完了を許可した場合は、その理由と残件の追跡先を記録する
8. 次に着手するIssueを確認し、設計内容や進捗一覧をContextへ複製しない

### 詳細設計を追加・更新するタスク

1. 対象ユースケースと不変条件を確認する
2. 既存のMDX、Mermaid、実装可能schema、Git履歴上の削除前資料を調査する
3. 概要だけでなく、属性、constraint、データパターン、操作順序、失敗時処理を抽出する
4. 最新設計と競合する情報は自動採用せず、人間の判断対象にする
5. 採用する情報を現在のドキュメント構成へ統合する
6. サイドメニュー、相互link、用語、実装差分の引用ブロックを更新する
7. 元資料を削除する場合は、必要情報の移行完了を確認する

### Product domainの設計書を追加・再構成する

1. [ドキュメント管理方針](/documentation-policy)でdomain構成と正本の所有境界を確認する
2. [設計書テンプレート](/design-document-templates)でページごとの章立て、粒度、表形式を確認する
3. 物理モデル、認証・認可、Transaction、削除、入力検証、冪等性の共通方針を確認し、共通ルールをdomain文書へ複製しない
4. 対象domainの概要、ユースケース、権限、論理モデル、物理モデル、レコードパターン、Transaction、設計判断を確認する
5. 情報を所有domainへ配置し、他domainには責務境界とlinkだけを記載する
6. `_meta.js`、Home、README、AGENTS、Context、関連Issueの参照先を同期する
7. 人間向け本文とContextへ同じ設計内容を複製しない

## タスクcontextに含める情報

Issueまたは依頼には、次を記載します。

- 達成したい結果
- 対象リポジトリ
- 受け入れ条件
- 変更してよい範囲
- 参照する設計書
- 実行する検証
- 互換性、セキュリティ、データ移行の制約
- 関連するIssue・PR

設計内容を貼り付ける代わりに、正本のパスと、今回のタスクで追加された制約を記載します。
