# Issue棚卸しプロセス（試行案）

> **識別子**: issue-inventory-review  
> **版**: 0.1  
> **状態**: 草案・限定検証用。正式運用は未承認。  
> **関連Issue**: [#204](https://github.com/hazuki3417/memoria-design/issues/204)

## 1. 基本情報

- **識別子**：issue-inventory-review
- **名称**：Issueの定期棚卸し
- **版**：0.1
- **状態**：草案
- **適用する共通実行ルール**：[作業プロセスの共通実行ルール](/context/workflow-execution-rules)（実行時点の最新版）

## 2. 目的と適用範囲

### 目的
Issueの記載内容・完了判定・依存関係・親子関係を最新の設計・実装・検証結果と照合し、現状に一致した管理状態を維持する。

### 適用条件
[開発プロセスのIssue定期棚卸し](/development-process#issueの定期棚卸し)に定める開発再開、イテレーション開始・終了、関連PRの複数マージ、設計・リポジトリ構成変更など。固定周期を必須としない。

### 対象範囲
原則として `memoria-design`、`memoria-web`、`memoria-api`、`memoria-IaC` の関連Issue・PR・Actions・設計・実装。対象を限定した試行では、その範囲を明示し、全体棚卸しの完了とは扱わない。

### 対象外
Issue本文から新しい要求を推測して採用すること、未検証の項目を完了扱いすること、Issue整理のために設計・実装仕様を暗黙に変更すること。**本版の試行ではGitHubへの更新・クローズ・Issue新規作成は実施しない。**

## 3. 開始条件

| 必須入力 | 内容 | 不足時の対応 |
| --- | --- | --- |
| 対象 | 対象Issueまたは調査対象リポジトリと絞り込み条件 | ユーザーに確認 |
| 実行区分 | 正式な棚卸し／限定した読み取り検証 | 不明なら確認。v0.1では読み取り検証のみ |
| 確認時点 | 対象ブランチ（原則最新develop）と参照時点 | 最新状態を取得できなければ中断 |

- **開始前の確認**：対象リポジトリのAGENTS.md、Context map、開発プロセス、GitHub運用規約、対象Issue・PRの最新状態を確認する。
- **開始できない場合**：対象を一意に定められない、必要なGitHub情報へアクセスできない場合は判定不能として不足を報告する。

## 4. 作業対象と網羅性

- **対象を列挙する単位**：リポジトリ名とIssue番号の組。関連PRはリポジトリ名とPR番号、検証はワークフロー実行IDと対象コミットで識別する。
- **対象の探索方法**：指定リポジトリのIssue検索でOpen Issueを列挙し、関連Closed Issue・親子Issue・参照PRを辿る。対象を限定する試行では、指定Issueを起点に関連資料を探索する。
- **対象に含める条件**：指定範囲に該当するIssueと、その完了判定に必要な親子・関連Issue、PR、正本、検証結果。
- **対象から除外する条件**：指定範囲外のIssue。除外対象と理由を記録し、全体棚卸し完了の根拠にしない。
- **探索完了の確認**：各リポジトリの検索結果のページを最後まで確認し、列挙件数・対象一覧・参照から発見した追加対象を突合する。検索の上限・権限不足・対象指定の限定を記録する。
- **探索できなかった範囲**：リポジトリ、Issue番号帯、関連先、Actionsなどの未探索範囲と理由を明示し、対象Issueまたは全体の完了判定を保留する。

探索の完了は未知の関連対象が存在しないことの保証ではない。

## 5. 参照情報

| 情報 | 情報源 | 探索範囲 | 取得完了条件 |
| --- | --- | --- | --- |
| 棚卸し規約 | [開発プロセス](/development-process#issueの定期棚卸し)、[Context map](/context#issueを定期的に棚卸しする) | 該当節と関連するIssue管理・完了条件 | 既存の10手順と例外を確認 |
| Issue | 対象GitHubリポジトリのIssue | Open、関連Closed、親子・依存Issue | 指定対象を全件列挙し、各対象の本文・状態を取得 |
| PRと変更 | GitHub PR、最新develop、関連ファイル | 対象Issueに関係する変更 | 対応PRの状態と該当変更を確認、存在しなければ不存在と記録 |
| 検証 | GitHub Actions、該当テスト結果 | 対象変更のコミット・PR | 結果・対象コミット・未実施の区別を記録 |
| 設計・実装 | Context mapから到達する正本、実装リポジトリ | 対象Issueの要求・依存範囲 | 必要な正本を特定し、取得結果と不足を明示 |

- **関連資料の追加探索**：親子関係、参照PR、設計書リンク、実装変更から依存する資料を追加で確認する。対象範囲の拡大が必要なら確認する。
- **情報が存在しない場合**：未作成・該当なしを根拠付きで記録する。
- **取得できない場合**：アクセス不可・ツール失敗を区別し、必須情報なら判定不能とする。
- **内容が不足する場合**：不足項目を明示し、推測で補わない。
- **情報間の矛盾**：[Context mapの情報優先順位](/context#情報の優先順位)に従い、独断で解消しない。

## 6. 作業工程

### 工程 S1：対象と最新状態の確定
- **種類**：固定
- **必須区分**：必須
- **実行条件**：開始条件が満たされている
- **先行工程**：なし
- **入力・参照情報**：対象指定、Issue一覧、最新ブランチ
- **実行内容**：対象Issueを列挙し、Open／Closed、親子・関連Issue、PR、対象developのコミットを確認する。さらに各Issueを通常の作業Issue／Design Coverage Issueに分類し、分類根拠と適用する追加規約を記録する。
- **判断基準**：対象が一意で、確認漏れの有無を説明できる
- **許可される裁量**：対象を変えない範囲で検索方法を選択
- **承認条件**：対象範囲の変更にはユーザー確認
- **成果物**：対象一覧と参照時点
- **完了条件**：指定対象を列挙し、取得済み・取得不能とIssue種別を区別した
- **確認する証拠**：Issue／PR URL、コミットSHA、取得結果
- **失敗時の対応**：同じ読み取りを無制限に繰り返さず、取得不能を報告
- **次工程への移行条件**：対象と取得状況が確定した

### 工程 S2：要求・進捗・依存関係の照合
- **種類**：裁量
- **必須区分**：必須
- **実行条件**：S1完了
- **先行工程**：S1
- **入力・参照情報**：Issue本文、親子Issue、正本、PR差分、Design Coverage Issueでは `content/design-coverage.mdx` と `content/development-process.mdx` の固有規約
- **実行内容**：目的・対象・優先順位・依存関係を最新の要求・設計・実装と照合し、参照path・コマンド・環境の陳腐化、重複・不要・前提失効を確認する。Design Coverage IssueではState・Evidence・Blocking・DeferredとCapabilityの過不足を、Coverage固有の6項目に従って照合する。
- **判断基準**：Issueの記載と正本の一致・不一致・判定不能を区別できる
- **許可される裁量**：対象に必要な関連資料の探索
- **承認条件**：要求や優先順位の実質変更は人間の判断
- **成果物**：Issueごとの差異と修正候補
- **完了条件**：指定対象について一致・差異・不明を記録した
- **確認する証拠**：Issue本文、設計書path、関連PR・変更ファイル
- **失敗時の対応**：情報不足を記録し、根拠なしの修正判断を行わない
- **次工程への移行条件**：差異と未確認項目が整理された

### 工程 S3：受け入れ条件・検証の判定
- **種類**：固定
- **必須区分**：必須
- **実行条件**：S2完了
- **先行工程**：S2
- **入力・参照情報**：受け入れ条件、PR、変更ファイル、Actions
- **実行内容**：通常Issueでは各受け入れ条件を実績と照合し、完了・未完了・未確認を判定する。Design Coverage Issueでは各Capability／AspectのState・Evidence・Blocking・Deferredを個別に照合し、Ready／Validated維持の可否を確認する。どちらもbuild、test、手動確認、security検証を未確認のまま完了にしない。証拠は「確認済み」「未取得（取得できない）」「未実施（実行されていない）」「対象外（今回の限定範囲外）」「該当なし（適用されない）」に区別し、未取得・未実施・対象外を完了の根拠にしない。
- **判断基準**：完了には該当条件を満たした直接の証拠がある
- **許可される裁量**：なし
- **承認条件**：未完了のまま先行完了とする判断は人間の明示的承認
- **成果物**：項目ごとの判定と証拠
- **完了条件**：通常Issueの各受け入れ条件、Coverage Issueの各対象Aspectについて判定または判定不能理由があり、未取得・未実施・対象外・該当なしを区別した
- **確認する証拠**：PR差分、GitHub Actionsの対象コミットと結果
- **失敗時の対応**：証拠不足は未確認に戻す
- **次工程への移行条件**：根拠と判定の対応が明確

### 工程 S4：整理方針の作成
- **種類**：裁量
- **必須区分**：必須
- **実行条件**：S3完了
- **先行工程**：S3
- **入力・参照情報**：S2・S3の判定
- **実行内容**：通常IssueではIssue本文・親子チェックリスト・参照先の更新案、Close／Open維持、重複統合・中止の候補を整理する。Design Coverage Issueでは現在のCoverage Map／Evidence／Blockingを最新状態に保つ更新案と、意味のある変更理由をコメントに残す案を整理し、過去のStateを取り消し線で蓄積しない。両種別で後続Issue、次に着手するIssueと判断待ちを整理する。
- **判断基準**：通常Issueは全条件達成ならClose候補、一部未完了ならOpen維持。Design Coverage IssueはCoverage状態の一覧を維持する役割を優先し、全AspectがReadyでも機械的にCloseしない。例外的な先行Closeには人間の判断と残件の追跡先が必要
- **許可される裁量**：修正案の提示と優先順位の提案
- **承認条件**：実際の更新・Close・統合・中止、優先順位変更、後続Issue作成は権限と人間の合意を確認
- **成果物**：変更提案、未完了事項、次の着手候補
- **完了条件**：各対象の推奨状態と理由が示された
- **確認する証拠**：S2・S3の照合結果
- **失敗時の対応**：判断不能のまま変更を確定しない
- **次工程への移行条件**：提案と保留事項を分離できた

### 工程 S5：結果の報告
- **種類**：固定
- **必須区分**：必須
- **実行条件**：S4完了または中断条件に該当
- **先行工程**：S4（中断時は完了済み工程）
- **入力・参照情報**：工程結果と証拠
- **実行内容**：対象、参照時点、工程状態、判定・差異・未確認事項、更新案を会話で報告する。限定試行ではGitHubのIssue状態を変更しない。
- **判断基準**：確認済みと未確認を混同せず、対象範囲を明示している
- **許可される裁量**：読みやすい報告形式
- **承認条件**：なし
- **成果物**：会話への結果報告
- **完了条件**：根拠、未解決事項、次の操作が説明された。工程の実行完了は、Issueの完了・整合性が保証されたことを意味しない
- **確認する証拠**：各工程の参照先
- **失敗時の対応**：報告できない事項と理由を明記
- **次工程への移行条件**：なし

## 7. 工程間の関係

- **基本的な実行順序**：S1 → S2 → S3 → S4 → S5
- **分岐条件**：S1で通常Issueと判定した対象には通常の受け入れ条件・チェックリスト照合を適用し、Design Coverage Issueには `content/design-coverage.mdx` の6項目（State/Evidence、Blocking解消、新Blocking、Deferred再検討、Ready/Validated維持、Capability漏れ）と `content/development-process.mdx` の本文更新例外を適用する。種別が判定不能なら分類を確認するまで更新提案を確定しない。必須情報の取得不能時は判定不能としてS5へ移行する。関連PRが存在しない場合は「該当なし」とし、他の証拠を照合する。正式なIssue更新は本草案の実行経路に含めない。
- **並行実行**：S1で確定した複数Issueの読み取りは並行可。判定の集約はS2・S3の完了後。
- **繰り返し処理**：S2・S3は対象Issueごとに一度ずつ評価し、追加情報が判明した場合のみ該当対象を再評価する。対象が増える場合は範囲を再確認する。

## 8. 判断と承認

- **AIが判断できる事項**：根拠に基づく一致・不一致・未確認の分類、更新案・次の着手候補の提示。
- **人間の承認が必要な事項**：実質的な要求・優先順位変更、例外的な先行Close、対象範囲の拡大。本試行ではGitHubのIssue変更を許可しない。
- **判断不能な場合**：不足情報と影響する判定を報告し、必要な追加確認を求める。

## 9. 中断と再開

- **中断条件**：必須情報を取得できない、正本の矛盾が未解決、承認待ち。取得結果が不明な場合は「存在しない」とみなさず、必要な確認を特定する。
- **中断時の報告**：完了済み工程とその証拠、未完了工程、取得済み・未取得・未実施・対象外の範囲、中断理由、再開条件を記録する。これはS5の通常の完了報告とは別の状態通知であり、試行完了を意味しない。
- **再開条件**：不足情報・承認の取得、対象と目的の再確認。必須資料が引き続き取得不能なら再開せず、判定不能として報告する。
- **再開時の確認**：最新のIssue・PR・develop・Actionsを再取得し、Issue状態・本文、PRのhead SHA、検証対象コミット、依存先の変更を中断前の記録と比較する。差分があれば影響するS1〜S3の判定をやり直す。過去の判定を無条件に引き継がない。
- **再実行**：読み取りと判定は情報更新があった場合に再実施できる。読み取りが失敗した場合は一度だけ対象・権限・参照先を確認し、復旧が確認できない場合は無制限に再試行せず中断する。
- **重複防止**：本試行は読み取り専用。再開時は同一の確認結果を新しい証拠として重複計上しない。将来の更新版では変更前にIssue本文・コメント・状態を再取得し、既存変更を確認する。

## 10. 作業全体の完了条件

- **プロセス試行の完了**：指定した限定対象についてS1〜S5を実施し、分類・判定・証拠・未確認範囲を報告できた状態。対象Issueの正式な棚卸し完了は意味しない。
- **対象Issueの棚卸し完了**：対象Issueに適用されるすべての確認項目について必要な正本・関連PR・検証結果を取得し、差異と更新要否を確定できた状態。未取得・未実施・対象外が完了判定に必要な項目に残る場合は未完了とする。
- **全体棚卸しの完了**：事前に合意した全リポジトリ・全対象について上記の棚卸し完了条件を満たし、必要な変更の反映を確認できた状態。v0.1では読み取り専用のため到達しない。
- S1〜S5を実施し、取得不能時は中断・判定不能として区別する。
- 対象Issueごとに受け入れ条件・検証・推奨状態の根拠を示す。
- 読み取り検証を全体の正式棚卸しと誤認させない。
- 未解決事項と次の操作を明示し、GitHubのIssueを変更していないことを確認する。

## 11. 実行結果の記録

- **会話での報告事項**：対象Issue、参照したコミット・PR、各工程の結果、判定不能の理由、推奨更新案、試行上の改善点。
- **Issueを利用する判断基準**：複数Issue・複数回の試行や中断・再開を追跡する場合。新規Issueは作成前にユーザーへ確認する。
- **既存Issueの再利用**：本定義の検討・試行は [#204](https://github.com/hazuki3417/memoria-design/issues/204) に記録する。別の棚卸し作業は既存の管理Issueを確認する。
- **Issue利用時の記録**：目的、対象、定義の版、完了条件、重要な判断・試行結果・中断・再開をコメントで追跡する。
- **成果物の反映先**：恒久的な定義はこの文書、運用規約は既存の正本。実行報告専用ファイルを原則コミットしない。
- **未解決事項の管理方法**：会話で報告し、継続的な追跡が必要なら既存Issueまたは合意した後続Issueへ記載する。

## 12. 固有の制約

- [開発プロセス](/development-process#issueの定期棚卸し)の既存10項目と例外条件を緩和しない。
- Issueチェックリストは作業実績に基づき、未完了を完了扱いしない。
- 固定頻度の自動実行、GitHub Projects、Milestones、新しい管理台帳を必須としない。
- **v0.1は読み取り専用の試行定義**であり、正式運用の更新工程・承認経路は今後の検討事項とする。

## 正式な棚卸しへ拡張する場合の全体設計案（未有効化）

> 承認方式は合意済み。ただし本節の更新工程は未有効化であり、現在の読み取り専用試行では実行しない。既存の開発・GitHub運用規約を優先する。

### 開始から変更案まで

- 入力：目的と実施契機、対象リポジトリ・Issueの範囲、参照する最新develop、読み取り／提案／承認後の更新の実行区分。
- S1：Open Issueの全ページを列挙し、一覧に混在するPRを除外する。関連Closed Issue・親子・依存Issue・PR・Actions・正本を辿る。取得できない範囲と除外理由を残す。
- S2・S3：通常Issueの受け入れ条件と、Design Coverage Issueの固有6項目を照合する。未取得・未実施・対象外・該当なしを区別し、必要な証拠が欠ける判定は保留する。
- S4：各Issueの変更案、Open維持・Close候補、後続課題、判断待ちを整理する。関連先の発見だけで対象範囲を拡大しない。

### 承認後の更新工程

| 工程 | 実行内容・前提 | 完了条件・証拠 | 例外 |
| --- | --- | --- | --- |
| U1 変更案と承認 | Issue番号、変更前後、根拠、依存、操作区分を提示。通常の本文・参照・チェックリスト・Coverage Map更新は一括承認。Close・統合/中止・新規Issue・要求/優先順位の実質変更は対象別の明示承認 | 操作と対象ごとの承認範囲が確定 | 曖昧な回答・未承認は保留 |
| U2 変更直前の照合 | Issue本文・状態・コメント、親子Issue、PR・Actions・developを再取得し、承認時点と比較 | 承認の前提が維持されている | 判断に影響する差分はS2〜S4・U1へ戻して再承認 |
| U3 本文と関連情報の同期 | 承認済みの本文・参照・チェックリスト・親子リンク・Coverage Mapを更新。完了チェックは直接証拠がある場合のみ | 更新先を再取得し変更内容を確認 | 結果不明なら再実行せず読み取り確認 |
| U4 状態・後続課題の整理 | 承認済みのClose、統合/中止、後続Issue作成・リンクを実施。親Issueは子Issueだけでなく統合後のGoalを確認 | Issue状態、理由、Evidence、後続リンクを再取得 | 部分失敗は確認済みと未反映を区別 |
| U5 全体照合と報告準備 | 更新済み・未承認・保留・判定不能・対象外を対象一覧と照合 | 最新のGitHub状態と結果が一致 | 完了を宣言せず残件を示す |

- **工程順序**：S1→S2→S3→S4→U1→U2→U3→U4→U5→S5。変更不要な対象はU3/U4を「不要」として記録する。U3/U4中に新たな変更が必要になればU1に戻す。
- **承認の有効範囲**：承認されたIssue番号・操作・変更内容・根拠のみ。承認後に実質的な差分があれば再承認。承認がない操作は実行しない。
- **一括・部分承認（合意済み）**：変更案はIssue番号と操作を一意に識別できる単位で提示する。通常更新の全件承認は提示済みの通常更新案だけに適用し、Close・統合・中止・後続Issue作成・要求/優先順位変更には拡張しない。一部のみ承認された場合は承認されたIssue・操作だけを実行し、保留・非承認の操作は変更しない。承認範囲を特定できない返答は実行せず確認する。
- **Closeの判定**：受け入れ条件とDefinition of Doneを満たしても承認を要する。未達の先行Closeは未達条件・理由・後続Issueを示し個別承認。重複・不要・前提失効のCloseは完了Closeと区別して理由を記録。PRの自動Closeが先行した場合も状態を再取得して確認する。
- **Coverageの扱い**：現在のCoverage Map・Evidence・Blockingを直接更新できるが、State変更やCapability追加・除外など意味のある変更は理由とEvidenceをコメントに記録する。通常Issueの履歴保持規約は維持する。
- **更新順序（合意済み）**：操作間の依存関係を先に整理し、子Issueの状態とEvidenceを確認してから親Issueのチェックリストを同期する。子IssueがすべてClosedでも親IssueのGoalと受け入れ条件を独立に確認し、承認なしで親IssueをCloseしない。Coverage Mapや後続Issueのリンクは、それぞれの参照先の最新状態を確認してから更新する。独立した操作には一律の番号順を強制しない。
- **部分失敗と重複防止（合意済み）**：複数Issue更新は原子的ではない。途中失敗時はGitHubを再取得して成功済み・未反映・結果不明を区別する。結果不明の書き込みは直ちに再送しない。確認済み変更を推測で巻き戻さず、未完了の操作と再開位置を記録する。再開時は依存先と承認の前提を再確認し、実質的な差分があれば変更案を再評価して再承認を得る。
- **承認不要の作業（合意済み）**：読み取り・判定・変更案作成・会話での報告に加え、既存Issueへの事実・確認結果・証拠・変更理由・進捗・保留事項のコメント投稿は事前承認なしで行える。投稿前に対象Issueと既存コメントを確認し、重複や誤記を防ぐ。コメントは本文・状態・要求・優先順位の変更を承認したものとみなさず、コメントに書くだけで新たな仕様や方針を確定しない。本文更新・Close・統合・Issue作成などは従来どおり承認対象とする。

### 記録・完了・検証

- **記録**：対象・探索範囲、参照コミット・PR・Actions、判定と根拠、変更案と承認、操作結果と再取得結果、保留理由を既存Issueとコメントに記録する。新たな専用台帳は作らない。
- **正常完了**：対象を列挙し、必要な判定と承認済みの更新を完了し、再取得で確認し、未解決事項と次のIssueを報告した状態。承認待ちの変更が残る場合は「判定完了・更新保留」とする。
- **中断・再開**：完了済み工程、未完了工程、実行済み変更、再開条件を記録。再開時は最新状態との差分を確認し、影響工程から再評価する。
- **段階的検証（方式合意済み）**：第1段階は既存の通常Issue #204 とCoverage Issue #170を読み取り専用で扱い、変更案・根拠・承認区分を確認する。第2段階は専用の試験Issueを用い、本文・チェックリスト・コメント・Close・中断再開を検証する。試験Issue作成と個々の変更操作の具体的承認を得るまでは第2段階を実行しない。既存の開発Issueを試験目的で変更しない。障害を無理に起こさず、意図的な停止・再開で確認する。

### 最終確認で合意する事項

1. **合意済み**：一括承認は提示済みの通常更新案に限定し、Issue・操作単位で部分承認、保留、非承認を区別する。
2. **合意済み**：事実・根拠・進捗・変更理由のIssueコメント投稿は承認不要。コメントによる仕様・方針の確定や他の変更操作の承認代替は禁止する。
3. **合意済み**：依存関係順に更新し、子Issueの状態・Evidence確認後に親Issueを同期する。部分失敗では成功済みを維持し、未完了から再開する。再開時の最新状態確認と必要な再承認を必須とする。
4. **合意済み（方式）**：第1段階は既存の通常Issue #204 とCoverage Issue #170を読み取り専用で検証し、第2段階は専用の試験Issueで本文・チェックリスト・コメント・Close・中断再開を検証する。試験Issueの作成と各変更操作の具体的な承認は実行前に取得する。既存の開発Issueは試験目的で変更しない。
5. 正式有効化の条件と正本への組み込み先。PRのDraft解除・マージは別途判断する。
