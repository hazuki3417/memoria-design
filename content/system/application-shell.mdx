# Application Shell：機能仕様

## 概要と適用範囲

Application Shellは、画面を横断する共通ヘッダー、利用範囲の切り替え、ナビゲーション、アカウント操作を提供します。

適用画面と例外の網羅的な一覧は、現段階では未確定です。ただし、一部の画面では利用者が進行中の操作に集中できるよう、サイドメニューの開閉と利用範囲の切り替えを意図的に提供しません。これは機能の欠落ではなく、画面ごとの設計上の制約です。

## 共通領域と役割

- **ヘッダー**: Memoriaの名称、ナビゲーション開閉操作、現在の利用範囲、アカウント操作を提供します。現在の利用範囲に応じたアクセント色を使用します。
- **利用範囲の切り替え**: PersonalとCommunityの選択肢を表示し、現在の利用範囲を識別します。PrototypeではPersonal、家族のアルバム、旅行の思い出を例示します。
- **ナビゲーション**: 現在の利用範囲に応じた項目を表示し、選択中の項目を識別します。開閉できる領域として表示します。
- **アカウント操作**: ユーザー情報に基づくメニューを提供します。
- **本文領域**: 個別画面の内容を表示します。Application ShellのPrototypeではダミーのコンテンツ領域を使用します。

上記はPrototypeから確認できる責務の整理です。実際の認可、通信、遷移先の確定は別途関連仕様を確認します。

## 共通操作を提供しない画面

一部の画面では、Application Shellを利用していてもサイドメニューの開閉や利用範囲の切り替えを提供しません。これらの操作を常に表示・利用可能にすることを共通仕様とはしません。画面ごとに提供しない操作とその理由を明示し、実装・Storybookで意図せず復活させないようにします。

Web実装の `applicationChrome.tsx` は `authenticated`、`pre-registration`、`restricted-flow` の表示区分を持ちます。`pre-registration`（`/register`）と `restricted-flow`（`/settings/account/delete`）では、ナビゲーション、利用範囲切り替え、アカウントメニューを表示しません。共通のApplication Headerを使用し、非表示のナビゲーションTriggerの領域を確保してMemoriaタイトル位置を通常画面と一致させます。`restricted-flow` ではNavigation Drawerも提供しません。削除画面の離脱は画面内の明示的な中止操作で行います。ほかの例外画面は個別に検討します。

## 現在のPrototypeで確認できる状態と操作

| 対象 | 現在のPrototypeで確認できること | 未接続・未確定のこと |
| --- | --- | --- |
| 利用範囲 | Personalと2つのCommunityを切り替えられる | 実データの取得、利用可能な範囲の判定 |
| ナビゲーション | 開閉し、現在の利用範囲に応じた項目を選択できる | 実際のURL遷移、画面データの読み込み |
| 利用範囲の変更 | 共通Destination（Dashboard、Media Browser、Groups Browser）は選択先contextの対応画面へ移動し、それ以外は選択先Dashboardへ移動する。ナビゲーションは閉じる | 遷移途中の未保存データ、切り替え失敗時の扱い |
| アカウント操作 | メニューを表示するための共通部品を使用する | 設定画面への遷移、ログアウト処理 |
| Community作成 | 操作を受け取るための接続点がある | 実際の作成画面への遷移と作成処理 |

## Context Switcherの一覧・検索

候補の表示名解決、検索、並び替えはWebのApplication Shell機能層が取得済みの本人用データから行う。BackendはCommunity ID・正式名称・本人の別名を提供し、Context SwitcherのUI Componentは構築済み候補の描画とIDによる選択を担当する。ソートキーは表示名のみとし、ID等の第2ソートキーは定義しない。日本語ロケールによる文字列比較を用い、漢字の読み仮名による順序の保証は要求しない。

- Context Switcherの各Contextには選択状態に関係なく、そのContextのAccent Colorを左側のラインとして表示する。選択状態はチェックアイコンや選択背景で区別する。
- Personalへの切り替えは常に一覧の上部から利用できるようにする。現在のContextがCommunityなら、そのCommunityをPersonalの下かつ検索欄の上に固定表示し、検索欄の下にはそのCommunityを除く切り替え候補を表示名の日本語ロケール順に表示する。現在のContextがPersonalならPersonalに選択状態を示し、参加Communityを表示名の日本語ロケール順に表示する。同一Communityを複数箇所へ重複表示しない。
- Community検索は取得済みの参加Communityのうち現在選択中以外の候補を対象としてフロントエンド内で実行し、検索入力ごとにバックエンドへ問い合わせない。大文字・小文字を区別しない部分一致とし、検索中の一致候補は表示名の日本語ロケール順で一覧に表示する。選択中Communityは検索文字列に関係なく検索欄の上に固定し、検索を解除すると切り替え候補の全件表示へ戻る。検索対象となる一覧の再取得は検索入力とは独立させる。
- Communityを未参加の場合、検索結果が0件の場合、取得中・取得失敗の場合を別の状態として扱う。取得失敗時にはCommunity候補を非表示にし、エラーメッセージと再試行を提供する。Personalへの切り替えを妨げない。
- Community作成への入口は一覧のスクロール位置や検索条件によらず到達可能とし、作成操作の条件は[Community作成](/screens/community-creation)に従う。
- 一覧表示の容量は[読み込み系の上限](/system/cross-cutting/limits/read)のCommunity参加数と整合させる。候補が多い場合にも検索と選択を利用でき、一覧の長さによって基本操作が隠れない。

- 各Communityの表示名は本人の別名が設定されていれば別名のみ、未設定なら正式名称とする。検索もこの表示名のみを対象とする。別名はUser × Communityの個人設定であり、他の参加者が見る正式名称を変更しない。別名未設定時や同一の表示名が複数並ぶことを許容し、名前の重複だけを理由に候補をまとめたり選択不能にしたりしない。Communityの選択先は安定したCommunity IDで判定する。識別子は表示せず、アクセント色だけを同名候補の識別根拠にしない。

## Context Switcherのデータ同期契約

- Application Shellの参加Community一覧を、Context Switcherの候補および現在Contextの表示名・Accentを解決する共通の参照元とする。Community IDを候補のidentityに使い、再取得で並び順が変わっても別Communityへ選択状態を移さない。
- Backendから取得するのは所属CommunityのID、正式名称、本人向けの別名とAccent Colorである。WebのApplication Shell機能層で表示名を解決し、取得済みデータから検索・日本語ロケール順の単一キーソートを行って表示Componentへ渡す。検索欄への入力でAPIリクエストを発生させない。
- 初期取得成功前は未取得と空一覧を区別する。再取得中は既存候補と検索入力を維持する。取得失敗時は成功済み候補をキャッシュから削除せず、Switcher上では一時的に非表示にして再試行可能な状態を伝える。失敗した更新結果を成功済みとして反映しない。
- SwitcherのOpen操作を受けた機能層が最新一覧の取得を要求する。取得中の同一要求があれば重複開始しない。画面描画や検索文字変更では再取得しない。Closeによって成功済み候補を破棄せず、次回Openで再検証する。
- Community作成・参加・離脱・除外・削除・正式名称変更、および本人のCommunity別名・Accent Colorの保存成功後は、既存の参加Community一覧の参照元を更新または無効化・再取得し、同じデータを参照するHeader・Switcherに反映する。別名の入力途中や保存失敗では共有表示名を更新しない。
- 複数MutationやOpen時の再取得が重なる場合は、古い取得結果が確認済みの新しい保存結果を上書きしないようにする。具体的なApollo Clientのキャッシュ更新、無効化、リクエスト順制御はWeb実装で決める。別名とAccent Colorの部分更新で省略fieldの保存値を変更しない。
- Membership失効などで現在のContextが無効になった場合は、古い候補一覧を認可の根拠にせず、Application IAの安全な遷移とError表示の契約に従う。

## Context Switcherの取得・切り替え失敗

- Community候補の初回取得に失敗しても現在のContextとPersonalへの移動手段を維持する。取得できないことをCommunity未参加と見なさず、候補領域で再試行できるようにする。
- Context Switcherを開くたびに参加Community一覧の再取得を開始する。取得済みの候補があれば直ちに表示し、再取得中も候補の検索・選択を利用できるようにする。同じ一覧の取得が進行中であれば、開閉の繰り返しや表示更新によって重複した取得を開始しない。再取得の契機はSwitcherを開く操作であり、画面の再描画そのものには依存しない。
- Communityの作成・参加・離脱・削除、正式名称・個人向け別名・利用者向けAccentの変更が成立した場合は、Switcherを開くまで待たず、一覧へ変更を反映する。検索文字列の変更では通信しない。定期的な再取得は行わない。
- 一度取得した候補の再取得失敗では、検索入力を維持しつつCommunity候補を非表示にする。再試行に成功すれば取得できた候補を再表示する。取得済みキャッシュを削除する必要はない。
- Context切り替え中は重複した切り替えを防ぎ、完了前に選択先を現在Contextとして確定表示しない。遷移先を利用できない場合は成立していない切り替えを成功扱いせず、元の利用可能なContextへ戻れるようにする。
- 現在のCommunityのMembership失効・対象消失によって画面の継続ができない場合は、候補一覧の取得失敗とは区別し、共通エラー画面とPersonalへの移動手段を提供する。認可されないCommunityの保護情報を表示しない。

## 利用範囲を切り替えた際の遷移規則

利用範囲を切り替える際は、現在のDestinationが選択先contextにも存在する場合、その対応画面へ遷移します。Initial ReleaseではDashboard、Media Browser、Groups Browserを共通Destinationとします。例えばPersonalの`/media`からCommunityへ切り替えると、選択先Communityの`/communities/[communityId]/media`へ移動します。対応画面がない場合は選択先contextのDashboardへ遷移します。遷移先URLとcontextの対応は[Application Information Architecture](/system/application-information-architecture)を正本とします。

切り替え時に引き継ぐのはDestination種別です。切り替え前context固有のMediaやGroupの識別子、画面内の選択・絞り込み状態を同一のものとして引き継ぎません。未保存入力の扱いと切り替え失敗時の復旧は未確定のままとします。

ページ種別を維持することは、切り替え前の利用範囲に属する個別のメディアやグループの識別子まで引き継ぐことを意味しません。未保存の入力がある場合の扱いなど、別途判断が必要な事項は未確定のままとします。

## Viewportとスクロール

Header固定、Main contentのScroll領域、ViewportとActionへの到達性に関する共通Contractは[Application Shell Pattern](/design-system/patterns/application-shell#scroll--viewport-contract)を正本とします。Mantine `AppShell.Main` のOffsetや高さ制約等の実装方式は[Frontend実装規約](/system/web/implementation-conventions#scroll-containerの実装規則)に従います。

## 画面幅と入力方法

現在のStoryは `Personal`、`Community`、`Compact` の3種類です。画面幅によって共通領域の配置・開閉方法・情報量が変わる場合も、必要な操作に到達できるようにします。

ナビゲーションの開閉操作には、現在の実装で開閉状態を示す属性と説明が用意されています。キーボード操作や焦点移動を含む動作は、実装とStorybookで追加確認が必要です。

## テストの役割分担

StorybookとVRTは、共通ヘッダー、ナビゲーション、利用範囲の切り替えUIの表示状態・レイアウト・画面幅ごとの差分を確認します。VRTの撮影対象はStoryのCanvasとし、実際のURL遷移は行いません。

E2Eテストでは、利用範囲の切り替えによるURL変更、遷移先画面とデータ、ブラウザ履歴を確認します。Dashboard・Media Browser・Groups Browserでは選択先contextの対応画面へ、対応画面がないDestinationでは選択先Dashboardへ遷移することを検証します。必要に応じて遷移先の判定を単体テストで補いますが、画面遷移の最終的な確認はE2Eで行います。

## 確認が必要な事項

次の事項は現行Prototypeだけでは決定できないため、現時点で仕様として確定しません。

- 上記以外で共通操作を提供しない画面の一覧と、画面ごとの制限理由

- 権限喪失、利用範囲の取得失敗、対象消失時の表示と復旧
- 設定画面、ログアウト、Community作成への接続
- 画面幅と入力方法ごとの追加検証が必要な振る舞い
