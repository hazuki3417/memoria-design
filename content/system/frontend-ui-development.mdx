# Frontend UI設計・開発方針

## 目的

Memoria WebのUI設計・実装を、AIを中心に効率よく進めながら、利用者にとってシンプルで質の高いUI/UXを継続的に提供するための基本方針を定義します。

この文書は画面ごとの詳細仕様を定義するものではありません。画面設計、Design System、実装、Visual Reviewの責務と開発方法を定義します。

## 基本方針

- Figma等による静的モック作成を標準工程とはしません。
- UIの意味、要求、状態、操作、Navigation、Memoria固有のDesign Systemは `memoria-design` をSource of Truthとします。
- React/Mantineによる具体的な実装は `memoria-web` が所有します。
- Storybookは設計のSource of Truthではなく、UI実装を独立して観察・検証・Visual Reviewするための実行可能なExampleとして扱います。
- 既存の画面・Componentは仕様そのものとはみなしません。新しい設計に適合するものは再利用し、適合しないものは再設計できます。

## Screen SpecificationとStorybook

Screen Specificationでは、UIが満たすべき意味と振る舞いを定義します。主に次の情報を対象とします。

- 画面の目的
- 提示する主要な情報
- 利用者が実行できる主要な操作
- Loading、Empty、Error等を含む重要な状態
- Navigationと画面間の関係
- その画面固有の制約

pixel単位の配置、特定のReact/Mantine API、Component構成に加え、`Dialog` / `Drawer` / `Modal` / `Page` / `Sidebar` / `split view`等の具体的presentationも原則としてScreen Specificationへ含めません。Screen Specificationは「何を確認・判断・操作できる必要があるか」を定義し、「それをどのUI形式で実現するか」は後続のUI具体化とVisual Reviewで決定します。

Storybookは、Screen SpecificationとDesign Systemに基づいて実装されたComponentや画面状態を確認するために利用します。Storyは仕様そのものではなく、仕様を検証するための実行可能なExampleです。

### 配置と標準構成

Screen Specificationは製品UIの仕様として `content/screens/` に配置します。特定domainやWeb実装へ従属させず、画面単位の仕様として管理します。画面数が少ない間はflatに配置し、規模が増えて分類の必要性が明確になった場合にsubdirectoryを導入します。

各Screen Specificationは原則として次の観点を記述します。

- Purpose
- Related Use Cases
- Information
- Actions
- States
- Navigation
- Constraints
- Responsive Behavior

Related Use Casesでは、`media/use-cases.mdx` 等の既存Use Caseを明示的に参照し、画面が提供する利用者価値を追跡可能にします。

Screen SpecificationはUIが満たすべき意味と振る舞いを記述し、特定のlayout、pixel値、Mantine Component、Dialog / Drawer / Page等のpresentationを実現方法として固定しません。presentation自体がProduct要件となる例外では、その必要性と制約を仕様上説明します。またStorybookのStory一覧を仕様へ複製しません。Storyや実装側から対応するScreen Specificationを参照できる関係を基本とします。

## UI設計・レビュー時のSource of Truth確認

画面の詳細設計、Visual Prototypeの実装、UI Reviewを行う際は、会話上の直前の判断や一般的なUI/UX知識だけを根拠にせず、作業開始時に `memoria-design` の最新状態を確認します。

確認対象は、対象画面のScreen Specification、Frontend UI設計・開発方針を含む関連するUX Principles / Patterns / Design System、および対象機能に関係する既存仕様です。これらを確認したうえで設計・実装・Reviewを行い、Memoria側に定義済みの方針を外部Design Systemや一般論で上書きしません。

外部Design Systemや一般的なUI/UX guidelineは、Memoria側で未定義の論点を検討するReferenceとして利用できます。採用する場合も、Memoriaのユースケースに適する理由を確認し、再利用可能な判断として確定した場合にのみMemoria自身のDesign Systemへ反映します。

## AIを利用したUI開発

UIデザインと実装を完全に分離した工程にはせず、実際のReact Componentをinteractive prototypeとして利用します。

基本的な流れは次のとおりです。

1. Screen Specificationを定義する。
2. AIがDesign Systemと既存Componentを確認する。
3. 設計上の判断が必要な場合は、AIが選択肢とtrade-offを提示し、人間と合意する。
4. AIがStorybook上で実際のUIを実装する。
5. AIが仕様との整合、表示崩れ、情報階層等を一次Reviewする。
6. 人間が実際の表示をVisual Reviewする。
7. AIがfeedbackを反映する。
8. 承認したUIをApplicationへ統合する。
9. 必要なVRT、interaction test、E2E等で回帰を保証する。

最終的なVisual Approvalは人間が行います。

### 詳細設計中のPrototypeとPR境界

Storybookのinteractive prototypeを使ったVisual Reviewは、詳細設計を確定するための設計作業として扱います。Prototypeが一通り表示・操作できることや、作業branch上でcommitがまとまったことだけを、PR作成へ進む条件とはしません。

詳細設計中は、必要に応じて `memoria-web` の作業branchへprototypeをcommitし、人間とのVisual Reviewと修正を継続できます。この段階では通常の実装Taskにおける「実装の一区切り」と同一視せず、PRを作成しません。

UI詳細設計では原則として次の順序で進めます。

1. Screen Specificationと関連する要求・Design Systemを確認する。
2. Storybook上にinteractive prototypeを作成し、作業branchへ必要な変更をcommitする。
3. 人間がVisual Reviewし、情報階層、presentation、interaction、responsive behaviorを調整する。
4. 合意した重要な判断を `memoria-design` のScreen Specification、Design System、関連設計へ反映する。
5. 未解決事項がある場合はIssueへ記録し、詳細設計として残す範囲を明確にする。
6. 人間と詳細設計の完了を確認する。
7. その後にPR作成前のformat等、通常のPR準備へ進み、PRを作成する。

したがって、prototypeの作成・修正中は「Visual Reviewのための作業branch」、詳細設計完了後は「Review・統合する変更」として扱います。一般的な小さなPRによる継続統合よりも、詳細設計のためにprototypeを反復している間はこの境界を優先します。

ChatGPTはprototype完成、commit作成、Story追加などを独自にPR作成の許可と解釈しません。詳細設計完了前にPRを作成する必要がある場合は、人間からそのTaskについて明示的な指示を受けます。

Visual Reviewで得られた判断をすべてDesign Systemへ追加するのではなく、複数の画面で再利用する価値がある原則・PatternだけをDesign Systemへ昇格させます。

## Design System

Memoria Design Systemは、最初から完成したComponent catalogとして設計しません。実際の画面設計・実装とともに段階的に成熟させます。

### 実装Foundation

`memoria-web` ではMantineをUI実装のFoundationとして継続利用します。

Mantineが既に提供するComponent、theme scale、interaction等を理由なく再実装しません。Media DetailのTag入力はfree textを要件とし、WebではMantine `TagsInput`の利用を想定します。既存Tagの候補選択を必須にせず、未登録名の入力からTag作成・付与へ進めます。Memoria固有の要求を実現できない場合に限り、拡張または独自実装を検討します。

### 外部Design System

GitHub Primer、Shopify Polaris、Atlassian Design System、Material Design等の成熟したDesign SystemをReferenceとして積極的に利用できます。

ただし、特定の外部Design SystemをMemoriaの仕様としてそのまま採用しません。外部のPatternや原則は、Memoriaのユースケースに適する理由がある場合にMemoria自身のルールとして採用します。

### Memoria Design Systemの成長

Design Systemは概ね次の関係で扱います。

- Foundation: Mantineを中心とした実装基盤
- UX Principles: Memoriaとして一貫して守るUI/UX原則
- Patterns: 実際の画面から見つかった再利用可能な設計
- Components: `memoria-web` における具体的な実装

画面固有の判断は画面実装に留め、再利用可能な判断だけを共通Patternへ昇格させます。

### FoundationとPatternの境界

FoundationはMantineが提供するtheme scale、primitive、Accessibility、基本的なinteraction behaviorを中心とします。Memoria独自のtokenやprimitiveは、実際の画面設計から必要性が確認された場合に追加します。既存の `memoria-web/src/components` に存在するComponentは、存在していることだけを理由にFoundationやPatternとはみなしません。

PatternはComponent catalogではなく、複数の画面で繰り返し発生するUI/UX上の問題に対するMemoriaとしての標準的な解決方法です。画面固有の判断を先回りしてPattern化せず、Screen Specification、実装、Visual Reviewを通して再利用性が確認されたものを昇格させます。ただし、明らかに複数画面へ適用される横断要件について、機械的に2つ目の利用例を待つ必要はありません。

Patternの目的、適用条件、振る舞い、Variation、制約等の意味的な仕様は `memoria-design` をSource of Truthとし、具体的なReact / Mantine Component、Story、testは `memoria-web` をSource of Truthとします。

Patternを追加する場合は、少なくともPurpose、When to Use、Behavior、Variations、Constraintsを記述します。必要に応じてResponsive BehaviorやAccessibility上の固有要件を追加します。Component API、CSS、pixel値等の実装詳細は原則としてPattern仕様へ含めません。

既存Componentを一括してDesign Systemへ登録する棚卸しは行いません。各Screenを設計・実装する際に、既存Componentが現在のScreen SpecificationとUX Principlesへ適合するかを確認し、適合するものは再利用し、適合しないものは変更または廃止します。

## UI/UXの方向性

Memoriaは、機能を減らすことで単純に見せるのではなく、利用者が現在必要としている情報と操作を適切に提示することで、知覚する複雑さを抑えることを目指します。

Visual Designはシンプルかつコンテンツ中心とし、UI自体がMediaより過度に主張しないことを重視します。一方で、操作性、feedback、interaction quality等はUI/UX上の重要な品質として扱います。

画面設計・提案・Visual Reviewでは[UX設計・レビュー基準](/design-system/ux-review)を適用し、主要Taskの導線、入力、Feedback、失敗からの復旧、一貫性と画面固有の適応、Accessibilityを確認します。外部サービスとの差別化は見た目の独自性だけで判断せず、Mediaの発見・整理・共有を少ない迷いと手間で達成できるか、実装後の利用者FeedbackとTask評価で検証します。

### UX Principles

Memoriaの画面設計、AIによるUI生成、Visual Reviewでは次の原則を共通の判断軸として利用します。

1. **Content First / Media First**: Userが最も関心を持ち、管理する対象はMediaです。GroupsはMediaの発見・閲覧・整理を支える手段とし、Groupの専用詳細画面を経由させる等、Mediaへの到達を不必要に遅らせるNavigationを避けます。一方、将来のTags管理画面はMedia閲覧ではなく、表記ゆれの修正と検索語彙の整備を目的に設計します。画面ごとのUserの動機を優先し、すべての画面へ一律にMedia中心の構成を強制しません。Mediaや利用者のデータを主役とし、UI自体は必要以上に主張しません。
2. **Progressive Disclosure**: 利用者が現在必要な情報と操作を優先し、高度または低頻度なものは必要な文脈で提示します。
3. **Contextual Action**: 操作は対象や現在の状態との関係を理解しやすい場所に提示し、画面全体へ無秩序にActionを並べません。
4. **Predictable Interaction**: 同じ意味や操作には一貫したPatternを利用し、理由なく一般的なWeb UIの慣習から逸脱しません。
5. **Immediate Feedback**: 操作の受付、進行、成功、失敗、状態変化を適切なtimingで明確に伝えます。

これらは個別画面のlayoutを固定する規則ではなく、複数の実現方法からUIを選択・Reviewするための原則です。実際の画面設計から再利用可能な具体的Patternが見つかった場合はDesign Systemへ追加します。

## Responsive Design

Memoriaは、原則として端末によって提供するユーザー目的やCapabilityを変えません。同じ機能を利用できることを基本としつつ、UI表現は利用可能な表示領域や入力環境へ適応させます。

同じCapabilityを提供するために、情報配置、Navigation、操作の提示方法等が端末間で同一である必要はありません。Responsive Designはdesktop向けUIを単純に縮小する作業ではなく、同じユーザー目的をそれぞれの利用環境に適したUIで実現する設計として扱います。

端末によってCapabilityを制限する必要が生じた場合は、実装都合で暗黙に制限せず、個別の製品設計判断として明示します。

Responsive対応は完成後に追加する補助対応ではなく、Screen SpecificationとUI実装の時点から考慮します。

breakpointはMantineの標準設定を基本とし、製品上の必要性が確認されない限りMemoria独自のbreakpointを追加しません。特定のdevice modelを設計上の境界にはせず、利用可能な表示領域に応じてUIを適応させます。

設計時は表示領域を **Compact / Medium / Wide** の3つの代表的な領域として確認します。smartphone、tablet、desktopは理解のための代表例であり、特定のdevice modelを仕様上の境界にはしません。具体的なpixel値はVRTやE2E等のtest infrastructureで代表値として決定します。

viewportとinput modalityは独立した設計軸として扱います。pointer、touch、keyboardの利用を想定し、重要な操作をhoverだけに依存させません。touchでも十分に操作可能な対象を確保し、keyboardで主要操作へ到達・実行でき、focusを視認できるようにします。高精度なpointerを前提とする細かすぎる操作を必須にしません。

Screen SpecificationではCompact / Medium / Wideや各input modalityについて機械的に同じ記述を繰り返しません。表示領域や入力方式によってInformation、Action、Navigation等の表現・優先順位が変化する場合に、その差と維持すべきCapabilityをResponsive Behaviorとして記載します。

## Browser Support

Memoria Webは特殊な互換性要件を持たないため、modern evergreen browserをsupport対象とします。

対象はChrome、Edge、Firefox、Safariの現行安定版を基本とし、mobile環境ではiOS SafariとAndroid Chromeを対象とします。古いBrowser versionや特定versionの長期supportは原則として行いません。

support対象であることと、CIで常に全Browser・全viewportの組み合わせを検証することは分離して考えます。自動テストでは代表的なBrowserとviewportを選択し、cross-browser固有のriskや不具合が確認された場合に必要な検証を追加します。

製品上または利用者環境上の要件が生じた場合は、このsupport policyを見直します。

## Inputのフォーカス時の視覚的安定性

- Memoria全体で、Input等の入力コンポーネントをクリック・タップ・キーボード操作でフォーカスした際に、コンポーネント自身や周辺レイアウトの位置・寸法が揺れたり、ずれたりしないことを原則とします。
- フォーカス状態は視認できる必要があります。border色、outline、box-shadow等、レイアウトを変化させない方法を優先し、フォーカス表示自体は削除しません。
- 既存の入力コンポーネントと新規画面の双方に適用します。具体的な原因の特定と修正は `memoria-web` の実装・検証で行います。

## Accessibility

Memoria Webは認証後に利用するApplication UIです。Accessibilityは後付け対応ではなく通常のUI品質として扱い、認証後の主要な操作を利用者が支障なく実行できることを重視します。

設計・実装上はWCAG 2.2 Level AAを基準とします。ただし、現時点では不特定多数へ公開する情報サイトとして網羅的な適合性を証明するための認証・監査運用までは要求しません。

keyboard操作、focus visibility、semantic HTML、accessible name、contrast、色だけに依存しない状態表現、画像の適切な代替情報、操作対象の大きさ、状態変化の伝達等、Applicationの操作可能性に直接関係する事項は通常の実装品質に含めます。

標準HTMLとMantine等が提供するaccessibleなprimitiveを優先し、独自Componentで既存のAccessibilityを損なわないようにします。自動検査で検出可能な問題はStorybook等で継続的に検出します。CIで強制する範囲はUI quality gateの方針として別途定めます。

## UI Quality Gate

UI品質の検証は、それぞれの検査手段が適した責務を担当します。通常の静的検査とUnit Testを基本とし、UIに影響する変更ではStorybook、Accessibility検査、Visual Regression Test、Interaction Testを利用します。Application E2Eは重要なUser Flowを対象とし、自動検査だけで判断できないVisualやUXはHuman Visual Reviewで確認します。

検査はすべての変更で一律に実行するのではなく、変更の影響範囲に応じて必要なものを選択します。共通Componentやtheme等の変更による間接的な影響も考慮します。対象外となった検査は、未実施との違いをCI上で確認できるようにします。

Memoriaの共通UI ComponentとしてComponent化したものは、原則として同時にStorybook Storyを実装します。StorybookをVisual ReviewだけでなくVisual Regression Testの観測点として利用し、Component単体で主要なvisual state、interaction state、必要なvariationを再現できる状態をComponentの実装完了条件に含めます。単にdefault stateを表示するだけではなく、Componentのvisual contractに影響する状態がある場合は、それらをVRTで安定して観測できるStoryとして用意します。

画面固有のCompositionや内部実装上の小さなComponentまで機械的に個別Storyを要求するものではありません。Design Systemまたは複数画面から利用する共通UI Componentとして昇格させる場合に、このStorybook要件を適用します。

### Human Visual Review前の実行可能性Gate

Visual Prototypeを含むUI変更をHuman Visual Reviewへ渡す場合、確認者が実行時errorやsource破損の調査を行わず、意図したUI/UXの確認から開始できる状態をReview開始条件とします。

実装をcommitしたこと自体をReview可能とはみなしません。変更後はGitHub上の最新sourceを再取得してwrite結果を確認し、変更範囲に応じたformat / lint / type check / build等の静的・構文検査を実行します。StorybookをReview surfaceとする変更では、対象Storyが少なくとも正常に描画でき、初期表示とReview対象の主要interactionへ到達できることを確認してからReviewを依頼します。

AIまたは開発者がsourceを直接更新した場合も同じGateを適用します。文字列置換、生成処理、remote API経由の更新等では、literal escape、閉じtagの不整合、import破損等が混入し得るため、write APIの成功だけを変更成功の根拠にしません。更新後のsource再取得と機械的検査を完了条件に含めます。

検査に失敗した状態ではHuman Visual Reviewを依頼せず、まず実装を修正します。環境上の理由等で必要な検査を実行できない場合は、実行できた検査、未確認事項、Reviewへの影響を明示し、動作確認済みであるかのように扱いません。

このGateはHuman Visual Reviewを自動検査へ置き換えるものではありません。機械的に検出可能な破損をReview前に除去し、人間の確認をVisual Design、Interaction、Responsive Behavior、UX判断へ集中させるための前提条件です。

### Design DocumentとStorybookの責務

Design Documentは、UI/UX上の判断、利用条件、意味、制約、Patternの選択基準を正本として保持します。Componentの具体的な見た目、visual state、variation、responsive behavior、interaction state等、実装と同期して確認すべきvisual contractはStorybookへ寄せ、Storyを **executable visual specification** として扱います。

Design DocumentへComponent API、pixel値、実装上のlayout detail、Storybookで直接確認できるvariationを重複して記録しません。これらを文書化する必要がある場合も、Design上の判断理由や守るべき制約を記述し、具体的な現行表現はStorybookを参照します。

一方、Storybookだけでは表現しにくい「なぜそのPatternを使うか」「どのsurfaceを選択するか」「どの状態を継続して提示する必要があるか」等のUX判断はDesign Documentに残します。Screen Specificationは、そのScreenがどのPattern / ComponentをどのProduct contextで組み合わせるかを所有します。

この分担により、Design Documentを実装Component Catalogとして肥大化させず、visual contractの二重管理を避けます。共通UI Componentを変更する場合は、実装だけでなく対応するStoryも同じ変更単位で更新し、Design上の判断自体が変わる場合にDesign Documentも更新します。

各検査を必須化する範囲は、test asset、実行時間、安定性を確認しながら段階的に拡大します。Visual Regression Testの基準画像は、意図した変更であることを人間が確認してから更新します。

具体的な変更検知方法、GitHub Actions構成、代表viewport、Browser matrixは `memoria-web` のtest infrastructure設計で決定します。


## Collectionの読み込みとNavigation

Memoria Webでは、一覧にページ番号を表示して移動するページ送り型Paginationを提供せず、**Relay Connectionを利用した無限ローディング**を標準とします。適用対象はMedia一覧に限らず、追加読み込みが必要なCollection全般です。各画面の具体的な取得条件・順序・空状態は対象ScreenとGraphQL契約で定義します。

Collectionの取得が正常に完了し、現在の条件に一致するItemが0件である場合は、空白の表示領域だけを残さず、該当するdataがないことを明示します。初期Empty、検索・Filter結果0件、relation等の部分Collectionが0件である状態を正常な結果として扱い、読み込み中・取得失敗と区別します。具体的な文言やEmpty State Componentは各Screen / Patternで定義できます。

追加読み込み中・終端・追加取得失敗を識別し、失敗時には表示済みItem・選択・検索・絞り込み・スクロール位置を可能な限り維持して再試行できるようにします。検索・絞り込み・並び順の変更時は該当条件のConnectionを取得し直しますが、明示選択済みItemを意図せず解除しません。未取得Itemを暗黙に選択する操作は提供しません。Viewportへの到達だけに依存せず、keyboard・支援技術でも追加取得と状態を利用できるようにします。具体的なcursor、fetch size、cache policy、virtualizationは実装詳細設計で決定します。

Collectionの件数をUserへ提示する場合は、現在Clientが取得済みのItem数ではなく、現在のscope・検索・絞り込み等の条件に一致するCollection全体の総件数を表示します。無限ローディングの取得進捗を標準の件数表示へ混在させず、`取得済み件数 / 総件数` のような表示はProduct上ロード進捗を明示する必要がある場合に限って個別に検討します。件数表示自体をすべてのCollectionへ必須とはせず、そのCollectionの規模を伝えることに利用者価値がある場合に提示します。

Collectionを基準とするDetailの前後Navigation等では、現在Clientが取得済みのItem集合をCollection全体の境界として扱いません。現在のCollection条件と順序上で移動先が存在する場合は、必要に応じてConnectionを追加取得してInteractionを継続します。追加取得失敗によって現在成立しているDetailや一覧状態を破棄せず、現在位置を維持したまま再試行可能にします。

検索・Filter・分類構造等、Collectionを規定する条件そのものがUser操作によって変更された場合は、旧Collectionとの差分をClient側で無理に再構築せず、変更後の条件に対応する新しいCollectionとして取得・表示できます。この場合は旧Collectionのスクロール位置維持を必須とせず、新しいCollectionの先頭から探索を開始するBehaviorを採用できます。単なる追加取得や一時的な再取得失敗とは区別し、成立済み条件が変わっていないCollectionを不必要に初期化しません。
