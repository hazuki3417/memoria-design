# Frontend UI設計・開発方針

## 目的

Memoria WebのUI設計・実装を、AIを中心に効率よく進めながら、利用者にとってシンプルで質の高いUI/UXを継続的に提供するための基本方針を定義します。

この文書は画面ごとの詳細仕様を定義するものではありません。画面設計、Design System、実装、Visual Reviewの責務と開発方法を定義します。

## 基本方針

- Figma等による静的モック作成を標準工程とはしません。
- UIの意味、要求、状態、操作、Navigation、Memoria固有のDesign Systemは `memoria-design` をSource of Truthとします。
- React/Mantineによる具体的な実装は `memoria-web` が所有します。
- Storybookは設計のSource of Truthではなく、UI実装を独立して観察・検証・Visual Reviewするための実行可能なExampleとして扱います。
- 既存の画面・Componentは仕様そのものとはみなしません。新しい設計に適合するものは再利用し、適合しないものは再設計できます。

## Screen SpecificationとStorybook

Screen Specificationでは、UIが満たすべき意味と振る舞いを定義します。主に次の情報を対象とします。

- 画面の目的
- 提示する主要な情報
- 利用者が実行できる主要な操作
- Loading、Empty、Error等を含む重要な状態
- Navigationと画面間の関係
- その画面固有の制約

pixel単位の配置や、特定のReact/Mantine API等の実装詳細は原則としてScreen Specificationへ含めません。

Storybookは、Screen SpecificationとDesign Systemに基づいて実装されたComponentや画面状態を確認するために利用します。Storyは仕様そのものではなく、仕様を検証するための実行可能なExampleです。

### 配置と標準構成

Screen Specificationは製品UIの仕様として `content/screens/` に配置します。特定domainやWeb実装へ従属させず、画面単位の仕様として管理します。画面数が少ない間はflatに配置し、規模が増えて分類の必要性が明確になった場合にsubdirectoryを導入します。

各Screen Specificationは原則として次の観点を記述します。

- Purpose
- Related Use Cases
- Information
- Actions
- States
- Navigation
- Constraints
- Responsive Behavior

Related Use Casesでは、`media/use-cases.mdx` 等の既存Use Caseを明示的に参照し、画面が提供する利用者価値を追跡可能にします。

Screen SpecificationはUIが満たすべき意味と振る舞いを記述し、特定のlayout、pixel値、Mantine Component等の実現方法を固定しません。またStorybookのStory一覧を仕様へ複製しません。Storyや実装側から対応するScreen Specificationを参照できる関係を基本とします。

## AIを利用したUI開発

UIデザインと実装を完全に分離した工程にはせず、実際のReact Componentをinteractive prototypeとして利用します。

基本的な流れは次のとおりです。

1. Screen Specificationを定義する。
2. AIがDesign Systemと既存Componentを確認する。
3. 設計上の判断が必要な場合は、AIが選択肢とtrade-offを提示し、人間と合意する。
4. AIがStorybook上で実際のUIを実装する。
5. AIが仕様との整合、表示崩れ、情報階層等を一次Reviewする。
6. 人間が実際の表示をVisual Reviewする。
7. AIがfeedbackを反映する。
8. 承認したUIをApplicationへ統合する。
9. 必要なVRT、interaction test、E2E等で回帰を保証する。

最終的なVisual Approvalは人間が行います。

Visual Reviewで得られた判断をすべてDesign Systemへ追加するのではなく、複数の画面で再利用する価値がある原則・PatternだけをDesign Systemへ昇格させます。

## Design System

Memoria Design Systemは、最初から完成したComponent catalogとして設計しません。実際の画面設計・実装とともに段階的に成熟させます。

### 実装Foundation

`memoria-web` ではMantineをUI実装のFoundationとして継続利用します。

Mantineが既に提供するComponent、theme scale、interaction等を理由なく再実装しません。Memoria固有の要求を実現できない場合に限り、拡張または独自実装を検討します。

### 外部Design System

GitHub Primer、Shopify Polaris、Atlassian Design System、Material Design等の成熟したDesign SystemをReferenceとして積極的に利用できます。

ただし、特定の外部Design SystemをMemoriaの仕様としてそのまま採用しません。外部のPatternや原則は、Memoriaのユースケースに適する理由がある場合にMemoria自身のルールとして採用します。

### Memoria Design Systemの成長

Design Systemは概ね次の関係で扱います。

- Foundation: Mantineを中心とした実装基盤
- UX Principles: Memoriaとして一貫して守るUI/UX原則
- Patterns: 実際の画面から見つかった再利用可能な設計
- Components: `memoria-web` における具体的な実装

画面固有の判断は画面実装に留め、再利用可能な判断だけを共通Patternへ昇格させます。

### FoundationとPatternの境界

FoundationはMantineが提供するtheme scale、primitive、Accessibility、基本的なinteraction behaviorを中心とします。Memoria独自のtokenやprimitiveは、実際の画面設計から必要性が確認された場合に追加します。既存の `memoria-web/src/components` に存在するComponentは、存在していることだけを理由にFoundationやPatternとはみなしません。

PatternはComponent catalogではなく、複数の画面で繰り返し発生するUI/UX上の問題に対するMemoriaとしての標準的な解決方法です。画面固有の判断を先回りしてPattern化せず、Screen Specification、実装、Visual Reviewを通して再利用性が確認されたものを昇格させます。ただし、明らかに複数画面へ適用される横断要件について、機械的に2つ目の利用例を待つ必要はありません。

Patternの目的、適用条件、振る舞い、Variation、制約等の意味的な仕様は `memoria-design` をSource of Truthとし、具体的なReact / Mantine Component、Story、testは `memoria-web` をSource of Truthとします。

Patternを追加する場合は、少なくともPurpose、When to Use、Behavior、Variations、Constraintsを記述します。必要に応じてResponsive BehaviorやAccessibility上の固有要件を追加します。Component API、CSS、pixel値等の実装詳細は原則としてPattern仕様へ含めません。

既存Componentを一括してDesign Systemへ登録する棚卸しは行いません。各Screenを設計・実装する際に、既存Componentが現在のScreen SpecificationとUX Principlesへ適合するかを確認し、適合するものは再利用し、適合しないものは変更または廃止します。

## UI/UXの方向性

Memoriaは、機能を減らすことで単純に見せるのではなく、利用者が現在必要としている情報と操作を適切に提示することで、知覚する複雑さを抑えることを目指します。

Visual Designはシンプルかつコンテンツ中心とし、UI自体がMediaより過度に主張しないことを重視します。一方で、操作性、feedback、interaction quality等はUI/UX上の重要な品質として扱います。

### UX Principles

Memoriaの画面設計、AIによるUI生成、Visual Reviewでは次の原則を共通の判断軸として利用します。

1. **Content First**: Mediaや利用者のデータを主役とし、UI自体は必要以上に主張しません。
2. **Progressive Disclosure**: 利用者が現在必要な情報と操作を優先し、高度または低頻度なものは必要な文脈で提示します。
3. **Contextual Action**: 操作は対象や現在の状態との関係を理解しやすい場所に提示し、画面全体へ無秩序にActionを並べません。
4. **Predictable Interaction**: 同じ意味や操作には一貫したPatternを利用し、理由なく一般的なWeb UIの慣習から逸脱しません。
5. **Immediate Feedback**: 操作の受付、進行、成功、失敗、状態変化を適切なtimingで明確に伝えます。

これらは個別画面のlayoutを固定する規則ではなく、複数の実現方法からUIを選択・Reviewするための原則です。実際の画面設計から再利用可能な具体的Patternが見つかった場合はDesign Systemへ追加します。

## Responsive Design

Memoriaは、原則として端末によって提供するユーザー目的やCapabilityを変えません。同じ機能を利用できることを基本としつつ、UI表現は利用可能な表示領域や入力環境へ適応させます。

同じCapabilityを提供するために、情報配置、Navigation、操作の提示方法等が端末間で同一である必要はありません。Responsive Designはdesktop向けUIを単純に縮小する作業ではなく、同じユーザー目的をそれぞれの利用環境に適したUIで実現する設計として扱います。

端末によってCapabilityを制限する必要が生じた場合は、実装都合で暗黙に制限せず、個別の製品設計判断として明示します。

Responsive対応は完成後に追加する補助対応ではなく、Screen SpecificationとUI実装の時点から考慮します。

breakpointはMantineの標準設定を基本とし、製品上の必要性が確認されない限りMemoria独自のbreakpointを追加しません。特定のdevice modelを設計上の境界にはせず、利用可能な表示領域に応じてUIを適応させます。

設計時は表示領域を **Compact / Medium / Wide** の3つの代表的な領域として確認します。smartphone、tablet、desktopは理解のための代表例であり、特定のdevice modelを仕様上の境界にはしません。具体的なpixel値はVRTやE2E等のtest infrastructureで代表値として決定します。

viewportとinput modalityは独立した設計軸として扱います。pointer、touch、keyboardの利用を想定し、重要な操作をhoverだけに依存させません。touchでも十分に操作可能な対象を確保し、keyboardで主要操作へ到達・実行でき、focusを視認できるようにします。高精度なpointerを前提とする細かすぎる操作を必須にしません。

Screen SpecificationではCompact / Medium / Wideや各input modalityについて機械的に同じ記述を繰り返しません。表示領域や入力方式によってInformation、Action、Navigation等の表現・優先順位が変化する場合に、その差と維持すべきCapabilityをResponsive Behaviorとして記載します。

## Browser Support

Memoria Webは特殊な互換性要件を持たないため、modern evergreen browserをsupport対象とします。

対象はChrome、Edge、Firefox、Safariの現行安定版を基本とし、mobile環境ではiOS SafariとAndroid Chromeを対象とします。古いBrowser versionや特定versionの長期supportは原則として行いません。

support対象であることと、CIで常に全Browser・全viewportの組み合わせを検証することは分離して考えます。自動テストでは代表的なBrowserとviewportを選択し、cross-browser固有のriskや不具合が確認された場合に必要な検証を追加します。

製品上または利用者環境上の要件が生じた場合は、このsupport policyを見直します。

## Accessibility

Memoria Webは認証後に利用するApplication UIです。Accessibilityは後付け対応ではなく通常のUI品質として扱い、認証後の主要な操作を利用者が支障なく実行できることを重視します。

設計・実装上はWCAG 2.2 Level AAを基準とします。ただし、現時点では不特定多数へ公開する情報サイトとして網羅的な適合性を証明するための認証・監査運用までは要求しません。

keyboard操作、focus visibility、semantic HTML、accessible name、contrast、色だけに依存しない状態表現、画像の適切な代替情報、操作対象の大きさ、状態変化の伝達等、Applicationの操作可能性に直接関係する事項は通常の実装品質に含めます。

標準HTMLとMantine等が提供するaccessibleなprimitiveを優先し、独自Componentで既存のAccessibilityを損なわないようにします。自動検査で検出可能な問題はStorybook等で継続的に検出します。CIで強制する範囲はUI quality gateの方針として別途定めます。

## UI Quality Gate

UI品質の検証は、それぞれの検査手段が適した責務を担当します。通常の静的検査とUnit Testを基本とし、UIに影響する変更ではStorybook、Accessibility検査、Visual Regression Test、Interaction Testを利用します。Application E2Eは重要なUser Flowを対象とし、自動検査だけで判断できないVisualやUXはHuman Visual Reviewで確認します。

検査はすべての変更で一律に実行するのではなく、変更の影響範囲に応じて必要なものを選択します。共通Componentやtheme等の変更による間接的な影響も考慮します。対象外となった検査は、未実施との違いをCI上で確認できるようにします。

各検査を必須化する範囲は、test asset、実行時間、安定性を確認しながら段階的に拡大します。Visual Regression Testの基準画像は、意図した変更であることを人間が確認してから更新します。

具体的な変更検知方法、GitHub Actions構成、代表viewport、Browser matrixは `memoria-web` のtest infrastructure設計で決定します。
