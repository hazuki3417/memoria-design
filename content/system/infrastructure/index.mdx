# IaCアーキテクチャ

## 概要

> 実装状況: AWS CDKにはEC2、非公開S3、最小権限IAMなど初期基盤の定義があります。API・Media Worker・Outbox Publisherの実運用構成、PostgreSQL / Redis HA、監視、backup、復旧手順は未実装です。
> 実装の正本: `memoria-IaC`

IaCはAWS CDKでruntime、network、IAM、storage、監視を構築します。

- stackは変更・deploy・rollbackの責務境界で分割し、「一マイクロサービス一stack」を規約にしません。
- 最小権限を基本とし、stateful resourceはretention、backup、migrationを明示します。
- 環境差分はbranchではなくCDK設定、GitHub Environments、AWS側で表現します。
- secretをrepository、output、設計書へ保存しません。
- 初期の実行基盤にはEC2とDockerを使用し、Productionでは単一hostへの全service同居を可用性Baselineにしません。
- API、Media Worker、Outbox Publisherは独立したcontainer・processとして実行します。Productionでは責務とFailure Domainに応じて複数hostへ配置できる構成とします。
- PostgreSQLはPrimary / StandbyによるHAをProduction Baselineとし、automatic failoverを採用する場合はleader election、quorum、fencing、split brain prevention、endpoint switching、failback / rejoinを含めて設計します。具体的なHA softwareは詳細設計で確定します。
- RedisはRedis ClusterではなくSentinel-based HAをProduction Baselineとし、Redis Data 1 Primary + 2 Replica、Sentinel 3台、quorum 2を基本Topologyとします。
- Productionでは可能な範囲でstateful nodeを複数Failure Domain / AZへ分散します。低コスト検証環境や通常のlocal developmentではSingle node構成を許容します。
- DevelopmentはDocker Composeを使用します。通常開発はSingle PostgreSQL / Single Redisを許容し、HA profileではProduction相当のsoftware topologyを再現します。
- Development用ComposeをそのままProductionへ配置するのではなく、container image、version、HA software、health check、基本configurationを共通化し、volume、secret、resource limit、multi-host / multi-AZ、backup、monitoringなどInfrastructure固有設定を分離します。
- ECS/Fargateは運用負荷や個別scalingの必要性が高まった場合の移行先とし、初期導入を前提にしません。
- 常駐するWorkerとPublisherをLambdaへ置き換えることは前提にしません。短時間で独立した処理が生じた場合に限り、用途ごとに評価します。
- PostgreSQLとRedisはDocker containerで運用し、永続領域をEBSへ配置します。RDSとElastiCacheは初期構成に含めません。
- 非同期配送にはRedis Streams、状態とOutboxにはPostgreSQLを使用します。
- EC2管理とdeployにはSSM、GitHub ActionsからAWSへの認証にはOIDCを使用し、SSH公開と長期Access Keyを標準にしません。
- S3 bucketはprivateとし、CloudFront Origin Access Controlと期限付き署名でMediaを配信します。
- APIとWorkerは責務に応じて別container imageとし、PublisherはAPI imageを再利用できます。

[EC2・Docker運用基盤](./ec2-runtime-operations)を初期実行構成の正本とし、[初回Releaseの範囲と成功条件](/first-release)を運用判断の基準とします。container配置、PostgreSQL / Redis HA、Deploy、Backup、復旧手順の具体化はInfrastructure詳細設計で扱います。

## EC2運用と将来的な移行

EC2を採用する場合、OS更新、containerの再起動、logの保存、backup、障害復旧は運用責務として管理します。機密情報はimageやrepositoryへ含めず、AWS上の権限と設定から取得します。

API、Publisher、Worker、PostgreSQL、Redisは実行基盤に依存しないcontainerとして分離します。ECS/Fargateやmanaged databaseへ移行する場合も、domain処理、Redis Streams、Transactional Outbox、Mediaの権限設計を変更せず、配置と運用方法を移行します。

stack名はresourceの責務を表す名称にします。`MemoriaRecord`は採用しないマイクロサービス構成を連想させるため使用せず、変更時はresource置換とdeploy影響を確認します。

## 可用性とBackupの原則

ProductionではApplication、PostgreSQL、Redisを単一EC2へ同居させる構成を可用性Baselineにしません。PostgreSQL replicationとRedis SentinelはAvailabilityのための仕組みであり、Backupの代替ではありません。

PostgreSQLはBase / periodic backupにWAL archiveを組み合わせ、S3などのObject Storageへ退避し、restore testを行う方向をBaselineとします。必要なRPOに応じてPITRを利用します。具体的なbackup softwareは詳細設計で決定します。

Local Docker上のHA profileはsoftware-level failover、reconnect、electionの検証に使用します。同一Docker Host上の複数containerをInfrastructure-level HAとはみなしません。Host failure、network partition、AZ failure、disk failureなどはAWS上の検証環境で確認します。

RPO・RTO、backup retention、監視項目、運用費用、構成の見直し条件は[非機能要件](/system/cross-cutting/non-functional-requirements)を参照します。Multi-Regionやmanaged serviceは初期必須とせず、実測された要求と予算に基づいて判断します。
