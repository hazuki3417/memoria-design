# インフラストラクチャ設計

## 目的

Memoriaの初回Releaseは、単一EC2上のDocker containerでApplicationとself-hosted PostgreSQL / Redisを実行します。Dockerを利用する目的は実行環境とprocess責務の分離・再現性であり、同一Host内にreplicaやSentinelを増やしてもEC2障害への可用性は向上しないため、初回Releaseでそのような見かけ上の冗長化は採用しません。

設計優先順位はCorrectness、Simplicity、Explicitness、Observability、必要性が観測された後のOptimizationの順です。

## 初回ReleaseのProduction baseline

- 単一EC2でWeb、API、Media Worker、Outbox Publisher、PostgreSQL、Redisを独立したDocker container / processとして運用します。
- PostgreSQLとRedisはそれぞれ単一instanceとし、Primary / Standby replicationやRedis Sentinelによる同一Host内の擬似HAは導入しません。
- DB等の永続dataはcontainer filesystemと分離し、EBSとbackup・restore手順で保護します。
- EC2 Host障害ではサービス停止を許容し、検知・復旧・データ復元を重視します。
- RDS / ElastiCache / ECS / Fargateは初回Releaseの必須構成としません。

## 将来の可用性拡張

可用性要求・運用実績・予算から冗長化が必要になった場合のみ、複数Host / Failure Domainへの分散、PostgreSQL Primary / Standby、Redis Replica / Sentinel、DB接続先の切替、fencingとfailover手順を改めて設計します。同一EC2内のcontainer増設だけではHost障害を防げません。将来のHAを初回Releaseの未完了要件として扱いません。

## Availability / Recovery

ReplicationとBackupは別責務です。

```text
Replication = Availability
Backup      = Recovery
```

PostgreSQLはperiodic/base backup + WAL archive + Object Storage + restore testを基本方向とし、必要なRPOに応じてPITRを利用します。RedisはAOF / EBSを利用可能ですがApplication Truthではなく、Redis Streams loss時はPostgreSQL Outbox / ProcessingJob stateからreconciliationして再配送します。

## Development / Production parity

Developmentでは初回Releaseと同じ単一PostgreSQL / 単一Redisを基本とし、container image・version・health check・基本configuration templateを可能な範囲で揃えます。ただしDevelopment用ComposeをそのままProductionへ配備することはしません。

```text
Development
→ Docker Compose: Single PostgreSQL / Single Redis

Initial Production
→ Single EC2 + Docker + EBS + production secrets / monitoring / backup

Future HA evaluation (when separately approved)
→ Multiple Host / Failure Domain + PostgreSQL replication + Redis Sentinel
```

将来HA検証を行う場合でも、同一Docker Host内のreplicaはsoftware-levelの動作確認に限り、Host / AZ failureを防ぐ可用性構成とは区別します。

## Observability

初回ReleaseではEC2 / containerの稼働、PostgreSQLの接続・WAL・disk・connection・backup / restore、Redisの接続・Streams・AOF / disk等を監視対象とします。replication lag、Sentinel、failover stateは将来HAを導入する場合の監視対象です。具体的thresholdは運用要件と実測に基づいて決めます。
