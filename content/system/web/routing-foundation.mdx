# Webルーティング基盤設計（レビュー案）

> 状態: レビュー案。業務固有の画面URL・遷移・業務権限は本書の対象外です。共通画面は表示確認を必要としない仕様から先行して設計します。
> 実装の正本: `memoria-web`。本書は2026-09-30時点の`develop`を参照した設計案です。

## 目的と対象

画面詳細設計に先行して、Next.js App Routerの共通基盤を定義します。対象はRoute Group／Layoutの責務、認証境界、エラー・Loading・Rendering、共通ナビゲーション規約、基盤テストです。業務固有のURL・導線・検索パラメータのキー・業務認可・操作後の遷移先は業務画面の詳細設計で決めます。共通画面のURL・責務・状態遷移・コンポーネント契約は、表示確認を必要としない範囲で先行して設計します。見た目と操作感はコンポーネントを実装し、表示可能な環境でレビューして確定します。

## 現行実装の確認

- `src/app/layout.tsx`: locale、共通Provider、HTMLとテーマを構成。
- `src/app/(authenticated)/layout.tsx`: Server側でSessionを確認し、GraphQL `GetMe`を実行し、ユーザーProviderと共通AppShellを構成。Sessionがない場合は`null`を返す。
- `src/app/(authenticated)/(library)/layout.tsx`: Client ComponentとしてContainerを配置。
- `src/middleware.ts`: Sessionと保護対象パスを確認し、未認証時にログインへRedirect。
- `src/lib/middleware/route.ts`: 保護対象を列挙し、`startsWith`で判定。`returnTo`には元のpathnameを設定。
- `src/components/Auth/Csr/AuthGuard.tsx`: Client側でUser Contextを確認し、未認証時にログインへ遷移。

現行実装の観察と、以下の設計案は区別します。現時点で`error.tsx`、`not-found.tsx`、`loading.tsx`の代表的な配置は確認できていません。別の階層やブランチを含めた網羅的な不存在確認ではありません。

## 1. Route GroupとLayout

- Route GroupはURLを決めるためではなく、共通Layout、認証境界などの技術的責務を共有するために使用する。
- Root LayoutはHTML、locale、アプリ全体のProviderなど全ルート共通の責務を保持する。認証必須のデータ取得をRootへ移さない。
- 認証済みLayoutはセッション確認、認証済み領域に必要な共通ProviderとShellを担当する。個別画面の業務データ取得や業務権限判定を持たない。
- 子Layoutは共通表示領域など、複数画面で共有する構造が明確な場合に設ける。現行の`(library)`を将来のURL分類として固定しない。
- Server Componentを基本とし、ブラウザAPI、イベント、Client専用Contextなどが必要な境界だけClient Componentにする。既存LayoutのClient指定を機械的に増やさない。

## 2. 認証境界

### 合意済み: 二段階の認証確認

- Middlewareで未認証アクセスを早期Redirectし、認証済みServer LayoutでもSessionを確認する。これは利便性と表示制御のための二段階チェックであり、どちらも単独ではデータの保護境界とみなさない。
- App RouterではClient Navigation中にLayoutが再利用され得るため、保護されたServer側データ取得、Server Action、Route Handlerなど実際のデータアクセス地点で必要な認証確認を行う。APIが最終的な業務認可を保証する。
- Client側AuthGuardは補助的な表示・遷移制御に限定し、保護の唯一の根拠にしない。
- 現行の認証済みLayoutのSessionなしで`null`を返す挙動は解消対象とし、Server側での明示的なRedirectを基本案とする。Redirect先、`returnTo`検証、ループ防止は認証復帰仕様の検討後に確定する。
- GraphQLプロキシの主目的は、WebとAPIが異なるドメインでもブラウザからNext.jsの同一Originへアクセスさせ、ブラウザとAPI間のCORS設定への依存を減らすことである。認証をプロキシに集約すること自体は、この構成の目的ではない。
- `src/app/api/graphql/route.ts`は現状、リクエストHeaderを転送する。プロキシ経由でもAPIが最終的な認証・認可を行う。認証方式と転送Headerの許可範囲、Cookieの扱いは実装時に確認する。LayoutのSession確認だけでAPIへのアクセスが保護されたと扱わない。
- 既存のAuth0／Next.js BFF構成とHttpOnly Session Cookieを前提とし、TokenをURL・公開Client State・Logへ露出しない。
- 認証済みでも個別リソースの利用権限は保証されず、APIが最終的な業務認可を行う。

### 合意済み: 保護対象は原則保護・公開URLを例外登録

- Middlewareが扱う画面Routeは原則認証必須とし、認証不要な画面Routeだけを明示的なAllowlistで管理する。将来追加する画面が未登録のまま公開されない構成とする。
- Auth0のLogin／Callback／Logout等の認証用Endpointは、Auth0 SDKが要求するMiddleware処理を妨げないよう別区分で扱う。実際のPathとMatcherは現行SDK設定・Route構成を確認して確定する。
- GraphQLプロキシ等のAPI Route、Next.js内部Asset、静的ファイルは画面RouteのAllowlistとは別に分類する。API Routeを画面用のログインRedirectに巻き込まず、各Endpointの認証・認可とエラー応答を独立して定義する。
- Path判定はSegment境界を考慮した厳密な一致または明示的な子Path一致とし、単純な`startsWith`による意図しない一致を避ける。Route Group名はURLに現れないため、Middlewareの分類条件に使わない。
- 未知の画面Pathに対しても認証確認を行うが、存在しないRouteの最終的な404処理はNext.jsに委ねる。認証不要な404表示の要否は公開ページ設計時に再検討する。
- 具体的な公開Path一覧、Auth0 Endpoint、Matcherの除外条件、Locale付きPathの扱いは実装前の調査事項とし、現時点で未確認のPathを決め打ちしない。

### 合意済み: 認証復帰（returnTo）の基本仕様

- 未認証で保護画面へアクセスした場合、元のPathとQueryを相対URLとして保持する。Fragment（#以降）はHTTPリクエストに送信されないため、Server側の復帰保証対象にしない。
- 認証復帰先はアプリ内の安全なPathのみ許可する。外部Origin、プロトコル相対URL（`//example.com`）、Backslash等を使った迂回、制御文字、不正なEncoding、認証用Endpointへの循環Redirectを拒否する。
- 認証に関わる一時Code、Token、State等を復帰先のQueryへ持ち込まない。既存の共有可能な画面状態（例: `?q=...`）を保持する。Query全体を保存する場合はサイズ上限と機密値の扱いを実装時に確認する。
- `returnTo`の検証は生成時だけでなく、認証Callback後に実際にRedirectする直前にも行う。Auth0 SDKのCallback／Login処理と衝突しない受け渡し方法を現行SDKの実装・仕様に照らして確定する。
- `returnTo`がない、不正、または復帰先が認証用Endpointである場合は安全な認証済み初期画面へ戻す。具体的なURLは画面詳細設計で確定する。
- Session期限切れで保護画面を再要求した場合も同じ規則で復帰先を保持する。ただし、未保存Form入力などURLに存在しないClient Stateの復元は保証しない。
- Open Redirect防止、二重Encoding、Query保持、期限切れSession、Callbackのループ防止を自動テストする。

## 3. エラーとLoading

### 合意済み: 共通Error／Loadingの配置方針

- Root LayoutはHTML、Locale、Mantine等の共通Providerを構築している。Rootの`global-error.tsx`はこのLayout自体が失敗した場合の最終Fallbackとして配置し、必要な`html`／`body`を自前で描画する。通常のProviderが使えることを前提にしない。
- Rootの`not-found.tsx`はURL不一致時の共通404を担当する。認証済み領域で共通Shellを維持する必要が明確になった場合は、その領域にも局所的な404境界を追加する。
- 認証済み領域の`error.tsx`は当該Layoutの**子Segment**の描画失敗を扱う。認証済みLayout自身のSession取得や`GetMe`失敗は同階層の`error.tsx`では捕捉できないため、親階層の境界と認証エラーの明示的な処理を分けて設計する。
- `loading.tsx`は実際に待機が必要なSegment単位で設け、全画面一律には配置しない。認証済みLayoutのSession取得／`GetMe`待機を子階層の`loading.tsx`だけで解決できる前提にしない。必要に応じて親側のSuspense境界とProvider依存を検証する。
- `notFound()`／`redirect()`は通常の例外表示と区別し、意図した404・認証遷移として扱う。`error.tsx`では機密情報を表示せず、再試行可能なケースに限り`reset()`を提供する。


- `error.tsx`は対象Segment配下の回復可能なRender Errorを扱い、再試行と利用可能な共通UIを提供する。
- `global-error.tsx`はRoot Layout自体の失敗に備える最終的な境界とする。
- `not-found.tsx`は存在しないRoute／リソースに対する404表示を扱う。認証・認可失敗を無条件に404へ置換しない。
- `loading.tsx`とSuspenseは、実際に非同期処理があり待機表示が必要なSegmentで使用する。すべてのRouteへの一律配置はしない。
- エラー表示にToken、内部Stack Trace、機密情報を露出しない。画面固有の文言やリトライ導線は各画面の詳細設計で決める。

## 4. URL設計規約

### 合意済み: Path命名

- URLのSegmentは英語・小文字・kebab-caseとする。リソース名は原則複数形とする。
- URLはリソース・機能を表し、見た目や内部Component名に依存させない。動的SegmentはNext.js App Routerの`[id]`形式で定義する。
- この合意だけを理由に既存URLを一括変更しない。変更時の互換性・Redirectは個別に検討する。

### 合意済み: リソース中心のURL階層

- リソースを中心に一覧（`/resources`）、新規作成（`/resources/new`）、詳細（`/resources/[id]`）、編集（`/resources/[id]/edit`）を基本形とする。これらは構造の例であり、業務画面の具体的なURL割当ではない。
- 明確なリソースの親子関係がある場合のみ階層を深くし、画面のメニューやComponentの構造をURL階層に転写しない。
- 既存URLの変更は互換性とRedirectを確認した上で個別に判断する。

### 合意済み: URL定義の責務と整合性

- Next.js App Routerの`src/app`ファイル構成を実際にアクセス可能なURLの正本とする。
- 既存の`src/constants/routes`と型定義・`resolveUri`は型安全なURL生成に活用する。タイトル・パンくず・ナビゲーション等の表示用メタデータはURL定義と責務を分け、管理方法の詳細は実装時に検討する。
- `src/app`とルート定義の不一致、動的パラメータの対応とエンコードを自動テストで検出する。Route GroupはURLの一部として扱わない。
- 既存の仕組みを即時廃止・一括変更せず、検証可能な範囲から段階的に整備する。

### 合意済み: Search Paramsと`q`の使い分け

- 一般的な検索・並び替え・ページングなど、意味が明確で個別に操作・共有する状態は、原則として個別のSearch Paramsを使用する。
- 複雑な構造化状態を一括保存・復元する必要がある場合は、既存の`?q=...`方式を選択できる。項目数やネストの深さによる機械的な閾値は設けず、画面の利用目的に照らして判断する。
- **個別のSearch Paramsを優先する目安**: URLの可読性・直接編集、外部連携、一部条件だけの更新、個別パラメータの共有が重要な場合。
- **`q`を検討する目安**: 条件間の関連が強く、状態全体を一括更新・復元したい場合、構造化された条件のスキーマ・バージョンを一体として管理したい場合。
- 複数の検索条件があるという理由だけでは`q`を採用しない。個別のSearch Paramsと`q`を併用する場合は責務を分け、同じ状態を重複保持しない。
- `q`は暗号化ではない。Token、認証Code、個人情報などの機密値を含めない。URL長、入力検証、不正値・未知バージョンの扱いは実装前に検討する。
- 画面固有のQuery Keyと既定値は、共通画面ならその詳細設計、業務画面なら業務画面詳細設計で定める。

### 合意済み: URL正規化・互換性

- 末尾SlashのないURLを正規形とし、Next.js標準の`trailingSlash: false`相当の挙動を利用する。独自Middlewareに同じ正規化を重複実装しない。現行`next.config.mjs`に明示設定はないため、実装時に設定要否を確認する。
- 静的Pathは小文字で定義する。リクエストURL全体を一律小文字変換せず、動的SegmentのID等の大文字小文字を保持する。
- URL変更時は旧URLから新URLへの明示的なRedirectを個別に検討し、恒久的な移行が確定している場合に恒久Redirectを使う。互換性のあるQueryは保持し、旧ブックマークや共有リンクへの影響を確認する。
- 未知のPathは類似Pathへ推測Redirectせず404とする。認証用EndpointとAPI Routeには画面URLの規約を機械的に適用せず、それぞれの契約を優先する。
- 既存URLの一括変更は本設計の合意だけでは実施しない。変更対象・移行方法・Redirectの終了条件は個別に決定する。

### 合意済み: 動的Segment・識別子

- Next.jsの動的Segmentは単一のIDなら`[id]`を基本形とする。同じURLに異なるリソースのIDが複数登場する場合は`[groupId]`／`[memberId]`など区別できる名前を用いる。
- URLには原則としてAPI契約で公開可能かつ安定した識別子を使い、変更され得る表示名よりIDを優先する。UUID／ULID等の具体的な形式はAPI契約に従い、Web側で先行決定しない。
- 動的パラメータのURL生成は共通関数でSegment単位の適切なエンコードを行い、呼び出し元での文字列連結を標準としない。現行`resolveUriPath()`は値をそのまま置換するため改善対象とする。
- 受信時は必須値・形式を検証する。不正な識別子や存在しないリソースは原則404とし、正しい形式でもリソースへのアクセス権限はAPIで別途確認する。認証・認可エラーを一律404に置換しない。
- 識別子の大文字小文字や形式をURL受信時に勝手に変換しない。Next.jsの`[id]`と既存URL定義の`:id`の表現差は、ルート整合性テストとURL生成関数で扱う。

### 合意済み: 操作URL

- 一覧は`/resources`、新規作成は`/resources/new`、詳細は`/resources/[id]`、編集は`/resources/[id]/edit`を基本形とする。これらは構造例であり、業務固有のURLを確定するものではない。
- 新規作成・編集は直接アクセスとブラウザ履歴への対応を考慮し、独立したURLを基本とする。
- 検索・絞り込みは一覧URLにSearch Paramsを付与し、個別Paramsと`q`の使い分け規約に従う。
- 削除は原則として専用の画面URLを設けず、画面内操作と確認UIから実行する。削除確認を独立した画面にする必要がある場合は画面詳細設計で例外を検討する。
- 削除その他の副作用を伴う処理をGETによる画面アクセスだけで実行しない。Server ActionやAPI等の変更用インターフェースで実施し、認証・認可と必要な入力検証を行う。
- 具体的な業務操作のURL・操作後の遷移・確認UIの見た目は各画面の詳細設計で確定する。

## 5. 遷移と状態の共通規約

### 合意済み: 公開トップページとログアウト後の遷移

- 認証不要のトップページを`/`に設ける。現段階ではサービス名・簡単な紹介・ログイン導線を中心としたシンプルな構成とし、製品紹介や有料プラン等は将来必要になった時点で拡張する。
- ログアウト時はAuth0 SDKのログアウト処理でセッションを終了し、完了後に公開トップページ`/`へ遷移する。具体的なSDKのLogout URLとReturn URLの設定は実装前に確認する。
- 認証済みユーザーが`/`にアクセスした場合は公開トップページを表示せず、認証済み初期画面へRedirectする。現行の`/dashboard`を暫定候補とし、正式な初期画面（メディア一覧等を含む）は画面詳細設計で決める。
- トップページの詳細な見た目は表示可能な環境でレビューして確定する。

### 合意済み: ログイン画面の基本構成

- Memoriaのブランドを適用したAuth0 Universal Loginを使用し、ログインフォーム・認証処理・パスワード再設定・MFA等はAuth0が提供する機能を基本とする。
- 現時点ではNext.jsアプリ内に独自のログインフォームやログイン案内ページを設けない。既存のAuth0標準画面はプロトタイプ上の選択であり、最終的なブランド表現ではない。
- Memoria側のログイン導線からAuth0 SDKのログイン処理へ遷移し、認証完了後は検証済みの`returnTo`、無効または未指定の場合は安全な認証済み初期画面へ復帰する。
- Auth0 Universal Loginの具体的なカスタマイズ可能範囲・デザイン・運用上の制約は画面設計時に確認する。Next.js内の独自フォームは将来の選択肢として残すが、今回の実装対象には含めない。
- Auth0 SDKの実際のLogin／Callback／LogoutのPathと、既存`/auth/login`・`/auth/logout`のルート定義との対応は実装前に確認する。

- Server側の認証RedirectはServer側のNavigation APIを基本とし、Client側の利用者操作による遷移はNext.js Router／Linkを使用する。ブラウザHistoryの直接操作を標準手段にしない。
- 共有可能な状態はURLで扱う既存方針を維持する。ただし具体的なKey、Default値、戻る操作の仕様は画面詳細設計に委ねる。
- Redirect先の検証やURL生成を共通化する際は、画面固有のRoute一覧をこの基盤設計に固定しない。

## 6. 基盤テスト方針

- 未認証での保護対象アクセス、認証済みでの通過、期限切れSession、認証Callback後の安全な復帰先を検証する。
- 保護対象パスの境界条件、URL Encoding、不正な`returnTo`、外部URL指定をテストする。
- Layoutの共通ProviderとServer／Client境界、SegmentのLoading・Error・Not Foundを対象にする。
- MiddlewareとServer Layoutで認証判定が不整合にならないことをIntegration Testで確認する。
- 実装時は`memoria-web`の既存Vitest・CI規約に従い、E2Eの範囲は既存テスト構成を確認して決める。

## 合意済みの基本方針と残る論点

1. **認証の二段階チェック（合意済み）**: Middlewareによる早期RedirectとServer LayoutのSession確認を併用する。データアクセス地点でも認証を確認する。現行の`null`応答は解消対象とし、具体的なRedirect先と復帰処理は論点3で決める。
2. **保護対象の管理方法（基本方針は合意済み）**: 画面Routeは原則保護し、認証不要の公開URLをAllowlistで管理する。Auth0 Endpoint・API Route・静的Assetは別区分とする。具体的なPath、Matcher、Locale処理は実装前に現行コードとSDK仕様を確認して確定する。
3. **認証復帰の仕様（基本方針は合意済み）**: 元のPathとQueryを保持し、生成時とCallback後のRedirect直前に安全なアプリ内Pathとして検証する。SDKとの接続方式、サイズ制限、安全なFallback先は実装前に確定する。
4. **共通Error／Loadingの配置（基本方針は合意済み）**: Rootの`global-error.tsx`／`not-found.tsx`、認証済み領域の子Segment用`error.tsx`、必要なSegment単位の`loading.tsx`を基本とする。認証済みLayout自身の失敗は親境界・認証エラー処理で扱う。

認証・保護対象・認証復帰・Error／Loadingの4項目の基本方針は合意済みです。URL命名は合意済みです。URL階層も合意済みです。定義管理とSearch Params／`q`の使い分けも合意済みです。URL正規化・互換性も合意済みです。動的Segment・識別子・操作URLも合意済みです。具体的な共通画面URLと遷移、実装詳細は引き続きレビューします。Auth0 SDKの具体的な接続、公開Path／Matcher、`returnTo`のサイズ制限・Fallback先、各画面の表示仕様は実装前または画面詳細設計で確定します。実装作業は別Issueで管理します。
