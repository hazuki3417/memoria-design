# Frontendテスト戦略

## 目的と適用範囲

本書はMemoria Webのテスト対象・階層・責務の選択基準を定める。テストコードの既存配置や既存の書き方を規範の根拠とはしない。既存テストを削除・移行する際は、従来検証していた有効な振る舞いを失わないようにする。

テストは実装詳細や単なるCoverage数値でなく、ユーザーから観測可能な振る舞い、外部との契約、不変条件、状態遷移、失敗時の回復を保証する。仕様が未定義のとき、テスト実装から推測して製品仕様を確定しない。画面の仕様はScreen Specificationと関連する製品設計を正本とする。

本書はFrontendのテスト戦略を所有する。全Repository共通のQuality GateとE2E環境原則は[テスト設計](/test-design)、Reactの責務分離は[Frontend実装規約](/system/web/implementation-conventions)、実装コマンドと設定は`memoria-web`を参照する。

## テストの分類

Unit / Component / Integration / E2Eは検証範囲の分類であり、Interaction / Accessibility / Visual Regressionは検証観点である。Storybook、Vitest、Playwrightはツールであって、階層と1対1には対応しない。

| 分類 | 主な保証対象 | 主な範囲・依存境界 | 保証しないもの |
| --- | --- | --- | --- |
| Unit | 判定、変換、Validation、純粋な状態遷移 | ReactやDOMを必要としない関数・モジュール中心 | 画面に正しく接続されること |
| Component | 単独のUI責務の表示、操作、イベント通知、局所的状態遷移、Focus | 対象Componentと必要最低限のProvider / 外部Callback | Backendや画面全体との接続 |
| Integration | 複数のUI・状態管理・Adapter・API Client等の責務間の接続、非同期結果のUIへの反映 | 実際のアプリケーション内部経路を可能な範囲で通し、外部境界を制御する | 実Backend・DBの整合性そのもの |
| Application E2E | 認証・画面遷移・API・永続化をまたぐ主要ユーザーフロー | 隔離された実Frontend・API・テスト用DBを使用 | すべての境界値や異常系の網羅 |
| Visual Regression | 意図しない表示・レイアウト・Responsive差分 | 安定したStoryとViewportの画像比較 | 操作の意味的な正しさ |

ComponentとIntegrationの境界はComponent数で決めない。単独Componentの責務を示す振る舞いを検証するならComponent、複数の独立責務が正しく接続されることを検証するならIntegrationとする。複雑なFeature Componentも、検証内容に応じてどちらにもなり得る。

## テスト階層の選択

1. 最初に検証したい仕様をGiven（条件）/ When（操作・イベント）/ Then（観測可能な結果）で表現する。内部State名や関数呼び出しに合わせて仕様を作らない。
2. その仕様を保証できる最小の適切な範囲を選ぶ。ただし実接続そのものがリスクなら上位階層でも検証する。
3. 正常系だけでなく、境界値、禁止操作、Loading、Error、Cancel、Retry、重複送信、権限、Keyboard / Focus等から、機能リスクに応じて選ぶ。全組み合わせを機械的には要求しない。
4. 重要度は不具合時の影響、発生可能性、状態・分岐の複雑さ、既存の保証で判断する。固定テスト数・固定ピラミッド比率・Coverage閾値を目的としない。
5. 同じユーザー向け結果を複数階層で確認する場合は、どの接続境界・欠陥を追加で検出するのか説明できるようにする。合理的な重複は許すが重複自体を目的としない。

例（実際のGroup画面の仕様ではない）：

| 保証したいこと | 基本的な検証階層 |
| --- | --- |
| 名前の空白判定が正しい | Unit |
| 入力すると送信ボタンが有効になる | Component Interaction |
| 送信結果のエラーがUIに表示され再試行できる | Integration（通信境界はMock） |
| 作成されたGroupがページ再読み込み後も存在する | Application E2E |
| DialogのDesktop / Mobile表示が変わらない | Visual Regression |

## Interaction Testの設計

- クリックの成立だけでなく、操作前後の状態とユーザーが観測できる結果を検証する。
- 代表的な状態と有効な遷移、禁止すべき遷移、失敗からの回復を優先する。静的な状態一覧と操作の自動検証を混同しない。
- 要素の特定はRoleとAccessible Name等の利用者に意味がある識別を優先する。DOM階層、CSS Class、内部State等を過度に固定しない。
- 非同期テストは結果条件を待機し、固定Sleepに依存しない。Loading検証では遅延を偶然に任せず、応答を制御する。
- 二重送信や「キャンセルでは削除しない」等の禁止事項では、外部境界の呼び出し有無・回数の確認も適切とする。無意味な内部関数Mockの呼び出し検証とは区別する。
- テストの独立性を保ち、順序依存・時刻・乱数・ネットワークの不安定要素を制御する。

## GraphQL境界のMock・Storybook Integration / VRT（2026-10-22合意）

- Component固有の表示・InteractionはProps / Callbackを使い、Apolloを不要にする。GraphQLとの接続を保証するFrontend Integrationでは本物のFeature Container、生成済みApollo Hook、Apollo Clientを通し、外部GraphQL応答をMockする。生成HookそのもののMockで接続検証を代替しない。
- 最初の標準方式はApollo Client 3の `MockedProvider`。Operation、Variables、応答Data / Errorの対応を明示し、一覧の成功・空・失敗・Retry・Mutation・Paginationを決定的に再現する。実Backend / Production APIへ接続しない。
- GraphQL Code Generatorの生成型・DocumentをFixtureの型とOperationの基準とする。固定Scenarioは仕様に意味のある値を明示し、Response shapeの変更を型チェックで検出する。
- `@graphql-tools/mock` は大量のFixtureやSchema整合性確認を補助する候補。Schemaからの自動生成だけでGroup Relation等の製品制約・境界ケースを保証した扱いにしない。
- Mock数やVariables照合、非同期応答の順序が複雑になり `MockedProvider` では可読性・保守性が低下する場合、MSWでGraphQL HTTP境界を制御する方式を別途判断する。最初から一律採用しない。
- VRTはStory内の同じScenarioを使用できるが、撮影はデータとUIの安定した状態を待ってから実行する。Interactionは操作後の意味的な結果、VRTは視覚的差分をそれぞれ保証する。無制御な通信遅延・固定Sleep・Production接続に依存しない。
- MockやFixtureはテスト用モジュールに隔離し、ProductionコードのGraphQL処理へ混在させない。正本の仕様・未確定事項をFixtureによって勝手に確定しない。

## Storybookの位置づけ
### Interaction Testでの要素特定とAssertion（2026-10-21合意）

テストのLocatorは、Component内部のDOM実装ではなく、利用者に提供される意味・操作を基準とする。実装側のSemantic HTMLとAccessible Nameの原則は[Frontend実装規約](/system/web/implementation-conventions)を正本とする。

- 原則として `getByRole` とAccessible Nameで操作対象を識別する。Formは関連付けられたLabelからの検索も適切とする。可視TextやPlaceholderは対象に応じて使用するが、Placeholderを恒久的なLabelの代替にはしない。
- Portal等で描画場所が異なる場合は、実際のUI Libraryの契約に沿った適切な検索Scopeを選ぶ。実装内部のDOM階層・CSS Class・`nth-child`に依存したSelectorは原則避ける。
- Role・Name・Labelによる特定が曖昧な場合に限り、`data-testid`を補助的な安定識別子として採用できる。全要素への機械的付与や、本来必要なAccessible Nameの欠落をテストIDで覆うことはしない。
- Assertionでは、実際の選択・非選択、Controlの利用可否、通知、Focus、操作結果などの観測可能な振る舞いを主対象とする。ARIA属性の確認はAccessibility上その属性自体が契約となる場合に用い、特定属性だけで操作結果の保証を代替しない。
- 非同期UIでは意味的な結果の出現を待ち、固定時間Sleep・任意の内部State参照を避ける。失敗時には保証すべき利用者の結果と実装詳細による偶発的な差を切り分ける。
- Component抽出後も既存の有効なCapability・Interaction・Responsive・Focusを維持する。抽出による機械的なStory / Testの1対1追加は要求せず、テストで保証する外部契約に合わせて選ぶ。


Storyは独立して再現可能なComponent状態と振る舞いの実行可能な例であり、製品仕様そのものの正本ではない。Storyの種類や個数を一律に義務化しない。単独Componentの操作はStoryのplay等を用いたInteraction Testを基本候補とする。複数責務の結合をStorybook上で実行する場合も検証対象によってIntegrationに分類する。

採用済みの画面UI/UX仕様は `memoria-design` の画面設計を正本とし、Storybookの画面・Component設計MDXは作成しない。Prototype前には必要な検証観点を整理し、Prototype・Visual Reviewで具体化した仕様からGiven / When / Then、Fixture、Mock境界、適切なテスト階層を選ぶ。**React Componentを作成・分割したことだけを理由に、同名Story・Unit Test・Component Testを一式必須とはしない。** 保証したい振る舞いと独立した検証価値に応じて、Componentをまとめて検証してもよい。

ProductionとStorybookで同じUI実装と意味的な振る舞いを共有する。Storybookのために同等の別UIを作らない。表示状態のFixture、外部Callback、Providerは適切に差し替え、テスト専用PropsをProduction APIへ無理に導入しない。

VRTは視覚的回帰、Interaction Testは振る舞い、Accessibility検査は自動で検出できるアクセシビリティ問題をそれぞれ担当する。いずれか一つで他の保証を代替しない。Visual Prototypeを使う場合も、既存のVisual / Behavioral / Responsive仕様を守る。

## Storybookカタログの分類・表示ルール（2026-10-22合意）

Storybookはテスト実行環境であると同時に、人が画面・部品を探して目視確認するカタログとする。Storyの主目的をUIから識別できるようにしつつ、分類変更によって既存のUI・操作・Fixture・Responsive Behaviorを変更しない。

- **既存Storyファイルを分類のために分割しない。** 1つのStoryファイルに目視確認向けと操作検証向けが同居してよい。
- **対象の種類の分類**は既存のMeta `title`階層で行い、`Design Prototypes`（画面Prototype）、`Components`（共通UI部品）、`Features`（機能固有の部品）の区別を維持する。階層を増やすこと自体を目的にしない。
- **Storyの主目的**は `visual`（人間が表示・状態を目視確認）または `interaction`（操作・振る舞いを検証）の用途タグで識別する。各Storyの主目的を判断し、原則いずれかを選ぶ。`play`の存在だけで機械的に `interaction` と判定しない。表示状態を再現するために `play` を利用するVisual Storyもあり得る。
- **ブラウザ上の視認性**のため、継続的な検証を所有するFeature / ComponentのStoryでは、Storyごとの `name` に `Visual · …` / `Interaction · …` の接頭辞を使用する。原則として既存の意味のあるStory名を残す。用途タグだけにサイドバー上の表示・グルーピング機能を期待しない。
- **Storyの表示名にテストマトリクスのケースID（例: `UI-06`、`SS-02`）を含めない。** `name` は人が理解できる状態・操作・期待する振る舞いを簡潔に表す。仕様とのTraceabilityはStory定義付近のコメント、テスト設計・Coverage対応表などCanvas外の情報で保持し、表示名をケースID一覧の代わりにしない。
- **Design Prototypesは例外**とし、Story名に `Visual` / `Interaction` の用途接頭辞を付けない。Prototypeは開発途中の中間成果物であり、継続テスト資産のownerではない。探索中の表示・操作確認は可能だが、継続的なInteraction / Integration / VRTの保証はFeature / Componentへ移行する。Prototypeからの移行時は既存の状態・操作・Responsive Contractを継承し、不要なPrototype Storyを整理する。
- **VRT撮影対象**は主目的と独立した `vrt` タグで選択する。Visual Storyのすべてを自動撮影しない。Interaction Storyでも撮影価値と安定化条件を満たせば対象にできる。
- 同一ファイル内のStory間で用途が混在する場合、用途タグはStory単位で指定する。Meta共通タグは対象Storyが同じ用途であることを確認できるときだけ使用し、誤継承を避ける。
- Story IDや従来のリンクを将来も必ず不変に保つことは今回の要件としない。ただし `name` の変更によりStory ID、テスト参照、VRT Baselineに影響し得るため、実装時に参照先の更新・テスト影響を確認する。

**Story実装・変更時の必須確認手順**: Storyの追加・変更に着手する前に、本節「Storybookカタログの分類・表示ルール」を参照する。対象がPrototypeかFeature / Componentかを確認し、`title`、表示名（用途接頭辞・ケースIDを含まない意味のある名前）、`visual` / `interaction` タグ、独立した`vrt`タグ、既存Storyとの整合を確認してから実装する。Review時にも同じ項目を照合し、表示名の変更によるStory ID・外部参照・VRT Baseline依頼中のCommit整合への影響を確認する。Baseline生成が進行中の対象ブランチでは、変更のタイミングと再生成の必要性を確認する。

この節は合意済みの**将来の実装方針**を定めるものであり、現行のStory一覧の分類更新が完了したことを意味しない。既存Storyを個別に棚卸ししてから、ファイル分割なしで表示名・用途タグを適用する。変更前後のStoryのrender・`play`・操作・Fixture・Viewportを比較し、回帰がないことを確認する。実装RepositoryのStory定義・設定・テストが実際の動作の正本となる。

## Mock・Fixture・実接続

- Mockは検証対象の外側の制御可能な境界へ置く。内部モジュールを過剰にMockして実際の接続欠陥を隠さない。
- Component TestではProps / Callback等から入力・イベントを制御する。IntegrationではHTTP / GraphQL境界等を制御し、対象に含めるClient・状態管理・表示の接続を通す。
- APIレスポンスの成功・失敗をMockしても、実Backendとの契約は保証されない。schema / operation整合性検証やApplication E2E等と役割を分ける。
- Application E2Eのデータ準備・外部サービス差し替え・実DBの利用は[テスト設計](/test-design)の共通原則に従う。
- Fixtureはテスト間で独立・決定的とし、エラー、空状態、遅延などを再現可能にする。

## 既存テストの移行と方針改善

既存テストコードは新規方針を正当化する根拠にせず、現行の保証対象を把握するために棚卸しする。適合するテストは維持し、階層の誤りや実装詳細への過度な依存は修正する。重複を整理する場合も有効な保証の消失がないことを確認する。欠けている重要なテストは追加する。変更前後の表示・動作・Keyboard・Responsiveへの意図しない回帰を許容しない。

個別テストの不備と横断方針の問題を区別する。複数事例で境界の曖昧さ、過剰な重複、実行の不安定さ、保守コスト、検出漏れ等が確認されたら、実例と代替案・Trade-offを示して方針を見直す。重要な方針変更は人間との合意後に本書へ反映し、未解決事項と移行作業はIssueで追跡する。

## 実装規約と導入範囲

本書はテスト階層と選択判断を定める。具体的なVitest / Storybook / Playwrightの構成、Mock実装、配置規則、コマンド、CIトリガーは既存環境を調査し、実装を通じて段階的に決定する。未検証の構成を導入済みとみなさない。CIの自動再開や既存テストの一括置換は本書の承認だけでは実施しない。
