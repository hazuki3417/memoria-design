# Group Browser：Frontendテストマトリクス

## 目的・適用範囲

[テストマトリクステンプレート](/design-document-templates#テストマトリクス仕様から導く検証条件)に沿って、Group Browserの確定済み仕様を実行可能な検証条件へ分解し、後続の実装・責務分離・テスト実装の目標を定義します。**現行Web実装に合わせて期待結果を弱めず、実装済み・テスト可能・テスト成功を意味しません。** Groupでは先にScreen SpecificationとUI Designを整理したため、今回は設計を先行してマトリクスを作り、以後のテスト実装と必要なリファクタリングに接続します。この工程順は全機能へ一律適用しません。他の機能では設計・実装・マトリクスが同時進行して構いません。

対象はGroup discovery、選択中Group、CRUD・relation操作、権限・失効、取得状態、表示・Responsive・Focusおよびこれらを成立させるGroupドメイン制約です。Media Detail自体の全Capability、Media Browserのbulk操作、API性能・DB運用の網羅は各所有先の検証へ委ね、Groupからの接続を本書で確認します。

## マトリクスの記述規則

| 項目 | 運用上の意味 |
| --- | --- |
| ID | Group Browserのテスト条件を追跡する安定ID。Component・Story名から生成しない |
| 仕様参照 | `S` / `U` / `D` と該当する節・G番号。正確な期待結果の正本はリンク先 |
| Given / When / Then | 前提／操作・イベント／利用者または外部境界から観測できる結果。内部関数名に依存しない |
| 推奨階層 | `Unit`=Pure Function、`C`=Component、`I`=Frontend Integration（必要なGraphQL境界をMock）、`E2E`=実際の利用者フロー、`BE`=Backend/DB Integration。候補であり同一条件を全階層で重複実装する指示ではない |
| 観点 | Interaction、VRT、Accessibility、Validation、Contract、Concurrency等。ツール名と検証階層を混同しない |
| Fixture・外部境界 | 独立して再現するデータ・状態と差し替え対象の例。具体的なStory名・実装ファイル名は後続で決定 |
| 設計状態 | 原則「定義済み」。外部API方式や図像など未決部分を含む場合は注記し、未決の詳細を仮定しない |
| 実装・実行状態 | **全件未照合**。既存テストの有無・実行可否・成功を意味しない。後続のGitHub最新実装調査・CI結果で更新する |

**検証単位と実装ファイルは1対1にしません。** 複数条件を一つのIntegration Testで確認することも、視覚状態をStoryとVRTで観測することもできます。純粋な計算・変換のみにReactを持ち込まず、GraphQL接続や処理結果とUI状態の連動には接続を通すテストを用います。

## Fixture・依存境界

- 各テストのUser / Community / Group / Media IDは決定的で独立させます。Personal、Community Administrator、Community Member、権限未取得・失効を区別します。
- GroupのDAGではdirect parent / child、複数parents、diamond型に同一descendantへ複数経路で到達する例、深度・上限境界を準備します。direct Mediaとdescendant由来のaggregate Mediaを別の集合として用意します。
- 一覧・候補・MediaのConnectionは初回／続き／終端・Loading／失敗／再試行をそれぞれ制御します。失敗した領域以外の取得済み情報とUI状態は残します。
- Operationの確定成功・確定失敗・結果不明を区別します。GraphQL Responseの具体的Error型・結果照会方式は未決定ならFixtureの概念条件として留め、実装詳細を発明しません。
- 画面幅はWide / Medium / Compactを対象とし、合意前の具体Breakpointを固定しません。VRTでは同じFont、時間、画像、Animationなどを安定化させます。
- Serverを保証すべきDAG制約・Atomic性・認可は、Frontend Mockだけで検証完了としません。Backendの実契約・DBを通る適切なレベルを確保します。

## 実装との対応・課題

このマトリクスはテストを先に定義する成果物です。**現行実装への適合判定とテスト実装・実行は別工程**として、各IDに対して次を後続調査で記録します。

1. 設計との適合状態：適合／仕様不一致／未実装／調査未了。既存動作を仕様に読み替えない。
2. テスト実装状態：既存テストで検証済み／一部のみ／未実装／実行不能／調査未了。テストコードの存在と成功実行を区別する。
3. 必要な変更：責務・状態・外部境界・Fixtureの問題と、UI仕様への適合修正を分けて特定する。Component境界をStoryやTestのIDへ機械的に合わせない。
4. 回帰防止：既存の画面・PrototypeのVisual / Behavioral / Responsive Contractと比較し、仕様変更が合意されていない既存Capabilityを失わせない。
5. 実行結果：Unit / Component / Integration / E2E / VRT / Accessibilityの実際の結果と未実施を区別して記録する。CIで確認できていないものを成功とは扱わない。

既存の `memoria-web` のGroup Browser実装、Group名・Relation変更のUnit Test、Wide / CompactのStoryは照合対象ですが、その存在だけでマトリクス各行を「検証済み」とはしません。必要な改修と追加テストは後続のIssue / PRで追跡します。
