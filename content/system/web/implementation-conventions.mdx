# Frontend実装規約

## 概要

Memoria WebのApplication Architecture、状態管理、Component、GraphQL、Form、Interaction、生成Code、Testの共通判断を定義します。具体的なroute、GraphQL Operation、script、設定は `memoria-web` を正本とします。UIの意味、要求、状態、操作、Navigation、Design Systemは[Frontend UI設計・開発方針](/system/frontend-ui-development)と各Screen Specificationを正本とします。

既存の `memoria-web` 実装は再利用候補・参考情報であり、それ自体を要求やArchitectureの正本とはみなしません。新しい設計に適合する実装は再利用し、適合しない実装は変更または廃止できます。既存実装を一括移行するための大規模Refactorは前提にせず、変更対象ごとに判断します。

## GraphQL / Apollo ClientとState Ownership（2026-10-17合意）

- Backendへの業務Query / Mutationは原則Apollo Clientへ統一する。業務GraphQL通信のためのNext.js Server ActionおよびブラウザCustomEventによる機能間同期を廃止する。認証情報の秘匿に必要なHTTP Route Handlerは許可するが、業務ロジックを重複実装しない。
- GraphQL Operationを定義し、Code Generatorが生成するApollo React Hooksを基本のQuery / Mutation Interfaceとする。単に名前や返り値を転送する独自Hookは作らない。
- 複数のOperation、共通の業務ルール、Error Mapping、Cache整合性などを一つの業務責務として組み立てる必要がある場合に限り独自Hookを設ける。単一Mutationでも有意味な業務境界なら許容する。React非依存の処理は純粋関数として分離し、モックと単体Testを容易にする。
- Server State（Community一覧、Membership等）はApollo Cacheを唯一のフロントエンド側の共有Sourceとし、同一情報をContextやuseStateへ複製しない。UI Stateは各Component、Navigation StateはURL/Routerが所有する。Contextは画面スコープの識別子など、本当に必要な情報に限る。
- Group Browser等のPreview fixtureおよび疑似Media生成は、実際のFeature Component内に埋め込まずStory / Mock Data境界から明示的に渡す。GraphQLとの接続は生成Apollo Hookに委ね、Storybook IntegrationではApolloのGraphQL OperationをMockedProviderでMockする。表示用のServer State Snapshotを独立したReact Stateへ複製しない。追加取得のカーソルとページ結合はApollo Query結果を正本とし、追加取得のLoading / Error / RetryのみをUI状態として扱う。
- Mutation後の整合性は関連Queryのrefetchを基本とし、正当性とTestを確認してからcache.modify等を採用する。通信結果不明時は無条件にMutationを再送しない。
- ApolloProviderと認証境界は一箇所で構成し、Client Componentが機密Access Tokenを受け取らない通信経路を用意する。全Consumerが生成Hookを通じて共有Cacheを参照する。
- Backend由来の設定値・情報は、各Featureで独立したReact Stateや自前のContextへ複製せず、Apollo CacheのQuery購読を通じて共有する。取得済み情報のみを利用する箇所では、生成Query Hookの `fetchPolicy: "cache-only"` 等、ネットワーク問い合わせを行わない参照方式を選べる。単なるQuery Hookの転送を目的とする独自Hookは作らず、共通の取得条件・値の正規化・Loading / Error等の責務がある場合だけ専用Hookを検討する。
- Cache参照専用のConsumerを設ける場合でも、初回表示・直接アクセス・再読み込み時に必要な情報を取得してCacheへ格納する責務を別途保証する。`cache-only` の未取得値を永続的に存在する前提で扱わない。Backendを永続データの最終的な正本とし、Apollo Cacheは共有するFrontend側の表現として扱う。
- 期待した更新が表示に反映されない場合、Mutation / refetch後のCache更新、同一Apollo Clientでの参照、Query購読、React側の値の保持・導出を順に調査する。原因を特定し、必要がある場合に限ってfetchPolicyやCache更新戦略を変更する。全Queryを機械的に`cache-only`へ統一しない。
- 移行は段階的に行い、既存の表示・動作・Interaction・Responsive Behaviorを維持する。新旧通信方式の混在中は更新漏れを確認し、最終的にCustomEventと業務Server Actionの利用箇所を全て撤去する。移行途中を完了扱いにしない。

## React / TypeScript Coding Convention

この節はCodeの**記述方法**を定義します。Architecture、Component API、State Ownership、Test、Security、Responsive Behaviorの意味的なcontractは後続の各節を正本とし、ここで重複定義しません。新規Codeと変更対象Codeに適用し、既存Codeの形式だけを揃える一括変更は行いません。Refactorでは変更前のvisual / behavioral / responsive contractを維持します。

### 判断原則と規約の強さ

実装の安全性、責務、変更時の予測可能性を優先し、品質差の小さい記述スタイルを過剰に強制しません。手入力の短縮だけを目的に暗黙の依存やProps転送を増やしません。

- **必須**: 安全性、Component contract、Architecture境界に関わる制約。例外は保証根拠と影響範囲を確認します。
- **推奨**: 読みやすさと一貫性のための標準形。合理的な代替表現は許容します。
- **例外許可**: Framework要件、Library API、明確なWrapper contractなど、標準形より適切な事情がある場合。

各規約はRule、Rationale、Examples、Exceptions、Verificationを意識して運用します。Formatter / Lint / TypeScriptで検出できるものと、意味的なレビューやTestが必要なものを混同しません。自動化可能であることだけを理由に新しいLint Ruleを追加しません。**一時停止中のQuality Gate / CIは今回変更しません**。再導入時に必要な自動検証を別途判断します。

### Component宣言・Props・Export

| 項目 | 標準形と理由 | 強さ・例外 |
| --- | --- | --- |
| Component宣言 | 名前付き `function ComponentName(...)` を基本とし、stack traceと識別性を高める | 推奨。 `memo` / `forwardRef`、Generic Component、Library API等は合理的な別形式を許可 |
| Props型 | `ComponentNameProps` をComponentの近くに定義し、必要なcontractだけを公開する | 推奨。Genericや既存Library型を直接利用する場合は例外 |
| Props受け取り | 通常は引数で分割代入し、利用する値を明示する | 推奨。Wrapper等でProps集合を保持すること自体が責務の場合は例外 |
| デフォルト値 | 省略可能なPropsの既定値は原則として分割代入で表現する | 推奨。正規化処理に独立した意味がある場合は例外 |
| Export | named exportを基本とし、Public APIは既存Module境界のexplicit exportに従う | 推奨。Next.jsの`page.tsx`等のdefault export要件は例外 |
| `React.FC` | 通常はPropsを関数引数へ明示し、`React.FC`に依存しない | 推奨。Library契約が要求する場合は例外 |
| Props spread | 無関係な値や外部Data shapeを暗黙に転送しない | 必須。転送先と許可Propsのcontractが明確なWrapperでは許可 |
| Handler | Componentから見たeventの意味で`onSelect`等と命名し、非自明な処理は名前付きHandlerへ分離する | 推奨。単純な直接転送はinlineでもよい |

```tsx
type MediaCardProps = {
  title: string
  selected?: boolean
  onSelect: () => void
}

export function MediaCard({
  title,
  selected = false,
  onSelect,
}: MediaCardProps) {
  return (
    <button type="button" aria-pressed={selected} onClick={onSelect}>
      {title}
    </button>
  )
}
```

Component自身のPropsと転送先のPropsを区別します。Wrapperは転送先のProps contractを意図的に公開し、Wrapper固有のPropsを除外してからrest Propsを転送できます。転送先の型が広すぎる、意味的制約がある、外部Data objectをそのまま展開する場合はspreadの安全性を再評価します。

```tsx
type ActionButtonProps = React.ComponentProps<typeof Button> & {
  label: string
}

export function ActionButton({ label, ...buttonProps }: ActionButtonProps) {
  return <Button {...buttonProps}>{label}</Button>
}
```

この例は**転送方法**の説明であり、単にMantineを隠すWrapperを新設することを推奨しません。Component APIの意味、controlled / uncontrolled、children / slotの判断は後続の「Component API」に従います。

### ExportするComponentのファイル境界

- **必須**: 1つの実装ファイルからexportするReact Componentは原則1つとし、ファイル名はそのComponent名に対応させる（1ファイル1export Component）。Feature内部だけで利用するnamed exportも対象とする。
- **許容**: exportしない小規模なprivate Componentは、責務を共有する親Componentと同じファイルに置いてよい。独立した変更・検証の境界が成立する場合は分離を検討する。
- **対象外**: Props・Type・定数・Pure Functionのexportや、公開入口である`index.ts`の複数re-exportはこのComponent数の制約に含めない。FrameworkやLibraryの明示的な制約がある場合は理由を確認して例外を判断する。
- **目的と検証**: export Componentの責務・参照先・ファイル名を1対1で発見できるようにする。変更対象のexport宣言とimportを確認し、分割時はvisual / behavioral / responsive contractを維持する。既存の無関係なコードを一括変更しない。

### UIアイコンの表現

- **必須**: UIの操作、状態、方向、並べ替え、展開・折りたたみ、Navigation、Feedback等を示す**アイコンを、テキスト文字・記号・絵文字で模倣して表示することを禁止**します。例: ソート方向を `▲` / `▼` / `↕`、矢印ボタンを `→`、Close Iconを `×`、状態Iconを絵文字で代用する実装。これらをIconとして使う場合は、Icon Componentを使用します。
- **必須**: Iconが必要な場合は、導入済みのIcon Library（Webでは `@tabler/icons-react`）や適切な既存UI ComponentのIcon APIを優先します。React Componentとしてsize、color、stroke、accessibility属性を管理し、文字のfont・glyph差異に依存させません。Mantineの`ActionIcon`、`Button`、`Group`等との組み合わせは、その操作・配置の意味に応じて選択します。
- **必須**: Iconへの置き換えで、既存のAction、状態、情報量、Focus、Keyboard操作、Responsive Behaviorを削除・変更しません。単にIconを追加するためだけのWrapperや汎用Componentは新設しません。
- **必須**: 装飾Iconには`aria-hidden="true"`を付け、Icon-only Buttonには操作を説明するAccessible Nameを付けます。Iconの形や色だけを状態・操作の唯一の情報源にせず、必要なText、`aria-sort`、`aria-expanded`、`aria-pressed`など意味に対応した状態表現を維持します。
- **適用対象の区別**: 本規約は禁止対象を「**Iconの代替として配置された文字**」に限定します。本文、User入力、数学・比較の記号、単位、句読点、内容そのものとして意味のあるUnicode文字（例: `%`、`+`、`×`、`→`を文章や式に使用する場合）まで一律に禁止しません。また、文字をIcon Componentで包むだけの見せかけの対応は許可しません。
- **検証**: UIの新規作成・変更時は、Icon代用文字が残っていないかCode Reviewで確認します。状態を持つIconは必要に応じてStorybookで未選択・選択・Disabled等を確認し、Keyboard / Accessible Name / Responsiveを既存contractに照らして検証します。既存画面をこの規約に合わせる場合も、対象変更の範囲とVisual / Behavioral Regressionの確認を優先し、無関係な画面の一括置換は行いません。

### TypeScriptの型安全性

| 項目 | Rule / Rationale | 強さ・例外 |
| --- | --- | --- |
| `any` | 新規Codeでは原則使用せず、型安全性を失う範囲を増やさない | 必須。避けられないLibrary境界では範囲と理由を限定 |
| `unknown` | 信頼性未確認の外部入力は検証・narrowing後に利用する | 必須。保証済みの生成型を理由なく再検証しない |
| `as` | 型Errorやcontract不整合を隠すために使用しない | 必須。保証根拠がある最小範囲では許可。`as const`等の推論補助は一律禁止しない |
| `!` | 明示的な存在確認・分岐を優先する | 推奨。存在保証が確認できる例外を許容 |
| `null` / `undefined` | absenceの意味を境界ごとのcontractに従って扱う | 必須。GraphQL由来のnullableを無条件にUIへ伝播させない |
| Generics | 入出力等の型の関係を表現する必要がある場合に使う | 推奨。抽象化自体を目的にしない |
| `satisfies` | 推論を保持したままcontractを検証できる場合に利用する | 推奨 |
| Error抑制 | `@ts-ignore`で通常の型Errorを隠さない | 必須。不可避なら理由付き`@ts-expect-error`を最小範囲に限定 |
| 型の配置 | 型のsemantic ownerに近接させる | 必須。Code種別だけの共有`types`置き場を新設しない |

有限なProduct Stateには必要に応じてunion / discriminated unionを使い、不正な組み合わせを表現しにくくします。一方、独立したStateを無理に単一unionへ統合しません。詳細は「UI State Modeling」と「TypeScript Value / Escape Hatch」を参照します。

### Hooks・Pure Logic・Effect

- **必須**: Reactを必要としない判断・変換・Validation・Derived StateはPure TypeScriptを優先します。Hookへ移すだけの抽象化を行いません。
- **必須**: Custom HookはReact State、Lifecycle、Context、外部Systemとの同期など、Reactへの接続自体が独立した責務である場合に抽出します。
- **必須**: Hooksの呼び出し規則を守り、条件分岐・反復処理の内部で呼び出しません。
- **必須**: `useEffect`を導出可能な表示Stateの再生成に使わず、外部Systemとの同期を中心に使用します。依存関係とcleanupを確認します。
- **推奨**: `useMemo` / `useCallback`は必要性がある場合に使用し、習慣的に追加しません。最適化を責務分離の代替にしません。
- **推奨**: Hookの抽出は行数ではなく独立したState / Lifecycle / Interaction contractで判断します。
- **推奨**: Custom Hookは`useXxx`、ComponentはPascalCaseで命名し、既存の「命名と品質」に従います。

### Async・Error・Stateとイベント処理

- **必須**: Event Handler内のAsync処理はpending、二重実行、失敗、復帰等のProduct contractを維持し、未処理のPromise rejectionを放置しません。
- **必須**: Server / GraphQL / LibraryのErrorを、そのままUser向け文言やComponent contractに流しません。
- **必須**: 既存のState authorityを尊重し、Props・Apollo・Form・local state間で同じ意味のStateを無用に二重所有しません。
- **推奨**: 複雑なinline callbackは、意図が読み取れるHandlerへ分離します。ただし単純なforwardingのためだけに関数を増やしません。
- **必須**: StateやComponentの整理を理由に、既存のloading / empty / error / disabled / readOnly等の意味やinteractionを削りません。

### Import・命名・Codeの整理

- **必須**: Module間はPublic APIを経由し、Feature間直接依存や禁止されたdeep importを導入しません。`import type`も依存関係に含めます。
- **推奨**: Module内部はrelative import、外部は`@/` importを使用します。
- **必須**: 意味のない共通化、先回りしたGeneric Component / Hook / Layerを導入しません。既存consumerのCapabilityを共通化の都合で削りません。
- **推奨**: 名前は実際の責務やeventの意味を表し、型やCommentで不明瞭な名前を補うより命名を改善します。
- **必須**: 三項演算子（`condition ? a : b`）を別の三項演算子の条件部・結果部へネストしません。複数条件による表示・状態選択は、`if / else`、`switch`、意味の明確なLookup、または責務に応じた小さな関数・Componentへ分離し、各条件と結果を読み取れるようにします。JSXの条件付き表示でも同様です。
- **許容**: 単純な二択の三項演算子、独立した三項演算子を並列に使用する場合は対象外です。分割のためだけに不必要な抽象化を増やさず、元の条件優先順位、Fallback、表示・状態遷移を維持します。
- **検証**: 変更対象のCode Reviewでネストの有無を確認します。既存Code全体の機械的な一括置換は行わず、Biome等のLint設定追加は別途影響を検討します。
- **必須**: Formatと一般的な静的解析は既存のBiome / TypeScriptの責務とし、競合するFormatterやLint基盤を追加しません。

### 検証と適用範囲

| 規約群 | 確認方法 | 今回の扱い |
| --- | --- | --- |
| Format・一般的なLint・型整合性 | Biome / TypeScript | 既存設定を維持 |
| 宣言形式・Props型命名・named export | Review。将来AST-based Lintの適否を評価 | 新規Ruleは追加しない |
| Props spread・Component API・Hook抽出 | Contract Reviewと必要なTest | 意味的な例外を許容 |
| Import / Architecture境界 | Dependency Review。将来静的解析を検討 | CI変更なし |
| アイコン表現 | Code Review、必要に応じてStorybook / Accessibility / Interaction | 文字・絵文字でのIcon模倣を禁止し、Icon Componentの表示と意味を確認 |
| Visual / Behavior / Responsive | Screen Specification、Prototype、Storybook、Interaction / VRT | 既存contractを維持 |
| Async / Error / State | Unit / Interaction TestとReview | 変更影響に応じて確認 |

規約違反の形式的な一括修正は目的としません。変更対象では既存contractを把握し、必要な範囲だけ規約へ寄せます。規約自体と自動検証の導入は別の判断です。

## Scroll Containerの実装規則

Scrollの利用者向けContractは[Application Shell / Scroll / Viewport Contract](/design-system/patterns/application-shell#scroll--viewport-contract)を正本とします。

- Mantine `ScrollArea` の標準Styleを優先し、表示方式は `type="hover"` を基本とします。独自Scrollbar CSSは原則追加しません。
- Header下のMain content、Drawer / Modal等のScroll containerには、実際にScrollする領域が高さを所有する構成を採用します。Viewport高さ、Header offset、Flex childの `min-height: 0` を確認します。
- Mantine `AppShell.Main` のHeader offsetと独自の高さ指定を重複適用しません。親要素や追加要素によってMainのScroll領域が意図せず短くならないことを確認します。
- 既存のDrawer / Modal等を機械的に一括置換せず、既存のVisual / Behavioral / Responsive Contractを維持します。Web本体とVisual Prototypeでは共通Componentを利用します。

## Architecture Principles

Memoria WebはPure Clean ArchitectureやPure Vertical Slice Architectureをそのまま適用しません。Product Featureを変更と凝集の主要単位としつつ、Feature内部と外部Integrationの責務・依存境界を明示します。

- Product設計を実装より優先し、既存Codeから要求を逆算しません。
- Feature / Capabilityを主要な変更・凝集単位とします。
- Vertical Sliceとして配置しても、すべての責務をFeatureへ閉じ込めません。UI、Application Logic、GraphQL Integration、Pure Product Judgmentを区別します。
- 境界の判断は[プロダクトビジョン・設計原則](/product-vision#責務と変更理由を起点に境界を決める)を正本とします。Webでは、GroupsとTagsのように表示や展開が現時点で似ていても、異なる責務と変更理由を持つものを単にPropsで切り替えるために共通Component化しません。
- Next.js、React、Mantine、Apollo Client等のFrameworkやLibraryは実装基盤であり、Product Architectureそのものにはしません。Framework非依存化だけを目的とした抽象化も行いません。
- Stateにはauthoritative ownerを定め、同じ意味のStateを複数の仕組みで独立して所有しません。
- Testabilityは責務分離の結果として得るものとし、Testだけを目的としたLayerを追加しません。

## Application Structure

Top-level directoryは「どの種類のCodeか」ではなく「誰がその責務を所有するか」を表します。

```text
src/
├── app/
├── features/
├── ui/
└── infrastructure/
```

### `app`

Next.jsのentry、routing、layout、page、route-level loading/error等を担当します。Product/Application Logicを蓄積する場所にはしません。route parameter等のNext.js固有入力をFeatureへ渡すことはできます。

### `features`

Media、Community、Account等のProduct Capabilityを所有します。Feature固有のUI、Interaction、State接続、Pure Logic、GraphQL Operation等を近接配置します。

Feature間の直接依存は原則として避けます。複数Featureで同じCodeが必要になっても、再利用性だけを理由に `shared` / `common` へ移動しません。同一のProduct Conceptが独立した責務として存在する場合は、そのConcept自身をownerとして昇格させます。

### `ui`

Memoria Design Systemと、特定Featureに依存しないUI primitive / patternの実装を所有します。Featureで複数回利用されるだけでは `ui` へ移しません。Product semanticsを持つComponentはFeatureに留めます。

`ui` から `features` へ依存しません。

### `infrastructure`

GraphQL Client、認証Integration、環境設定等、外部SystemやFrameworkとのIntegrationを所有します。`infrastructure` からProduct Featureへ依存しません。

`shared`、`common` はTop-level directoryとして設けません。また `utils`、`lib`、`hooks`、`types`、`constants`、`providers` のようなCode形態だけを表すTop-level directoryを標準化しません。既存の `src/components`、`src/lib`、`src/providers`、`src/prototypes` はlegacy / migration structureとして扱い、新規Codeの標準配置先にはしません。変更対象になった時点で意味のownerを再評価します。

上記4領域は閉じた絶対的な集合ではありません。既存分類へ自然に属さず、独立したArchitecture責務が実例として成立した場合は新しいTop-level Boundaryを設計できます。ただしFile数、Code種別、将来の可能性、整理上の都合だけを理由に先回りして追加しません。

Codeは再利用性や技術的な種類ではなく、**その意味を所有する対象・責務の近くへ配置する**ことを全体原則とします。複数箇所で似たCodeが存在するだけでは共通化せず、同じsemantic contractと独立したownerが確認できるまで局所的な重複を許容します。

## Feature内部構成

FeatureはURL、Screen、Entity、Code量ではなく、独立したUser Purpose / Use Case / Behaviorをownerとします。Feature directoryは `src/features` 直下へkebab-caseでflatに配置し、URLやProduct namespaceをDirectory hierarchyとして表現しません。同じFeatureを複数routeから利用できます。

```text
features/
├── media-browser/
│   ├── index.ts
│   ├── MediaBrowser/
│   │   ├── index.ts
│   │   ├── MediaBrowser.tsx
│   │   └── MediaBrowser.stories.tsx
│   ├── MediaTile/
│   │   ├── index.ts
│   │   └── MediaTile.tsx
│   ├── filterMedia.ts
│   ├── filterMedia.test.ts
│   └── GetMediaBrowser.graphql
├── media-detail/
├── media-upload/
├── community-members/
└── account-deletion/
```

Feature数の多さ自体をArchitecture問題とはみなしません。探索性、ownership、命名、dependencyに具体的な問題が発生してから境界を再評価し、将来の規模を予測してnamespace directoryを作りません。

### Componentの責務境界と実装・Story・Testの配置

Componentを作成・分割するかどうかは、独立した表示・操作、状態の所有、変更理由、再利用する意味的な契約、検証価値をもとに判断します。**名前を持つReact Componentは公開・非公開を問わず専用の同名Directoryを必須とします。** Story・Testは検証価値に応じて追加し、Componentの作成と一対一の必須セットにはしません。 初期PrototypeのComponent構成は仮の実装境界であり、Visual Reviewとテスト設計の結果を踏まえて責務を見直せます。

画面の意味・振る舞い・採用した具体的なUI/UX設計判断と理由は `memoria-design` のScreen Specification、必要な画面固有の関連Design、Design Systemを正本とします。**Storybookの画面／Component設計MDX（`*.design.mdx` 等）は新規作成しません。** 設計書をComponent実装のDirectoryへ複製せず、必要な場合は実装・Storyから正本を参照します。

- **Componentの実装**: React Componentは、exportの有無や利用者数にかかわらず、責務のowner付近に `<ComponentName>/<ComponentName>.tsx` の専用Directoryを設けます。Component Directoryには `index.ts` を必ず配置し、必要なsymbolだけを明示的にexportします。非公開のComponentはFeatureのPublic APIに含めません。Story・Testは必要な場合のみ同Directoryへ近接配置します。既存実装は変更対象から段階的に移行し、無関係なComponentの一括移動は要求しません。
- **Container / 接続CompositionのStory**: アプリケーションのロジック・状態・Router・GraphQL等の外部依存を組み立ててUIへ接続するContainer Componentは、Storyを作成しません。Storyを成立させるためのRouter/API依存注入やProduction API追加は行わず、接続の正しさと主要なユーザーフローはIntegration / E2Eで検証します。Containerが利用する独立したUI Componentの表示・操作はそれぞれStorybook / Interaction / VRTで、Pure Logic・HookはUnit / Hook Testで検証します。この原則はApplication Shellに限定しません。
- **Story**: UIの重要な表示状態・操作・Responsiveを独立して確認する価値がある境界へ `<ComponentName>.stories.tsx` 等を近接配置します。共通UI ComponentのStory同時整備に関する方針は[Frontend UI設計・開発方針](/system/frontend-ui-development#ui-quality-gate)に従います。すべてのComponentに1対1のStoryを強制せず、画面単位のStoryや複数Componentを構成したStoryも利用できます。
- **Test**: [Frontendテスト戦略](/system/web/frontend-testing)と対象のテスト設計に従い、Unit / Component / Integration / E2E、VRT / Accessibility等から必要な検証を選びます。対象LogicのTestはowner付近へ配置し、画面横断のE2E等は対象環境の実行単位に従います。Component単位のTestファイルやStoryとの1対1対応を要求しません。
- **Hook / Pure Logic / Type**: 独立した責務・変更理由のあるものだけ分離し、適切なownerの近くへ配置します。StorybookやTestだけのためにProductionの公開API・専用Layerを増やしません。

Component Directoryを設けても、それ自体はFeature外へのPublic API公開を意味しません。公開する境界では `index.ts` により明示的なexportを管理します。既存のComponent Directoryやexportを、設計MDX廃止だけを理由に移動・変更しません。

### Custom Hookのファイル責務と再export

独立したCustom Hookは原則として`useXxx.ts`（JSXを必要とする場合のみ`.tsx`）に`useXxx`を実装し、**ファイル名と主たる実装を1:1**で対応させます。小規模なHookを専用Directoryにする必要はありません。複数の独立したHookを名前の異なるComponentファイルへ同居させず、所有するFeature / Componentの近くに配置します。

他Moduleのsymbolを公開するための再exportは`index.ts`へ集約し、Component名の`.tsx`ファイルを兼用barrelや移行用再export入口として使用しません。外部consumerのimport変更が必要な場合は参照先を更新してから旧entryを削除します。Feature rootの`index.ts`は引き続き公開境界として扱います。

### Custom Hook・Reducerの公開インターフェースと状態表現

Custom HookやReducerが公開する状態・操作は、`setState`・`dispatch`などの内部実装手段ではなく、**対象ドメインの状態・操作・意図が利用側から理解できる名前**を優先します。内部でReact StateやReducerを利用していても、利用側へ実装都合の操作をそのまま露出する必要はありません。たとえばNavigation Drawerの`opened`、`toggle`、`close`は利用側の目的を表す公開インターフェースです。

状態表現は、状態数、遷移の複雑さ、意味の明確さに応じて選びます。意味が明確な二値状態にはBooleanを利用して構いません。複数の意味的状態、排他的な状態、遷移制約がある場合は、文字列Literal Unionや判別可能Unionなどの明示的な状態表現を検討します。Booleanを機械的にUnionへ置き換えることも、将来の拡張を理由に過剰な状態モデルを導入することも求めません。

UI Libraryが要求する型との整合性は判断材料ですが、Libraryの実装都合をドメインの公開APIに無条件で反映しません。また`toggle`のような反転操作は単純な二値状態に適しますが、非同期処理や複雑な状態遷移を扱う場合は`open`・`close`など結果が明確な操作を検討します。

### Component DirectoryのPublic APIと型の配置

Component Directoryには必ず`index.ts`を配置し、外部に公開するComponent・Props・関連型だけを**explicit named export**します。`index.ts`はそのComponentの公開入口であり、Directory内のすべてのsymbolを公開するものではありません。Component間で利用する場合は所有Componentの`index.ts`からimportし、`ComponentName/ComponentName`のような実装ファイルへのdeep importを避けます。Feature外部からのimportは引き続きFeature rootの`index.ts`を経由し、Component Directoryの入口をFeatureのPublic API境界の代替としません。

型は利用者数やファイル名ではなく**責務の所有者**に配置します。Propsと小規模なComponent固有型は通常`ComponentName.tsx`に定義し、実装と分離する実質的な必要がある場合のみ同Directoryの`types.ts`へ移します。`types.ts`は必須ファイルではありません。どちらに定義しても外部consumerは`index.ts`から公開型をimportします。Feature全体の契約はFeature owner、複数Featureにまたがる契約は適切な上位の所有境界で定義し、単に共有されるという理由でComponentの型を上位へ移動しません。

Component Directoryの標準構成例です。StoryとTestは検証上必要な場合に追加し、設計MDXは作成しません。

```text
ApplicationNavigationContent/
├── index.ts
├── ApplicationNavigationContent.tsx
├── ApplicationNavigationContent.stories.tsx  # 表示・操作の独立検証が必要な場合
└── types.ts                                # 実装と分ける理由がある場合
```

```ts
// ApplicationNavigationContent/index.ts
export { ApplicationNavigationContent } from "./ApplicationNavigationContent"
export type {
  ApplicationNavigationContentProps,
  ApplicationNavigationItem,
} from "./ApplicationNavigationContent"

// 同じFeature / owner内部の別Componentから
import type { ApplicationNavigationItem } from "../ApplicationNavigationContent"
```

Storybookの分類名（`title`）はComponent名や責務が分かる識別子を基本とし、利用者向けの日本語の操作文言（例：「Communityへ共有」「Groups編集」）をComponentの代替名にしません。Story名は実際に表示される意味のあるパターンを表し、Dialog / Modalでは単に`Opened`と`Closed`を列挙せず、表示されたDialogの内容・Context・状態の差異をStoryにします。閉じた状態は、閉じる動作そのものが検証対象である場合にInteraction Test等で確認します。

例えば `src/features/media-browser/` では、Componentを公開・非公開にかかわらず専用Directoryへ配置します。

```text
src/features/media-browser/
├── index.ts
├── MediaBrowser/
│   ├── index.ts
│   ├── MediaBrowser.tsx
│   └── MediaBrowser.stories.tsx
├── filterMedia.ts
├── filterMedia.test.ts
└── MediaTile/
    ├── index.ts
    ├── MediaTile.tsx
    └── MediaTile.stories.tsx  # 必要な場合
```

Feature内部は、Frontendで役割や変更理由を理解しやすい**責務・機能のまとまり**を起点に配置します。独立したまとまりが複数ある場合は `profile/`、`preferences/` 等、その意味を示すdirectoryへ分割し、各まとまりに属するComponent・Hook・Pure Logic・Type・Story・Testを近接配置します。Domainの厳密な境界やURL・Screenの階層を機械的にdirectoryへ写すのではなく、実際に一緒に変更・検証する単位で判断します。一つの明確な責務に収まる小規模Featureではflat構成を許容します。`components/`、`hooks/`、`types/`、`utils/`、`constants/`、`services/` 等のcode種別だけによる分類を標準化しません。Props、型、定数、Pure LogicはownerのFileへ置いて構いませんが、React Componentは専用Directoryへ配置します。Feature内部の分割で別の独立した利用目的や複数Feature間の依存を隠さず、外部から再利用される責務が明確な場合は独立FeatureとPublic APIを検討します。

Application Shellはアプリケーション全体のNavigationとContext切替を所有するFeatureとして `src/features/application-shell/` に配置します。Feature内に技術種別だけの `components/` directoryを設けず、`ApplicationShell/`、`ApplicationHeader/` 等の独立した責務ごとにFeature直下へ近接配置します。Productionの接続は実際に利用される `ApplicationShellContainer` が所有し、利用箇所のない別Composition実装を保守目的で重複させません。配置整理では既存のUI、状態、Interaction、Responsive BehaviorとStorybook / Prototypeのcontractを維持します。

Feature rootの `index.ts` はArchitecture BoundaryとしてPublic APIを定義します。外部consumerはFeature rootからimportし、内部Fileへdeep importしません。Public APIは実際に必要なsymbolだけをexplicit exportし、`export *` で内部実装を公開しません。Feature内部では `index.ts` を経由せずrelative importを使用します。

```ts
// Feature外部
import { MediaBrowser } from "@/features/media-browser"

// Feature内部
import { MediaTile } from "./MediaTile"
```

Feature間の直接依存はtype-only importを含め原則として禁止します。複数FeatureのCompositionは通常 `app` が所有します。Compositionが複雑な場合はroute-local Componentへ分離しますが、Compositionだけを目的としたfake Featureや汎用Screen Layerを作りません。

### `app` のroute-local構成

App Routerの通常DirectoryはURL route segmentを表します。routeを作らないprivate Componentは `app/.../_components/` へ配置できます。`_components` はApp Router上でroute-local Componentをまとめるための明示的な例外であり、`_hooks`、`_utils`、`_types` 等のtechnical bucketを一般化しません。

`page.tsx` は責務上thinに保ちますが、1 Featureだけをrenderする必要はありません。複数FeatureのCompositionも可能です。route-local Codeを別routeからimportせず、再利用が必要になった場合はownershipを再評価します。Route Groupはlayout、loading、access boundary等のrouting上の意味がある場合に使用し、File整理だけを目的にしません。

### `ui` のModule Boundary

`src/ui` はFeature-independentなMemoria UI Component / Patternをownerとします。Mantineを隠すためだけのwrapperや、複数箇所で利用されるだけのComponentを移しません。

UI Component / PatternはPascalCase DirectoryをModule Boundaryとして持ち、root `index.ts` からexplicitなPublic APIを公開します。`src/ui/index.ts` の巨大なglobal barrelは標準化しません。

```text
ui/
└── EmptyState/
    ├── index.ts
    ├── EmptyState.tsx
    ├── EmptyState.stories.tsx
    └── EmptyState.test.tsx
```

### `infrastructure` のModule Boundary

`src/infrastructure` は外部technology / service / runtime integrationをownerとし、integration purposeでDirectoryを分けます。Library名より `graphql`、`auth`、`environment` 等の責務名を優先します。

各integration rootは `index.ts` でexplicitなPublic APIを定義し、consumerはrootからimportします。Product GraphQL OperationやProduct RuleをInfrastructureへ移しません。Providerもtechnical formだけを理由にTop-levelへ集約せず、GraphQL ProviderはGraphQL integration、Auth ProviderはAuth integration等、実際のownerへ配置します。Application-level Provider Compositionは `app` が所有し、必要なら `app/_components/ApplicationProviders.tsx` 等へ分離します。

### 利用環境をまたぐComponent Compositionと責務分離

### Media / Media Groupの共通表示境界（2026-10-22合意）

Media 1件およびMedia Group 1件の視覚的な基本単位は、Group Browser専用ではなくアプリケーション共通UIとして所有する。初期段階ではThumbnail・補助Artwork等のシンプルな表示に限定する。MediaTileの表示状態は `ready` / `loading` / `processing` / `error` を区別する。Feature側がGraphQL・変換Job・画像URLの取得状況を意味的な表示状態へ変換し、MediaTileはその状態の描画とブラウザ画像読み込み失敗の検知のみを担当する。変換失敗・URL取得失敗・画像読み込み失敗は共通の `error` 表示に集約し、原因の判定・記録はFeature / Data層で維持する。取得中と処理中はErrorと区別し、`src` の有無だけで失敗原因を判定しない。実際の変換JobやURL取得処理との接続はFeature単位で段階的に実施し、接続済みと誤認しない。

MediaGroupTileはMediaTileの読み込み・変換・エラー状態モデルを持たない。Group自体の取得状況やエラーはFeatureで扱う。MediaGroupTileは左の大セル1つ・右の小セル2つの固定3セルの装飾カバーとし、画像枚数に関係なくセルの配置、比率、Gap、外側のTileサイズを保つ。渡された `sources` の先頭3枚を順番に各セルへ `cover` でフィットし、不足セルにはMediaTileのErrorアイコン（`IconPhotoOff`）とは異なる画像モチーフ（`IconPhoto`）を控えめに表示する。0枚も背景のみの空白とせず、1枚でもMediaTileと区別でき、2枚から3枚へ変化しても配置が変わらない。`sources` の枚数は装飾画像数でありdirect / aggregate Mediaの総件数や正常な0件の確定を意味しない。Group BrowserのPreview Cell外形・選択操作と既存の画像順序を維持する。

各Feature（Media Browser、Group Browser、Dashboard、Media Upload / Update等）は、画面固有の選択・Navigation・Upload進捗・Retry・Grid配置といった操作・Compositionを所有する。共通Component化を理由に既存Featureの表示情報・Interaction・Responsive Contractを削らず、実装を移行する際はFeatureごとに差分を検証する。Media Groupのdirect Mediaとaggregate Mediaの区別、およびGroupにMediaがない場合の未確定表現はGroup Browser UI Designを正本とする。

同じUIをVisual Prototype、Storybook、Web本体で利用する場合は、**共通のComponent実装と意味的なcontractを再利用**します。環境ごとの要求を満たすためだけに、Storybook専用・Prototype専用・本体専用の同等なUI Compositionを複製しません。複製による表示・操作・状態表現の乖離を防ぐことを目的とします。

- **UI側の責務**: 画面構造、レイアウト、表示状態、共通のInteractionを所有します。必要に応じてProps、Callback、slot、children、compositionで差異を受け取ります。
- **利用側の責務**: Router、認証、データ取得、永続化、Storybook fixture等の外部依存を接続します。これらを共通UIに直接埋め込みません。
- **構造の判断**: Presentational / Containerは責務を考える際の参考概念であり、固定Layer、専用Directory、`Container`という名前のComponentを必須としません。既存のContainerやWrapperも、独立した責務がなければ再検討します。
- **抽出の判断**: 複数consumerが同じUI contractを必要とするなら共有Compositionを検討します。一方、共通化のためだけに大きな結合Componentを作らず、個別の既存Componentを組み立てる方が適切な場合はそれを許容します。
- **不変条件**: 既存consumerの情報、Capability、状態、操作、Visual / Behavioral / Responsive contractを維持します。単純なconsumerに合わせて複雑なconsumerの機能を削りません。
- **検証**: 静的なStoryだけでなく、表示状態、Keyboard / Focus、Interaction、画面遷移へのCallback接続、Mobile / Desktopの振る舞いを必要な範囲で確認します。Storybookの網羅性を得るために別実装のUIを作りません。

共通Componentが内部で所有するStateと、利用側から制御・注入するStateの境界は、各consumerの実際の要件に基づいて決めます。特定の実装（例: Application Shell）で得た判断を他Componentへ適用する際も、既存contractを確認してから変更します。

## Dialog / Modalのマウントと開閉State

Dialog / Modalは呼び出し元の画面がマウントされている間、原則としてComponentをマウントしたまま `opened` 等の開閉Stateで制御します。`{opened && <Dialog ... />}` のように開閉ごとにComponentを破棄・再生成する方式を通常の開閉手段にしません。閉じた状態でもDialog Componentをレンダリングし、開閉操作では開閉Stateを変更します。

Dialog Componentのマウントと内部Contentの描画・データ取得・初期化は別責務とし、重いContentや対象未選択の詳細領域は条件付き描画できます。対象を切り替えるDialogでは、対象IDや選択stateをprops / stateで更新し、Componentの破棄による暗黙の初期化に依存しません。入力値等の初期化条件はScreen Specificationに従います。

呼び出し元のアンマウントや明示的な例外要件がある場合は、理由と影響を設計書に記録します。Web本体とVisual Prototypeの双方に適用し、既存Dialogすべてが準拠済みとはみなしません。不一致はVisual / Behavioral Regressionを防ぎながら段階的に是正します。既存のAnimation、Focus、Keyboard、Overlay、Responsive Behaviorを維持し、Animationを揃える目的だけの独自Transitionは追加しません。利用者向けの開閉・状態保持Contractは[Overlay / Temporary Surface](/design-system/patterns/overlay-temporary-surface)を正本とします。

## Component Architecture

Componentは概念上、次の責務に分けます。これらを固定Directoryや固定Layerとして機械的に作成する必要はありません。

- **Feature / Slice Component**: `MediaCard`、`MediaGrid` 等、Product semanticsを持つUI。
- **Screen / Composition Component**: Feature外部のStateやIntegrationとFeature内部を接続し、画面またはSliceを構成するComponent。
- **UI Component / Pattern**: `src/ui` が所有するFeature非依存のUI。

依存の基本形は次のとおりです。

```text
                app
                 │
                 ▼
              features
              /      \
             ▼        ▼
            ui   infrastructure
             │
             ▼
          Mantine
```

Componentは再利用性とTestabilityのためGraphQL / Apolloを知りません。Feature ComponentはMedia等のProduct semanticsを知ることができますが、Generated GraphQL Type、Query shape、Apollo Hookへ直接依存しません。

Component分割は「将来再利用できるか」ではなく、独立した責務、State、Interaction、Visual Review、Testの境界があるかで判断します。意味のないJSX断片化と巨大Componentの双方を避けます。

### 表示責務と接続責務の分離

コンポーネント全般において、表示・操作を表す責務と、アプリケーションのデータ取得・状態管理・ルーティング等を接続する責務を分離します。これはApplication Shell専用の方針ではなく、Feature Componentや共通UIを含むフロントエンド全体の原則です。

- **表示・操作の責務（Presentational）**: 受け取った状態に基づく表示、局所的なUI状態、操作イベントの通知を扱います。GraphQL、Next.js routing、アプリケーション固有の外部接続へ直接依存させません。
- **接続・構成の責務（Container / Composition）**: API、URL、アプリケーション状態等と表示コンポーネントを結び付け、必要な表示状態とイベントハンドラーを渡します。実際のownershipに応じて配置し、固定の階層・名称は強制しません。
- **責務単位での再利用**: Storybook・Prototype・Productionでは、同一の表示・操作・状態遷移の責務を持つコンポーネントやモジュールを共有します。一方、利用側でのコンポーネントの組み合わせ（Composition）は個別に記述して構いません。JSXの組み立ての重複だけを理由に上位のPresentationコンポーネントを設けません。Storybookでは本番接続を検証用の状態・Callbackに置き換えます。
- **Storybookでの共通構成**: 複数Storyで繰り返す環境・レイアウトの提供にはDecorator、検証対象の共通の組み立てにはMetaのrender関数、Storyごとの差分にはArgsを優先します。Storybook専用Composition Componentの新設を前提としません。これらで表現できない明確な責務がある場合に限って抽出を検討します。
- **PrototypeとProductionの差異**: データ接続、Router、モック、Compositionの書き方、Prototype固有の検証機能の差異は許容します。実装構造の一致を目的化しません。ただし、合意済みのUI・主要操作・状態表現・Responsive Behaviorを意図せず変更することは許容せず、仕様差分と回帰を区別します。
- **固有のCapabilityの維持**: 共通化・責務抽出により、既存consumerの表示情報、操作、状態表現、Responsive Behaviorを失わせません。固有要件は適切なprops、slot、compositionまたは責務境界の再検討で保持します。維持できない場合は暗黙に簡略化せず設計変更として合意します。

この区分は責務を説明するためのものであり、各コンポーネントにPresentational/Containerの二つのファイルや層を必ず作る規則ではありません。Presentation全体を単一コンポーネントに集約することも必須としません。共通のUI責務が明確である場合に限って上位コンポーネントへの抽出を検討し、Propsの橋渡しや環境別の条件分岐だけを増やす抽象化は避けます。実際の責務と複雑さに応じて分割します。既存実装を抽出する際は変更前のvisual / behavior contractと比較し、Storybookを含む表示・操作・レスポンシブの回帰を確認します。

### Composition Root

GraphQL、Mapper、React State、Pure Logic、Feature Component等を接続するComposition責務は必要ですが、`Composition Root`、`Container`、`Presenter` 等の固定Layer・命名・Directoryを標準化しません。接続Codeは実際のownershipに最も近い境界へ配置し、下位Componentへ外部Integrationの詳細を漏らしません。

`page.tsx` はNext.js entryとして責務上thinに保ちますが、複数FeatureのCompositionを行えます。Compositionが肥大化した場合は新しい抽象Layerを先回りして追加せず、実際の責務に応じてPure Logic、Mapper、Custom Hook、route-local Component等へ分離します。

## Logic Isolation

Product/Applicationの判断、変換、Validation、State Transition、Derived State等でReactを必要としないものはPure TypeScriptとして実装し、React、Mantine、Apollo、DOMなしでUnit Testできる状態を基本とします。

```text
Component
    ↓
Custom Hook（React接続が必要な場合）
    ↓
Pure Logic
```

Custom HookはComponentからLogicを隠すための汎用的な移動先ではありません。React State、Lifecycle、Contextとの接続そのものが責務である場合に使用します。Reactを必要としない責務はPure TypeScriptを優先します。

`useEffect` は外部Systemとの同期を主目的とし、導出可能な表示StateをEffectから再生成しません。`useMemo`、`useCallback` は意味的な責務分離の手段として使用せず、必要性がある場合に利用します。

## State Ownership

Stateの保存先をLibraryから決めず、まずauthoritative sourceとlifecycle / scopeを決定します。

| State | Authoritative owner / mechanism |
| --- | --- |
| 永続的なProduct Data | Backend / GraphQL API |
| GraphQL Remote StateのFrontend表現 | Apollo Client |
| Formの編集中State | React Hook Form |
| Navigation・共有可能なScreen State | URL / Next.js |
| 一時的なInteraction State | React local state |
| React subtreeで共有する依存・State | React Context |
| Judgment、Transition、Derived State | Pure TypeScript |

Apollo cacheはBackend Product DataのFrontend表現であり、最終authorityではありません。Query Dataを理由なくReact Stateへ複製しません。

Form draftとServer上の保存済み値のように意味が異なるStateは重複とはみなしません。React Hook Formは編集中の値を所有し、保存後のauthorityはBackendへ移ります。

URL Stateは「保持できるから」ではなく、そのStateがNavigation上Screenを識別し、共有・bookmark・reload・history復元するProduct上の意味を持つ場合に使用します。

Redux、Zustand、Jotai、Recoil等のGeneric State Managerは標準採用しません。将来、React標準API等では責務を適切に表現できない具体的要求が生じた場合はArchitecture判断として再検討できます。

## Derived StateとInteractivity

操作可否はComponentやApolloが独立して所有するStateではなく、Permission、Pending、Validation、Product State、Selection等のauthoritative stateから導出します。

```text
Authoritative States
 ├ Permission
 ├ Pending
 ├ Validation
 ├ Product State
 └ Selection
        ↓
   Pure derivation
        ↓
Interaction availability
```

`canDelete`、`canSubmit` 等の判断にProduct/Application上の意味がある場合はPure Logicとして表現できます。`disabled` と `readOnly` は同義とはみなさず、Product meaningに応じて使い分けます。

## Server / Client Boundary

Server Componentを最大化すること自体を目的にしません。Server / ClientはBusiness Layerではなくexecution environmentの境界です。

Product FeatureのGraphQL Remote Stateは **Client Apolloをdefault** とします。Server Queryを毎回対等な選択肢として比較せず、Serverで処理する明確な責務がある場合に採用します。

Server側の代表的な責務は次のとおりです。

- authentication / session
- server-only credential
- Application Shellの初期化
- Clientへ到達する前に必要なredirect / navigation decision
- Browserへ公開してはならない処理

Media Browser、Media Detail、Group Browser、Settings、Form、Search、Mutation等の通常のProduct FeatureはClient Apolloを基本とします。

Server initial fetchからApolloへhydrateする構成を標準化しません。ServerとClientで同一Remote Stateを二重所有し、cache synchronizationを複雑化させないためです。将来、明確な価値があるFeatureでは例外を設計できます。

Client ComponentはInteraction、Client State、Browser API、Client-only runtimeが必要な範囲へ配置します。Error解消だけを目的に `"use client"` を上位へ移動しません。

## GraphQL Integration

Apollo ClientはGraphQL Remote Stateを扱うspecialized infrastructureです。Product/Application LogicやGraphQLと無関係なUI StateをApollo cacheへ持たせません。

### GraphQL Boundary

```text
GraphQL / Apollo
      │
      ▼
Generated Type
      │
      │ boundary / mapping
      ▼
Feature Model
      │
      ├── Pure Logic
      └── Components
```

ComponentとPure Product/Application LogicへGenerated GraphQL Typeを漏らしません。境界は必須ですが、Mapper fileやFeature Model fileを機械的に作成する必要はありません。単純な変換はComposition内で行えます。変換に独立した意味、再利用性、Test価値が生じた場合はPure Mapperとして分離します。

Generated Apollo Hookを常にCustom Hookで包みません。単純なCompositionでは直接利用できます。Pagination、Refetch、Mutation、Cache、Lifecycle等のReact接続自体が独立した責務になった場合にCustom Hookを検討します。

### OperationとFragmentのownership

GraphQL Operationは取得Entityではなく、そのOperationを必要とするProduct Use Case / Feature / Sliceが所有します。`*.graphql` sourceをFeatureの近くへ配置し、GraphQLという技術分類だけを理由に全Operationを一箇所へ集約しません。

Fragmentも自動的な共有GraphQL Componentとはみなしません。Fieldの重複だけでは共有せず、同じsemantic contractが存在する場合に最も狭い共通Product ownerへ配置します。巨大なEntity共通Fragmentを作成してFeature間を結合しません。

FragmentはComponentの最終Modelではなく、FeatureがBackendへ要求するGraphQL側のField Contractとして利用できます。Generated Fragment TypeもComponentへ直接渡しません。

### SchemaとGenerated Code

GraphQL API契約のSource of Truthは `memoria-api/schemas/graphql/` です。Web側Schemaはその契約のlocal mirrorであり、Webが独立して所有するSchemaではありません。

目標配置は次のとおりです。

```text
src/
├── features/
│   └── .../*.graphql
└── infrastructure/
    └── graphql/
        ├── schema/
        ├── generated/
        ├── client.ts
        └── cache.ts
```

`src/infrastructure/graphql/schema/` はAPI-owned contract mirror、`src/infrastructure/graphql/generated/` はmachine-owned artifactとして扱います。Generated Codeは手編集しません。生成物内部の構造やFile sizeを人間向けArchitectureの判断材料にはしません。

Generated Codeへ依存できるのはCompositionやMapper等のGraphQL BoundaryにいるCodeに限定し、Feature ComponentやPure Logicへ漏らしません。

API SchemaからWeb Schema mirrorへの同期・drift検出方法は実装運用上の独立課題として扱い、推測で同期方式を固定しません。

### MutationとCache

Mutation後はBackend authorityとの整合性と実装の単純さを優先します。

1. Mutation responseによるApollo normalized cacheの自然な更新を優先する。
2. 十分でない場合は明示的なcache updateを検討する。
3. Query semanticsをClientで安全に再現することが複雑な場合は、affected queryをrefetchする。

Refetchは失敗した最適化ではなく、複雑なClient-side cache semanticsより正確性を優先する有効な選択肢です。

Optimistic Updateは標準適用しません。利用体験上の価値があり、Server結果を高い確度で予測でき、rollbackが明確な場合に利用します。認可、部分成功、競合が重要な操作ではServer responseを優先します。

## Query UI State

Apolloの `loading`、`error`、`data`、`networkStatus` をそのままComponentのUI Contractにはしません。Feature BoundaryでProduct / UI上の意味へ解釈します。

FeatureごとにInitial Loading、Content、Empty、Refresh、Load More、Not Found、Forbidden等の必要なStateを定義し、汎用 `AsyncState<T>` を先回りして全Featureへ強制しません。

既に有効なProduct DataやUser Interaction Stateが存在する場合、後続のRefresh、Load More、Mutation等のPending / Failureだけを理由に破棄しません。Collection追加取得失敗時の詳細は[Frontend UI設計・開発方針](/system/frontend-ui-development)に従います。

Empty Stateは単なる `data.length === 0` ではなく、空のLibrary、検索結果なし等のProduct contextに応じて解釈します。

## MutationとError Interpretation

ComponentはApollo Mutation Stateや `ApolloError` を直接UI Contractとして扱いません。Composition等のFeature BoundaryでServer response、cache/refetch、Feature State、Feedbackを調整します。

Technical ErrorとUser-facing presentationを直接対応付けません。同じAuthorization Errorでも、画面自体を利用できない場合、編集中に権限を失った場合、Bulk Actionの一部だけ失敗した場合ではProduct上の意味とFeedbackが異なります。

巨大な共通 `AppError` hierarchyを先に作らず、Feature固有のError interpretationから始めます。複数Featureで本当に同じsemantic contractが確認された場合だけ共通Conceptへ昇格させます。

Backendの生Error messageをそのままUser向け標準表示には使用しません。Authorization、Validation、Conflict、Not Found、Partial Failure、Unexpected Failure等をFeature contextで解釈します。

## Collectionの取得とNavigation実装

追加取得を伴うCollectionは[Collection Discovery](/design-system/patterns/collection-discovery)のInfinite Loading標準・例外条件・状態保持・Accessibility Contractに従います。WebではRelay Connectionに基づくcursor paginationを標準的な取得方式とし、具体的なcursor、fetch size、cache policy、virtualization、GraphQL query、SelectionとDetail Navigationの接続は対象Feature / ScreenとAPI契約で決定します。利用者向けのPagination / Load More / Infinite Loading選択を、Relayの内部取得方式と混同しません。

## Interaction & Feedback

InteractionはApolloやReact Hook Formのtechnical stateではなく、Userから見たlifecycleとして設計します。

```text
User Intent
    ↓
Action
    ↓
Pending
    ↓
Result
 ┌──┴───┐
Success Failure
    ↓       ↓
State Update / Feedback
    ↓
Ready for next interaction
```

各Feature / Screenでは少なくともTrigger、Pending presentation、Interaction availability、Success、Failure、既存Stateの維持、Recovery / Retryを検討します。

Pendingは原則として操作対象に最も近い場所で表現します。画面全体を操作不能にするのは、操作中に画面全体の整合性を維持できない場合に限定します。

既に成立しているUI Stateを、後続通信のPending / Failureだけを理由に破棄しません。Initial Load failureでは画面のError Stateになり得ますが、RefreshやLoad Moreのfailureでは既存Contentを維持し、必要なFeedbackとRetryを提供します。

成功時のFeedbackは[Design SystemのFeedback Pattern](/design-system/patterns/feedback)を正本とします。明示的な作成・保存・更新・削除・退会等のAction成功時は原則として成功Notificationを提示し、UIの変化だけを理由に省略しません。明示的な保存・確定Actionを伴わない設定項目の即時反映や、単なる選択・表示切替・NavigationではNotificationを機械的に重ねません。成功成立の確認、Navigation後の通知維持、Failure / RecoveryはDesign Systemと各Screen / API契約に従います。

Feedback presentationはError typeだけで決めず、Userがその情報をどこで、どの程度継続して必要とするかで判断します。

- Field: 特定入力に対する問題
- Inline: 特定操作・局所領域に継続的に関係する情報
- Notification: 一時的な操作結果
- Page-level Alert: 現在の画面を利用するうえで継続して認識すべき状態
- Blocked / Error State: 画面の主目的そのものを成立させられない状態

具体的なFeedbackのvisual / behavioral patternはDesign Systemが所有し、本ArchitectureではState lifecycle、ownership、interpretation boundaryを定義します。

## Formと認証

Form StateはReact Hook Formへ一元化し、Client側Validationは利用者支援として扱います。最終的なValidationと認可はAPIが保証し、Server Validation ErrorをFeature contextで解釈して対応Field等へ反映します。

認証はNext.jsがHttpOnly Session Cookieを保持し、必要なAccess TokenをAPI呼び出しへ渡すBFF寄りの構成を基本とします。TokenをBrowserの公開State、URL、Logへ露出しません。具体的な認証設定は[認証・認可・Privacy共通方針](/system/cross-cutting/authentication-authorization-privacy)とUser設計に従います。

## Testing Architecture

TestはCoverage数値のためではなく、責務に適した方法でBehavior、Contract、不変条件、失敗を確認します。

| 対象 | 主な検証 |
| --- | --- |
| Pure Logic | Vitest Unit Test |
| 意味のあるMapper / Transformation | Vitest Unit Test |
| React Adapter / Custom Hook | React接続自体にTest価値がある場合に検証 |
| Feature Component | Storybook、Interaction / Component Test |
| UI Component / Pattern | Storybook、Accessibility、Visual Review |
| 重要なUser Flow | Playwright E2E |

Pure LogicのUnit TestではReact、Mantine、Apollo、DOMを必要としない状態を基本とします。Testは対象Codeへ近接配置します。

StorybookはProduct Specificationではなく、実装を独立して観察・検証するための実行可能なExampleです。Visual Regression Test、Accessibility、Human Visual Review、E2Eの役割は[Frontend UI設計・開発方針](/system/frontend-ui-development)と[テスト設計](/test-design)に従います。

## Implementation Conventions

- `types.ts`、`constants.ts`、`utils.ts` をCode種別だけを理由に巨大な共有置き場へしません。
- Pure FunctionをCustom Hookへ変換しません。
- Apollo、Generated GraphQL Type、React Hook Form等の実装詳細を下位Componentへ漏らしません。
- Feature AからFeature Bへの直接依存を原則として避けます。
- 複数箇所で利用されるだけではFeature Componentを `ui` へ移しません。
- Frameworkから独立させること自体を目的に抽象化しません。
- FrontendへRepository、Service、Gateway等のLayerを機械的に導入しません。
- Barrel exportはArchitecture Boundaryを表現する目的がある場合に利用し、import短縮だけを目的に全Directoryへ導入しません。
- Generated Codeを直接編集しません。
- 新しいDirectory分類を導入する場合、その名称と意味をWeb全体で一貫させます。

### File / Componentの分割

File sizeやComponent sizeに固定の行数上限を設けません。大きさは責務混在を発見するsignalにはなりますが、それ自体を違反とはみなしません。独立したcontract、変更理由、Interaction lifecycle、Test / Story boundary、React非依存のProduct Judgment等が識別できる場合に分離を検討します。Code量を減らすことだけを目的にComponent、Hook、helperへ分割しません。

### Component API

PropsはGraphQL等の外部data shapeではなく、そのComponent自身が必要とする意味のある最小contractとして設計します。primitiveへ機械的に分解せず、Componentにとって意味のあるまとまりはModelとして渡せます。

Callbackはconsumer側の実装手段ではなく、Componentから見たeventの意味で `onSelect`、`onDelete`、`onLoadMore` 等と命名します。Booleanは肯定的で意味が明確な名前を使用し、`is` / `has` / `can` prefixを機械的に強制しません。

`children` / slotはComposition自体がcontractである場合に使用し、抽象化やProps数削減だけを目的に導入しません。Props spreadによってGraphQL object等の外部data shapeを暗黙にComponent contractへしません。

Controlled / uncontrolledはStateのauthoritative ownerで決定します。外部Compositionが所有する必要があるStateはcontrolled、Component内部だけで完結する一時的Interactionはlocal stateとします。同じStateを親子で同期保持せず、将来の再利用を予測したcontrolled/uncontrolled両対応や `defaultXxx` APIを先回りして追加しません。

### UI State Modeling

Loading、Error、Empty、Processing等はScreen Specification上の意味を保持します。排他的なStateを複数Booleanで表してinvalid combinationを許容する場合はdiscriminated union等で有効なStateを型として表現します。一方、独立して同時成立するStateを巨大な単一State Machineへ統合しません。

Empty、Error等もProduct上意味が異なる場合は区別します。主要なUI StateはStorybook等から自然に再現できるComponent contractとし、Story / Test専用PropsをProduction APIへ追加しません。

#### 非同期表示を持つComponentの状態・Layout Contract

Loading / Ready / Error等を一つの情報表示領域のVariationとして提供する場合は、取得元の都合ではなく、**利用者にとって一体として認識されるComponentの意味的な単位**で表示状態を設計します。複数のAPIやContextから情報が得られること、ある値だけ先に確定することを理由に、同じ情報領域の一部だけを無条件にReady表示へ切り替えません。部分表示がProduct / UX上必要な場合に限り、その独立した意味と状態境界を明示します。

- **状態の所有と受け渡し（必須）**: Feature / Composition側で非同期取得結果をComponent固有の表示Stateへ解釈し、描画ComponentにはGraphQLの生の`loading` / `error`や取得経路を伝播させません。同じ表示Stateを参照すべきTrigger・Panel等は整合する状態を共有します。
- **有効なProps Contract（必須）**: 排他的な状態によって必要な表示情報が異なる場合は、必要に応じて判別可能Unionを用い、Readyでのみ必要な情報をLoading / Errorでも必須にしません。Stateと無関係な固定値・ダミー値を要求したり、未取得データを空文字で偽装したりしません。小規模な単一Booleanで意味が十分に表せる場合は過剰なUnionを要求しません。
- **Layoutの一貫性（必須）**: Loading Variationを設ける場合、Readyとの共通の配置・Spacing・Alignment・Responsive Behaviorを維持します。Skeletonを別の独立した画面構造として複製せず、可能な限り同じLayout / Elementを使って表示を切り替えます。LibraryのSkeleton wrapperや共通Layout抽出等、実際に寸法・DOM・Accessibilityのcontractを保てる手段を選びます。未知のテキスト長等、必然的に変化する寸法まで完全一致を強制しません。
- **取得済み情報とError（必須）**: Refresh時に有効な情報がある場合は、既存のQuery UI State方針に従い原則維持します。初回Loadingと取得失敗を混同せず、Errorでは無期限にSkeletonを表示しません。Error時の情報・操作・復旧導線は対象のScreen / Component contractに従います。
- **検証（必須）**: Storybook / Visual Review等でLoading・Ready・Errorのうち実際に提供する状態を比較し、表示領域の位置・寸法・間隔、Layout Shift、Compact等のResponsive Behavior、読み上げや操作の継続性を確認します。静的な型・Lint検証だけでVisual / Behavioral Regressionの確認を済ませません。

この規則は**Skeletonの一律採用を意味しません**。Skeletonを採用する対象やComponent Loading Variationの標準化についての未決定事項は[Issue #277](https://github.com/hazuki3417/memoria-design/issues/277)で継続して扱い、既存の[Loading / Pending State 共通方針](/system/frontend-ui-development#loading--pending-state-共通方針)を維持します。


### Responsive Behavior

Responsive BehaviorはScreen Specification / Design SystemをSource of Truthとします。Spacing、Layout、Visibility等のvisual differenceはCSS / Mantine responsive APIを優先し、BehaviorやComposition自体が変化する場合だけ `useMediaQuery` 等によるJavaScript判定を使用します。

Desktop / Compactを別Featureとして分離しません。BreakpointをComponentごとに恣意的に追加せず、Design Systemの定義を利用します。Responsive切り替えによって同一Product Stateを不必要に失わず、主要なResponsive StateはStorybookで検証可能にします。

### Styling / Mantine

Mantine ComponentはFeature / UIから直接利用でき、Libraryを隠すことだけを目的としたwrapperを作りません。`src/ui` への抽出はMemoria独自のFeature-independentなvisual / interaction contractが成立した場合に行います。

Styleも対象責務の近くへ配置し、汎用 `styles/` Directoryを標準化しません。Mantine Props、CSS Module等は責務を最も明確に表現できる方法を選びます。Design System上意味を持つ値はTheme / Tokenを利用しますが、局所値を機械的にglobal token化しません。Mantine等のLibrary内部DOMや生成classへ依存せず、公開されたextension pointを利用します。

### Async Operation / Error

External / Library ErrorをそのままFeature UI contractへ露出しません。ExpectedなProduct FailureはFeatureのState / Resultとして解釈し、unexpected exceptionと区別します。Backend / GraphQL / Libraryの生Error messageをUser向け標準表示に使用せず、Screen Specificationに基づくpresentationへmappingします。通常発生し得るProduct FailureをError Boundaryへ委ねません。

Async OperationはtechnicalなPromise StateではなくProduct上のlifecycleとして表現します。単純なOperationは単純なStateで実装し、複雑性が生じた場合だけ明示的なState Modelへ昇格させます。Pending中の操作可否、Cancel、Retry、Navigation、二重実行はProduct Behaviorとして扱います。

同一Operationの意図しない重複実行をUIで防止しますが、必要なidempotency / concurrency保証をFrontendだけに依存させません。Optimistic UpdateはLibrary capabilityではなくProduct Behaviorとして妥当でrollbackが定義できる場合に利用します。非同期であることだけを理由に汎用 `useAsync` 等へ抽象化しません。

### TypeScript Value / Escape Hatch

Primitive Valueを一律にValue Object / branded typeへ変換しません。ID、Date / Time、URL等は少なくとも命名でProduct semanticsを保持し、型安全性に実益がある場合に型を強化します。有限なProduct Stateにはunion等を活用します。Display stringや外部表現を無自覚にProduct contractへ伝播させません。

GraphQL由来の `null` をFeatureへ機械的に伝播させず、Feature上のabsence semanticsに合わせます。`null` / `undefined` の全面禁止は行いません。

`any`、type assertion (`as`)、non-null assertion (`!`)、`@ts-ignore` を型Errorを消す通常手段として使用しません。型不明な外部値には `unknown` を使用し、Boundaryでvalidation / narrowingします。不可避なescape hatchはintegration boundaryの最小範囲へ隔離します。意図的な型Error抑制が必要な場合は理由を伴う `@ts-expect-error` を優先し、型推論を維持してcontractを検証できる場面では `satisfies` を活用します。

### Comment / JSDoc / TODO

CommentはCodeから自明な「何をしているか」の翻訳ではなく、Codeだけでは表現できない「なぜ」を残すために使用します。Commentで複雑な設計や不明瞭な命名を補う前にCode構造を改善します。

JSDocを全exportへ機械的に付与せず、型だけでは表現できない非自明なPublic Contractがある場合に使用します。CommitされるTODO / FIXME / HACKは原則として追跡可能なIssue等へ関連付け、理由と解消条件を明確にします。長期的な設計判断やProduct SpecificationをCode Commentだけに保持しません。

### Import / Dependency

Module内部はrelative import、Architecture Module外部は `@/` absolute importを基本とします。Architecture Boundaryを越える場合はModule rootのPublic APIを経由し、Feature / UI / Infrastructureの内部Fileへdeep importしません。Module内部から自身の `index.ts` を逆輸入しません。

Feature間の直接dependency、UIからFeatureへのdependency、InfrastructureからFeatureへのdependency、route-private Codeのroute間共有を避けます。`import type` もArchitecture dependencyとして扱います。Circular dependencyはimport techniqueで隠さずownershipを再評価します。

### Environment / Configuration

Environment variableはexternal runtime integrationとして扱い、Feature / UIから `process.env` を直接参照せず、`infrastructure/environment` 等のownerでvalidation / normalizationします。Server-only secretとClientへ公開可能なconfigurationを明確に分離します。

Environment configurationによってProduct Ruleを暗黙に表現しません。Feature FlagはEnvironment variableと同一視せず、実際の要件が生じた時点でevaluation ownership、lifecycle、removal条件を含めて設計します。Raw environment valueへnon-null assertionで依存せず、Application Boundaryでconfiguration contractを検証します。

### Security-sensitive Coding

AuthenticationとAuthorizationを分離し、Product上の権限判断をAuthentication状態だけから推測しません。Frontend上の表示制御をsecurity boundaryとせず、最終AuthorizationはBackendで保証します。

Token、Cookie、Session、CSRF等の認証技術詳細をFeatureへ漏らさず、適切なInfrastructure Boundaryで一貫して扱います。URL、Form、Storage、File等の外部inputを信頼済みとして扱わず、riskとcontractに応じてBoundaryでvalidationします。

Raw HTML、redirect、external URL、file upload等のsecurity-sensitive処理はad-hoc implementationを避けます。Frontend validationをsecurity guaranteeとみなさず、Secretや不要なsensitive dataをClient / Logへ露出させません。Auth、Cookie、CSRF、Environment exposure等のsecurity contract変更は通常のRefactorとして扱わず、明示的なsecurity reviewを必要とします。

### Accessibility
### Semantic HTML・Accessible Name・Label（2026-10-21合意）

Componentの操作要素は、テスト用Selectorより先に、利用者と支援技術へ伝わる意味を基準に設計する。既存のUI Library（Mantine等）が提供する適切なNative Element・Role・Keyboard behaviorを優先し、不要なARIA Roleや独自Interactionを追加しない。

- Button、Input、Dialogなどは適切なSemantic HTMLとRoleを使用する。Roleはテスト都合で付け替えない。
- 操作可能なControlは役割を識別できるAccessible Nameを持つ。IconのみのButtonや同名の複数操作は、Contextと対象を識別できる名前を検討する。可視Labelがある場合は意味的な整合性を保つ。
- Form Inputには目的を示す可視Labelを関連付けることを基本とする。Placeholderは入力例・補助情報であり、Labelの代わりにしない。画面の表示仕様上可視Labelがない場合は、既存契約とAccessibilityを照合して適切な代替名付けを判断する。
- `aria-label` や `aria-labelledby` は必要な場合に使用する。Labelが既に適切に提供されている場合、競合する名前を重複指定しない。
- 選択状態・無効状態・Errorとその理由は、UI Libraryの契約に沿って支援技術とKeyboard操作へ伝える。特定のARIA属性だけを実装の正しさの代用にしない。
- `data-testid` は意味的な識別が不十分で、安定した検証点が必要な場合の補助手段。DOM/CSS構造への依存を避けるために利用できるが、利用者向けのRole・Name・Labelの欠落を隠す目的では追加しない。

既存Componentの抽出・共通化では、Visual / Behavioral / Responsive / Focus contractを不変条件とする。Accessibility上の改善が必要な場合は影響する名前・Keyboard・操作・状態表現を確認し、仕様変更となる内容を暗黙に混在させない。既存の各Consumer固有のCapabilityを維持する。


Native semantic HTMLと既存Componentのaccessible behaviorを優先し、ARIAによる独自再実装を避けます。重要な操作はMouse / Touchだけに依存せずKeyboardでも利用可能にします。Interactive controlには認識可能なaccessible nameを持たせ、Form ErrorやStateを色・視覚表現だけで伝えません。

Dialog等ではfocus managementを含むInteraction contractを維持します。Responsive変更によって操作や情報へのaccessを失わせません。AccessibilityはDesign / Component contractの一部として扱い、可能な範囲をautomated testで検証しますが、自動検査だけを適合性の保証とはしません。

### Performance

PerformanceをProduct Qualityの一部として扱いますが、具体的な要件、明確なcost、measurementなしに予防的な複雑化を行いません。`useMemo`、`useCallback`、`memo` を機械的に使用せず、必要性を説明できる場合に利用します。Derived StateをPerformance目的で複製しません。

Large List、virtualization、code splitting等は実際のscaleとUX contractを踏まえて判断します。Mediaは用途に適したthumbnail / preview / original等のrepresentationを利用し、Original assetの不要な取得を避けます。GraphQL / Network optimizationのためにFeature ownershipやUse Case Boundaryを壊しません。Performance問題は可能な限りmeasurementに基づいて改善します。

### Test Levelの選択

Testは実装単位ではなく、守るべきcontractに最適なlevelで記述します。React非依存のProduct Judgment / State TransitionはVitest、Userから観測可能なComponent BehaviorはComponent / Interaction Test、visual / state variationはStorybook、重要なsystem-wide User FlowはPlaywrightを基本とします。

Implementation detailへのTest dependencyと過剰なinternal mockを避けます。Bug regressionは再発を防止できる最も低い適切なTest Levelへ追加します。固定のTest Pyramid比率やCoverage percentageを品質目標とせず、重要なProduct / Behavior contractが検証されていることを優先します。

### Quality Gate / Definition of Done

Implementationの完了はCode changeだけでなく、変更によって影響を受けるcontractの検証までを含みます。Repositoryで定義されたstatic checkと関連Testを実行し、UI変更ではScreen Specification、Prototype、既存contractと比較してvisual / behavioral / responsive regressionがないことを確認します。

Storybook、Code Generation、Documentation等も変更内容に応じて更新・検証します。すべての変更へ同一のQuality Gateを機械的に適用せず、影響するcontractに応じて必要な検証を選択します。実行できなかった検証を成功扱いせず、verified / unverifiedを明確に報告します。

### Coding Agent Implementation Workflow

Coding Agentは実装前にGitHub上の最新Source of Truthと対象implementationを確認し、変更するcontractと維持するcontractを特定します。その後、意味のownerを決定し、現在必要な最小のArchitectureで実装します。

仕様・Architecture上の重要な未決事項を実装者判断で補完せず、必要な合意を得ます。将来利用を予測したgeneric abstraction、shared layer、base component、factory、汎用Hook等を先回りして作りません。「最小」は既存Behaviorや必要なCapabilityを削る意味ではありません。

実装後は影響するcontractを検証し、Refactorでは変更前とのvisual / behavioral regressionも確認します。新たに確定した長期的判断や未解決事項は適切なSource of Truth / Issueへ反映します。GitHubへのwriteは成功responseだけで完了とせず、最新状態を再取得して実際の反映を確認します。

### Source Codeの自動編集と改行

AI、GitHub API、script等を利用してSource Codeを作成・更新する場合、tool呼び出し用のescape表現と、実際にfileへ書き込むSource Codeを区別します。

- 改行が必要な箇所へ、文字列としての `\\n` や `\\r\\n` をSource Codeへ埋め込みません。file contentには実際の改行文字を書き込みます。
- 複数行のSource Codeを組み立てる場合は、可能な限りmultiline textをそのままwriteし、既存Codeへescape済み文字列を連結する方法を避けます。
- search / replaceで複数行を挿入する場合、replacementへescape表現がそのまま残らないことを確認します。
- Source Codeへのwrite後は、成功responseだけで完了とせず、変更したfileを再取得またはlocalで確認し、意図しないliteral escape sequence、構文崩れ、重複挿入がないことを確認します。
- 同じ方法で複数fileを生成・更新した場合、1件でescapeや構文の問題が見つかった時点で、同じ方法を使用した変更も確認対象とします。
- format / lint / typecheck等のQuality Gateを実行できる環境では、変更完了を報告する前に対象変更へ適切な検査を実行します。実行できない場合は未実施であることを明示し、write後のSource確認を最低限行います。

これらはLF / CRLFの選択を新たに定義する規則ではなく、自動編集時のserializationによってSource Codeへ意図しないescape文字列を混入させないための実装規約です。

## 命名と品質

Directory名は原則kebab-caseとし、React Component FileはPascalCase、Hookは `useXxx.ts`、React非依存のTypeScript責務はcamelCase Fileとします。Storyは `<Component>.stories.tsx`、Testは対象Fileに対応する `.test.ts` / `.test.tsx` として近接配置します。GraphQL Operation名はPascalCaseとし、1 Operationを1 `.graphql` Fileに配置してFile名をOperation名へ一致させます。Operation-private Fragmentは同じFileに置けますが、複数Operationで同じsemantic contractとして共有するFragmentは独立したFragment名のFileへ分離できます。Fragment名はsemantic ownerと対象が識別できる名称にします。

TypeScriptのstrictな型検査を基本とし、`any` を避け、外部から受け取る未知の値は `unknown` から絞り込みます。FormatとLintには既存のBiomeを使用し、同じ責務のESLintやPrettierを追加前提にしません。検証は[テスト設計](/test-design)とGitHub ActionsのQuality Gateに従います。
