## 目的・正本

- `content/system/web/implementation-conventions.mdx` のState Ownership・Form規約をSettingsへ適用する。
- FormのDraft / Dirty / Field ValidationをReact Hook Form（RHF）で一元管理し、Apollo ClientをGraphQL Server Stateの共有表現とする。
- 保存順序、Debounce、Mutation、Cache更新、Rollback、Retryなどの既存振る舞いとUI / Responsive / Storybook Contractを維持する。
- 新しいSettings UIや汎用Form Frameworkの構築ではなく、既存実装の責務抽出として進める。

## Action / Feedback実装の一貫性（2026-11-12合意）

Personal / Community Settingsで現在見られるCustom Hookの責務・粒度、Action結果からFeedbackまでの実装方式、状態・操作の公開名、Feedbackモデルの組み立て場所の差異は、**これまで内部構造を個別に委ねて実装した結果生じた、意図しない不整合**として扱う。既存コードの違い自体を、合意済みの例外や維持すべきArchitecture Contractの根拠にしない。

- **同種の操作は共通の処理パターンを持つ**：外部接続を持つAction → 共通の保存結果契約（`SaveActionResult<T>`）→ Form / 保存状態のOwner → 意味的なFeedbackと復旧操作 → UI表示という責務の流れを基準とする。この記述は概念上の責務であり、一律のファイル数、階層、Generic Hook / Componentを要求しない。
- **明示保存の比較基準**：Profile / Community Name / Community Aliasについて、同じ役割のHookの公開状態・操作・命名、Resultの解釈、Validation、Unknownの照会・再送・破棄、Feedbackの導出・描画・通知を比較し、設計上の理由のない実装方法のばらつきを是正する。特定Featureの現在の実装を無条件に全体へ採用しない。
- **異なるケースの扱い**：通常の処理パターンと異なる必要がある場合は、個別の例外として理由・適用条件・維持すべきContractを明示するか、反復的に必要な処理方式なら独立したパターンとして定義する。自動保存はTrigger、入力継続、Queue、Preview、Session寿命の点で明示保存とは別パターンとするが、共通するAction結果やFeedbackの意味を重複定義しない。
- **例外の根拠と回帰**：Domain制約、保存対象、状態の寿命、画面固有の必要な表示・操作などを根拠に、必要な差異だけ保持する。例外の判断は既存コードの形だけから行わない。内部構造の整理で合意済みの文言・情報・レイアウト・操作・状態表現・Responsive Behaviorを暗黙に変更しない。
- **実装判断**：共通化の実現方法や新しいHook / Feedback Componentの境界は、実コード・Consumer・Story/Testを比較して検討する。重要な境界変更や仕様変更は人間と合意してから実装する。本節への反映はリファクタリング完了・動作検証済みを意味しない。

## Settings共通Loading / Errorと責務境界

本節はPersonal Settings（Profile / Preferences / Account / Usage）およびCommunity Settings（General / Members / Preferences / Usage）の**画面領域に共通する契約**を扱う。Personal SettingsはUser本人の独立したdestinationであり、Community切替によってPersonalの値・集計scopeは切り替えない。各Screen Specification、特に[User Settings](/screens/user-settings)、[Community Settings](/screens/community-management)および[Usage](/screens/usage)の機能・権限・復旧仕様を上書きしない。実装の具体的なpath・Storyのexport名・テストRunnerは`memoria-web`を正本とする。

### Loading / Errorの表示契約

- 初回Loading、必須データ欠落、初回取得失敗でもApplication Header、Application Shell、Settings Navigationを保持し、選択されたPageの**Content領域のみ**をLoading / Errorへ切り替える。
- 共通の`PageStatusBoundary`でLoader / Error / Readyの表示を行う。LoaderはContent領域中央に配置し、短時間の取得で点滅しないよう**300ms遅延**する。
- 初回取得失敗・必須データ欠落では再読み込みを案内する共通Errorを提示する。**共通Boundary自体は再試行ボタンや再取得処理を所有しない。** Usageの初回取得ErrorではFeature UIが「再試行」を提供する例外があり、対象Custodianの再取得・Error→成功/再失敗は[Usage UI設計](/screens/usage-ui-design)と[Usageテストマトリクス](/system/web/usage-test-design)を正本とする。
- 取得済みの有効なDataが存在するBackground Refetchでは既存Contentを保持し、Loader / Skeletonへ戻さない。Background Refreshの失敗は正常に取得済みの内容を破棄せず、非ブロッキングなError Notification等で伝える。
- UsageはSkeletonを表示しない。確定済みの集計情報がないInitial Loading / Errorでは集計表を表示せず、共通BoundaryのLoading / Errorを使用する。Accountも必須CurrentUserを待つ。Authorizationの喪失は単なる取得Errorと同一視せず、Community Membership喪失時は非公開情報を保持表示せず安全なdestinationへ遷移するなど、[Community Settings](/screens/community-management)と[Application Information Architecture](/system/application-information-architecture)の権限契約を優先する。
- Visual / Interaction / Responsive検証ではWide・CompactでShell / Navigationが維持されること、Loader遅延、Background Refetch、Usage固有Retry、権限喪失を確認する。共通Boundaryの各状態はそのComponentのStory、Usage固有UIはUsageのStory / Integrationで確認する。

## 2026-11-02 合意：Zod / zodResolverの適用と共通化の境界

- Settingsの各独立RHF Formに、フォームのInput / Outputを区別したZod Schemaと`zodResolver`を適用する。入力中のDraftはRHFが所有し、ZodはValidationと保存時の正規化を定義する。

- Personal PreferencesのPatch保存は入力イベント起点、Community Accentは有効HEX入力だけを既存保存Controllerへ通知し、`handleSubmit`へ保存方式を変更しない。未完成HEXをRHF Draftとして保持する。

- Community名・Tag名・Group名のように複数ユースケースで同一ドメイン制約が必要になれば、その段階で各ドメインのSource of Truthを確認して抽出する。**今回の作業はPersonal / Community Settingsのみ**とし、他のFeatureへの共通化を行わない。
- `react-hook-form`、`zod`、`@hookform/resolvers`は既存依存を利用する。Backend最終Validationを置き換えない。
- Git commitの`[skip ci]`はPR作成済みブランチへの追加コミット時のみ付ける。PR未作成ブランチのコミットには付けない（今回の作業指示であり恒久的設計規約ではない）。

## 2026-11-02 合意：Zod OutputとGraphQL InputのMapping

- Form内のDraftはRHFが所有する。Zod Schemaは入力Validation、Trim、空欄からNullable値への正規化など、Applicationが扱う検証済み値の生成に責任を持つ。
- GraphQL固有のInput Shape、Generated Type、Enum変換、Partial Patchの構築はAction / GraphQL Boundaryに所属する。単純な `{ input: { communityId, name } }` のような組み立ては接続箇所で直接行い、Mapperを必須としない。
- 複雑な構造変換や独立した契約が存在する場合だけPure Mapperを抽出する。既存の `src/features/settings/preferences/userPreferencesGraphqlAdapter.ts` はその実例であり、`toGraphqlUserPreferencesPatch` が入力PatchをGenerated GraphQL Enumへ変換する。既存の `userPreferencesGraphqlAdapter.test.ts` を対応Testとして維持する。
- Schemaの型は `z.input` と `z.output` / `z.infer` を意図に応じて使用し、Mutation InputはCodegen型をGraphQL Boundaryで使用する。両者が同じ形なら直接渡せるが、等価であると推測してMappingを省略しない。
- Community Aliasの空文字 `null` 化はApplicationへ渡す正規化値であり、Zodの責務とする。SchemaにGraphQL依存を導入しない。
- 本変更では既存のMutation・保存Queue・Rollback・UI・Storybook Contractを変更しない。Settings以外への横断的Mapper / 共通Schemaの導入は対象外。

## 2026-11-02 合意：Mapperの型I/F契約

- **フォーム専用Mapper**は、入力を対象Schemaの `z.output<typeof schema>`（または `z.infer`）、出力をGraphQL Codegen生成Input型として明示する。フォームの未検証InputをMapperへ直接渡さない。型契約に加えて近接Unit Testで変換結果を保証する。

各Settings Formの初期値はForm所有者の`defaultValues`に直接記述する。ZodにRHF初期値生成の責務を持たせない。初期値構築が複雑になるか、複数のFormで実際に同じ初期化ロジックが必要になった場合のみPure Functionを検討する。初期値とサーバー再取得時の`reset`は別の契約として扱う。

## 2026-11-02 合意：Form Draftの同期UX

- Formは画面で確認した初期値から編集する。Apollo Cacheの内部差異や多端末競合表示を共通Form機能として扱わない。
- 未編集のDraftはServerから届いた新しい値を表示してよい。編集中・保存中・保存失敗で未確定の値があるときはその入力を上書きしない。Context変更時は新しいContextとして初期化する。
- 保存成功時は確定した値を保存基準へ反映する。明示保存中は入力を停止する。自動保存等で保存中に新しいDraftが生じる場合や応答が遅れて届く場合も、古い保存応答で新しいDraftを消さない。
- 明示保存には[Form Actionの接続境界と共通動作](/system/web/implementation-conventions#form-actionの接続境界と明示保存の共通動作)を適用する。自動保存には入力継続・Queue・Preview等の固有の仕組みがあり、手動保存の入力停止条件を適用しない。保存Queue、Rollback、Cache操作をこの方針のためだけに新しい共通Layerへ移さない。
- Community Nameは今回の合意でServer Props変更時の無条件上書きを廃止し、未編集時のみ自動追従する。Interaction Storyで再取得時の未編集同期と編集中保護を検証する。
- Profile・Alias・Preferences・Accentの既存挙動は、追加の回帰確認なしに広範囲を変更しない。特に自動保存中のサーバー応答とRollbackはそれぞれ既存の保存契約を優先し、個別のテストで確認する。

## 共通実装ルール

### 初期値と同期

- `useForm<FormValues>({ defaultValues: ... })` に初期Server Snapshotまたは既存Story Fixtureを渡す。RHFの`defaultValues`は通常の再Renderだけでは自動更新されないため、同期が必要な場合はフォーム単位で明示する。
- Dirtyの意味は現行契約が優先。現行がTrim/正規化後に比較するFieldでは、RHFの生の`isDirty`をそのまま保存可否に転用しない。`getValues`・`useWatch`で値を取得し、Pure Functionで正規化した値を保存基準値と比較して導出する。
- 保存成功時は確認済みServer Response / 保存対象の値を基準に`reset`を検討する。ただし、保存中の新しいユーザー入力を上書きしない。入力が凍結される明示保存フォームと、操作が継続する自動保存フォームとで同期方法を分ける。
- Apolloの`cache-and-network`再取得のたびにDraftを無条件`reset`しない。現在の同期挙動に変更が生じる場面は「未決定事項」に記す。
- 明示保存Formで再取得値を採用してよいかは共通Pure Logic `resolveConfirmedSourceSync`で判定し、`unknown`中は非採用、確定直後の古いQuery echoは非採用、未編集時だけDraftを同期する。保存済み基準、前回Query値、待機中echo、実際のRHF `reset`は各Formが所有する。ProfileのRetryable中に`reset`しない条件は引き続きProfileが指定する。
- Field ValidationとServer保存失敗は別物。RHFの`errors`は入力制約を中心とし、`retryable`/`blocked`/保存中・通知は現行のInteraction Stateと表示契約を維持する。
- React Hook FormはApollo Cache、Mutation実行順序、Queue、Context AccentのAuthorityを所有しない。
- `mode`・Validation表示時機・`onBlur`等は既存UIのError表示時機を回帰条件として選択する。初回表示で空欄エラーが出るStoryなどを消さない。

### TextInputの接続

- `Controller`でMantineのControlled Inputへ`field.value`/`field.onChange`を橋渡しする。可能なら`field.ref`/`field.onBlur`も接続し、Focus / Accessibilityを維持する。
- Trim、空欄許容、Unicode code point等のドメイン判断はPure Functionで行う。必要に応じて`rules.validate`へ渡すが、Serverからの制約強化を推測で追加しない。
- Save前のGuardは入力Validity、正規化後Dirty、権限、保存中/blockedから導出する。重複したBoolean Stateを増やさない。

## 2026-11-02 合意：保存Feedbackは自動・明示保存に共通する契約

**適用対象の明確化**：保存結果の意味、Field / Form Errorの分類、表示位置、復旧操作、SaveStatusのPresentation責務は、**自動保存専用ではなく、ユーザーが明示的に保存する操作も含む共通契約**とする。この後の「自動保存」という章は、入力イベントから保存を開始する場合のQueue・Debounce・Preview・寿命に関する**追加的な詳細**を定めたものであり、共通Feedbackの適用範囲を狭めない。

| 関心事 | 共通する契約 | 操作別の決定 |
| --- | --- | --- |
| 保存の結果 | Confirmed / Rejected（Field・Form・Domain）/ Retryable / Blocked / Unknownを判別し、Draftを保護 | 保存トリガー、送信順序、二重Submit / Queue、再試行安全性 |
| Short Status | `SaveStatus`は表示専用Component。Pending / Saving / Confirmed / Error等の短い状態を、Layoutを変動させないSlotへ描画できる | Header右Slot、保存ボタンのLoading等、表示自体の要否・適切な場所 |
| 詳細Error | Field ValidationはField近傍、復旧手順を要するErrorはForm上部など解決操作が可能な場所へ。生のGraphQL Errorを直接表示しない | Domain固有の手順、Field Groupの対象、Errorを表示するContainer |
| 成功Feedback | Confirmedのみ成功として扱い、Refetch失敗と区別する | 明示保存は原則Notification、自動保存は控えめなInline Status |
| 離脱警告 | 操作の重要度・喪失影響・復旧可能性で要否を判断 | 軽微な自動設定保存には一律警告を要求せず、重要な手動操作も個別に評価 |
| Layout / Accessiblity | 短いStatusの出現・消失でHeaderを伸縮させず、Error内容の発見性と読み上げを保証 | DialogなどHeaderを持たない操作にHeader Slotを強制しない |

**Component境界**：`SaveStatus`（短い状態のPresentation）、既存の`FeedbackAlert`（理由と解決操作）、`Notification`（明示操作の完了等）は再利用可能な責務として扱う。`SaveStatus`を自動保存専用にしない。`PageHeader`を拡張する場合、既存Consumerのタイトル・説明・高さ・Responsive契約を不変として、任意のtrailing Slot等でcompositionする。共通Componentは表示状態のOwnerではなく、Form / FeatureがOperationのResultを解釈しUIを選択する。

**現時点の判断境界**：タイトル右Slotと詳細ErrorのA案（Headerの短いStatus＋Form側の持続Alert）は有力なUI提案であり、採用とCompactのレイアウト・時間閾値は別途合意する。手動保存時にNotificationを維持する既存合意を、Header Statusの追加だけで暗黙に廃止しない。

## 2026-11-02 合意：保存結果とForm FeedbackのUI/UX

この章は2026-11-02の追加合意による**次段階の設計基準**である。前章のRHF移行時に維持した既存Feedback仕様を自動的に変更したものとは扱わない。実装変更は各Featureの状態・Story・Screen Contractを比較した上で別途行う。Web共通原則は`implementation-conventions.mdx` の「Form Feedback / Validation UX」を正とする。

### Feedbackの選択基準

| 事象 | 主要な表示先 | 次の行動 |
| --- | --- | --- |
| ClientまたはServerの単一Field Validation | 該当FieldのError | Fieldを修正 |
| 関係Field間の不整合 | 関連Fieldの近傍またはForm Alert | 関係する入力を修正 |
| Form全体のValidation・業務制約 | Form Alert | 指示された条件を修正 |
| 明示保存の成功 | 成功Notification | 必要なら次の操作 |
| 自動保存の成功・進行中 | 控えめなInline Status。通知連発なし | 原則不要 |
| 明示保存の一時失敗 | 消えないForm Alert | Draftを保ったまま再試行 |
| 保存結果を確認できない | Form Alert（未確定と明示） | 状態を確認し、重複保存に注意 |
| 操作権限喪失・継続不可 | Form Alert | 再読み込み・権限確認等 |
| Background Refetch失敗（表示済みデータあり） | 非ブロックのNotification / Status | 必要なら再取得 |
| 初期取得失敗（フォーム利用不能） | Page Error | 再取得・画面離脱 |
| 破壊的な明示操作の成功 | 成功Notificationまたは遷移先の状態表示 | 完了を確認 |

Validationは未操作時に表示しない。原則BlurまたはSubmit後に表示し、その後の編集に追従して解消する。保存可否を判断する内部Validationと、Error文言を提示するタイミングは別に管理する。Field Errorは該当入力に関連付け、Form Alertは保存操作と問題内容が分かる位置に置く。同じ失敗をNotificationとAlertの両方で繰り返さない。

### 非同期保存・結果契約

- Form Ownerは編集中のDraftと見た目のError / Statusを管理し、API / Application Boundaryは成功、入力の不備、業務制約、再試行可能な失敗、継続不可、結果不明を意味的に識別できる情報として返す。例外文言やHTTP codeだけでUI分岐しない。
- 手動保存はSubmit開始時に検証し、成功が**確認できた値**のみ保存基準へ反映する。Submit後の追加編集を以前の応答で消さない。失敗時はDraftを保持し、可能な修正・再試行・状態確認の行動を示す。
- 自動保存は入力イベント起点のPatch・保存順序・追加編集の保護を保証し、静かな保存状態を提供する。成功後に保存済みFieldのDirtyを適切に解消するが、未送信・in-flight・失敗中の値は保存済みと誤認しない。
- 保存の失敗は一律の`false`や汎用例外に潰さない。Promise rejectを放置せず、UIに必要な失敗分類が届くようにする。フィードバックの表示責務が接続層とForm層に分散し、重複通知されないようにする。
- 自動保存失敗時に`Rollback`するか、未保存Draftを残して再試行させるかは入力の種類・即時Preview・誤解のリスクにより選択する。一律のRollback義務は設けない。

| Backend | 最終Validation、認可、永続化、確定した結果・機械判定可能なError情報を提供 | Frontend向け表示位置・Notification選択 |
| GraphQL / Application Boundary | Mutation結果・GraphQL Error・通信Errorを取得し、根拠のある結果情報へ変換。更新確定と後続Refetch失敗を区別 | Notificationの直接表示、Form Draftの変更、未知のErrorをField Errorと推測 |
| Form Owner | RHF Draft、保存操作、Field / Form Error、確定済みBaseline、Resultごとの再試行導線 | GraphQL例外メッセージの文言解析、Apollo Cache同期Layerの所有 |
| Feedback UI | 与えられたErrorと保存状態をField / Form / Inline Status / Notificationとして描画し、支援技術へ通知 | 保存結果・ビジネスルールの独自判定 |

既存`Promise<boolean>`や接続側の失敗Notificationは、Featureに結果の意味を伝達できない。Community Nameの後続改修では成功のみを`true`とし、失敗理由を失うI/Fを廃止する。保存成功NotificationはForm Ownerのみが発火させ、保存失敗の主表示はForm Alertとする。

### 結果分類と振る舞い

| 結果 | 判定根拠 | Draft / Baseline | 主表示と次の操作 |
| --- | --- | --- | --- |
| confirmed-success | 更新Mutationの確定結果（更新対象と応答値を照合） | Confirmed値のみBaselineへ反映。送信後の新Draftは維持 | 手動：一度だけ成功Notification／自動：静かな保存済みStatus |
| field-invalid | APIがFieldを機械判定可能に特定できる / RHF・Zod Field Validation | Draft保持。Baseline不変 | 対応FieldのError、修正後再検証 |
| form-invalid | 入力群の関係または業務制約。Fieldへ一意に帰属しない | Draft保持。Baseline不変 | 持続するForm Alert、修正する条件を提示 |
| retryable-failure | **再試行してよいと確認できる**一時失敗 | Draft保持。Baseline不変 | 持続するForm Alert＋再試行 |
| blocked | 権限喪失・認証切れ等の継続不可が確認できる | Draftは可能な限り保持。保存操作は抑止 | 持続するForm Alert＋権限確認・再読込・認証導線 |
| unknown-outcome | 書込要求の応答がない等、反映の有無を断定できない | Baselineを勝手に進めない。Draft保持 | 未確定と明示。状態照会を先に案内。再送安全性が未確認なら自動再試行しない |

`BAD_REQUEST`は必ずしも単一Field Validationではなく、`INTERNAL_SERVER_ERROR`も再試行安全性の証明にならない。通信Timeout・切断でMutation実行済みの可能性がある場合も、安易に`retryable-failure`へ変換しない。

**Mutation成功とRefetch失敗**：Mutationの確定結果を取得後、後続`refetchQueries`が失敗した場合は保存成功を取り消さず、「データ更新の再確認ができない」別の非ブロック状態として扱う。MutationのResponse確認前の通信失敗は`unknown-outcome`候補として扱い、原因別に判定する。現行の`awaitRefetchQueries: true`や接続側の保存判定は、この区別を保証するために見直し対象とする。

**Client ValidationとError表示**：Zod/RHFが検証を担当する。未操作時はエラー文言を表示せず、BlurまたはSubmit後に表示する。いったん表示されたField Errorは入力変更に追従して更新・解消する。保存ボタンの可否を決める内部妥当性判定は表示契約と分離する。Server Field ErrorはField Pathを根拠にRHF`setError`へ反映し、関連する入力の変更で適切に再検証する。単純な通信失敗に`setError`を使わない。

**同一Resultの表示**：Fieldに帰属する失敗はField Error、Form全体・保存操作に属する失敗はForm Alertを主とする。同一結果をNotificationとAlertに二重表示しない。持続的なエラーは通知が消えても再試行導線が残ること。読み上げ・Focus移動はエラー発生時の優先順位を考慮し、入力中に無闇にFocusを奪わない。

### 明示保存Actionの結果インターフェース

明示的な保存操作では、各Featureの保存ActionがGraphQL Mutationの結果と失敗を解釈し、Formへ`Promise<SaveActionResult<TValue>>`を返す。FormはGraphQL ErrorやApolloの例外を直接分類せず、利用者の操作可否・Validation・復旧手順を結果の意味から決定する。

| 結果 | Formへ渡す情報と保証する動作 |
| --- | --- |
| `confirmed` | `value: TValue`。Mutationで確定した保存値を渡し、保存済み基準に採用する。送信値とServer確定値が異なる場合は確定値を優先する |
| `validation` | `violations`。公開された入力違反のField Pathを保持する。Fieldを特定できなければForm全体のErrorとする |
| `retryable` | 明確に再試行可能と判明した失敗。Draftを保護し、明示的な再試行を案内する |
| `blocked` | 利用者に提示できる`feedback`を伴う継続不可。公開された理由だけから安全な説明を組み立て、保存と入力を停止する |
| `unknown` | 保存成立を否定できない失敗。自動再送を避け、現在値の照会と利用者による明示的な解決を待つ |

`useExplicitSave`は上記の結果、送信前の入力妥当性・変更有無、照会結果を受けて、保存中・Blockedの入力停止、通常の保存可否、重複送信防止、Unknown復旧を扱う。RHF Draft、Zod、Field Error、保存済み基準と再取得の同期、画面ごとのFeedback文言は各Formが所有する。GraphQLの型・例外分類はForm Hookへ戻さない。

Storybook / Prototypeでは本番のGraphQL Mutationを使わずに同じForm UIへ意味的なAction結果を渡し、例外を返す既存Story Mockの変換はStory側で行う。環境別のAdapterをFormの公開Propsへ追加しない。

処理が予期せず失敗した場合、保存が拒否されたと断定せず結果不明と扱う。保存中を表す状態は結果を受け取って解除するが、失敗状態は自動消去しない。Context ID変更後に旧Contextの応答を新しいFormへ反映させない。自動保存のQueue・Snapshot・結果確定処理にはこの明示保存Actionの契約を無条件に適用しない。

### 手動保存：状態遷移

1. `pristine`：初期値を表示。取得値更新へ追従。未操作のValidation Errorなし。
2. `editing`：RHF Draft保持。編集対象Fieldは新しい取得値で上書きしない。
3. `submitting`：Submitで検証したSnapshotを送信する。入力と同じ保存Actionを停止し、二重送信を防止する。Draftを保持し、遅延応答で別Contextや新しい状態を上書きしない。
4. `confirmed-success`：確定したSnapshotをBaselineへ反映。追加編集がない場合のみRHF表示値へ同期。成功Notificationは操作単位で一度だけ。
5. `field-invalid`／`form-invalid`：Errorを該当場所に保持。正しい編集・再試行で解消。
6. `retryable-failure`：Draft維持・Form Alert・再試行。失敗原因が残っている間は成功を表示しない。
7. `blocked`：Draftを保持したまま入力と保存を停止する。無意味な再送を許さず、判明している理由と可能な次の操作を案内する。
8. `unknown-outcome`：Draftを保持し、現在値の照会前に再送しない。照会一致は過去のMutation成功と断定せず明示確認、不一致なら明示的な再保存／破棄を提供する。照会失敗は未確定のまま保持する。

### 自動保存：Queue・Baseline・Feedback

#### 共通保存ActionとTriggerの違い

手動保存／自動保存の**保存Actionは同じ`SaveActionResult<T>`**を返す。分類は`confirmed`（保存確定値）、`validation`（Typed InputViolationまたはForm全体の拒否）、`retryable`（安全に再試行できると判明した拒否）、`blocked`（公開情報に基づく操作不可と安全なFeedback）、`unknown`（保存の成立を否定できない失敗）とし、GraphQL Error・Apollo例外の解釈はFeature Action接続内に閉じる。

明示的な保存は`useExplicitSave`がユーザーのボタン操作をTriggerとし、保存中の入力・重複操作を制御する。自動保存は**有効な入力変更を起点にDebounceして同じActionを呼び出す**。保存中も次の入力を受け付けるため、送信中の値と新しい入力を区別し、実際の通信を直列化して最新値だけを次に送る。Trigger以外の業務的なAction結果分類は共通とする。

既存の自動保存Queue / Controllerが要求する`Promise<T>`（成功確定値／失敗時reject）はConnectionで`requireConfirmedSave(SaveActionResult<T>)`として変換する。未確定な結果は`SaveActionError`に共通`SaveActionFailure`を格納して渡し、Controllerが`getSaveActionFailure`で解釈する。これは従来のQueueを保持するためのAdapterであり、`AutoSaveFailure`など別のAction結果Contractを設けない。未分類例外は`unknown`として自動再送を禁止する。

Personal Preferencesは400ms DebounceでField Patchを結合して直列送信する。Community Accentは有効HEXのPreviewを即時反映し、最後の有効な入力から400msのDebounceでActionを起動する。送信中に新しい選択があった場合、後続の値はDebounce満了と先の通信完了の両方を待って送る。未完成HEXが最新入力になった場合、送信前の有効HEX予約はキャンセルする（既に始まった通信は取消済みと扱わない）。CommunityごとのSession、失敗時の表示色復元、未保存Draft、結果不明の照会・明示復旧は維持する。認証済みApplication Shellが終了した場合、未送信の保存予約は取り消すが、開始済みの通信を取消済みとは判断しない。

自動保存に`useExplicitSave`の入力停止や汎用`useAutoSave`を導入しない。Preview・Patch生成・Cache・Queueの寿命・復旧表示は各Featureが所有する。Storybookの例外MockはStory側で共通Action契約へ変換し、本番FormのAPIへテスト専用Propsを追加しない。

- `Draft`（RHF）が最新の選択・未完成入力を表し、Queueが`pending`／`in-flight` Patch、成功確定した値が`confirmed baseline`を表す。各Fieldの`dirty`を「最後に保存を要求したか」の意味で代用しない。
- Successには**成功したPatch／送信時の値**が必要。Queueに成功Snapshotを伝搬する契約を設ける。受信したServer全体のPreferencesを無条件`reset`することは禁止。
- Fieldごとに、確定値と送信時以降の新しいDraftを比較する。未送信・in-flight・失敗・さらに編集中のFieldは保護し、確定済みで未編集のFieldのみ保存基準を進める。未完成`accentDraft`は、HEXが未完成の間は保存済みと混同しない。
- 保存失敗時に`pending` Patchを失わない。再試行可能な失敗と`unknown-outcome`を分け、前者はRetry、後者は確認手段を提示する。Backend側の冪等性が確認できないまま自動再送しない。
- Status表示は自動保存の多頻度Notificationを避け、保存中・未保存・保存済み・失敗を区別する。複数Fieldの同時更新で「保存済み」と誤表示しない。
- Community Accentの即時Context反映、保存失敗後RollbackはUX判断待ち。確定色へ戻す場合でも、不完全HEX・保存中の新しい選択・未確定応答を誤って上書きしない。Rollbackする対象と再試行導線を先に決定する。

### GraphQL Errorの実際の公開契約（2026-11-02 API確認）

確認元：`memoria-api` `develop` の `graph/handler.go`、`graph/handler_test.go`、`graph/{user,community}.resolvers.go`、`internal/service/{user,community}/service.go`、`schemas/graphql/{user,community}.graphql`。**GraphQL `extensions.code`の正本は`graph/handler.go`のErrorHandler**であり、`internal/errors/common.go`に存在する`BAD_REQUEST`などの定数をそのままGraphQL公開契約とみなさない。

| GraphQL `extensions.code` | 確実に判定できる意味 | Settings FormへのMapping方針 |
| --- | --- | --- |
| `VALIDATION` | 検証失敗。Settings MutationではField Pathなし | Form Alertを既定とする。Client Zodが対象Fieldを特定できる場合は別途Field Error。APIからField Errorを断定しない |
| `UNAUTHENTICATED` | 認証状態が無効 | Blocked：認証再確認を案内 |
| `UNAUTHORIZED` | UnauthorizedErrorによる認可関連の失敗 | 原因を確認できる範囲でBlocked。MessageをUI分岐に使用しない |
| `FORBIDDEN` | 権限不足 | Blocked：権限確認・離脱等を案内 |
| `NOT_FOUND` | 対象を参照できない | Blocked / Stale対象：表示中のContextを再確認。Field Errorと推測しない |
| `CONFLICT` | 競合や業務制約。Settingsでは詳細reasonなし | Form Alert。入力の単純な再送で解決すると推測しない |
| `INTERNAL_SERVER_ERROR` | サーバー内部失敗 | 結果確定を推測できない場合はUnknown Outcomeとして扱い、安易に自動再送しない |
| `UNKNOWN_OUTCOME` | 一部のMutationに限った結果未確定 | Unknown Outcome。Settings各Mutationの公開契約として現時点では存在しない |
| Transport / Timeout / Network failure | 通信できない、応答を確認できない | 書込が到達した可能性があるときはUnknown Outcome。Request送信前と確実に判定できる場合のみ再試行可能候補 |

`VALIDATION`と`CONFLICT`はServerの`extensions.reason`や`fieldPath`がSettingsについて定義されていないため、Frontendがエラーメッセージの文字列を解析して個別Fieldへ割り当てることはしない。Serverから詳細が返せるようになった時点でMapperの分類を拡張する。現行`graph/handler.go`はMedia Groupの一部にのみ`reason`を付与しており、それをSettingsへ一般化した仕様として扱わない。

**保存確定の条件**：ProfileはMutation ResponseのUser/Profile/Nickname、Community NameはCommunity/Name、PreferencesはPreferences、Community AccentとAliasはSettingsの戻り値で、対象となる保存値が確定したことを確認する。Mutationが成功した後のRefetch Errorを同一Operationの失敗として握りつぶしてはいけない。Current Web実装の`awaitRefetchQueries: true`は成功判定とRefresh判定を結合し得るため、更新確定と後続再取得を別に観測する設計へ切り替える。Backendの応答値が正規化される場合、要求と完全一致しなくても確定した正規化値をBaselineとする条件をOperationごとに定義する。

**分類の優先順位**：1. 確定Mutation Payloadがある場合は保存確定を優先し、後続Refetch失敗は非ブロックの別Result。2. 確定していない明示的Error Codeがある場合は上表で分類。3. 書込の結果自体を確認できない場合はUnknown Outcome。4. 定義されていないCode・複合Errorを安易にRetryableやFieldへ分類しない。Userへ表示する文言はApplication側で安全に用意し、APIの内部Messageをそのまま露出しない。

**Context/対象の確認**：後続の再取得により同じContextで確定済み値と一致することは確認できるが、「今回のMutationが成功した」とまで証明できないケースがある。未知結果を確定扱いにするかは、更新Version / 冪等性 / 操作固有のResult照会Contractを確認してから決める。現時点のSettings Mutation Payloadには保存Request ID / Version / Idempotency Keyがなく、厳密な因果関係の判定には使えない。

#### 実装単位の提案（コード変更前の設計）

1. GraphQL BoundaryにFeatureから使用する小さなError分類関数を設ける。Apollo Error / GraphQL `extensions.code`を安全に参照し、既知のCodeだけを意味カテゴリへ変換する。Errorの文言を分類条件にしない。
2. 各保存ActionでMutation Responseを検証し、**Confirmed Value**／**分類済みFailure**をForm Ownerへ返す。既存の`Promise<boolean>`を段階的に置換する。TypeやResult Wrapperは具体的なConsumerの要件が判明してから最小で選ぶ。
3. Form OwnerがFeedbackの主要表示先を決める。Field ErrorはRHF、Form Errorは持続するFeedbackAlert、明示保存の確定SuccessはNotification、自動保存はInline Statusとする。接続層の重複Notificationは移行時に除去する。
4. 連続保存のQueueはPatch単位でSuccess/Failureを通知し、古いResponseで後続Draftを上書きせず、確定したFieldだけBaselineを進める。QueueにSnapshot ID等を持たせる必要性は実装時に検証する。
5. Unit TestはError Codeと未定義CodeのMapping、Mutation成功・Refetch失敗の独立性、Mutation不明結果、連続Patch確定を検証する。Interaction TestはField / Form Error・再試行導線・成功通知と静かな自動保存を検証する。

### 最終判断を要するもの

1. APIのField Path・Business Error・Retryable・Unknown識別に必要な機械判定情報を追加するか、既存Error codeと個別Operationで扱える範囲に限定するか。
2. `unknown-outcome`をどの操作で再照会・再送可能とするか。BackendのIdempotency・更新Version・結果照会契約の有無を確認して決定する。
3. 自動保存Statusの表示位置・表示保持時間・再試行操作と、成功通知を不要とする条件。
4. Community AccentのRollback方針（確定色へ復元／未保存の選択を保持）と未完成HEXの扱い。


## 2026-11-02 合意：GraphQL Hybrid Error Model

**設計ステータス：Hybrid Modelの基本方針は確定、Operation別のSDL・公開Error Code・同時更新/冪等性は詳細設計待ち。** 既存Backendの実装互換性や差分最小化を優先せず、GraphQLのSchema表現力・利用者の回復可能性・運用上の信頼性を基準に設計し直す。現行Source of Truthの`content/system/api/graphql.mdx`は「Transport / Application Errorは`errors[].extensions.code`」を採用しているため、次の提案は**旧契約を置き換える合意済み方針**であり、APIのGraphQL設計正本にも反映済み。Web #235、API #128と連携し、確定後にAPI GraphQL設計正本・Schema・Web設計を同期する。

### 選択肢の比較

| 方式 | 利点 | 注意点 |
| --- | --- | --- |
| A. 全失敗をGraphQLトップレベル`errors`へ集約 | GraphQL標準Execution Errorを利用可能、既存の`extensions.code`に適合 | 期待される業務的失敗をGraphQL型として表現しにくい。ClientがCode / Field判定に依存する |
| B. 業務上の失敗をMutation Payloadの型付きResult（Union）に表現、認証・実行失敗はトップレベル`errors` | ResultをSchema・Codegen・Exhaustive Handlingへ明示でき、Operation単位の期待される失敗が自己記述的 | Union分岐・型の増加。初期の契約変更は大きい |
| C. すべての例外・失敗をUnion Payloadにする | Query時と違いMutationの戻り値は単一の成功／失敗型に統一可能 | 認証・インフラ障害まで通常の業務結果と同一視し、GraphQL Execution Errorと混同する |

**採用：BのHybrid。** GraphQL Specificationは業務ErrorをUnionにすることを義務付けていないが、予期される・利用者が対処できる業務結果はSchemaの型で表現するメリットが大きい。Protocol・認証・権限制御・実行障害はGraphQLトップレベル`errors`とTransportで扱う。複数更新対象の部分成功は、既存Bulk Item Resultをこの分類と整合させる。全Mutationに機械的にUnionを追加せず、予期される業務失敗のあるCommandへ適用する。

### Resultの意味とSchema例（設計候補）

```graphql
type UpdateUserProfileSuccess {
  profile: UserProfile!
}

type InputViolation {
  # GraphQL response pathではなく、Mutation Input内のField path
  inputPath: [String!]!
  code: String!
}

type InputValidationFailure {
  violations: [InputViolation!]!
}

type DomainRuleFailure {
  code: String!
}

type StateConflictFailure {
  code: String!
}

union UpdateUserProfileResult =
    UpdateUserProfileSuccess
  | InputValidationFailure
  | DomainRuleFailure
  | StateConflictFailure

extend type Mutation {
  updateUserProfile(input: UpdateUserProfileInput!): UpdateUserProfileResult!
}
```

例はContract Boundaryの説明用であり、同名のGeneric Error型を全Mutationで共有する確定仕様ではない。`inputPath`は`nickname`等の**Input Modelのpath**であり、GraphQLのExecution Errorの`errors[].path`（失敗したResponse Fieldのpath）と混同しない。Fieldの問題が一意でない場合はForm LevelのDomain Failureとする。Field ErrorのcodeはUI文言ではなく安定した機械判定用識別子であり、MessageはWebのlocale・Form Contextに応じて組み立てる。必要な入力や業務制約のみ、型・コード・対象Pathの粒度をOperation単位で定義する。

成功Resultは保存済みの最終値を返す。成功判定後の別Queryの再取得失敗を保存失敗へ格下げしない。UnionのFailureは**更新が確定していない業務上の拒否**を意味し、Successと同時に発生させない。認証失敗・権限不足・対象秘匿・サーバー障害の扱いはAPI Security Contractに従い、Unauthorized等を一般のUser Error型に混在させない。

### GraphQL Execution ErrorとTransportの契約

- `errors[].extensions.code`はTransport、Authentication、Authorization、Schema/Execution、Infrastructureの識別に用いる。GraphQLの`errors[].path`は失敗したResponse Fieldの位置であり、入力不正Fieldの代用としない。
- 認証：`UNAUTHENTICATED`、認可：`FORBIDDEN`、不存在と存在秘匿：`NOT_FOUND`という既存Security上の原則を継承する。内部Error・Stack Trace・DB名などの情報は外部へ返さない。
- `INTERNAL`等の公表Codeについて現行の`INTERNAL_SERVER_ERROR`を含む不一致を整理し、仕様・実装・Testを同じ契約へ揃える。HTTP StatusとGraphQL Error Codeは別概念であり、GraphQL ResponseのError配列／nullableの挙動とApollo `errorPolicy`の組み合わせを検証する。
- Mutationが応答の途中で失敗した場合、Clientは書き込みの成否を判断できないことがある。**Unknown Outcomeは必ずしもBackendが返すError CodeではなくClientの知識状態**である。接続タイムアウトを`Retryable`と同義にしない。
- 予期されるField / Domain FailureはUnion等のSchema Resultへ、Authorization等の実行不可はGraphQL Errorへ、Network断・Timeout等の応答未確認はClient Transport Statusへ分ける。ValidationのうちGraphQL Input Coercion / Syntaxの失敗はMutation Resolverに到達せずGraphQL Request Errorとなり、業務Validation Resultとは別に扱う。

### 冪等性・同時編集・回復

- 最終状態を同じ値へ設定するSetting更新は、一般に重複送信しても同じ最終値へ収束するが、監査・イベント・非同期副作用まで自動的に冪等とは限らない。手動保存は重複実行防止と送信Snapshotの特定を前提にし、再送が安全なOperationを明示する。
- User Preferences / Community Accent等の自動保存は、Queueの直列化と後続編集の保護を保証する。送信Snapshotと確定応答を照合し、後続Draftを消さない。通信断時に「既に保存された」と判断しない。
- Idempotency Keyは削除・作成・支払い等の重複副作用が問題になるCommandで必須候補とし、全Mutationへ無条件に要求しない。事後状態の再取得は現在値の確認には使えるが、**どのRequestが成功したか**を一般に証明しない。
- 同時編集で他端末／他操作の更新を失わせない必要がある場合、Version / Preconditionの導入をCommandの性質から検討する。Web側のQueueだけでは複数Client間のLost Updateを防止できない。
- APIの確定したMutation Responseを保存基準にし、Cache反映・追加Refetchは別の結果とする。GraphQL Data / Errorの部分成功はQueryの独立FieldとBulk Item Contractに従い、単一Form保存のConfirmed判定と混同しない。

### Unknown OutcomeとRetryの状態遷移

| Event | Controllerの状態 | 画面での動作 |
| --- | --- | --- |
| 有効な変更 | Pending（最新FieldをCoalesce） | Draft更新、控えめな「保存待ち」 |
| Flush | In-flight（Snapshotを固定） | 「保存中」。後続編集は別Pendingへ |
| `*Success` | Snapshot分のConfirmedのみ確定、後続Pendingを継続 | 古いResultでDraftを消さない。全て終了なら「保存済み」 |
| `InputValidationFailure` / 明確な業務拒否 | Rejected、当該FieldのDraft維持 | Field / Form Error。再編集で更新 |
| 確実に未実行と判定可能な一時失敗 | Retryable、Patchを保持 | 再試行可能なForm Alert。ユーザー起点Retryを基本 |
| Timeout / Network断 / Response未確認 | Unknown、未確定Snapshot保持、Queueを停止 | 「保存結果を確認できません」。既存QueryのRefreshで現在状態確認 |
| 認証切れ・権限不足 | Blocked、Queueを停止 | 認証・権限確認。無条件Retry禁止 |
| Mutation成功後のRefetch失敗 | Confirmed、RefreshのみError | 保存成功を取り消さず、Refresh Errorを別扱い |

**Unknownの復旧（合意済み）**：新規Saveを一旦停止し、既存Queryを`network-only`等で再取得する（CacheをServer照会結果の代用にしない）。現在値が希望値に一致すれば**現在状態の一致**としてUIを回復可能。ただし当該Requestの実行成功と断定しない。値が異なる場合は最新DraftとServer値を提示し、ユーザーが明示的に再保存する導線を提供する。**Unknownから自動再送は行わない。**新たな保存操作に進む前に、遅れて届く旧Requestの書き込みが後勝ちになる可能性があるため、旧Requestがまだ実行され得る場合は**単純Refetchだけで完全な順序保証はできない**。厳密に保証するならRequest CancelのServer保証、Operation識別・結果照会、Keyによる再実行の排除等が必要。一般Settingsへこれらを標準導入するかは費用対UXで判断し、保証できないことを保証済みとして実装しない。

**Retryable/Unknownを分ける基準**：Requestが確実に送信されていない等、保存不成立が識別できる場合のみRetryable。送信後のTimeout等はUnknown。LWWという性質だけで`retryable`に分類しない。自動再送・無制限Retryは導入しないことを基本候補とする。ユーザーによる再保存でも**後続Draftより古いSnapshotを再送しない**。

### 画面離脱・Browser終了時の契約案

| 境界 | 推奨動作 |
| --- | --- |
| Settings内Tab移動 / Client-side Route変更 | 長命ControllerがPendingをFlushして処理継続。Form unmount後もControllerが結果とFailureを管理 |
| 同User/同Communityへ戻る | ControllerのPending/Unknown/Failureを画面へ再接続。Server値より新しい未保存編集を保護 |

### Community Accent：Preview / Draft / Confirmedの区別

- **Confirmed**：Serverが確定した`accentColor`。Apollo正規化Cacheはこの値の参照元とする。
- **Preview Overlay**：有効HEXが入力された時点で即時表示できる一時色。**適用範囲は現在選択中のCommunity Context Shell全体**（Switcherの当該ContextのAccent表示を含む）と設定画面。別Communityや永続Server Cacheには反映しない。
- **Draft**：RHFが所有するColorInputの文字列。未完成HEXも保持。未完成値は保存しない、Previewは最後の有効色のまま。
- **成功**：Mutation Resultの確定色をCacheへ反映。保存確定した選択と今のDraftが同じならOverlay解除。より新しいDraftがあればそのOverlay維持。
- **確実な失敗 / Unknown（確定）**：Overlayを解除してShellの表示を最後の確定色へ戻し、ColorInputには最後のユーザー選択を保持すること。Form近傍に持続するFeedback Alertと「再試行」または「変更を破棄」。Unknownでは「未保存」と断定しない。破棄でのみDraftを確定色へ同期する。
- **Context切替**：旧ContextのOverlay解除。旧Contextへ戻る場合は未保存Draft・FailureをControllerに保持するかどうかを別途決める。旧Contextの遅延結果を新Contextの表示へ適用しない。
- AccentとAliasのPartial PatchはFieldごとの保存確定を区別し、片方の保存成功がもう片方のPreviewや未完了Draftを上書きしない。

### StatusのPresentation案

SettingsのPage Header付近にフォーム単位の小さなStatusを置く。値は「保存待ち」「保存中」「保存済み」「保存結果を確認できません」等。PendingとSavingの頻繁な切り替わりを読み上げないよう、`role="status"`を更新制限し、成功Notificationは省略する。保存済みは**全Pending/In-flightがなく、全対象Fieldの確定が確認できたときのみ**表示し、短時間で非表示とする案。エラーはForm Alert/Field Errorとして残し、Statusと重複しない。Compact/Medium/Wideで位置とFocus/AnnouncementをStoryで検証する。

### 検証シナリオ

1. A→B→Cの色連続変更中にAが成功し、CのDraft/Overlayが巻き戻らない。
2. Accent in-flight中にAliasを保存しても、両方のPartial PatchとCacheの最新Fieldが残る。
3. 画面Unmount後、保存成功/失敗がControllerに残り、再訪時に正しいStatus/再試行導線を表示する。
4. Community ID/Account切替後、旧Requestは新Contextへ影響しない。
5. Timeout後のRefetchが一致/不一致/失敗/遅延した各場合に、成功・未保存を誤断定しない。
6. 最後の確定色への見た目復帰時に、ColorInputの未完成/未保存Draftを保持する。

| --- | --- |
| Next.js Client-side route変更 / Settings内画面変更 | 警告せず、認証Session QueueにPending / In-flightを残し継続する |

| 状態 | 視覚表示 | 提示条件 / 終了条件 |
| --- | --- | --- |
| `pristine` | 何も表示しない | 初期値を閲覧しただけ |
| `pending` | 「保存待ち」 | Userが有効値を変更し、まだMutation送信前。400ms Debounce中。即時表示でも読み上げなし |
| `saving` | 「保存中」 | In-flightがありConfirmedでない。短い通信の点滅を抑えるため、**開始から300ms以上続いた場合に表示する案** |
| `saved` | 「保存済み」 | 全対象QueueのPending/In-flightがなく、最新Draftに有効な未保存変更がなく、Confirmed Successを得た場合。**約2秒表示後に消す案** |

| `blocked` | 持続するForm Alert「設定を変更できません」 | 認証・権限などの問題が解消されるまで保持 |

**表示優先順位**：Blocked / Unknown / Rejected / 入力Error ＞ Pending ＞ Saving ＞ Saved ＞ Pristine。異なるFieldにPendingとIn-flightが並存する場合は「保存中」または「未保存の変更あり」を示し、すべて保存済みと誤認させない。個々の短いMutationごとに「保存済み」を繰り返さず、**最後の変更群の確定**を1回の表示イベントとする。

### 離脱警告のリスク判定規則

一般Settingsの個人表示設定・Accent色・日付形式・サムネイル等は、喪失しても再設定でき、取り返しのつかない影響を通常生まない。**標準ではBrowser離脱警告を要求しない**。ただし保存失敗・Unknown状態をユーザーが認識できる常設Feedbackは別責務として維持する。

重要なドメイン操作で離脱警告を検討する場合は、`操作の不可逆性 / 再入力の負担 / 金銭・権限・データへの影響 / 回復可能性 / 実際の保存寿命`を材料に判断し、操作の契約に判断理由を残す。`beforeunload`が確実に発火することを前提とした保護は認めない。実際の重要操作ではDraftの永続化、原子的Commit、Idempotency、明示Confirm等を優先して設計する。

| Category | 例 | 方針 |
| --- | --- | --- |
| 軽微で再現可能な表示設定 | Theme / Personal Preferences / Community Accent | 警告を標準化しない |
| 再入力コストの高い編集 | 長文入力・複雑な構成変更等 | Operationに応じて警告／Draft保存を検討 |
| 不可逆・高影響 | 削除、権限・Membership等 | Domainの明示Confirm・冪等性・安全なTransactionを主とし、警告は補助的に検討 |

この表は新たなDomain操作の仕様変更を自動的に承認するものではない。

### SaveStatusの配置：タイトル右側にレイアウト予約

- `SaveStatus`はController SnapshotからのRead-only Presentation。Timerや`aria-live`はPresentation Ownerに閉じ、通信Queueの保存状態を変化させない。

**案A（推奨）：タイトル右は短いStatus、エラー詳細はフォーム上部の持続Alert**。

- Header右Slot：成功/進行中は短いStatus、Error時は`要確認`または`保存エラー`の短いStatusのみ。レイアウト予約幅は一定。
- Header説明文の下、設定項目の前に`FeedbackAlert`を表示し、`理由（1文） / ユーザーへの影響 / 次にできる操作`を提示する。Field固有ValidationはそのField直下へ置き、Form Alertと同じ内容を二重提示しない。
- 長いError Detailにより**下の設定項目が押し下がることは許容**する（状態変化として内容の追加があるため）。問題となるStatusの表示有無によるHeaderの高さ変動は起こさない。Alertの高さまで常時予約するのは通常のFormを不必要に広くするため推奨しない。
- `retryable`：変更内容は保持していると明記し、`再試行`。 `unknown`：`現在の状態を確認` → 一致時`確認完了`、必要時`もう一度保存`。 `blocked`：認証・権限の回復行動。`InputValidationFailure`：該当Fieldの修正。
- AlertはDismissだけで未保存情報を失ったように見せない。成功Notificationを繰り返さず、AlertとStatusの同一文言による読み上げ重複も避ける。

**案B：タイトル右のStatusを押すとPopoverで詳細を表示**。Header以下のレイアウト変動は小さいが、Errorの見逃し・キーボード導線・Screen Readerの発見性に課題がある。未保存Draftの解決に重要なErrorはPopoverだけに閉じ込めず、必要に応じて持続Alertを併用する必要がある。

**案C：Header下に常時高さを確保したError専用領域**。Error出現時のForm押し下げも抑制できるが、通常時に空白が大きく、Compact画面の情報密度を悪化させる。標準方式として推奨しない。

### Unknown「確認完了」の意味と状態遷移（確定）

1. `unknown`へ遷移したら同一Queueの自動送信を停止し、最新Draftと未確定Snapshotを保持する。
2. `現在の状態を確認`から**既存QueryでServerへ照会**する。Query失敗はUnknownを維持。取得した現在値と最新のユーザー希望値を、該当対象Fieldの正規化済み値で照合する。
3. **一致**：画面には「現在の設定は選択した値と一致しています」と説明し、`確認完了`ボタンを出せる。クリック時にUnknown Alertを閉じ、現在値を確認済みBaselineとして採用する。これは最新の**現在状態の承認**であり、元のMutationの成功認定ではない。
4. **不一致**：Unknown Alertを維持し、現在値を表示する。ユーザーが`もう一度保存`を押す場合に限り、古いSnapshotではなく最新Draftを送信する。必要なら`変更を破棄`で現在のServer値へ戻す。
5. 確認完了後も古いMutationが遅れてCommitし得る。一般Settingsは合意済みLWWで扱うため、強い順序保証は主張しない。確認完了は成功Notificationや「当該Requestが完了済み」の表示には変換しない。
6. QueueのPendingに新しいField変更が混在する場合は、対象Field単位で照合し、すべての未確定対象が一致することを確認するまで全体の`confirmed`表示へ進めない。

### Regression / Accessibility Gate

- Status Slotの存在・非表示・短文変更でタイトル／説明文／コンテンツ位置が意図せず動かないこと。Wide / Medium / Compactで検証する。
- Error表示は常にHeader右Slotの範囲に収まり、詳細内容が短縮されずにForm側で読めること。ErrorとField Validationを重複表示しない。
- Error Alertの表示/復旧でFocusを奪わず、キーボードで各アクションへ移動でき、Screen Readerが長文を何度も読み上げないこと。
- Confirm済み／未保存あり／Unknown／Browser終了時の警告判定をリスク分類に照らして検証し、一般Settingsへ一律`beforeunload`を適用しない。
- Unknown Query一致→`確認完了`ではMutation Retryを送信しないこと。Query不一致→手動保存は最新Draftだけ送信すること。Query失敗ではUnknownを維持すること。

### 残る合意が必要な判断

- **E1**：Error UIを**A：Header右に短いStatus + Form上部の持続Alert**とするか。Error発生時の設定項目の押し下げを許容するか。
- **E2**：CompactでタイトルとStatusが共存できない場合、固定二段Layoutを採用するか。
- **E3**：300ms後にSaving表示、Saved約2秒、Saving読み上げ2秒後という既存の時間案を採用するか。原則として視認性と過剰な変更通知抑制のバランスをStoryで検証する。

### レイアウトとCL​​S契約

**Wide / Medium**：

### Hybrid Mutation Result、Error分類、Context境界

- Settingsの保存MutationはApolloの`errorPolicy: "all"`による部分応答を許容する。対象Operationに型付き`*Success`があればその確定結果を優先し、`InputValidationFailure`なら拒否された入力としてField/Formへ返す。他Fieldの部分Dataを根拠に対象Mutationを成功扱いしない。対象Resultが欠落したときだけ公開`errors[].extensions.code`を解釈する。
- `UNAUTHENTICATED`、`USER_REGISTRATION_REQUIRED`、`USER_DELETING`、`FORBIDDEN`、`NOT_FOUND`をBlockedとし、自動・盲目的な手動再送を止める。`INTERNAL`、`UNKNOWN_OUTCOME`、再送保証のない`RATE_LIMITED`、混在・未知Code・通信断はUnknown Outcomeとし、照会と明示操作を優先する。別Domainの旧`VALIDATION`／`CONFLICT`はField Pathを推測せずForm-levelに置く。新しい公開Codeの正本は[GraphQL契約](/system/api/graphql)。
- 確定Mutationと後続Refetch失敗を別に扱う。Unknown状態の現在値確認は旧Mutationの成功証明ではない。照会に使用する`CurrentUserDocument`／`CommunityMySettingsDocument`は必要に応じて`no-cache`で取得し、古い照会応答でより新しいApollo Cacheの確定状態を巻き戻さない。
- Community単位の保存Controller・Previewを独立させ、別Communityの遅延したMutation／Execution Errorが現在ContextのConfirmed、Draft、Cacheを書き換えない。同一CommunityのAccent/Aliasも各Patchで確定したFieldだけをCommitする。対応するUnit、Apollo Link Integration、Storybook Interactionの実装と検証対象は`memoria-web`を正本とする。

Savingが2,000ms継続したときだけ「保存中です」を一度`aria-live="polite"`で通知し、Saved確定時は「変更を保存しました」を一度告知する。Errorの読み上げは持続Panel側が所有する。State遷移時に古いTimerを解除し、Queue、400ms Debounce、Rollback、Unknown Recoveryなどの意味的契約を変更しない。他Consumerの`SaveStatus`既定動作は変更しない。これらは`memoria-web/develop/src/components/SaveStatus/SaveStatus.tsx`の実装値と一致する。

### FeedbackPanelとProfileの明示的Recovery

合意された`FeedbackPanel`はPresentationのみを所有し、Error分類とRecoveryの安全性はFeature側が所有する。[Feedback Pattern](/design-system/patterns/feedback)を参照する。Profileでは、確定Successの既存Notificationを一度だけ表示し、Validationは対応FieldまたはForm内Panelへ表示する。Blockedは公開Code別に安全な案内を行い、Unknown OutcomeではDraftを保護して通常の再送を停止する。

ProfileのUnknown時は明示的な「現在の状態を確認」で`CurrentUser`のNicknameを照会する。最新Draftと一致すればユーザーの「確認完了」で観測値を採用するが、旧Mutationの成功通知は出さない。不一致なら照会済みのServer値を示し、ユーザーが「もう一度保存」または「変更を破棄」を選ぶ。照会失敗ではUnknownを維持し、自動再送しない。照会中にDraftが変わった場合は古い結果を破棄する。この契約は`memoria-web/develop/src/features/settings/profile/SettingsProfile/SettingsProfile.tsx`の実装と照合済み。

Personal Preferences／Community AccentのBlocked原因案内もFeatureごとに所有し、API生Messageをそのまま表示しない。Community MembersのRole変更・除外で結果未確定となる場合は既存の確認Modal内の持続Panelで案内し、失敗Notificationの重複や確認前の再送を避ける。既存のRole制約、確認操作、成功Notificationを維持する。
