# Personal / Community Settings：React Hook Form移行詳細設計

> 状態：実装前詳細設計。2026-11-02に合意済みの原則と、実装前に確認する提案を区別する。対象コードは`memoria-web/develop`（2026-11-02時点）。
>
> 本文はPersonal / Community ContextのSettingsのみを対象とする。Media Detail、Account Registration等の他Featureへの展開は含まない。

## 目的・正本

- `content/system/web/implementation-conventions.mdx` のState Ownership・Form規約をSettingsへ適用する。
- FormのDraft / Dirty / Field ValidationをReact Hook Form（RHF）で一元管理し、Apollo ClientをGraphQL Server Stateの共有表現とする。
- 保存順序、Debounce、Mutation、Cache更新、Rollback、Retryなどの既存振る舞いとUI / Responsive / Storybook Contractを維持する。
- 新しいSettings UIや汎用Form Frameworkの構築ではなく、既存実装の責務抽出として進める。

### 合意済み

1. 各フォームを独立したRHF Formとして管理する（Page全体・複数Contextで単一のFormを共有しない）。
2. 既存Queue、Mutation、Rollbackを維持し、入力値管理の責務のみRHFへ移す。
3. 移行順序：Personal Profile → Community Alias → Community Name → Personal Preferences → Community Accent。
4. 変更前後のVisual / Behavioral / Responsive Contractを維持する。既存のCapabilityを共通化のために削除しない。


### 2026-11-02 追加合意（実装時の決定）

- サーバー再取得時のCommunity Name未保存Draftは、既存どおり `communityName` Props変更時に上書きする（今回の移行で挙動を変えない）。
- Context IDが変わる場合、フォームをContextごとに独立させ、新しいContextの初期値で初期化する。保存Controllerの対象IDとDraftが混在しないようContext境界で明示的に識別する。
- Personal PreferencesはRHFが編集中の入力値を所有するが、保存対象Patchは従来どおり入力イベントで生成する。RHFのDirty Fieldを保存対象抽出へ新たに利用しない。

## 2026-11-02 合意：Zod / zodResolverの適用と共通化の境界

- Settingsの各独立RHF Formに、フォームのInput / Outputを区別したZod Schemaと`zodResolver`を適用する。入力中のDraftはRHFが所有し、ZodはValidationと保存時の正規化を定義する。
- `z.input<typeof schema>` は入力値、`z.output<typeof schema>` は検証済み保存値として扱う。RHFは必要に応じて`useForm<z.input<typeof schema>, unknown, z.output<typeof schema>>`を使用する。
- Mantine UIと既存のError表示タイミングは変えない。`safeParse`による保存可否の導出などが必要な場合も、同一Schemaを唯一のValidation正本とし、別のValidationルールを二重実装しない。
- Personal PreferencesのPatch保存は入力イベント起点、Community Accentは有効HEX入力だけを既存保存Controllerへ通知し、`handleSubmit`へ保存方式を変更しない。未完成HEXをRHF Draftとして保持する。
- 各Schemaは対応するドメイン・フォームの近くに配置する。記述の類似だけを理由に名前やField Schemaを共通化しない。
- Community名・Tag名・Group名のように複数ユースケースで同一ドメイン制約が必要になれば、その段階で各ドメインのSource of Truthを確認して抽出する。**今回の作業はPersonal / Community Settingsのみ**とし、他のFeatureへの共通化を行わない。
- `react-hook-form`、`zod`、`@hookform/resolvers`は既存依存を利用する。Backend最終Validationを置き換えない。
- Git commitの`[skip ci]`はPR作成済みブランチへの追加コミット時のみ付ける。PR未作成ブランチのコミットには付けない（今回の作業指示であり恒久的設計規約ではない）。

## 2026-11-02 合意：Zod OutputとGraphQL InputのMapping

- Form内のDraftはRHFが所有する。Zod Schemaは入力Validation、Trim、空欄からNullable値への正規化など、Applicationが扱う検証済み値の生成に責任を持つ。
- GraphQL固有のInput Shape、Generated Type、Enum変換、Partial Patchの構築はAction / GraphQL Boundaryに所属する。単純な `{ input: { communityId, name } }` のような組み立ては接続箇所で直接行い、Mapperを必須としない。
- 複雑な構造変換や独立した契約が存在する場合だけPure Mapperを抽出する。既存の `src/features/settings/preferences/userPreferencesGraphqlAdapter.ts` はその実例であり、`toGraphqlUserPreferencesPatch` が入力PatchをGenerated GraphQL Enumへ変換する。既存の `userPreferencesGraphqlAdapter.test.ts` を対応Testとして維持する。
- Schemaの型は `z.input` と `z.output` / `z.infer` を意図に応じて使用し、Mutation InputはCodegen型をGraphQL Boundaryで使用する。両者が同じ形なら直接渡せるが、等価であると推測してMappingを省略しない。
- Community Aliasの空文字 `null` 化はApplicationへ渡す正規化値であり、Zodの責務とする。SchemaにGraphQL依存を導入しない。
- 本変更では既存のMutation・保存Queue・Rollback・UI・Storybook Contractを変更しない。Settings以外への横断的Mapper / 共通Schemaの導入は対象外。

## 2026-11-02 合意：Mapperの型I/F契約

- **フォーム専用Mapper**は、入力を対象Schemaの `z.output<typeof schema>`（または `z.infer`）、出力をGraphQL Codegen生成Input型として明示する。フォームの未検証InputをMapperへ直接渡さない。型契約に加えて近接Unit Testで変換結果を保証する。
- **複数ユースケースで共有されるMapper**は、フォームSchemaではなく共有Application Model / Patch型を入力とする。現実に必要になるまで専用Application Modelを増やさない。
- Personal Preferencesの `userPreferencesGraphqlAdapter.ts` は、RHFのInputに加えて入力イベント由来のPartial Patchと取得結果を扱う境界である。入力契約 `UserPreferencesPatch`、出力契約 `UpdateUserPreferencesInput` を維持する。Zodの `preferencesSchema` には表示用 `accentDraft` が含まれるが、これをAPI Mapperへ流出させない。
- 既存のMapperは新ルールへの適合が確認できれば機械的に書き換えず、Mapperが必要なフォームで初めて型契約を追加する。

## Form defaultValuesの合意（2026-11-02）

各Settings Formの初期値はForm所有者の`defaultValues`に直接記述する。ZodにRHF初期値生成の責務を持たせない。初期値構築が複雑になるか、複数のFormで実際に同じ初期化ロジックが必要になった場合のみPure Functionを検討する。初期値とサーバー再取得時の`reset`は別の契約として扱う。

## 現行の責務と移行境界

| 対象 | Draftの現在地 | 保存の現在地 | 移行するもの | 維持するもの |
| --- | --- | --- | --- | --- |
| Personal Profile | `SettingsProfile` の `name`/`saved` | `SettingsProfile`→`usePersonalSettingsActions` | nicknameのDraft、基準値、Dirty、必須Validation | 保存ボタン、通知、retryable / blocked、Apollo Mutation・refetch |
| Community Alias | `CommunityAliasControl` の `draft` | `ConnectedCommunityPreferences` の `onSave` | Alias Draft、Dirty、100 Unicode code point上限 | 空欄解除、成功通知、失敗時Draft保持、Cache更新・best-effort refetch |
| Community Name | `useCommunityNameSettings` の `name`/`draft` | `useCommunitySettingsActions.onSaveName` | name Draft、基準値、Dirty、必須Validation | Admin制約、保存ボタン/通知、Mutation、MyCommunities refetch |
| Personal Preferences | `useUserPreferences` の `preferences`/`accentDraft` | `usePreferencesSave`→`createPreferencesSaveQueue`→Apollo Mutation | 編集中Field、ColorInputの未完成入力、Field更新とPatch作成 | 400ms Debounce、Patch結合、直列化、失敗後の値保持・retry、画面離脱時Flush、blocked |
| Community Accent | `CommunityPreferencesContent` の `draft` + `ConnectedCommunityPreferences` の `accent` | 接続側 `flush`/Apollo Cache | HEX Draftのみ | Preview、valid HEXだけ即時Context反映、最新選択の直列保存、失敗時最後の保存色へ復元 |

実装上の既存Component API・表示文言・ARIA・Props・Storyの契約は原則維持する。Field Componentに`control`、`UseFormReturn`等のRHF型を漏らさず、Form所有者で`Controller` / `useController`を使用して`value` / `onChange` / `error`等の既存Propsへ射影する。既存表示Component自身がフォーム所有者なら、その内部にRHFを持ってよい。機械的なComponent増加は行わない。

## 共通実装ルール

### 初期値と同期

- `useForm<FormValues>({ defaultValues: ... })` に初期Server Snapshotまたは既存Story Fixtureを渡す。RHFの`defaultValues`は通常の再Renderだけでは自動更新されないため、同期が必要な場合はフォーム単位で明示する。
- Dirtyの意味は現行契約が優先。現行がTrim/正規化後に比較するFieldでは、RHFの生の`isDirty`をそのまま保存可否に転用しない。`getValues`・`useWatch`で値を取得し、Pure Functionで正規化した値を保存基準値と比較して導出する。
- 保存成功時は確認済みServer Response / 保存対象の値を基準に`reset`を検討する。ただし、保存中の新しいユーザー入力を上書きしない。入力が凍結される明示保存フォームと、操作が継続する自動保存フォームとで同期方法を分ける。
- Apolloの`cache-and-network`再取得のたびにDraftを無条件`reset`しない。現在の同期挙動に変更が生じる場面は「未決定事項」に記す。
- Field ValidationとServer保存失敗は別物。RHFの`errors`は入力制約を中心とし、`retryable`/`blocked`/保存中・通知は現行のInteraction Stateと表示契約を維持する。
- React Hook FormはApollo Cache、Mutation実行順序、Queue、Context AccentのAuthorityを所有しない。
- `mode`・Validation表示時機・`onBlur`等は既存UIのError表示時機を回帰条件として選択する。初回表示で空欄エラーが出るStoryなどを消さない。

### TextInputの接続

- `Controller`でMantineのControlled Inputへ`field.value`/`field.onChange`を橋渡しする。可能なら`field.ref`/`field.onBlur`も接続し、Focus / Accessibilityを維持する。
- Trim、空欄許容、Unicode code point等のドメイン判断はPure Functionで行う。必要に応じて`rules.validate`へ渡すが、Serverからの制約強化を推測で追加しない。
- Save前のGuardは入力Validity、正規化後Dirty、権限、保存中/blockedから導出する。重複したBoolean Stateを増やさない。

## フォーム別詳細

### Phase 1：Personal Profile

**対象**：`src/features/settings/profile/SettingsProfile/SettingsProfile.tsx`。接続APIは`SaveProfile = (nickname: string) => Promise<void>`を維持。

- `useForm<{ nickname: string }>`。既存`initialNickname`、`initialSaveState`、`blockedMessage`をそのまま受け取る。
- `initialSaveState` は保存・エラー状態だけを表し、`initialNickname` の値を改変しない。2026-11-02に合意した修正として、以前のComponent抽出時に混入した初期Draft末尾への「新」の付加を削除する。`saving` / `retryable-error` を指定したStoryでは初期ニックネームがそのまま表示されることを検証する。
- `normalized = nickname.trim()`、`invalid = normalized.length === 0`、`dirty = normalized !== savedBaseline`とする。RHFの`formState.isDirty`だけではTrim同値判定を代替できない。
- 保存中/blockedは既存どおり入力不可。保存成功時に`onSave(normalized)`の解決後、基準値を更新し`reset({ nickname: normalized })`する。
- 失敗時はDraftを保持し、`retryable-error`または`blocked`を表示する。保存成功通知、文言、Buttonの`更新/再試行/更新中`、disabled条件は変更しない。
- 回帰：Trimだけの変更は保存可にしない、空白のみの入力、成功・失敗・blocked・Story初期状態。

### Phase 2：Community Alias

**対象**：`src/features/community-settings/CommunityAliasControl/CommunityAliasControl.tsx`。接続`onSave(alias: string | null)`を維持。

- `useForm<{ alias: string }>`。`savedAlias ?? ""`を初期値とし、入力中はstringで管理する。APIへ渡す時だけ`trim()`後の空文字を`null`へ変換する。
- `Array.from(normalized).length > 100`を既存どおりの無効条件とし、UTF-16 lengthに置き換えない。
- 保存可否は`normalized !== (savedAlias ?? "")`、`!saving`、`!invalid`。成功時にDraftを解放・次の表示をServer値へ同期するが、Mutation成功前にDraftを消さない。
- 保存失敗ではDraftとエラー表示を保持し、後続入力時にエラーを消す。既存の成功通知・入力のdisabled・Alias解除契約を保持。
- `savedAlias`更新時の`reset`と入力中Draft保護は、現在の`draft ?? savedAlias`の振る舞いを比較して実装する。保存結果を未確認のうちに新しい値を保存済み扱いにしない。

### Phase 3：Community Name

**対象**：`src/features/community-settings/useCommunityNameSettings.ts`と`CommunityNameSection`、Consumerの`CommunitySettings`。

- `useForm<{ name: string }>`を既存のForm state ownerに置く。現在の`draft` / `setDraft` / `invalid` / `dirty` / `savingName` / `saveName`として公開される意味的Propsを基本的に維持する。下位SectionへRHF固有APIを渡さない。
- `normalized = name.trim()`、`invalid = !normalized`、`dirty = normalized !== savedName`。Admin以外は入力不可、保存ボタン非表示を維持。
- `onSaveName(updated)`の戻り値trueだけを成功として保存済み基準値を進める。falseでは保存済み扱いしない。Mock/PreviewでCallbackがない場合の既存成功表示は保持する。
- 現行`useEffect([communityName])`はServer側名の変化でDraftまで上書きする。RHF移行で`reset`するときの同一挙動と、編集中の値を保護する改善案のどちらにするかは仕様変更の可能性があるため、実装前に明示確認する。
- `onSaveName`がrejectした場合の既存`finally`経路など、未処理例外を含む既存挙動を先にテストで可視化し、仕様変更を無断導入しない。

### Phase 4：Personal Preferences

**対象**：`useUserPreferences`、`SettingsPreferences`。既存`usePreferencesSave`・`preferencesSaveQueue`・`usePersonalSettingsActions.savePreferences`は維持。

- RHFは`UserPreferences`に相当する入力Fieldsを所有し、特にColorInputの未完成HEX入力は表示専用のDraftとしてForm内で所有する。`useState(preferences)` / `useState(accentDraft)`は撤去する。必要なFieldの追加構造は実装時に型名を決定する。
- Date Format、File Size、Thumbnail、Navigation Wrap、初期情報表示の選択イベントで、RHFのField値を更新し、同じ有効値の単一Field Patchを既存Queueへ`enqueue`する。全値を送る`handleSubmit`や`watch`→`useEffect`での保存トリガーへ置き換えない（初期同期や`reset`で意図しない保存を起こさないため）。
- ColorInputは不完全HEXを表示保持し、有効な`/^#[0-9a-fA-F]{6}$/`に達した場合だけ`personalAccentColor`のUppercase Patchを送る。既存の`changeAccentDraft`相当の契約を維持する。
- 既存400ms Debounce、Patch結合、in-flight中の追加変更、失敗値と後続値の結合、`retry`、unmount`flush`、`blocked`を変更しない。
- 保存成功Responseで新しいDraftを上書きしない。自動保存中に入力したFieldを保護する。Dirtyの基準値をどう扱うかはRHF内の表示要件の有無を踏まえ、保存済み値を別の可変RHFフォームとして二重所有しない。
- Mantine `useMantineColorScheme`のTheme選択はRHFへ移さない（現行の管理主体と保存方式を維持）。
- 既存`createPreferencesSaveQueue`のUnit Testを回帰基準とし、RHF接続の追加テストで「入力→Patchが一度だけEnqueueされる」「初期化/Reset時にはEnqueueされない」「無効HEXはEnqueueされない」を検証する。

### Phase 5：Community Accent

**対象**：`CommunityPreferencesContent`、接続側`ConnectedCommunityPreferences`の境界。Aliasとは別フォーム。

- `CommunityPreferencesContent`のColorInput Draftを`useForm<{ accentDraft: string }>`で所有する。`setAccent`の既存PropsとPreview契約は維持し、HEX正規表現を満たす入力だけ接続側へ通知する。
- 接続側の`saved`、`desired`、`inFlight`、`active`、`flush`、Apollo `readFragment/writeFragment`は保存状態のControllerとして維持する。RHFへ移管しない。
- `accent` Propsが保存成功・Rollback・外部Server更新によって変化した時の`reset`は、現行`useEffect([accent])`のDraft同期契約と整合させる。ただし未完成のHEX入力を無関係なRenderで破棄しない。
- 保存中の連続選択は最後の選択値を処理する。Mutation失敗時は共有CacheとInputを最後の保存色へ戻す。Alias更新時のAccent保持、Accent更新時のAlias保持を保証する。
- `isPreview`時は保存もContext更新も行わず、既存のプレビュー表示とStoryの挙動を維持する。

## テストファイルの配置（追加合意）

実装の主たる責務をテストの単位とし、Storyと同様に各実装ファイルの近傍でbasenameを対応させる。Schema Unit Testは`profileSchema.test.ts`、`communityAliasSchema.test.ts`、`communityNameSchema.test.ts`、`preferencesSchema.test.ts`、`communityAccentSchema.test.ts`とする。互いに独立したSchemaのUnit Testを`settingsFormSchemas.test.ts`のような画面単位の大きなテストファイルへまとめない。

横断的な検証が必要なら、個別Unit Testの寄せ集めではなく、具体的な連携BehaviorやContractを検証するテストとして対象と配置を明確化する。テスト内容・期待値は分割によって削除・簡略化しない。

## 実装単位とテストGate

1. 各Phaseでまず既存の正常・失敗・未完成入力・権限・Story状態を比較し、必要なComponent/Interaction Testを追加する。
2. 次にそのPhaseのフォーム入力StateだけRHFへ移し、保存ControllerとGenerated Hookには不要な変更を加えない。
3. Phaseごとのコミットは単一目的に限定する。`[skip ci]`はPR作成済みのブランチへの追加コミットでのみ利用する。PR未作成のブランチでは付けない。この一時的な指示は恒久的な設計規約ではない。
4. Typecheck、Unit、Storybook Interaction、Visual Regression、Next.js BuildをPR上で確認する。少なくともCompact / Medium / Wideで既存Storyと画面レイアウトを比較する。
5. 未解決の仕様変更は実装側で決めず、合意を得てから変更する。PR作成・マージは別途明示的承認が必要。

## 確定事項・実装上の注意

1. **サーバー再取得中の未保存Draft**：Community Nameの `communityName` Props変更時のDraft上書きは既存挙動を維持する。Dirty中保護は今回導入しない。
2. **Context切り替え時**：Context ID単位でフォームのライフサイクルを分離する。Context ID変更時は該当Contextの入力を初期化し、異なるContextへDraft・保存対象を混入させない。
3. **Personal Preferences**：RHFをフォーム値の所有者とする。保存Patchは入力イベントから生成し、Dirty Fieldsを保存トリガーにしない。
4. **既存実装の不整合・潜在不具合の扱い**：Community Name保存reject時の表示など、移行以外の振る舞いは黙って変更しない。必要な改善は別途合意する。

## 実装後の完了条件

- 5フォームの編集中Stateがそれぞれ独立したRHFに管理され、同一意味のDraftをReact local stateへ二重保持していない。
- 既存Queue / Mutation / Cache / Retry / RollbackのBehaviorが維持される。
- UI、文言、操作、Accessibility、Responsive、Storybookの既存契約が維持される。
- Preview / Production両Contextの画面状態が意図せず変わらない。
- 対象の変更はSettings Featureに限定され、必要なGitHub Actionsの結果が成功する。
