# Media Upload HTTP契約

## 位置づけ

Image Originalのupload transportを定義します。Mediaの閲覧・分類・共有・削除・Processing状態はGraphQLを使用し、file bodyだけは同じmemoria-apiが提供する専用HTTP endpointで受信します。認証、認可、Application Use Case、Transaction、Outbox、Processing JobはGraphQLと同じApplication境界を再利用します。

## Endpoint

`POST /api/media/uploads`

Content-Typeは `multipart/form-data` とし、1 requestで1 Mediaだけを登録します。複数file選択UIはWebがfileごとに独立requestを送信します。

## Request

| part | 必須 | 内容 |
| --- | --- | --- |
| `file` | yes | Original binary。1 fileだけ |
| `scopeType` | yes | `PERSONAL` または `COMMUNITY` |
| `communityId` | conditional | `COMMUNITY` の場合だけ必須。Personalでは指定禁止 |

再送制御はbusiness bodyから分離し、HTTP `Idempotency-Key` headerを必須とします。Authorizationもheaderで受け取り、Client指定User ID、Custodian ID、Uploader IDは受け取りません。

filenameとContent-Typeはtransport metadataでありfile formatの正本にはしません。Server-side decode / canonical MIME判定をMedia processing正本どおり実施します。

認証は通常のBFF→API Access Token境界を使用します。PERSONALは認証済みACTIVE User本人、COMMUNITYはcommunityIdと現在MembershipからCustody / authorizationを決定します。

## Success

DB commitまでにOriginal、Media / subtype / Custody、Processing Job、Outbox、Idempotency recordが既存Media transaction契約どおりdurableになった場合だけ成功します。Redis deliveryやVariant生成完了は待ちません。

HTTP `201 Created`:

```json
{"mediaId":"01...","processingStatus":"PROCESSING"}
```

HTTP uploadは受付結果だけを返します。詳細Media modelはGraphQLの `media(id:)` から取得し、HTTP JSONへGraphQLのMedia表現を複製しません。同一`Idempotency-Key` + 同一request hashの再送は同じ受付結果を返し、新しいMediaを作りません。

## Error

```json
{"error":{"code":"VALIDATION","message":"..."}}
```

HTTP statusはtransport分類、Client分岐の正本は安定したApplication error `code` とします。GraphQL `errors[].extensions.code` と可能な範囲で同じApplication error semanticsを使用し、Transport表現だけを分離します。代表mappingは未認証401、権限不足403、不存在404、validation / unsupported media 400、state conflict / idempotency conflict 409、size超過413、予期しない障害500です。内部SQL、Storage key、stack trace、decode detailを公開しません。

## Streamingと上限

APIはrequest body全体をmemoryへ読み込まずstreamとして扱い、既存128 MiB Original上限をtransportでも早期に適用します。Content-Lengthだけを信頼せずstreamed byte countでも超過を拒否します。dimension / pixel / decode上限はMedia processing正本に従います。

S3 Original PUT成功後のDB失敗と補償DELETEはMedia consistency正本に従います。

## Web retry

network failureやresponse喪失時は同じfile commandへ同じ`Idempotency-Key`を再利用します。Userが明示的に再度uploadを開始した場合は新しいkeyを生成します。複数file uploadはfileごとに独立key / requestとし、一部失敗を他fileのrollback理由にしません。


## Schema-first契約とコード生成

HTTP Uploadの機械可読なI/Fの正本は `memoria-api/schemas/openapi/media-upload.yaml` (OpenAPI 3.0.3) とします。本ページは振る舞い・設計理由の正本であり、リクエストフィールド・レスポンス構造・HTTP statusなどはOpenAPIと一致させます。差分が生じた場合は黙って片方を優先せず、設計レビューで解消します。

- BackendはOpenAPIからGoのHTTP型・Handler interface・ルーティング用コードを生成し、手書きAdapterが共通Application Use Caseへ委譲します。
- Frontendは同じOpenAPIからOrvalでTypeScriptのHTTP Client・型・MSW mock handlerを生成し、手書きのUpload orchestrationは生成Clientを利用します。API mockはMSWを介して利用し、生成Clientと同じHTTP契約に従います。
- GraphQLのSchema/gqlgen生成物とは独立した出力ディレクトリに配置し、同じmemoria-apiプロセス内で共存させます。
- 生成物を直接編集しません。生成コマンドをリポジトリへ保存し、再生成・差分検出をCIに組み込みます。
- multipart binaryを128 MiB上限内でstream処理できること、およびBFF経由の認証・Idempotency-Key中継を維持することを生成結果で検証します。
- 生成Clientが担当しないUI状態・複数fileの同時実行制御・曖昧な失敗の再試行判断は手書きのApplication/Presentation側へ残します。

OpenAPIはGraphQLに置き換わるものではありません。GraphQLのQuery/Mutationは従来どおりgqlgenを利用します。GraphQL multipart UploadはInitial Releaseでは引き続き対象外です。

## 対象外

GraphQL multipart Upload、1 request複数Media、direct browser-to-S3、resumable / chunk upload、video固有transportはInitial Release対象外です。
