# 入力検証


## 概要

> 実装状況: GraphQL型、ULID、validator、DB constraintによる検証は一部実装されています。Media file検査と設計ルールの網羅には差分があります。

| 層 | 責務 |
| --- | --- |
| GraphQL | 型、必須、列挙値、scalar形式 |
| resolver・入力変換 | API固有の形式と正規化 |
| Service・domain | 業務ルールと認可 |
| Repository・DB | 一意性、参照整合性、競合 |
| Storage | size、media type、key境界 |

## 全domain共通の入力検証

- Web側の検証は利用者支援であり、API側の検証を省略する根拠にしない。
- 必須の表示名は前後空白を除去し、空文字や空白だけの値を拒否する。
- 文字数、禁止文字、用途別rate limitの具体値は各domainの詳細設計で確定し、共通の保護対象と制限方針は[Security・Privacy要求](/system/cross-cutting/security-privacy-requirements)に従う。
- ULID、列挙値、状態、参照先の存在を、責務に応じた層で検証する。
- 業務ルールと認可はService・domainを正本とする。
- DB error、token、credential、内部identifierをそのまま利用者へ返さない。
- 拡張子だけを信用せず、申告されたContent-Type、file signature、実data、decode可能性、file size、画素数を検査する。
- 許可形式以外のfile、文書、PDF、実行file、動画、SVGは初回Releaseで受け付けない。
- MongoDB JSON SchemaをAPI全体の入力検証規約にはしない。

nickname、Community名、Group名、Tag名などのdomain固有の制約は、それぞれのdomain設計を正本とします。[認証・認可・Privacy共通方針](/system/cross-cutting/authentication-authorization-privacy)も参照してください。
