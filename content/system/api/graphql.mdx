# GraphQL契約

## 概要

> 実装状況: 実行可能なGraphQL契約は `memoria-api/schemas/graphql/*.graphql` です。現在のSchemaにはUser、Community、Media、Groupおよび関連するTag等の型・操作が存在します。ただし本ページに記載されたすべての操作が実装済みとは限りません。実装済みの操作と設計上の操作を混同せず、個別のSchemaとResolverを照合してください。

本ページはInitial ReleaseでWeb Clientから利用するGraphQLの型、Query、Mutation、認可、error、pagination、非同期状態の契約を定義します。APIはschema、Webはoperation・fragment・生成型を所有します。resolver、DataLoader、schema進化、Access Token、GraphQL Errorの実装規約は[GraphQL・gqlgen実装規約](./graphql-implementation)を参照します。

GraphQL I/Fは現時点のProduct / Domain契約から確定できる範囲を実行可能SDLへ引き渡します。Original downloadは既存Security / Storage契約に従い単一Mediaの短期署名URL発行まで確定しています。Account deletionの再認証bindingは、BFFによるAuth0強制再認証とPostgreSQL上の短期Server-side bindingをSecurity境界として確定しています。Browser向けSDLにはproofを公開せず、`reviewToken` と有効なbindingを最終確定時にServer側で照合します。Product / domain semanticsは変更しません。

## 契約原則

- **全ドメイン共通**: GraphQL SchemaのQuery / Mutationは特定画面・ユースケース専用にせず、公開ドメインモデルと操作の責務に基づく再利用可能なI/Fとします。User、Community、Membership、Media、Group、Tag、Account関連のすべてに適用し、ドメイン別の重複型・同義Query / Mutationを安易に増やしません。
- **Web Operationとの責務分離**: Webは画面・ユースケースごとの名前付きGraphQL OperationとFragmentを所有し、SchemaのQuery / Mutationと関連fieldを組み合わせます。Schemaのfield名を画面名やWeb Operation名へ寄せず、同じ責務は異なる画面から再利用します。API内部のApplication Use Caseは認可・整合性・transactionを担当し、Web Operationと1対1対応させません。
- **汎用性とscopeの境界**: 共通化は意味・認可・副作用が一致する責務の範囲で行います。Personal IDとCommunity IDはいずれもULIDであり、ID値・形式から種類を推定しません。既存resourceのIDで対象を特定でき、保存済みの所属情報からscopeを確定できるQuery / Mutationには重複するscope引数を要求しません。一覧・新規作成など対象resource IDがない場合や、同じMediaの分類など指定scopeで結果が変わる場合は、`ScopeInput`等でコンテキストを明示します。Personalは認証済みUser本人を基準とし、Clientから本人のUser IDを要求しません。異なる種類のIDを受け取る必要がある場合は、ULIDから推測したり曖昧な汎用IDにせず、型または意味を明示する引数・fieldを設計します。複数scopeの横断取得や無関係な操作の統合は、具体的な要件がない限り導入しません。Mutationは共通I/Fであっても、共有・退会・削除など異なるUser intentを一つにまとめません。

- Queryは状態を変更せず、Mutationは1つのUser intentを表す動詞と対象の組み合わせにします。
- MutationはInput ObjectとPayloadを使用します。Clientが指定すべきでないUser ID、role、時刻、Custodian等をInputへ含めません。
- Mutationのnestは許可せず、同階層のMutationはそれぞれ独立したtransactionです。
- 単一resource操作は成功時の現在状態をPayloadで返し、Clientが不要な推測や追加取得をしなくてよい契約にします。
- 明示選択した複数Mediaへの操作はMediaごとに認可・現在状態を再検証し、domain仕様が部分成功を許す場合は全件atomicにしません。
- 操作ごとに現在のUser状態、Membership、role、Custody、UploaderをServer側で確認し、Client指定の識別子や表示状態を認可根拠にしません。
- 非公開resourceの存在、SQL、stack trace、Storage key、Auth0 identifier等をresponseへ不要に公開しません。
- request size、Query depth / complexity、取得件数、rate limitに用途に応じた上限を設けます。
- DB更新と非同期処理の連動はTransactional Outboxを利用し、Redis配送完了をMutation成功条件にしません。
- 管理主体委譲、User起点Join Request、動画OperationはInitial ReleaseのGraphQL契約へ含めません。

## GraphQL protection limits

request size、query depth / complexity、execution timeoutは防御機構を必須とし、consumerで使用する全OperationをCIで検証します。具体値はSchema / Operation実装後の計測で確定し、実測前の値を恒久contractとは扱いません。

Initial provisional valueは次のとおりです。

| 項目 | 暫定値 |
| --- | --- |
| GraphQL HTTP request body | 1 MiB |
| Query depth | 12 |
| Query complexity | 1000 |
| Execution timeout | 10秒 |

既存NFRのrate limit（User 60 requests/minute、burst 20）とConnection取得件数（default 30、max 100）は別layerの既存contractとして維持します。実装後、正規のconsumer Operationを計測し、正常な最大Operationへ十分なmarginを持つ値へ更新します。

## モデル中心の公開境界

GraphQLはDBの外部キーをそのまま公開するのではなく、Clientへ公開するドメインモデルと本質的な関連を表現します。Queryはモデルへの入口、関連fieldはモデル間の移動、MutationはUser intentを表します。関連の逆方向は利用目的がある場合だけ公開し、単に技術的に辿れるという理由では追加しません。

- Communityの関連fieldは所属を表す `members: CommunityMembershipConnection!` に限定します。Membershipは共通 `User` とCommunity固有のroleを結ぶ関連モデルであり、単純なUser配列にはしません。親Communityへの逆参照やCommunity専用の重複User型は設けません。
- CommunityのMedia / Group / TagはCommunity自身の構成要素として公開しません。これらはそれぞれ独立したドメインモデルであり、Communityを利用範囲として指定するQueryから取得します。
- 一覧関連はConnectionでページングし、DataLoaderは1 GraphQL request内でbatch/cacheします。DataLoaderは深いnestや大量取得を制限する仕組みではないため、query depth / complexityと取得件数の制限は維持します。
- ネストしたRelay ConnectionはGraphQL全体で許容します。親モデルから辿ることがドメイン上自然であれば関連fieldとして公開し、ネストしているという理由だけで重複するトップレベルQueryを追加しません。独立した取得・認可・利用上の理由がある場合は別Queryを検討します。
- Apollo Clientでは親モデルをIDで正規化し、Connection fieldごとに引数・filterを考慮したpagination policyを定義します。Media削除、関連追加・除外など一覧の構成が変わるMutation後は、影響するConnectionの無効化・再取得を初期方針とし、手動のedge更新は必要性を検証してから採用します。Mediaのevictだけで関連Connectionのedges・pageInfoが同期されるとは見なしません。
- 実装時はネストしたConnectionの初回取得・追加ページ取得・削除・関連追加／除外・filter変更を組み合わせ、複数の親モデルでキャッシュが混線しないことと、Mutation後に一覧・pageInfoが整合することを検証します。
- MediaのGroup / Tag分類はPersonalとCommunityで独立しているため、scopeを曖昧にした関連fieldを追加しません。Groupの親子・所属Mediaなど、必要な関連の具体的なSDLは既存ドメイン仕様と照合してレビューします。

## scope指定の横断検証

公開するQuery / Mutationと関連fieldを、対象の識別方法に基づき横断確認した結果を以下に固定します。ULIDの形式ではPersonal / Communityを識別しません。既存resourceはDBの所属・関連を参照し、認可は各操作時に再検証します。

| 対象 | scope / ID契約 | 理由・検証 |
| --- | --- | --- |
| `me`、Profile更新、Account削除Review / Confirm | scope不要、認証主体で特定 | Clientから本人のPersonal IDを受け取らない |
| `community(id:)`、Community更新・削除、Membership・Invitation管理 | `communityId` またはCommunityのIDを指定、scope不要 | Communityという対象種別がfield / Inputで確定する |
| `myCommunities` | scope不要、認証主体で特定 | 本人の所属Community一覧 |
| `media(id:)`、Media削除 | `mediaId` 等で対象特定、scope不要 | Media本体の識別と閲覧・削除認可は別。閲覧可能な複数scopeがあってもMedia本体は同一 |
| `mediaList`、`mediaGroups`、`mediaTags` | `ScopeInput!` 必須 | 一覧の取得範囲を選ぶ必要がある |
| `Media.groups`、`Media.tags` | `ScopeInput!` 必須 | 同一Mediaの分類はPersonal / 各Communityで異なる。Media IDだけでは分類scopeを決定できない |
| Group / Tag作成 | `ScopeInput!` 必須 | 作成前に対象Group / TagのIDが存在しない |
| Group / Tag詳細・名称変更・削除 | 対象Group / Tag ID、scope不要 | 対象の保存済み所属からscopeを確定する |
| Group間relation追加・解除 | `parentGroupId` と `childGroupId`、scope不要 | 双方の所属を取得し同一scopeを検証する。異scopeを許可しない |
| Group / TagへのMedia分類 | `groupId` / `tagId` と `mediaIds`、scope不要 | 分類先の所属からscopeを確定し、各Mediaがそのscopeで閲覧・分類可能か検証する |
| Media共有・共有解除 | `mediaIds` と `communityId`、scope不要 | 共有先のCommunityを明示し、各MediaのCustody・権限を検証する。Personal / Communityの汎用owner IDにはしない |
| Community削除Impact・Account削除のCommunity解決 | `communityId`、scope不要 | 操作対象のCommunity種別が明示されている |

`ScopeInput` は `type: PERSONAL` のとき認証済みUser本人を表し `communityId` を禁止します。`type: COMMUNITY` のとき `communityId` を必須とし、現在のMembershipと対象Mediaの可視性を検証します。既存resource IDから所属を解決する操作では、異なるscopeのIDを同時に指定しても暗黙に変換・横断処理しません。

## Error契約

### Hybrid Error Model（2026-11-02合意）

GraphQLにおける失敗を**業務結果・実行/Request Error・通信上の未確定状態**に区分する。これはGraphQL仕様がUnionを強制するという意味ではなく、Memoriaの型安全な公開契約とForm UXのために採用する設計方針である。既存の「Transport / Application Errorはすべて`errors[].extensions.code`で表現する」という規則を、この節の境界に置き換える。

| 区分 | 公開位置 | 意味 |
| --- | --- | --- |
| 期待される業務上の失敗 | Mutationの型付きResult（必要な操作ではUnion） | 入力検証、修正可能な業務制約、競合など、正常に評価した結果として操作が成立しなかった |
| Request / Execution Error | GraphQL `errors[]`（必要な`extensions.code`） | 不正なGraphQL文書/変数型、認証・認可、リソースの存在秘匿、Resolver/依存障害など、Operationが正常に完了しない |
| Transport / Unknown Outcome | HTTP/Network状態およびClient管理 | Responseを受け取れない等、Mutationが確定したかどうかをClientが断定できない |

**境界原則**：

- 期待される業務失敗はSchemaで表現する。すべてのMutationをUnion化するのではなく、そのCommandで定義すべきFailure分岐があるときだけ型付きResultを設ける。成功だけを持つMutationは通常のPayloadを使用できる。
- Success Resultは操作の**確定した永続化結果**を返す。業務的なFailure ResultはそのCommandが書き込まれず拒否されたことを意味する。Bulkの部分成功は各Item Resultの契約を優先する。
- 認証・認可・対象の存在秘匿・内部障害を通常の業務Resultへ混在させない。GraphQLの`errors[].path`はResponse上の失敗位置であり、Input FieldのPathではない。
- Input Coercion / GraphQL型不整合はResolver実行前のRequest Errorであり、Domain Validation Resultではない。
- GraphQL `data`と`errors`の同時返却、nullableのError伝播を許容するが、単一Mutationの成功PayloadとExecution Errorが混在した際の保存確定判定はOperationごとに定義する。応答がないことは保存失敗の証明ではない。
- APIはUIのNotification種別・文言配置を返さない。Error Codeは安定した機械判定識別子とし、国際化・表示文言・表示位置はClientの責務とする。

### 型付きMutation ResultのSchema規則

```graphql
type UpdateUserProfileSuccess {
  profile: UserProfile!
}

type InputViolation {
  inputPath: [String!]!
  code: String!
}

type InputValidationFailure {
  violations: [InputViolation!]!
}

type DomainRuleFailure {
  code: String!
}

type StateConflictFailure {
  code: String!
}

union UpdateUserProfileResult =
    UpdateUserProfileSuccess
  | InputValidationFailure
  | DomainRuleFailure
  | StateConflictFailure

extend type Mutation {
  updateUserProfile(input: UpdateUserProfileInput!): UpdateUserProfileResult!
}
```

上記SDLは**型と意味の設計例であり、現時点の実行可能Schemaや全Mutationの確定SDLではない**。例示したFailure型を一律に追加せず、各操作で現実に発生し得る業務Failureのみを列挙する。具体的な公開名・Code/Enum・各MutationのResult構成は後続のOperation別設計で確定する。必要があれば共有可能なFailure型を使うが、共通化のために独立したBusiness Ruleを曖昧にしない。

- Input Validationは1件以上のViolationで修正対象を示す。`inputPath`はMutation Input Object内のパス（例：`["nickname"]`）であり、複数入力にまたがりFieldへ帰属しないErrorはForm LevelのFailureとして定義する。内部DB名・非公開resource情報を露出しない。
- `code`はMachine-readableなReasonを意味し、Messageの一致検査に依存しない。ClientはCodegenにより`__typename`を判別し、必要なField ResultをType Safeに処理する。
- State Conflictは競合元や現在状態の開示が認可上安全な場合だけ詳細を返す。最新状態の再取得・再入力・再送などの回復手段はCommand単位の契約で定める。
- Bulk Mutationの部分成功は従来どおりPayload内のItem Resultとし、個別FailureをMutation全体のExecution Errorへ変換しない。

### GraphQL Request / Execution Errorの公開規則

`errors[].extensions.code`は、GraphQL Request / Executionの失敗をClientが安全に識別するために使用する。Domain Failureをすべてこの層へ戻さない。

| code | 意味 | 主な扱い |
| --- | --- | --- |
| `UNAUTHENTICATED` | 認証主体を確定できない | 再認証・Session確認 |
| `USER_REGISTRATION_REQUIRED` | 認証済みだがProduct登録前 | 登録導線 |
| `USER_DELETING` | Userが通常操作を実行できない状態 | 操作継続不可 |
| `FORBIDDEN` | 閲覧可能な対象に対する操作権限がない | 操作停止・権限確認 |
| `NOT_FOUND` | 対象不存在、または権限のない対象の存在秘匿 | 対象確認。存在有無を漏らさない |
| `RATE_LIMITED` | Rate Limit | 制限中の案内。Retry可能時刻等は明示契約がある場合のみ |
| `INTERNAL` | 安全な内部障害分類 | 技術詳細を隠蔽し、結果確認が必要なMutationではUnknown Outcomeを考慮 |

**公開コードの最終確定はAPI実装引き渡しで行う。** `INTERNAL`と現行`INTERNAL_SERVER_ERROR`、現行`UNAUTHORIZED`等の不一致を整理し、Schema設計・Presenter・Integration Testを一致させる。旧来の`VALIDATION`・`CONFLICT`は業務Resultへの移行対象だが、GraphQL Request Coercion等に由来するRequest ErrorとDomain Validationを混同しない。Reasonが業務失敗であると確認できる場合にだけResultへ写像する。既存公開Error Codeは明示的な移行計画なしに削除しない。

**閲覧可否に基づく公開エラー**：存在しない対象と現在主体が閲覧権限を持たない非公開対象は、どちらも`NOT_FOUND`として扱い、存在差を公開しない。現在主体が閲覧可能な対象への権限外操作は`FORBIDDEN`、認証主体を確定できない場合は`UNAUTHENTICATED`を優先する。

**Transport**：GraphQL ResponseのHTTP Statusは`extensions.code`をHTTPの403・404等へ機械的に変換する契約ではない。Request Parse/Validation、Execution、HTTP Failureを分けて設計・試験する。Network Timeoutや通信断はError Codeが返ったものとみなさず、ClientのUnknown Outcomeで管理する。

**結果未確定と再送**：Unknown Outcomeはサーバーから`UNKNOWN_OUTCOME`が返るケースもあり得るが、一般にはClient側の知識状態である。再送してよいかはCommandの冪等性、監査・Event等の副作用、Idempotency Key / Version / 事後照会の契約で判断する。設定値のSet操作でも、最終値が等しいことだけで再送の全副作用が安全とは限らない。Mutationの確定Successと後続Refetch失敗は独立したResultとして扱う。

### 実装への引き渡しと現行実装との差分（2026-11-02）

現在の`memoria-api/develop/graph/handler.go`は`UNAUTHENTICATED`／`VALIDATION`／`CONFLICT`／`FORBIDDEN`／`NOT_FOUND`／`UNKNOWN_OUTCOME`／`INTERNAL_SERVER_ERROR`などを`errors[].extensions.code`へ返しており、ここで確定したHybrid Modelとはまだ一致しない。特にDomain Validation / ConflictのResult型、Field Pathの帰属、API公表Codeの正規化は未実装である。

- APIの設計正本を変更した後、実行可能`schemas/graphql/*.graphql`、gqlgen、Error Presenter、Domain Error分類、GraphQL Integration Testを同じContractへ移行する。
- WebはGraphQL CodegenによるMutation Resultの型付き分岐と、Execution Error / Transport Errorの個別処理を持つ。既存の`Promise<boolean>`やConnection層の通知発火はFeature Form OwnerのFeedback契約へ置き換える。
- 既存Media Group / Bulkの部分成功・Reason表現、Account・Community削除などの冪等性と認可契約は影響分析してから移行する。既存UI / Behaviorを変更する箇所は個別にテストし、黙って簡略化しない。
- 既存の画面/UIが`errors[].extensions.code`だけを参照している間は移行期の互換性を明記し、一括置換で意図しないError表示を生まない。

### 既存GraphQL I/Fの直接改修方針（2026-11-02合意）

**Operation互換用の並列I/Fは作成しない。** 現行`memoria-api/schemas/graphql/*.graphql`のQuery / MutationをSource of Truthとして棚卸しし、Hybrid Error Modelで意味の変わる既存Fieldの戻り値・Error分類・必要なInputを直接更新する。古い契約を温存するための`*V2`、`*WithResult`、`*New`などのMutation / Queryを作らない。後方互換のための旧Field併存も原則禁止する。

- **OperationのUser Intentを維持**：既存Mutationの機能を複数の新Mutationへ分割したり、異なるUser Intentを横断的に統合したりしない。GraphQLの共通Failure Object / Enum / Union / Input型の新設は許容するが、Mutation / Queryの追加とは区別する。
- **非互換変更を許容**：戻り値をPayloadからResult Unionへ直接変更し、既存GraphQL Operation・Fragment・生成型・Resolver・Web Adapter・Testを同じ新契約へ改修する。Consumerを型付きResultへ移行する責務を省略しない。
- **名称の不一致**：現行Schemaの`renameCommunity`とAPI設計正本の`updateCommunity`は不一致。既存の設計正本で決定済みの`updateCommunity`へ単一Fieldを**置換**する案を維持するが、`renameCommunity`と`updateCommunity`を同時公開しない。「Operation名も完全に保持する」意図なら命名規約との設計衝突があるため、実行前に最終合意を得る。
- **Query**：既存Queryは原則Data Modelを返すままとし、GraphQL Request / Execution Error・部分Data・認可・Nullableの契約を整える。Hybrid Modelの採用だけを理由にQuery用Union・新Queryを追加しない。
- **Bulk**：既存Bulk MutationのItem Resultと部分成功の意味を維持し、共通FailureとOperation Errorの分類を整合させる。既存Consumerの個別結果情報を削らない。
- **切替手順**：GitHub上でAPI / Web双方の変更対象を確定し、GraphQL SDL→gqlgen / Resolver / Error Presenter→API Contract Test→Web Operation / Codegen→Form UI / Cache / Interaction Testを整合した単位で変更する。本番配備・Releaseは別途承認が必要。新旧APIの同時稼働を前提としたcompatibility layerは用意しない。
- **検証**：既存GraphQL Schema上のQuery / Mutationを横断検索し、業務FailureをGraphQL ErrorにするべきでないOperation、実行ErrorをPayloadへ混ぜているOperation、Bulkの部分成功、Authentication/Authorization、Error Path、Null Bubbling、Data+ErrorsをAuditする。すべてのOperationを機械的にUnion化しない。

#### 共有FailureとValidation Codeの採用基準（2026-11-02合意）

`InputValidationFailure`と`InputViolation`は、複数Mutationで同一の意味を持つ共有Objectとして採用する。具体的なUnion MemberはOperation別に列挙し、必要のないFailureを追加しない。`InputViolationCode`は安定した汎用的な入力制約カテゴリを表すGraphQL Enumを採用する。SDLドラフトの`REQUIRED`、`INVALID_FORMAT`、`INVALID_VALUE`、`TOO_LONG`、`OUT_OF_RANGE`、`INVALID_COMBINATION`は候補集合とし、実際のDomain制約を監査して正式な列挙値を確定する。

`inputPath: [String!]!`はInput Objectに相対のField Pathを表す。必ずしも単一FieldへErrorを割り当てられないケースを、空のPath等で曖昧に表現しない。Cross-field / Form-levelの機械可読な帰属表現は次の詳細設計で確定し、Clientが未知のPath / Enum値を受信した場合には安全なForm AlertにFallbackする。

Domain RuleやState Conflictは`InputValidationFailure`へ混在させない。操作固有の制約は専用Reason Enum / Failure型を優先し、実際に複数操作で意味を共有することを確認できた場合に限り共通化する。GraphQL Enumの将来追加に備えてClientのunknown handlingを契約とし、公開ReasonをUI文言として直接描画しない。

### Settings Mutationの型付きResult：Operation別SDLドラフト（2026-11-02、詳細合意待ち）

この節は**Hybrid Error Model確定後のOperation別設計提案**であり、実行可能Schemaへ適用済みではない。GraphQLで有効な型構成と、実装に必要な契約・追加判断を示す。既存仕様と異なるOperation名・Failure Case・Idempotency / Revisionの選択を合意なしに実装へ適用しない。

#### 共有Failureの境界

```graphql
"""
Mutation Input Object内のパス。例: ["nickname"], ["dateFormat"]。
GraphQL errors[].path（Response Field path）とは異なる。
"""
type InputViolation {
  inputPath: [String!]!
  code: InputViolationCode!
}

enum InputViolationCode {
  REQUIRED
  INVALID_FORMAT
  INVALID_VALUE
  TOO_LONG
  OUT_OF_RANGE
  INVALID_COMBINATION
}

"""
各Violationは入力修正で解決可能な情報に限る。
空配列を返さないことをResolver契約で保証する。
"""
type InputValidationFailure {
  violations: [InputViolation!]!
}

enum DomainRuleCode {
  OPERATION_NOT_ALLOWED_IN_CURRENT_STATE
}

type DomainRuleFailure {
  code: DomainRuleCode!
}

enum StateConflictCode {
  STALE_STATE
}

type StateConflictFailure {
  code: StateConflictCode!
}
```

- **共有する条件**：結果の意味・参照するClient UI分岐・安全な公開情報が同じ場合に限る。操作特有の失敗理由は無理に汎用Enumへ足さず、専用Failure Object / Reason Enumの利用を優先する。上記EnumのValueは**候補**であり、実際に発生するDomain Failureがない限りOperationへ含めない。
- 入力Fieldの識別子はGraphQL Inputの公開Field名を使い、UI Component名やFormのLabelを含めない。`inputPath`の先頭はInput変数ではなくInput Object直下を表す。非公開ID・DBの構造・Security上の情報を含めない。未知のPathはClientでForm AlertへFallbackする。
- GraphQL Enumを用い、Codegenで既知の値を型として扱う。将来Enum値が増えた場合のUnknown FallbackをClientに設ける。CodeをUI文言として表示しない。複数Field間のValidationで修正可能Fieldが特定できない場合はForm LevelのFailureを検討する（空Pathの使用規則は別途確定）。
- GraphQL Unionに含まれる共通Failureは、別Operationからも利用できるが、Unionを列挙する単位はOperationごと。Clientは`__typename`とOperation文脈で分岐する。複数のUnionで同名の共通Failure Objectを利用することはGraphQL Schema上可能。
- Failure Resultは**業務制約を評価した結果、該当Commandの永続化が成立しなかった**ことを表す。原子性を持つ単一resource更新の途中成功や、成功後のRefetch失敗をFailure型にしない。

### Cross-field Validation・同時更新・Unknown Outcome：詳細設計案（2026-11-02、選択事項は合意待ち）

この節はHybrid Error Modelと「既存I/Fを直接改修する」合意に従う詳細設計案である。Cross-fieldの帰属規則、更新競合のPrecondition、結果未確定からの復旧を**相互に混同しない**。以下に示す追加FieldやVersionは新Mutation / Queryの導入を意味しない。後述の判断事項が確定するまでSDLへの実装は行わない。

#### Cross-field / Form-level Validationの帰属

現在の`InputViolation { inputPath: [String!]!, code: InputViolationCode! }`は単一Fieldを表すには十分だが、複数Fieldの関係やFieldへ帰属できないInput制約を自然に示せない。空Pathを暗黙のForm Errorとして流用せず、**Errorの対象Scopeと関連するInput Pathを別の情報として型で表す**ことを推奨する。

```graphql
enum InputViolationScope {
  FIELD
  FIELD_GROUP
  FORM
}

type InputFieldPath {
  segments: [String!]!
}

type InputViolation {
  scope: InputViolationScope!
  code: InputViolationCode!
  inputPaths: [InputFieldPath!]!
}

type InputValidationFailure {
  violations: [InputViolation!]!
}
```

上記は既存ドラフトの`InputViolation`を**置換する候補**であり、同名型を別に追加しない。Resolver / Serviceで次の不変条件を保証し、Integration Testで検証する。

- `FIELD`は関連Pathがちょうど1件、`FIELD_GROUP`は関連する相異なるPathが2件以上、`FORM`は0件または説明用の関連Path群。Field指定が曖昧であれば`FORM`を選ぶ。
- `InputFieldPath.segments`は1件以上のGraphQL Input Field名からなる。配列要素等のPath表現は必要なOperationで形式を追加定義し、現在のClientが理解できないPathはForm ErrorへFallbackする。
- `FIELD_GROUP`の`inputPaths`は「関連する入力」を識別するための情報であり、すべてのFieldの下に同じ文言を重複表示する指示ではない。
- Clientは`FIELD`をField Error、`FIELD_GROUP`を関連Field群の近傍またはForm Alert、`FORM`をForm Alertに表示する。可視Text・Focus・Accessible Descriptionの関連付けはForm Ownerが制御する。
- `code`は公開された汎用制約の分類であり、詳細なDomain ReasonやUI文言ではない。Operation固有の条件を既存Enum値へ無理に写さず、必要に応じて専用Reason型を使用する。
- GraphQL Request Coercion ErrorはResolver実行前なので、この型付きFailureではなく`errors[]`へ残る。

**採用を推奨**するが、このSDL変更はまだ合意済みの個別Schema仕様ではない。

#### 同時更新：Server側Preconditionの責務

同じClient内でのMutation直列化は別端末・別タブのLost Updateを防止しない。Serverが参照した確定状態と同じRevisionを前提に更新する**Optimistic Concurrency Control（OCC）**を、同時編集で他の確定値を失わせるべきでないAggregateへ導入する設計を推奨する。

- ProfileはUser Profile、User PreferencesはUser Preferences、Community名はCommunity、Community Alias / Accentは**User × Community Settings**を独立した更新対象とする。異なるAggregateのRevisionを混用しない。
- 各更新対象の既存Query / PayloadでOpaqueな`revision`を公開し、既存Mutation Inputに`expectedRevision`を追加する案。RevisionはServerが発行し、Clientは値の内部形式・大小比較へ依存しない。
- Serverは認証・認可・入力検証後、同一Transactionで`expectedRevision`と現行Revisionを比較し、一致時だけ更新・Revision更新を確定する。未一致なら永続化せず型付き`StateConflictFailure`を返す。Conflict時の現在値を公開してよいかは認可上検証する。
- *部分更新では未指定Fieldを変更しない*ことを維持する。Aggregate全体のRevisionだと異なるFieldへの独立編集も競合するため、Conflict時は最新Queryと保護されたDraftとの差分を再評価し、ユーザー操作や再送Policyを定義する。差分を見ずに旧Patchを自動再送すると新しい確定値を失う可能性がある。
- ProfileやCommunity名の同値更新・Normalized Valueの扱い、Alias解除(`null`)時のRevision増分、「実質変更なし」でRevisionを進めるかはDB更新契約に明記する。
- 自動保存はPatchごとに送信Snapshotと`expectedRevision`を保持。成功レスポンスの確定Revisionへ進め、Queue中の新Draftを維持する。Conflict時はQueueを止めてRefetch、差分評価とFeedbackへ移る。SnapshotとRevisionが不一致のまま再送しない。

**代替案**：単一Fieldを同じ値へ収束させるSettingsの一部ではLast Write Winsとし、すべてのSettingへOCCを導入しない。OCCは不要な競合・再試行の負担を増やすため、実際の編集損失リスクとUIの解決導線をOperationごとに判断する。**一律OCC導入はまだ確定しない。**

#### Unknown Outcome：Clientから観測できる事実と復旧の設計

通信断・Timeoutは「Mutation未実行」を証明しない。結果未確定は保存失敗、Serverが返す`StateConflictFailure`、一時的なRefetch失敗と区別する。

| 観測結果 | Clientの保存判定 | 復旧候補 |
| --- | --- | --- |
| 型付きSuccessを受信 | Confirmed。応答の値・RevisionをBaselineへ | 必要なら背景Refetchを独立実行 |
| 型付き業務Failureを受信 | Commandは不成立 | Field / Form Error、Conflictなら差分確認 |
| Responseを受信できない | Unknown Outcome | 同一対象の既存Queryで現状態を確認。因果関係は推測しない |
| Mutation成功の後にRefetch失敗 | 保存はConfirmed、Refreshのみ失敗 | 元の保存成功を取り消さずRefreshの再試行 |
| Queryで現在値が以前と一致 | Request不成立の証明にはならない | 未確定表示を維持し、再送条件を検討 |
| Queryで送信値と一致 | 現在状態は送信意図と一致。ただし当該Requestの成功証明とは限らない | 後続操作の副作用と整合条件を確認してUIを回復 |

**回復の選択肢**：

- **最終値を設定するだけの単純なSetting更新**：再送で副作用が重複しないとAPIが保証するなら、現在Revisionを確認し、まだ適用されていないField Patchのみ再送可能とする。ただし通常のGet後に他端末が更新し得るため、必要ならPreconditionを付ける。
- **副作用が重複するOperation**：既存`content/system/api/idempotency.mdx`のKey契約（同一Key＋同一Request、24時間保証）をOperationの必要性に応じて採用する。同じ操作をRetryする際に新しいKeyを発行しない。期限外は重複防止を保証しない。
- **安全な再送も明確な結果照会もできない場合**：Clientが保存完了を断定したり自動再送したりせず、未確定状態と現在データを示す。重複副作用のある操作では再確認の導線が必要。

Keyだけで別端末のLost Updateを防ぐことはできず、Revisionだけで同一Requestの二重副作用を防げるとも限らない。OCCは*並行変更の整合性*、Idempotency Keyは*同じ論理要求の重複副作用防止*、Refetchは*現在状態の観測*という別の役割を持つ。

#### 変更対象と検証条件

- API：既存QueryのRevision Field（採用対象のみ）、既存Mutation InputのPrecondition、同名MutationのSuccess / Failure Union、RepositoryのAtomic Compare-and-Set、Operation単位のError / Idempotency Test。互換用の新Query / Mutationを追加しない。
- Web：各Formの最新Draft・送信Snapshot・Confirmed Baseline・Revision・Unknown Outcomeを分離し、Result毎にFeedbackを選択。Apollo CacheとServer確定値の帰属を維持する。自動保存QueueはConflict / Unknownで無条件再送を停止する。
- Test：2Clientの同時更新、異なるFieldのPartial Patch、同値更新、Validation FailureのField / Group / Form、通信断の前後、成功後Refetch失敗、In-flight中の新Draft、同一Idempotency Key Retry、Expired Key、Context切替後の古いResponseを、必要なOperationのUnit / Integration / Interactionで検証する。

#### 追加合意が必要な判断

1. InputViolation Scope + 関連Path群の構造を採用するか。
2. OCC / Revisionを導入するAggregateの範囲と、Aggregate全体Revisionによる独立Field競合を許容するか。特に自動保存のSettingsは競合解決UXと一体で選ぶ。
3. Settingsの各更新を再送安全なSet操作として保証する範囲と、監査・Outbox等への副作用の重複を許容するか。
4. Unknown Outcome時、再取得後に自動再送するか、ユーザーによる確認後に再送するか。
5. Community名のOperation名を既存設計の`updateCommunity`に統一するか（旧`renameCommunity`との並存は禁止）。

### Personal Preferences / Community Accentの並行更新・自動保存UX設計（2026-11-02、実装判断待ち）

Hybrid Error Model、既存Query / Mutationの直接改修方針、および前節のCross-field / OCC / Unknown Outcome案を、2種類の自動保存へ具体化した設計案。**ここでのRevision選択・競合回復・色のRollbackはまだ個別合意前であり、実行可能SDL / Repositoryは未変更**。

#### 実装上の確認事項

- 現行`memoria-api`の`updateUserPreferences`は指定Fieldのみ更新し確定した`UserPreferences`を返す。User Preferencesの公開モデルにRevisionはない。`User × Community Settings`もAccentとAliasを一つの設定行で管理し、`updateCommunitySettings`は指定FieldだけをUPDATEし両Fieldの確定値を返す。こちらもRevisionはない。
- 現行WebのPreferences Queueは400ms Debounce、Patch結合、直列実行、失敗Patchの復帰を行うが、`onSaved`は送信Snapshotを受け取らず、RHFの確定済みField / Dirtyの解消も保証しない。
- 現行Community Accentは選択直後にApollo Cacheへプレビューを反映し、失敗時に保存済み色へ戻す。Aliasは同じ`updateCommunitySettings`を独立に送信するため、2操作を同時に処理した場合の同一Aggregate Revision/Cacheの整合を設計する必要がある。

#### 推奨する整合性モデル

**第一候補：Aggregate Revision + Field-aware 3-way Merge + Atomic CAS**。

- `UserPreferences.revision`と`CommunitySettings.revision`を既存Queryで参照できる形に追加し、対応する既存Mutation Inputへ`expectedRevision: String!`を付与する案を採る。GraphQL上はOpaque String。Community Settingsは**User × Community**単位であり、Community本体のRevisionと混同しない。
- BackendはTransaction内で同一Aggregateの現在Revisionと期待Revisionを比較し、一致時のみPatchをatomicに確定させて確定値＋新Revisionを返す。不一致なら書き込まず型付き`StateConflictFailure`を返す。認証／権限／存在秘匿はExecution Errorを維持する。
- Webは`base`（送信Snapshotを構築した時点の確定値）、`desired`（最新のユーザー意図）、`serverCurrent`（再取得した確定値）をField単位で比較する。同Fieldが他Clientによって変更されたかは`serverCurrent[field] !== base[field]`で判定する（正規化済み値）。別Fieldのみ変更されている場合は現在Revisionを使った**必要FieldだけのPatch**を自動再構成できる。
- 同じFieldが他Clientで変更され、なお`desired[field] !== serverCurrent[field]`なら**真の競合**としてQueueを停止し、ユーザーの選択を保ったまま現在値との比較・採用操作を提供する。同じ確定値へ収束している場合は、現在値として受理できるが「どの要求で書き込まれたか」を断定しない。
- 同じAggregate内のAliasとAccentも共有Revisionで直列化する。別Fieldへの変更を安全に再適用するときも、参照したRevisionでCASを行う。競合再試行は無制限に繰り返さず、さらに競合すれば手動判断へ移す。
- **制約と代替案**：Aggregate Revisionは別Field編集でもConflictが発生し、追加Refetchが必要。Field単位Revisionは競合頻度を下げるがSchema/DB/Codegenを複雑化する。採用前にField数・競合頻度・既存のUIと照合する。Revision導入の必要性と粒度は明示合意を得る。

#### PreferencesのQueue契約

`confirmed`、`editing draft`、`pending patch`、`in-flight snapshot`、`save status`を区別し、RHFは表示用Draftの唯一のOwner、Queueは通信順序・結果のOwnerとする。別のRHF Formを「保存済み値」管理に導入しない。

1. 有効な入力変更のみPatch化し、400ms DebounceでPendingへ結合する。未完成HEX入力は表示用Draftとして保持し、完全なHEXになるまで送信しない。
2. FlushではPatch・Base Revision・送信前確定値をSnapshotとして固定。in-flight中の追加編集は次Pendingへ蓄積し、古い応答で上書きしない。
3. Successでは**送信したFieldと確定レスポンス**を照合し、Confirmed BaselineとRevisionを進める。Fieldが送信後に再編集されていなければRHFの未保存・Dirtyを解消する。再編集されていればRHF Draftを保持し、次のPatchを処理する。レスポンスの全Fieldを無条件`reset`しない。
4. Conflictでは新規送信を止めて既存QueryをRefetchし、3-way Mergeを行う。別Fieldへの安全な変更だけ再送、同Field競合はユーザーの確認があるまで送らない。新しい入力と元の入力内容を破棄しない。
5. Operationが拒否されたことが確定したValidationは、該当Field / Formに持続表示する。Unknown Outcomeは送信済みPatchの状態を`unconfirmed`に保持し、再取得の結果に応じて復旧。単純な通信Errorを確実な未保存に変換しない。
6. Unmount時は、単に`flush()`を呼ぶだけで保存結果の管理責務を失わないよう、Pending / in-flightの寿命とナビゲーション境界を定義する。画面外継続が必要ならQueue Ownerを画面Componentより長命な場所に配置し、結果未確定の状態も観測可能とする。

#### Community Accentの表示・Rollback案

**推奨：共有の確定状態と一時プレビューを分離し、失敗時もユーザーが選択した色のDraftは保持する。**

- `confirmedAccent`：Backendで保存確定した色。Apolloの共有Server Stateに反映する。
- `previewAccent`：ユーザーの最新選択（未確定）。画面やContextの見た目へ即時反映できるが、Apolloの確定済みServer値と同一視しない。Preview Ownerが生存中の一時的Overlayとして管理する。
- `accentDraft`：ColorInputに入力中の文字列。不完全HEXは保持し、Mutationへ送らず、プレビューの変更も有効な値のときだけ行う。
- **Confirmed Success**：Backendが確定した色＋RevisionをBaselineに反映。より新しい選択がなければOverlayを解除。Aliasの確定状態を上書きしない。
- **Validation / 明確な保存失敗**：共有表示のAccentを最後に確定した色へ戻す一方、ColorInputの**最後の選択値を保持**し、Form近傍に理由・再試行／変更破棄を表示する。ユーザー意図を丸ごと消さない。
- **Unknown Outcome**：Overlayを確定値として扱わない。共有表示は直近の確定色へ戻す案を基本とし、選択Draftは`保存結果を確認できません`とともに保持、既存Queryで現在値を確認する。自動で同じMutationを再送しない。
- **Conflict**：別端末の確定色とユーザーの選択を並べ、現在色を採用／自分の色で更新（新Revision CAS）の明示操作を提供する候補。Aliasが同時に変更された場合は、その確定Aliasを維持してAccentだけをPatchする。
- Communityの切替後に旧CommunityのOverlay・in-flight結果が新Communityへ漏れないことを保証する。Shellへの見た目反映を行う場合はOverlayの所有範囲・終了条件を設計する。

#### 自動保存StatusのUX案

| Condition | Presentation | 備考 |
| --- | --- | --- |
| 入力中・Pending | 控えめな「保存待ち」 | 絶えず表示切替して騒がしくしない |
| In-flight | 控えめな「保存中」 | 複数Patchをまとめて表示 |
| PendingもIn-flightもないConfirmed | 「保存済み」を一時表示後、必要なら非表示 | 最後の成功が確定している場合のみ |
| Retryable / Validation | 消えないForm AlertまたはField Error | ユーザーの修正／再試行が必要 |
| Unknown Outcome | 消えないForm Alert：「保存結果を確認できませんでした」 | 状態確認を先に促す |
| Conflict | Form Alert + 比較・選択導線 | 一律のToastで済ませない |

Statusはフォーム単位とし、すべてのSetting Rowに常時ラベルを置かない。スクリーンリーダーへの保存中/保存済み通知は重複読み上げを抑え、エラーでは`role="alert"`等を適切に使い、Focusを不必要に奪わない。表示位置・一時保持時間・Compact / Medium / WideはStoryで確定する。

#### API / Webのテスト条件

- Atomic CAS：同Revisionでの2Client更新では1つが確定、他方がConflict。異なるFieldの変更ではRefetch後の再適用が安全であること。
- AccentとAlias：同じUser × Community Settings Revisionを共有し、片方の更新結果で他方を巻き戻さない。Alias解除`null`とHEXの正規化もテストする。
- Queue：Debounce、in-flight追加変更、送信SnapshotごとのSuccess、Dirty解消、Conflict停止、RefetchとField Merge、Unknown Outcomeでの送信停止。
- UI：未完成HEXを維持、プレビューと確定色を区別、失敗後に選択Draftを保持、Statusが誤って「保存済み」にならない、Context切替で旧状態を混入させない。
- Refetch ErrorはMutation Successと別に扱い、GraphQL Result UnionとExecution / Transport Errorを混同しない。

#### 合意が必要な選択肢

1. Aggregate Revision + Field-aware 3-way Mergeを両Settingsに採用するか。特に別Field競合時の自動再適用を許容するか。
2. Community Accentで**共有確定色へ見た目を戻しつつ、ColorInputのユーザー選択Draftを保持する**UXを採用するか。Preview OverlayのShell適用範囲も確認する。
3. Statusの「保存待ち／保存中／保存済み」の配置・保持時間と、Conflict解決UIの詳細。
4. Unknown OutcomeでのRefetch後の自動再送可否、画面離脱中のQueue寿命と失敗通知方法。
5. CAS用Revisionが増える条件（実質同値Patchを含むか）、Conflict再試行回数、同時更新の負荷・UIコスト。

### 複数GraphQL Field ErrorのWeb表示

GraphQLは`data`と`errors`が同時に返る場合があるため、Operation全体のエラーを1件に潰して判断しない。

- 認証失敗を示す公開コードが含まれる場合は、対象Operationのデータを利用せず、認証状態を再確認して再ログインへ誘導する。
- `NOT_FOUND`と`FORBIDDEN`が混在する場合、Operation全体の404／403へ単純変換せず、各`error.path`と画面に必須なFieldを照合する。秘匿対象の存在が推測できる部分データ・他のError文面を表示しない。
- 一覧等の独立Fieldで安全な部分データが返った場合の表示可否は、Operation単位で定義する。Mutationの認証・認可失敗を部分成功として扱わず、既存のBulk item resultはPayload契約に従う。
- 同一Operationで認証エラー以外の複数Errorが発生した際、画面の必須Fieldが失敗した場合は画面全体をエラー表示とする。独立した補助Fieldのみが失敗した場合は、権限上安全な部分データの表示を許可する。認証失敗時は部分データを表示せず認証状態を再確認する。GraphQL Error PathとNullable設計、Client Cacheの挙動は実装前に検証する。

## Relay Connection

一覧はRelay Cursor Connections Specificationに沿います。

```graphql
type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}
```

- forward paginationは `first` と任意の `after`、backward paginationは `last` と任意の `before` を使用します。
- 既定取得件数は30件、最大取得件数は100件です。
- 0以下、上限超過、`before + first`、`after + last`、`first + last` は `VALIDATION` とします。
- edgeは `cursor` と `node`、connectionは `edges` と `pageInfo` を返します。
- Connection / Edge / `node` / `cursor` / `pageInfo` と `first` / `after` / `last` / `before` の意味はRelay Cursor Connections Specificationへ準拠します。
- cursorはopaqueとし、ClientがDB key構造へ依存しないようにします。Pagination mechanismは共通化しますが、business上のsort semanticsは各Query契約で定義します。
- Media一覧は既存設計どおり `createdAt DESC, id DESC` を論理順とします。
- Group / Tag一覧はname ASC、同名時ID ASCとし、対応するopaque cursorを使用します。Community / Membership一覧の具体的sortとcursor keyは、Product仕様で未確定のため本契約だけで新規決定しません。

## User

### 型

```graphql
type User {
  id: ID!
  profile: UserProfile!
  preferences: UserPreferences!
  usage: UserUsage!

  updatedAt: DateTime!

}

  JPEG

  me: User

  nickname: String!
}

}

}

  mediaDetailInitialInfoWide: Boolean
  mediaDetailInitialInfoMedium: Boolean

  preferences: UserPreferences!
}

extend type Mutation {
  registerUser(input: RegisterUserInput!): RegisterUserPayload!
  updateUserProfile(input: UpdateUserProfileInput!): UpdateUserProfilePayload!
  updateUserPreferences(input: UpdateUserPreferencesInput!): UpdateUserPreferencesPayload!
}
```

UsageはCustodian scopeで集計します。me.usageはUserがCustodianであるPersonal Mediaだけを対象とし、Community管理Mediaを含みません。communityUsageは指定CommunityがCustodianであるMediaだけを対象とし、User管理の共有Mediaや他CommunityのMediaを含みません。いずれも登録が確定したOriginalのみを件数・容量に算入し、Variant等の派生物を除外します。formatBreakdownはOriginal実内容の検証済みcanonical formatに基づき、JPEG（.jpg / .jpegを統合）、PNG、WebP、HEIF family（.heic / .heifを統合）のOriginal件数・Original byte数を返し、総値と内訳の合計を一致させます。file extensionやClient申告MIMEは分類の正本にしません。communityUsageは有効なMembershipを持つAdministrator / Memberが閲覧できます。Initial ReleaseではPersonal accountと各CommunityのeffectiveLimitBytesをそれぞれ5,000,000,000 bytesとし、独立して適用します。

`me` はUser自体をnullableとし、Access Tokenが有効でMemoria Userが未登録の場合は `null` を返します。Userはissuer・subject、email、内部状態を公開しません。DELETING Userは通常Product操作と同様に拒否します。

`registerUser` はAccess Tokenから認証主体を確定し、Clientからissuer・subjectを受け取りません。登録済み主体による再登録は `CONFLICT` です。

`updateUserProfile` はACTIVE User本人だけが実行でき、Initial Releaseではnicknameを更新します。同時更新にversion mergeは導入せず、成立した更新の最終状態を返します。

`User.preferences` はaccount同期するpresentation preferenceの正本です。Themeはbrowser / device-localでありGraphQLへ含めません。Language / LocaleとTimezoneはInitial Releaseで選択UIを提供しないため、先行してfieldを追加しません。各fieldの初期値はUser SettingsのScreen Specificationを正本とします。

`updateUserPreferences` は複数のaccount同期Preferenceを1つのモデル更新I/Fとして部分更新します。Inputは少なくとも1 fieldを指定し、未指定fieldは現在値を維持します。明示的な `null` は設定値として受理せず `VALIDATION` とします。Personal Accentは `#RRGGBB` を受理し、他のPreferenceと同様に成功時の保存済み `UserPreferences` を返します。連続する即時保存はWebがrequestを直列化し、保存中の変更を必要に応じてcoalesceして最新のUser intentを次requestとして送ります。APIにPreference versionやClient sequenceを追加せず、各Mutationは受信時の入力をatomicに保存します。

`User.usage`はUser Settings > Usageで必要なPersonal Mediaの登録済みOriginal件数、Storage使用byte数、有効上限、file format別内訳を返します。Community管理Mediaは含めません。`communityUsage(communityId)`は有効なMembershipを持つAdministrator / Memberが閲覧でき、指定CommunityがCustodianである登録済みOriginalだけを返します。共有されたUser Custodian MediaはCommunity Usageに含めません。各内訳はJPEG、PNG、WebP、HEIC / HEIFのOriginal件数・byte数を返し、.jpg / .jpegと.heic / .heifはそれぞれ統合します。各対応formatの行を常に返し、件数・容量0も明示します。Initial Releaseでは5 GB（5,000,000,000 bytes）の上限をUser accountごと・各Communityごとに独立適用し、effectiveLimitBytesとして返します。Plan / Quota等の算出モデルはGraphQL契約へ露出しません。使用率・残容量・表示単位への変換はWebで導出します。累積Storage値は32-bit `Int` の範囲を超え得るため、`Int64`を使用し、GraphQL responseでは符号付き64-bit整数を10進文字列としてserializeします。Webは生成型上もnumberとして扱わず、表示・計算時にBigInt等の安全な表現へ変換します。

Usageの `OriginalImageFormat` は保存済み `media.media.mime_type`（Upload ServerがOriginal実内容を検証して確定・保存したcanonical MIME）から導出する。canonical format専用のDBカラムは追加せず、拡張子・Client申告MIME・HTTP Content-Type・Variant形式は分類の根拠にしない。JPEG / PNG / WEBPとHEIC・HEIFをまとめたHEIF familyへ分類し、HEIF familyのcanonical MIMEの受理集合はUpload側の検証契約に従う。未知のMIMEを黙って除外・別形式に推測分類せず、総件数・総byte数と内訳が一致しない成功レスポンスを返さない。Uploadでのcanonical MIME確定・保存は[Media処理と派生物](/media/processing)の必須契約とする。

## Community

### 型

```graphql
type Community {
  id: ID!
  name: String!
  members(first: Int, after: String, last: Int, before: String, sort: CommunityMemberSort = NAME, direction: SortDirection = ASC): CommunityMembershipConnection!
  myMembership: CommunityMembership!
  mySettings: CommunityUserSettings!
  createdAt: DateTime!
  updatedAt: DateTime!
}

type CommunityMembership {
  user: User!
  role: CommunityRole!
}

type CommunityUserSettings {
  accentColor: String!
  alias: String
}

type CommunityMembershipEdge {
  cursor: String!
  node: CommunityMembership!
}

type CommunityMembershipConnection {
  edges: [CommunityMembershipEdge!]!
  pageInfo: PageInfo!
}

type CommunityEdge {
  cursor: String!
  node: Community!
}

type CommunityConnection {
  edges: [CommunityEdge!]!
  pageInfo: PageInfo!
}

extend type Query {
  community(id: ID!): Community
  myCommunities(first: Int, after: String, last: Int, before: String): CommunityConnection!
}
```

`community` と `Community.members` は有効なMembershipを持つUserだけが利用できます。Community外Userへ内部情報を公開しません。`myCommunities` は現在Userが有効なMembershipを持つCommunityだけを返し、公開Community検索や現在Communityにおける本人role取得の代替には使用しません。Application IAではCommunity contextへ移動後、対象Communityの情報と現在Userの権限を参照します。`Community.myMembership` は現在の認証User本人の有効なMembershipを直接返し、ページングされた `Community.members` に本人が含まれるかどうかに依存しません。`members` は本人を除外せず、全参加者を対象とします。両fieldは同じ保存済みMembershipを参照し、二重保存しません。`community(id:)` は有効なMembershipを持つUserにのみ公開するため、取得可能なCommunityの `myMembership` は非nullです。Membership失効時はCommunity取得と各fieldの認可を再評価し、Clientの表示済みroleを認可根拠にしません。

`Community.mySettings` は現在の認証User × Communityに属するpresentation settingを返します。Accent Colorと本人の個人向け別名を持ち、Community brandingやCommunity本体の属性にはしません。`myCommunities` から各 `Community.mySettings.accentColor` と `alias` を取得できるため、Context Switcher専用の設定Queryは追加しません。有効なMembershipを持つUserだけがCommunityを取得できるため、取得可能なCommunityでは `mySettings` も非nullです。

`Community.members` の既定順は現在のnickname昇順、同値時はUser ID昇順です。`sort: NAME` はnickname、`sort: ROLE` はroleを主keyとし、指定directionを主keyへ適用した後、安定化keyとしてUser IDを同方向で使用します。cursorは `(sort kind, direction, normalized primary value, user id)` に対応するopaque値で、Clientは内容を解釈しません。nicknameはUser domain所有のため、Query ServiceはMembershipと現在User Profileをjoinして同一snapshot内でpage境界を評価します。role / nicknameがpage取得間に変更された場合、cursor paginationは最新状態を基準に再評価されるため、Webは管理操作後に対象Connectionをrefetchします。参加日時sortはInitial Releaseへ追加しません。

Community参加者とAccount削除の後任候補には共通の `User` 型を使用します。参加者画面で必要な情報は `User.id`、`User.profile.nickname` と `CommunityMembership.role` です。`Community.myMembership` は本人のrole取得、`Community.members` は本人を含む全参加者一覧の取得に使います。`Community.members` の親Communityは取得済みのため、Membershipから同じCommunityへの逆参照は設けません。`User` 型を共用しても、将来追加する本人専用fieldはfield単位で認可し、Membershipを通じて公開しません。email、profile画像、Auth0 identifierはInitial Releaseの `User` に含めません。

`updateCommunitySettings` はCommunity本体ではなく、現在User本人のUser × Community settingを部分更新します。有効なMembershipを持つ全Memberが自身のAccentと個人向けCommunity別名を変更でき、Administrator権限は要求しません。Inputでは `accentColor` / `alias` の少なくとも一方を明示し、省略したfieldの保存値は維持します。`accentColor` は指定時に `#RRGGBB` を受理し、明示的な `null` は `VALIDATION` とします。`alias` は未設定なら `null` を返し、入力の前後空白を除去してUnicodeコードポイント単位で最大100文字とします。空文字・空白のみ、および明示的な `null` は別名解除を意味します。別名の重複は拒否しません。更新は入力のfieldだけを原子的に変更し、成功時は保存済みの `CommunityUserSettings` を返します。Community作成時およびInvitation参加成立時はMembershipと同じtransaction境界で初期Accentを生成・保存し、Membershipだけ成立してsettingが欠落する状態を作りません。初期生成では同一Userが現在所属する他CommunityのAccentとの完全一致を避けます。具体的な生成範囲・乱数方式・再試行上限はImplementation Detailとして別途確定します。

User × Community settingはMembership lifecycleに従属します。退会・除外時にsettingも削除し、同じCommunityへ再参加した場合は過去の別名を復元せず新しいAccentを生成します。新規Membershipの別名は未設定（`null`）とします。既存Membershipを維持している間はCommunity集合の変化だけを理由に再生成しません。Accentの連続即時保存はUser Preferencesと同様にWeb側でrequestを直列化・coalesceし、APIへClient sequenceを追加しません。

## Image UploadとProcessing

Initial Releaseではファイル本体をGraphQL multipart Mutationで受け取らず、同じmemoria-api内の専用HTTP upload endpointで受信します。ファイル送信時に必要な最小限のmetadata（`custody.type`、Communityの場合の`communityId`、`idempotencyKey`）も同じHTTP requestで渡します。endpointの具体的path、multipart field名、response schemaはHTTP API詳細設計で確定します。GraphQLは登録済みMediaの取得・分類・共有・削除・Processing状態取得を担当します。

`custody.type` が `PERSONAL` ならPersonal Media、`COMMUNITY` ならCommunity直接Uploadを意味します。`COMMUNITY` では `communityId` が必須で、`PERSONAL` では指定を禁止します。Serverは指定Communityへの現在Membershipを検証します。ClientからUser Custodian IDやUploader IDを受け取りません。

1 request / 1 Processing Job / 1 Mediaを維持し、複数画像選択はClientが個別HTTP upload requestをbounded concurrencyで実行します。1回のUI選択は最大100 filesですが、100 filesを単一のatomic requestにはしません。HTTP endpointとGraphQL resolverは共通のApplication Use Caseと認証・認可規則を利用し、受信経路ごとにMedia登録・Storage保存・Job発行を重複実装しません。

Initial Releaseの入力形式、128 MiB、100 megapixels、width / height上限等はMedia処理設計を適用し、違反は `VALIDATION` とします。

Initial ReleaseのOriginal file size上限は128 MiBであり、`Media.fileSize` と `ImageVariant.sizeBytes` にはGraphQL標準の32-bit signed `Int` を使用します。画像のwidth / heightも同じ `Int` とし、`BigInt` / custom integer scalarは導入しません。将来この範囲を超える値が必要になった場合は、該当fieldの型変更とClient互換性を別途設計します。

Original保存とDB transactionが成功した時点でHTTP upload requestを成功とし、Variant生成完了やRedis配送完了を待ちません。返却Mediaの `processing.status` により非同期状態を観測します。terminal `FAILED` でもMediaは残り、通常権限に従って削除できます。Initial ReleaseではUser向けmanual reprocess Mutationを提供しません。

Uploadは再送による重複Media作成を避ける必要があるため `idempotencyKey` を要求します。keyの形式・保持期間は[冪等性と再試行](./idempotency)および未決定Implementation Detailで確定します。

`mediaGroupRelationCandidates` はrelation編集専用の候補評価Queryです。対象Groupの保存済みscopeを使用し、同一scopeのGroupだけをname順で検索します。自己Groupや既存relationを候補から隠さず、各候補について現在の `isParent` / `isChild` と、Parent / Child各方向の追加可否を返します。WebはDAG全体を取得・再構築してcycle、深度、直接relation数上限を判定しません。

`MediaGroupRelationActionAvailability.canAdd = false` の場合は `unavailableReason` を必須とし、`canAdd = true` の場合は `null` とします。理由はUI文言そのものではなくDomain semanticsを表し、WebがProduct文言へ変換します。現在保存済みrelationに対する `ALREADY_RELATED` と、同一Draftで反対方向へ選択済みというClient-local状態は区別します。後者はServer候補Queryの状態ではないため、WebがDraft上で `OPPOSITE_RELATION` 相当としてActionを無効化します。保存時はServerが最終Draft全体を再評価するため、候補取得後のDAG変更を安全性の根拠にしません。

`updateMediaGroup` はGroup Browserの編集Dialogで構成した「同じGroup自身の名前とrelation Draftを保存する」という1つのUser intentを表します。`name` と `relationChanges` は部分指定でき、少なくとも一方を指定します。同一request内で同じrelationへの矛盾したchange、同じ候補をParentとChildの双方へ追加するchange、自己参照等のrequest自体の矛盾はMutation全体を `VALIDATION` として拒否します。

name更新はGroup本体の更新として先に検証し、nameが不正・重複等で成立しない場合はrelation changeを開始せずMutation全体を失敗させます。nameが成立した後のrelation changeはInput順へ意味を持たせず、Serverが最新DAGに対する1つのDraft差分集合として評価します。relation change同士は部分成功を許容しますが、処理順によって同じrequestの可否が変わらないよう、追加予定relationを含む最終候補graphを基準にcycle・深度・parent / child上限を検証します。成立可能なchangeだけをtransaction内で反映し、各結果を `relationResults` で返します。

保存時には現在のrole、scope、Group存在、relation、cycle、DAG深度、parents / children各10件上限を再評価します。候補Query時点で `canAdd` だったことを認可・整合性の根拠にしません。部分成功後の `group` は成立済み変更を反映した最新状態を返し、Webは `parents` / `children` と候補availabilityを再取得して残Draftを再評価します。descendant集合が変化し得る成功が1件でもあれば、Group Browserのaggregate Media Connectionも最新relationを基準に再取得します。

relation解除は指定relationだけを削除し、0 parents / 0 childrenを許容します。Group削除はMedia本体を削除せず、対象GroupのMedia relationとGroup relationだけを削除します。

Group IDから分類先scopeを確定し、各Mediaがそのscopeで閲覧・分類可能かを検証します。Group IDとMedia IDのULID形式からscopeを推測しません。複数Media分類は各Mediaを再認可して部分成功を許容します。query結果全件を暗黙対象にするInputは提供しません。

**Media Browser複数Group一括追加（2026-10-26合意）**: UIは複数Mediaと複数既存Groupの集合を一つのUser操作として指定できる。**全Group集合の存在・同一scope・権限はAction共通のprecondition**であり、集合の一部が無効ならMediaの更新を一件も確定しない。各MediaではそのGroup集合への追加を不可分として適用し、Media間の部分成功のみ許容する。これは既存の `addMediaToGroup(groupId, mediaIds)` の複数回呼び出しによっては保証できない。[API PR #114](https://github.com/hazuki3417/memoria-api/pull/114) の作業ブランチでは、既存Consumer向けの `addMediaToGroup(groupId, mediaIds)` を維持し、Media Browser向けに `addMediaToGroups(input: {groupIds, mediaIds})` を別Mutationとして追加した（未merge）。全件共通のGroup集合をLock付きで検証し、1 DB Transaction＋Media別SAVEPOINTで各Mediaに対するGroup集合を原子的に適用する。Group集合の不成立はMutation全体を失敗させ、Mediaの認可/存在不成立はMedia item resultの `FAILED`、全Group所属済みは `ALREADY_APPLIED`、少なくとも1 Group追加済みなら `SUCCEEDED` とする。外側のTransactionのCommit自体が失敗した場合はitem resultを確定成功として返さない。実環境の競合・ロック・大規模入力・Rollback検証は引き続き[API Issue #115](https://github.com/hazuki3417/memoria-api/issues/115)で追跡する。[画面設計](/screens/media-browser-detail)を参照。

### 最終確定

```graphql

  reviewToken: String!
  idempotencyKey: String!
}

  accepted: Boolean!
}
```

最終確定ではACTIVE User、review対象、Community / Membership / Mediaの現在状態、再認証結果を再検証します。Review後に計画対象が変化した場合は `CONFLICT` とし、最新状態でReviewからやり直します。

成功時は必要なAdministrator昇格・Community削除対象を確定し、User管理Media等の削除snapshotを固定してUserをDELETINGへ遷移させます。非同期cleanup完了をMutation responseで待ちません。

`reviewToken` は削除Reviewを識別するopaque handleであり、Browserが保持するSecurity proofではありません。APIはreviewのowner User、削除計画snapshotまたは同等の整合性情報、作成時刻・有効状態をServer-sideで管理します。Clientはtoken内容を解釈しません。

Auth0強制再認証とcallback処理はBFF（Next.js）が担当します。再認証成功後、BFFはBrowserへAuth0由来のproofを露出せず、通常の認証済みAccess Tokenと対象 `reviewToken` を用いてAPIの内部reauthentication binding境界へ「このACTIVE UserがこのReviewについて再認証済み」であることを登録します。この内部境界はBrowser向けGraphQL Schemaには公開しません。APIはAccess Tokenから解決したissuer / subject / Userとreview ownerが一致することを必須とし、Clientから渡されたUser IDを信頼しません。

APIは `User + reviewToken + reauthenticatedAt + expiresAt + consumed/revoked state` 相当の短期Server-side bindingを保持します。具体的な保存方式はImplementation Detailです。bindingは再認証成立時から10分間だけ有効とし、期限切れ時は削除を開始しません。Account deletion専用Auth0 Authorization requestはBFFが `prompt=login` + `max_age=0` で開始します。

`confirmAccountDeletion` の公開Inputには `reauthenticationProof` を含めません。最終確定時にAPIがreview ownerと有効なServer-side bindingを照合し、ACTIVE User、Community / Membership / Mediaの現在状態を再検証します。review後に削除計画を変更・再生成した場合、旧reviewに対するbindingは新reviewへ流用しません。最終確定成功時はbindingをconsumedとして再利用不能にし、reviewも再利用不能にします。再認証失敗・取消し・期限切れ・callback不成立時はbindingを成立させません。

Auth0再認証成功だけでは削除operationを開始しません。BFF callbackはbinding登録と安全な内部URLへの復帰までを担当し、削除開始にはFinal Confirmation画面からの明示的な `confirmAccountDeletion` を必須とします。

## 冪等性

Initial Releaseで少なくとも次のCommandは再送による副作用重複を防ぐ必要があります。

- HTTP Media upload endpoint（HTTP requestの `idempotencyKey`）
- `deleteMedia`
- `deleteCommunity`
- `confirmAccountDeletion`

これらはGraphQL MutationではInput、HTTP uploadではrequestに `idempotencyKey` を必須とする契約案とします。共有・分類等のrelation操作はunique constraintと現在状態を利用して重複適用を防ぎ、bulk itemごとに現在状態を返します。

全Mutationへ一律にidempotency keyを要求しません。keyの長さ、形式、retention、response snapshot表現は[冪等性と再試行](./idempotency)とIssue #61で確定します。

## 非同期処理との境界

- Upload成功はOriginal保存とPostgreSQL commitで確定し、Variant生成完了を待ちません。
- Processing状態はMediaから観測できます。内部Job errorやRedis状態はClient契約にしません。
- Media削除は `DELETING` 受付を同期結果とし、Object Storage cleanup完了を待ちません。
- Community削除は `ACTIVE → DELETING` と削除対象確定を同期結果とし、Community管理Mediaの物理cleanupとCommunityの物理削除完了を待ちません。
- account削除はUserをDELETINGへ遷移させた時点で利用終了とし、cleanup完了をBrowserで待たせません。
- Transactional OutboxのRedis配送成功をGraphQL Mutationの成功条件に含めません。

## 実装引き渡しチェック

画面仕様（Group Browser、Media Detail、Media Upload）とMedia Group / Tagドメイン仕様、`memoria-api/develop` の既存GraphQL schemaを照合した結果、主要なドメイン境界と画面Interactionに矛盾は認められません。以下は実装引き渡し時の確認事項です。

- 既存APIの `scalar Upload` と `scalar Int64` は既存schemaに存在するが、新しいMedia upload transportは専用HTTP endpoint、Initial ReleaseのMedia size/dimension fieldは標準 `Int` とする。既存scalarの削除はこの契約だけを根拠に行わない。
- Group relationの表示は `MediaGroup.parents` / `children` / `media` を使用する。関連追加の候補検索は表示用Connectionと別の契約が必要であり、候補の絞り込み・DAG循環禁止をAPIで再検証する。
- Media一覧は `mediaList(scope:)` を共通I/Fとし、Personal / CommunityごとのWeb Operationから利用する。Dashboardも専用Queryを作らず `first: 32` で同じConnectionを利用する。1 Connection内でscopeを混在させない。Media Detailの現在scopeの分類は `Media.groups(scope:)` / `tags(scope:)` を使用する。Personalと各Communityの分類を混在させない。
- User Preferences / Community User Settingsはaccount / Membership scopeに従って永続化し、ThemeをGraphQLへ含めない。Context Switcherは `myCommunities -> Community.mySettings` からAccentを取得する。Storage Usageのbyte値は `Int64` を使用し、wire上は10進文字列として扱う。
- Community削除はCommunity管理Mediaの存在を `CONFLICT` 条件にせず、`ACTIVE → DELETING` とMedia削除Lifecycleを実装する。
- `mediaOriginalDownload` は単一Mediaの5分署名URL + `expiresAt` を実装引き渡し対象とする。複数Media ZIPはInitial Release対象外とする。Account deletionは公開GraphQLから `reauthenticationProof` を除外し、`reviewToken` とServer-side reauthentication bindingを使用する。BFF→APIのbinding登録境界はBrowser向けGraphQL Schemaとは分離する。
- 専用HTTP upload endpointのpath、multipart request / response詳細は[Media Upload HTTP契約](./http-media-upload)を正本とする。既存の認証・認可、Application Use Case、Transactional Outbox、Redis Streams処理基盤を再利用する。

## レビュー時の要判断事項

既存設計だけでは一意に決められない事項を以下で追跡します。採用方針は各項目に明記します。

1. **Operation naming（確定）**: 対象モデルの更新を表す `updateCommunity` 方式を採用する。Communityの名称変更は `updateCommunity`、Profile変更は `updateUserProfile` とし、単一属性に限定した `renameCommunity` 等は設けない。Membershipの除外や退会、Media削除など更新とは異なる独立したUser intentは、既存案どおり `removeCommunityMember` / `leaveCommunity` / `deleteMedia` 等の操作名で表す。
2. **scope Input表現（確定）**: `ScopeType` enum（`PERSONAL` / `COMMUNITY`）を明示する。共通 `ScopeInput` をGroup / Tagの取得・作成で使用し、HTTP Image Uploadのcustody指定も同じenumと検証規則を使用する。`COMMUNITY` は `communityId` 必須、`PERSONAL` は指定禁止とし、不整合は `VALIDATION`。
3. **Bulk result表現（確定）**: 共有・共有解除・Group分類・Tag分類に専用のitem result型を設ける。状態の意味は共通 `BulkItemStatus`（`SUCCEEDED` / `ALREADY_APPLIED` / `FAILED`）で統一し、各resultは `mediaId` / `status` / `errorCode` を持つ。操作固有の結果fieldは必要になった時点で個別に追加する。
4. **Invitation secret返却（確定）**: APIが完全な招待URLを生成し、Administrator向け `CommunityInvitation.url` で返す。Web ClientはURLを組み立てない。招待URLはsecretとして取り扱い、非Administrator向けQueryへ公開しない。
5. **Original download契約（確定）**: Initial Releaseの単一Media Original downloadは `mediaOriginalDownload(mediaId:)` で認可後に5分の期限付き署名URLと `expiresAt` を返す。Storage keyは公開しない。複数Media ZIPはInitial Release対象外とし、将来別契約で設計する。
6. **Account deletion binding（確定）**: BFFがAuth0 `prompt=login` + `max_age=0` で強制再認証し、成功callback後にAPIへ内部境界でbindingを登録する。APIはPostgreSQLに `review + User + reauthenticatedAt + expiresAt + consumed state` を保持し、10分だけ有効とする。Browser向けSDLには `reauthenticationProof` を公開せず、`confirmAccountDeletion` は `reviewToken` とServer-side bindingを照合して成功時にconsumeする。
7. **Idempotency対象（確定）**: Community削除にも `idempotencyKey` を必須とする。通信断や再送時は同一keyで同じ削除受付結果を再現し、削除処理を重複実行しない。Upload・Media削除・account削除と同様に[冪等性と再試行](./idempotency)の共通規則を適用する。
8. **Group / Tag list sort・search matching・cursor（確定）**: Group・Tag一覧はname昇順、同名時はID昇順で順序を固定する。`search` はnameの大文字・小文字を区別する部分一致とする。Relay Connectionのcursorはこの並び順に対応したopaqueな値とし、Clientに内部keyを公開しない。
9. **Group relation editor契約（確定）**: `MediaGroup.parents` / `children` / `media` を表示用Connectionとして公開し、編集候補は `mediaGroupRelationCandidates` から現在relationとParent / Child各方向のAction availabilityを取得する。保存は `updateMediaGroup` でnameとrelation Draft差分を1つのUser intentとして送信し、relation changeは部分成功を許容する。APIは最新DAGに対してcycle・深度・直接relation数上限を再検証する。
10. **Media scope固有分類取得とモデルfield（確定）**: Group詳細の関連Connectionと同様に、Media詳細の直接関連情報は `Media.groups(scope:)` / `Media.tags(scope:)` の独立したRelay Connectionとして取得する。scopeは必須とし、現在scopeでのMedia可視性を検証する。Group / Tag本体の一覧・検索・管理は独立Query、Communityの子fieldにはしない。
11. **Upload transport（確定）**: ファイル本体は同じmemoria-api内の専用HTTP upload endpointで受信し、必要最小限のcustody情報とidempotency keyも同じrequestで受け取る。GraphQLはMediaの取得・分類・共有・削除・Processing状態取得を担当する。既存Redis Streamsによる非同期処理基盤を再利用し、HTTP endpointとGraphQLはApplication Use Caseおよび認証・認可規則を共有する。具体的なHTTP routeとrequest / response形式は詳細設計で確定する。
12. **整数scalar（確定）**: Initial ReleaseのOriginal file size上限128 MiB、画像寸法・Variant size等の現在の上限をGraphQL標準の32-bit signed `Int` で表現する。`BigInt` / custom integer scalarは導入しない。将来2,147,483,647を超える値を公開する要件が生じた場合は、該当fieldのscalarとClient互換性を別途設計する。

13. **User Preferences更新（確定）**: account同期Preferenceは `User.preferences` から取得し、`updateUserPreferences` の部分更新Inputで保存する。Themeはbrowser / device-localのためGraphQLへ含めない。
14. **Community Accent lifecycle（確定）**: AccentはUser × Community settingとして `Community.mySettings` から取得する。Membership作成と同一transactionで初期生成し、退会・除外時に削除する。再参加時は過去値を復元せず新規生成する。
15. **即時保存ordering（確定）**: Accent / Preferenceの連続変更はWebがrequestを直列化し、保存中の変更をcoalesceして最新意図を次requestへ送る。APIへClient sequence / versionを追加しない。
16. **Media Update / UploadのTag保存（確定）**: 画面専用の最終Tag集合Mutationは追加せず、Tag作成とTag分類CommandをWeb Operationが編成する。各Mutationは独立transactionとし、部分失敗後はServerの成立済み状態を再取得して差分を再評価する。
17. **Usage契約（更新）**: `User.usage`はUser Custody Media、`communityUsage`は指定Community Custody Mediaの登録済みOriginalだけを集計する。Initial Releaseでは5 GB（5,000,000,000 bytes）の上限をUser accountごと・各Communityごとに独立適用する。APIは総Original件数、Original使用byte数、effective limit、JPEG / PNG / WebP / HEIC・HEIFのformat別件数・byte数を返す。派生Variantは算入しない。Plan / Quota等の算出モデルは公開せず、使用率・残量・表示単位はWebで導出する。累積byte値は既存 `Int64` scalarを使用し、wire上は10進文字列としてserializeする。

これらは既存domain semanticsを変更せず、Transport contractまたはImplementation Detailを選択する判断です。本ページに記載した契約を実行可能SDLへ引き渡します。上記項目はInitial ReleaseのTransport contractとして確定済みです。専用HTTP upload endpointのroute / multipart形式など、GraphQL外のtransport詳細はSystem-wide detailed designで引き渡します。
