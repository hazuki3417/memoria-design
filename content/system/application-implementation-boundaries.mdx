# Application実装境界

## 目的

Domain semanticsをTransport、DB、Workerへ漏らさず、GraphQL / HTTP / async runtimeが同じApplication規則を再利用できる実装境界を定義します。具体package名よりdependency directionを正本とします。

## Dependency direction

`transport / worker -> application -> domain`

`persistence / redis / storage / auth0` はApplicationが要求するportを実装するadapterです。Domain / Applicationからgqlgen generated type、HTTP request、SQL row、Redis message、AWS SDK typeを参照しません。

## Public Application Use Case

Public operationはGraphQL fieldのmirrorではなくUser intent / business transactionを表します。User、Community、Membership、Invitation、Media、Group、Tag、Settings、Account deletionの既存domain operationごとにcommand/query boundaryを持ちます。

Command handlerは認証済みPrincipal、入力値、必要なidempotency contextを受け、authorization・state validation・transaction orchestrationを行います。Resolver / HTTP handlerは入力変換とerror mappingだけを担当します。

Query serviceはauthorization、stable sort / cursor、N+1回避を担当し、Command aggregateを無理に再利用しません。Initial Releaseで別DB/read storeは導入しません。

## Transaction Runner

ApplicationはDB transactionを開始・commitする具体driverへ依存せず、transaction callback内で同じtransaction-scoped repository setを利用できる境界を持ちます。transactionを跨いだrepository handleの保持を禁止します。

row lockが必要なUse CaseはApplicationが「何を直列化するか」を決め、Persistence adapterが `FOR UPDATE` 等へ落とします。Repository内部が独自判断でtransactionを開始しません。

外部S3 / Auth0 / Redis I/Oは既存正本で明示された例外を除きDB transactionへ含めません。

## Ports

Applicationが必要とするportは能力単位に分離します。

- Repository / Query: PostgreSQL persistent truth
- ObjectStorage: Original / Variant PUT, GET delivery, DELETE
- EventDelivery: Outbox PublisherからRedis Streamへ配送
- IdentityProvider: Auth0 lifecycle / identity operation
- Clock: expiry / retry / lifecycle判定
- IDGenerator: ULID等のserver-generated ID
- TransactionRunner: atomic DB boundary

巨大なInfrastructure service interfaceや全table共通generic repositoryを作りません。Domain固有queryは型付きの明示的operationにします。

## Internal operations

Outbox Publisher、Media Processing Worker、Storage Operation Worker、orphan reconciliation、User / Community deletion cleanupはBrowser向けPublic Use Caseと分離したinternal Application operationです。

Worker entrypointはmessageをbusiness commandとして直接信用せず、messageの最小identifierからPostgreSQL stateを再取得します。Redis message / PEL ownershipはdelivery / current execution ownershipでありbusiness truthではありません。

retry、claim、heartbeat、fencing、publication条件は各async正本に従います。Worker adapterが独自に状態遷移を追加しません。

## Error

Domain / Applicationはstable categoryと必要最小限のmachine-readable detailを返し、GraphQL / HTTPがTransport errorへmappingします。DB driver error、AWS error、Auth0 responseをそのままPublic boundaryへ返しません。

expected validation / conflict / forbidden / not-foundとunexpected infrastructure failureを区別します。retry可否はInfrastructure error文字列ではなく分類済みerror semanticsから決定します。

## Composition

process startupでadapterとUse Caseを組み立てます。global mutable singletonへbusiness dependencyを隠しません。DB pool、Redis client、S3 client、Auth0 client等のthread-safe expensive clientはprocess単位で共有します。

API serverとWorkerを同一binaryのmodeとして提供するか別binaryにするかは実装選択を許容しますが、ProductionではHTTP servingとlong-running async ownershipを独立して停止・再起動できるprocess responsibilityとして扱います。

## Test seam

Application unit testはport fake / stubでbusiness branchを検証します。Repository SQL / transaction / lockはPostgreSQL integration test、Redis ownershipはRedis integration test、S3 contractはadapter integration testで検証し、mockだけでconcurrency correctnessを証明しません。
