# PostgreSQL・Redis運用

## 概要

> 実装状況: PostgreSQL / RedisのDocker運用、HA topology、EBS、backup、AOF、復旧手順は詳細設計と実装が必要です。

PostgreSQLとRedisは初回Releaseで単一EC2上の独立したDocker containerとしてそれぞれ単一instanceを運用します。同一Host内にreplicaを置いてもEC2障害は防げないため、初回ReleaseでPostgreSQL HAやRedis Sentinelを構成しません。RDS、ElastiCacheや複数HostのHAへの移行は運用負荷、可用性要求、予算に基づいて再評価します。

## Dataの正本

| 対象 | 正本・役割 | 障害時の優先度 |
| --- | --- | --- |
| PostgreSQL | User、Community、Media、Custody、Processing Job、OutboxなどのPersistent Application Truth | 必須復旧対象 |
| S3 Original | 利用者がuploadした原本 | 必須復旧対象 |
| Image Variant | Originalから再生成できる配信用data | 必要に応じて再生成 |
| Redis | Stream、cache、delivery trigger、一時状態 | PostgreSQLから再構築可能 |
| EC2 | containerを実行するhost | IaCとimageから再構築 |

PostgreSQLとRedisの永続領域をcontainer filesystemだけに依存させず、EBS volumeまたは明示的なhost mountで保持します。volumeの保護、暗号化、容量監視は[memoria-IaCの運用設計](/system/infrastructure/ec2-runtime-operations)に従います。

## 将来のPostgreSQL HA

初回Releaseは単一Primaryとし、Host停止時は復旧手順によって再開します。複数Failure Domainへの冗長化が必要となった場合にはPrimary / Standby構成を検討します。StandbyはAvailabilityのために使用し、Read Scalingは別要件として扱います。replication lagによるread-after-write inconsistencyがあるため、必要性が観測されるまで無条件にreadをStandbyへroutingしません。

Automatic Failoverを採用する場合、単純なhealth checkだけでPrimaryを昇格させません。最低限、leader election、quorum / consensus、fencing、split brain prevention、endpoint switching、failback / rejoinを設計対象とします。Patroni等は候補ですが、具体softwareはPostgreSQL HA詳細設計で確定します。

将来PostgreSQL HAを導入する場合の監視対象はPrimary / Standby availability、replication lag、WAL generation / retention、replication slot lag、disk capacity、connections、CPU / memory、checkpoint関連metric、backup success、restore test、failover stateです。

## BackupとRecovery

ReplicationはAvailability、BackupはRecoveryのための仕組みとして分離します。誤DELETEや論理破損はStandbyにもreplicateされるため、replicationをbackupとして扱いません。

Production backupはBase / periodic backup、WAL archive、非公開・暗号化されたS3などのObject Storage、restore testを組み合わせる方向をBaselineとします。必要なRPOに応じてPITRを利用します。pgBackRest、WAL-G等の具体softwareは詳細設計で決定します。

backupは取得しただけで完了とせず、別環境へのrestore、必要なtableの整合性、復旧手順を定期的に確認します。RPO、RTO、retentionは[非機能要件](/system/cross-cutting/non-functional-requirements)を正本とし、HA構成の導入によってbackup要件を弱めません。

## 将来のRedis Sentinel HA

RedisはPostgreSQLの代替となる業務dataの正本にしません。初回Releaseは単一Redisを利用し、Sentinelは導入しません。複数Hostへの冗長化が必要になった場合にSentinelの採否を評価します。以下はその際に検討するtopologyであり、初回Releaseの要件ではありません。

```text
Redis Data
- Primary x 1
- Replica x 2

Sentinel
- Sentinel x 3
- quorum = 2
```

Sentinelを導入する場合は異なるFailure Domainへの分散を前提とし、同一HostにSentinel 3台を配置して冗長構成とはみなしません。その段階でApplicationにSentinel-aware clientとPrimary切替契約を追加します。初回Releaseの単一RedisにSentinel-aware接続を必須としません。

Redis ClusterはSharding / Horizontal Scaleが具体的に必要になった場合に再評価し、初回Releaseでは採用しません。

Redis Streamsを使用するためAOFをBaselineとし、永続領域を明示します。初回Releaseでは強いmessage durabilityを保証せず、単一Redisの永続化とPostgreSQLからの再配送・reconciliationを基本とします。`WAIT` / `WAITAOF`などの追加の書き込み確認は初期前提にせず、必要な配送保証が具体化した時点で再評価します。具体的なfsync方式、memory上限、eviction policyなどの運用parameterは、実装・検証・運用で必要性が判明した時点で調整します。

Worker停止によるpending messageはConsumer GroupのPELと`XAUTOCLAIM`などで回復します。通常のfresh messageとreclaimされたpending messageは実行資格を区別し、`NEW + PROCESSING`をduplicateとして再実行しません。Redis dataが失われた場合は、旧Redis ownershipで動作していたWorkerを停止またはfencingして並行実行不能であることを確認してから、PostgreSQLのOutbox、Processing Job、配送状態を照合します。`PROCESSING` Jobは`PENDING`へ戻し、新しいOutbox Eventを同一transactionで作成して通常のPublisher経路から再enqueueします。fencing前にJobを`PENDING`へ戻しません。恒久失敗はPostgreSQLのJob状態を正本とします。

## Development topology

Developmentでは初回ReleaseのProductionと同様に単一RedisをDocker Composeで起動します。Sentinel topologyは将来HAの導入を具体的に検討する場合の任意の検証構成とし、通常開発の前提にはしません。

Redis Dataのservice名はroleに依存しない`redis-node-1`、`redis-node-2`、`redis-node-3`とします。初期Primary / Replicaの役割はstartup configurationで決定し、failover後もservice名とCurrent roleを同一視しません。Sentinelは`redis-sentinel-1`、`redis-sentinel-2`、`redis-sentinel-3`とします。Sentinel検証を行う場合のみApplicationをSentinel-aware clientで接続します。通常開発では単一Redisへ接続します。

Sentinelの初期configurationはRepositoryで共通templateとして管理します。Sentinelはruntime中にconfigurationを書き換えるため、複数Sentinel containerで同一の書き込み可能な設定ファイルを共有しません。各Sentinelは共通templateから生成した専用の書き込み可能なconfigurationを使用し、そのruntime configurationはSentinelごとの独立した永続volumeで保持します。Repository上のtemplateはruntimeから書き換えないread-onlyな入力として扱い、初期状態へ戻す場合は各Sentinelのruntime volumeを削除して再生成します。

Local Docker HAはsoftware-level failover、client reconnect、election、recoveryの検証用です。同一Laptop / Docker Host内の構成をInfrastructure-level HAとはみなしません。Host failure、network partition、AZ failure、disk failureなどはAWS上の検証環境で確認します。

Developmentと初回ProductionではPostgreSQL / Redis version、container image、startup command、health check、基本configuration template、metrics integration、service naming conventionを可能な範囲で共通化します。Redisは実装着手時点の最新安定版を確認して採用し、再現性のためcontainer imageのversionを明示的に固定します。Redis / Sentinel固有parameterはtopology成立に必要な設定を除いて標準設定を基本とし、性能・可用性・障害復旧要件と計測結果に基づいて調整します。一方、volume、credentials、resource limits、multi-host / multi-AZ、backup / archive、monitoring / alertingは環境固有設定として分離します。

## Query、cache、性能判断

正規化された業務model、実際のquery pattern、適切なindex、keyset pagination、EXPLAINによる確認を優先し、早期denormalizationを行いません。Read modelはQuery向けの表現であり、SQL VIEWだけを意味しません。

Redisが存在することだけを理由にcacheを導入しません。indexとSQL改善で不足する場合だけ、PostgreSQLを正本とするcache-asideとTTLを検討します。cache障害時は可能な範囲でDBへfallbackし、write-through、write-behind、分散lock、requestをまたぐDataLoader cacheを初期前提にしません。
