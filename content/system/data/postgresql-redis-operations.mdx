# PostgreSQL・Redis運用

## 概要

> 実装状況: PostgreSQL / RedisのDocker運用、HA topology、EBS、backup、AOF、復旧手順は詳細設計と実装が必要です。

PostgreSQLとRedisはmanaged serviceを初期前提とせず、EC2上のDocker containerとして運用します。ただしProductionでは単一PostgreSQL / 単一Redisを可用性Baselineにせず、PostgreSQL HAとRedis Sentinel HAを構成します。RDS、ElastiCacheへの移行は運用負荷、可用性要求、予算が変化した時点で再評価します。

## Dataの正本

| 対象 | 正本・役割 | 障害時の優先度 |
| --- | --- | --- |
| PostgreSQL | User、Community、Media、Custody、Processing Job、OutboxなどのPersistent Application Truth | 必須復旧対象 |
| S3 Original | 利用者がuploadした原本 | 必須復旧対象 |
| Image Variant | Originalから再生成できる配信用data | 必要に応じて再生成 |
| Redis | Stream、cache、delivery trigger、一時状態 | PostgreSQLから再構築可能 |
| EC2 | containerを実行するhost | IaCとimageから再構築 |

PostgreSQLとRedisの永続領域をcontainer filesystemだけに依存させず、EBS volumeまたは明示的なhost mountで保持します。volumeの保護、暗号化、容量監視は[memoria-IaCの運用設計](/system/infrastructure/ec2-runtime-operations)に従います。

## PostgreSQL HA

ProductionではPrimary / Standby構成をBaselineとします。StandbyはAvailabilityのために使用し、Read Scalingは別要件として扱います。replication lagによるread-after-write inconsistencyがあるため、必要性が観測されるまで無条件にreadをStandbyへroutingしません。

Automatic Failoverを採用する場合、単純なhealth checkだけでPrimaryを昇格させません。最低限、leader election、quorum / consensus、fencing、split brain prevention、endpoint switching、failback / rejoinを設計対象とします。Patroni等は候補ですが、具体softwareはPostgreSQL HA詳細設計で確定します。

PostgreSQL HAで最低限監視する対象はPrimary / Standby availability、replication lag、WAL generation / retention、replication slot lag、disk capacity、connections、CPU / memory、checkpoint関連metric、backup success、restore test、failover stateです。

## BackupとRecovery

ReplicationはAvailability、BackupはRecoveryのための仕組みとして分離します。誤DELETEや論理破損はStandbyにもreplicateされるため、replicationをbackupとして扱いません。

Production backupはBase / periodic backup、WAL archive、非公開・暗号化されたS3などのObject Storage、restore testを組み合わせる方向をBaselineとします。必要なRPOに応じてPITRを利用します。pgBackRest、WAL-G等の具体softwareは詳細設計で決定します。

backupは取得しただけで完了とせず、別環境へのrestore、必要なtableの整合性、復旧手順を定期的に確認します。RPO、RTO、retentionは[非機能要件](/system/cross-cutting/non-functional-requirements)を正本とし、HA構成の導入によってbackup要件を弱めません。

## Redis Sentinel HA

RedisはPostgreSQLの代替となる業務dataの正本にしません。ProductionのHA BaselineはRedis ClusterではなくSentinelです。

```text
Redis Data
- Primary x 1
- Replica x 2

Sentinel
- Sentinel x 3
- quorum = 2
```

Productionでは可能なら3 Failure Domain / 3 AZへ分散し、同一HostにSentinel 3台を配置して冗長構成とはみなしません。ApplicationはSentinel-aware clientを使用し、Master NameとSentinel addressからCurrent Primaryを解決します。固定Primary IP / hostnameを正本にしません。

Redis ClusterはSharding / Horizontal Scaleが具体的に必要になった場合に再評価し、初回Releaseでは採用しません。

Redis Streamsを使用するためAOFをBaselineとし、永続領域を明示します。具体的なfsync方式、memory上限、eviction policyは運用詳細設計で決定します。

Worker停止によるpending messageはConsumer GroupのPELとXAUTOCLAIMなどで回復します。Redis dataが失われた場合はPostgreSQLのOutbox、Processing Job、配送状態から未処理対象を照合し、冪等にRedis Streamsへ再publish / re-enqueueします。恒久失敗はPostgreSQLのJob状態を正本とします。

## Development topology

通常開発ではDeveloper Experienceを優先し、Single PostgreSQL / Single Redisを許容します。HA profileではPostgreSQL HAとRedis Data x 3 / Sentinel x 3をDocker Composeで再現します。

Local Docker HAはsoftware-level failover、client reconnect、election、recoveryの検証用です。同一Laptop / Docker Host内の構成をInfrastructure-level HAとはみなしません。Host failure、network partition、AZ failure、disk failureなどはAWS上の検証環境で確認します。

DevelopmentとProductionではPostgreSQL / Redis version、container image、HA software/version、startup command、health check、基本configuration template、metrics integration、service naming conventionを可能な範囲で共通化します。一方、volume、credentials、resource limits、multi-host / multi-AZ、backup / archive、monitoring / alertingは環境固有設定として分離します。

## Query、cache、性能判断

正規化された業務model、実際のquery pattern、適切なindex、keyset pagination、EXPLAINによる確認を優先し、早期denormalizationを行いません。Read modelはQuery向けの表現であり、SQL VIEWだけを意味しません。

Redisが存在することだけを理由にcacheを導入しません。indexとSQL改善で不足する場合だけ、PostgreSQLを正本とするcache-asideとTTLを検討します。cache障害時は可能な範囲でDBへfallbackし、write-through、write-behind、分散lock、requestをまたぐDataLoader cacheを初期前提にしません。
