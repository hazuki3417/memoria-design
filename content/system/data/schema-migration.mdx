# DB schema migration

## 概要

> 実装状況: memoria-apiのDevelopment環境ではgooseによるversioned migration、fresh PostgreSQLへの適用、`schema.sql` snapshot生成とGitHub Actionsによる整合性検証を導入済みです。Applicationのsqlc query / generated codeは新しいInitial schemaへ段階的に追従します。deploy工程での単一実行、Productionでの互換性確認、復旧手順は引き続き詳細設計と実装が必要です。

PostgreSQL schema、migration SQL、生成物はmemoria-apiが所有し、実行環境、権限、deploy手順はmemoria-IaCが所有します。初回Releaseに必要な再現可能な初期化と安全な適用を優先し、高度な無停止移行は適用条件に応じて扱います。

## Migrationの所有と実行

- version管理されたSQL migrationを利用し、migration toolにはgooseを採用する。具体versionはmemoria-apiの開発環境定義で固定する。
- migration fileをschema変更履歴の正本とし、一度Productionへ適用したmigrationは原則として変更・削除しない。
- Initial Release前はProduction dataと適用履歴が存在しないため、開発中のmigrationを整理し、現在schemaをInitial migrationとしてbaseline化できる。
- `schema.sql`はmigration履歴の代替ではなく、最新Application schema全体を表す生成snapshotとして扱う。fresh DBへmigrationを適用した結果を`pg_dump --schema-only`で生成し、sqlc入力やschema reviewに利用する。goose自身のmigration管理relationはApplication schemaではないためsnapshotへ含めない。
- table / column等のDB commentはmigration SQLに`COMMENT ON`として記録し、snapshotにも保持する。DB clientはER図確認やDDLの試行に利用できるが、確定した変更はmigrationへ反映し、client上の状態だけを正本にしない。
- migration file、directory、command、goose設定はmemoria-apiの実行可能な定義を正本とする。
- migration数の増加だけを理由に適用済み履歴をsquashしない。将来、fresh DB構築時間等が実際の問題になった場合はbaseline / snapshotから開始する方式を別途設計する。
- API、Worker、Publisherの通常起動時に自動migrationを実行しない。
- deploy工程で専用の一時migration containerを起動し、対象environmentごとに一度だけ適用する。
- 複数EC2や複数processが存在しても、各instanceから重複実行しない。
- migrationが失敗した場合は後続Application deployを開始せず、既存dataと適用履歴を確認する。

## Initial Release前のschema再構築

Initial Release前でProduction dataとProductionへのmigration適用履歴が存在しない期間は、legacy PostgreSQL schemaとの互換性を要件としません。既存実装と確定した物理データモデルが大きく乖離している場合、legacy tableを段階的に変形するのではなく、設計書で確定した物理データモデルからInitial migrationを再構築します。

この再構築では開発DBの既存data保持を保証せず、旧table・旧query・旧APIを動作させるためだけの互換relationや互換codeを追加しません。Applicationが一時的にbuildまたはruntime検証を満たさない期間を許容し、DB、persistence、domain/service、GraphQL/API、Webを確定した設計へ段階的に追従させます。

ただし、物理データモデルの未決定事項を推測してInitial migrationへ固定しません。PostgreSQL Implementation Detailed Designで対象relationのcolumn、constraint、FK、index等を確定してから、実行可能DDLへ反映します。

再構築期間中に新schema未対応を理由として成立しないQuality Gateは、復帰条件と追跡Issueを明示した上で一時停止できます。CI全体を`[skip ci]`等で恒常的に回避せず、引き続き有効な検証は実行します。特にmigration適用、fresh DB再現性、schema snapshot整合性など、新しいDB migration基盤自体を検証できるGateは原則として維持します。

## Deploy順序と互換性

新しいApplication artifactを準備し、migrationを適用し、成功後にApplicationをdeployします。複数instanceを順に切り替える場合、移行期間中は旧versionと新versionの両方が同じschemaで動作できる状態を維持します。

既存本番dataや稼働中Userが存在しない初回Releaseでは、expand／migrate／contractを常に要求しません。既存data保持、無停止切替、複数version共存が必要な破壊的変更では、後方互換な追加、必要なbackfill、旧構造の削除を段階に分けます。

## Data変更、rollback、検証

大量dataの変換は小さなbatchと再実行可能なbackfillを検討し、lock、timeout、DB負荷を確認します。大きなindex追加ではCREATE INDEX CONCURRENTLYなどPostgreSQLの標準機能を条件に応じて評価します。

rollbackはdown migrationを安易に実行せず、後方互換なschema上で以前のimmutable Application imageへ戻す方法を優先します。不可逆なschema変更ではbackup、restore、roll-forwardの条件を事前に確認します。

schema、SQL、sqlc生成物、migrationの整合はGitHub Actionsで検証します。fresh DBではInitial migrationから最新まで適用できること、gooseのmigration管理relationを除外してsnapshotを再生成し、Repository上の`schema.sql`と差分がないことを検証対象とします。Developmentでのsnapshot生成とGitHub Actionsはmemoria-apiが提供する同じ生成commandを使用し、手順差によるsnapshot差分を作りません。Release後は、必要に応じて既存versionからlatestまでのupgrade pathも検証します。具体的な運用手順、既存data移行、停止許容、復旧判断は[DB schema migrationの詳細設計](https://github.com/hazuki3417/memoria-design/issues/28)と[EC2運用設計](https://github.com/hazuki3417/memoria-design/issues/45)で確定します。
