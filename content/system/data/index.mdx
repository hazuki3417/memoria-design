# データ設計

## 概要

> 実装状況: PostgreSQLはImage、Image Group、Tag、Userが中心です。Media、Custodian、Media Event、動画属性には差分があります。実行可能なschemaは`memoria-api/schemas/postgres/`を正本とします。

データは、ドメインの整合性を保持するPostgreSQLと、原本・派生fileを保持するObject Storageへ分離します。初期構成ではPostgreSQLとRedisをEC2上のDocker containerとして運用し、Redisは再構築可能な配送・一時状態として扱います。

## PostgreSQL

- Mediaの属性、Uploader、Custodian、Community公開、Group、Media Eventを保持します。
- CustodianはUserまたはCommunityのどちらか一つであることを保証します。
- foreign key、unique、check constraintで表現できる整合性はDBでも保証します。
- Groupの多段循環などDB constraintだけで表現しにくい規則はServiceで保証します。
- transactionはユースケース単位で、DB更新と外部I/Oの失敗を考慮して設計します。

ID、日時、命名、制約、index、削除の共通方針は[物理データモデル共通規約](./physical-model-conventions)を正本とします。domain固有のtable定義は[Media物理データモデル](/media/physical-data-model)、[Community物理データモデル](/community/physical-data-model)、[User物理データモデル](/user/physical-data-model)を参照します。file配置は[Mediaストレージ](./storage)、自己運用と復旧は[PostgreSQL・Redis運用](./postgresql-redis-operations)、schema変更は[DB schema migration](./schema-migration)を参照してください。

## MongoDBを主要永続化先にしない理由

同じドメイン情報をPostgreSQLとMongoDBへ重複保持すると、正本、transaction、整合性、migrationが複雑になります。Mediaの主要metadataはPostgreSQLへ集約します。MongoDBを利用する場合は、PostgreSQLでは満たせない具体的なユースケースとdata ownershipを先に定義します。
