# 物理データモデル共通規約

## 概要

PostgreSQLへ保存するProduct domain共通の型、命名、制約、日時、削除方針を定義します。本ページを共通規約の正本とし、Media・Community・Userの物理データモデルではdomain固有のtable構造と例外を定義します。実行可能なSQL schemaの正本はmemoria-apiです。

## 識別子

- entityの識別子はapplicationが生成するULIDとする。
- ULID内のtimestampを業務上のcreated_atや状態変更時刻の代替として扱わない。
- ULIDはPostgreSQLのvarchar(26)で保存する。
- 同じentityを参照するFKは、参照先PKと同じ型を使用する。
- 複合PKや外部serviceのsubjectなど、ULIDでない識別子は所有domainで明示する。
- 内部IDと外部認証identifierを公開用account identifierとして扱わない。

## 列挙値と状態値

状態・種別等の有限な値集合は、原則として文字列型とCHECK constraintで表現します。PostgreSQL ENUMを一律に禁止はしませんが、値集合が十分に安定したdomain conceptであり、独立したDB typeとして複数箇所で共有する明確な利点がある場合に限って個別に採用を検討します。

異なるlifecycleやstate transitionを持つstatusを、値名が似ていることだけを理由に共通typeへ統合しません。Application側のdomain typeとDB constraintの対応は各domainの詳細設計で明示します。

## 日時

- 時刻はPostgreSQLのtimestamptzを使用する。
- 登録・更新時刻は原則としてcreated_at、updated_atとする。
- joined_at、uploaded_at、expires_at等の業務上の時刻は意味に応じて命名する。
- タイムゾーン変換や画面表示は保存形式と分離し、日時比較はUTCなど同じ基準で行う。
- GraphQL DateTimeの通信形式はRFC3339 UTCを基本とし、日付だけのDateはYYYY-MM-DD、時刻だけのTimeはHH:mm:ssとして意味を分離する。
- 日付だけの値へtimezone変換を適用しない。DB精度やscalarの厳密な定義は既存schemaとGraphQL詳細設計で確定する。

## 文字列のcanonicalization

前後空白除去などUnicode文字列のcanonicalizationを業務規則として要求する場合、その変換はApplication側で実施してcanonicalな保存値をDBへ渡します。PostgreSQL固有の`btrim`や正規表現をUnicode whitespace規則の代替正本にはしません。DBではdomainごとの長さ・一意性制約に加え、canonicalization後の保存値が空文字でないこと等、DBで同じ意味を安定して表現できる最低限のCHECKを設定します。

## 命名

- table名とcolumn名は英小文字のsnake_caseを使用する。
- table名はdomainで意味を識別できる名称とし、複数domainで同じ名前を再定義しない。
- FK columnは原則として参照対象のentity名に_idを付ける。
- 状態columnはstatus、登録・更新時刻はcreated_at、updated_atを基本とする。

## 一覧の並び順

利用者向け一覧は、特段のdomain上の順序要件がない場合、原則として作成日時の新しいものから表示し、安定したcursor paginationのため `created_at DESC, id DESC` を既定のsortとします。

ただし、この既定sortをすべてのQueryへ機械的に適用しません。Membershipの参加順、Media Eventの発生順、upload完了順、retry対象時刻、Outbox配送順等、ユースケース上より適切な業務時刻・処理順序がある場合は、そのaccess patternに対応するsortとtie-breakerをdomain側で明示します。Worker / recovery queryは利用者向け表示順ではなく、処理の正しさと公平性に必要な順序を優先します。

## 制約とindex

- PK、FK、UNIQUE、CHECKで表現できる不変条件はDBでも保証する。
- columnは原則NOT NULLとし、NULLが有効な場合は業務上の意味をtable定義で説明する。
- 複合一意制約やpartial unique indexは、対象条件と防止する重複を併記する。
- indexは実際の検索、並び順、Job取得、復旧条件に対応する場合だけ追加する。
- 複数tableにまたがる不変条件はServiceのTransaction、lock、条件付き更新で保証する。

## 削除と参照

削除確認、物理削除、削除中状態、外部serviceとのcleanupは[削除・Lifecycle共通方針](/system/cross-cutting/deletion-lifecycle)を正本とします。本ページではDB固有の参照規則を定義します。

- FKのON DELETE CASCADE、RESTRICT、SET NULLは、所有関係と保持要件をdomainごとに選択する。
- 削除済みUserの参照を保持する必要があるMediaではFKをNULLにし、個人情報や認証identifierを退避しない。
- 外部I/OをPostgreSQL Transactionへ含めず、durable Jobまたはoperation tableで追跡する。

## PostgreSQL schema境界

Application relationは`public`へ集約せず、relationのlifecycleを所有するProduct domainに対応するPostgreSQL schemaへ配置します。

| Product domain | PostgreSQL schema | 主なrelation |
| --- | --- | --- |
| User | `identity` | `users`、`user_deletion_jobs` |
| Community | `community` | `communities`、`community_memberships`、`community_invitations`、`community_join_requests` |
| Media | `media` | Media、Image、processing、classification、Outbox、idempotency、storage operationを含むMedia domain所有relation |

User domainのschema名を`user`ではなく`identity`とするのは、PostgreSQL / SQLの`USER`との衝突や不要なquoted identifier依存を避けるためです。これはDB上のnamespace名であり、Product domain名やユビキタス言語のUserをIdentityへ変更するものではありません。

SQL、migration、constraint、queryでは`identity.users`、`community.community_memberships`、`media.media`のようにschema-qualified nameを明示し、Applicationの正しさを`search_path`へ依存させません。

domainをまたぐ参照にはcross-schema FKを使用します。例えばCommunity MembershipのUser参照は`community.community_memberships.user_id -> identity.users.id`、MediaのUploader参照は`media.media.uploaded_by_user_id -> identity.users.id`です。schema境界はFK、Transaction、JOINを禁止するservice境界ではありません。

技術的な用途だけを理由に`system`等の横断schemaへrelationを移しません。Outbox、idempotency、processing、storage operationのようなrelationも、lifecycleを所有するdomainが明確な場合はそのdomain schemaへ配置します。複数domainから独立したlifecycleを持つrelationが具体化した場合にのみ、横断schemaの追加を別途設計します。

`public` schemaはApplication relationの配置先として使用しません。extension等が`public`を必要とする場合は、その導入時に配置先と権限を個別に定義します。

## Domain固有の例外

共通規約から外れる型、命名、NULL条件、削除動作は、対象domainの物理データモデルで理由と適用範囲を明示します。domain間で共通になった例外は本ページへ昇格させます。
