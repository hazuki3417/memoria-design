# ログ・可観測性


## 概要

> 実装状況: APIのZap、OpenTelemetryとローカルJaegerは実装されています。Metric、alert、保存期間の運用設定には差分があります。

APIは構造化logにZap、traceにOpenTelemetryを使用し、ローカルではJaegerで確認できます。Logはevent、Traceはrequest経路、Metricは傾向、Auditは法的・セキュリティ証跡に用います。Media Eventは操作のtraceを目的とするドメイン情報で、汎用監査基盤ではありません。

- logは構造化して標準出力・標準エラーへ出します。
- request・traceの相関IDを伝播します。
- Web、API、PostgreSQL、Outbox Event、Redis Streams、Media Worker、Object Storageの間でtrace contextを引き継ぎ、非同期境界でも処理を追跡できるようにします。
- Job ID、Media ID、attempt、配送状態で処理を関連付け、署名付きURLやcredentialは記録しません。
- password、認証・招待token、署名付きURL、credential、Media本体、GPS、撮影情報、不要な元file名、nickname、Auth0 issuer・subjectを通常logやtraceへ記録しません。
- request body、GraphQL変数、認証headerを一律に出力せず、request ID、Job ID、操作結果、error code、処理時間と必要最小限の内部IDだけを記録します。
- 保護対象と運用上の残存riskは[Security・Privacy要求](./security-privacy-requirements)を正本とします。
- 保存期間の初期値はApplication log 30日、trace 7日、Media Event 90日とし、無期限保存を既定にしません。費用、検索性、Privacy要求に応じて見直します。
- DAM・APMという製品分類ではなく、観測目的とsignalで整理します。

## 性能検証との役割分担

k6は主要操作の応答時間やerror率がthresholdを超えたことを検知します。OpenTelemetryは同じ操作に対応するWeb、GraphQL、DB、Outbox、Redis、Worker、Object Storageのspanを関連付け、遅延や失敗が発生した処理境界を確認します。

local開発では必要に応じてJaegerなどでtraceを可視化します。通常のPRではCollectorとtrace伝播の検証を中心とし、可視化基盤全体を必須にしません。実行段階ごとの性能検証は[テスト設計](/test-design)を参照してください。

## 保持期間と運用目標

Application log、trace、Media Event、Outbox Eventは目的と保持期間を分離します。Media Eventは利用者操作の最小限のtraceであり、改ざん防止や長期保存を前提とした汎用監査logにはしません。

保持期間、request応答時間、Outbox滞留、Job失敗、backup失敗、alert閾値の正本は[非機能要件](./non-functional-requirements)を参照してください。

## OpenTelemetry Collectorとspan

EC2上でCollectorを運用する場合は、API、Worker、Publisherが同一hostのCollectorを共有し、OTLPで送信します。Collectorの停止をApplicationの必須readiness条件にはしません。

Applicationが手動で作成するspanはUse Caseを基本単位とし、resolver、Domain、Repository、Pipeline stepごとに機械的なspanを追加しません。HTTP、PostgreSQL、Redis、外部HTTPは標準instrumentationを優先します。

span attributeは必要な項目だけをallowlistで設定し、inputやoutput全体をJSONで記録しません。SQLはparameterized queryの構造を必要に応じて扱い、parameter値を記録しません。Zap logにはtrace_idとspan_idを必要に応じて関連付け、logとtraceの責務は分離します。

## Metricのcardinality

metricはrequestの個別追跡ではなく集計、傾向、warningの判断に利用します。operation、status、error分類、Media種別など低cardinalityの属性を使用し、User ID、Media ID、Job ID、event ID、trace ID、file名、自由記述をmetric labelへ含めません。

標準metricがある場合は独自metricを重複作成しません。既存の初期目標とthresholdは[非機能要件](./non-functional-requirements)を正本とし、sampling、bucket、dashboardの細部は実測と運用要求に応じて調整します。
