# 登録・処理上限ポリシー

- 対象: memoria-web および memoria-api（GraphQL/HTTP）
- 対象外: worker / outbox publisher の処理バッチ・同時実行

## 原則

1. **保持上限**（Scope / User / Community に蓄積できる件数）、**操作/APIの処理件数上限**、**同時実行上限**、**一覧取得のページサイズ**を混同しない。
2. ビジネス上の理由がない保持件数上限は原則設けない。ただし容量Quota、既存の構造上限、Community関連の暫定上限を例外とする。「無制限」はアプリ独自の件数Quotaを設けない意味であり、物理的な無限容量を保証しない。
3. UIは事前に防止・案内する。APIはUIを迂回した呼び出しも含めて境界を検証する。複数件の入力上限違反は**変更開始前**に拒否する。
4. 上限値は定数化し、フロントとAPIで定義を同期する（フロント値だけをセキュリティ・負荷制御の根拠にしない）。
5. 既存の部分成功契約がある操作は維持する。入力上限違反を部分成功として扱わず、既存の個別対象エラーと区別する。
6. 未実装の一括APIを、この文書のみを根拠に新設しない。将来追加時に該当する上限を使用する。

| 対象 | 暫定採用値 | 適用スコープ | 現状 |

| Tagカタログ件数 | アプリ独自の件数上限なし | Scope | 件数上限未確認 |

## 1操作 / 1 API入力の処理件数上限

| 操作 | 暫定採用値 | 備考 |
| --- | --- | --- |
| Media Upload UI操作 | 100ファイル | UIの候補保持上限。APIは1 Original / HTTP request |
| Media Upload同時転送 | 3リクエスト | フロントの標準concurrency |
| Media Upload原本サイズ | 128 MiB / ファイル | APIはmultipart本体に追加オーバーヘッド許容量あり |
| Media Tag状態更新 | 更新後30 Tag | 1 Media × Scope、既存契約 |
| Media一括Tag変更 | 100 Media / 操作 | **将来の一括操作がある場合の上限**。既存1 Media単位APIに無理に適用しない |
| 1 GroupへのMedia一括分類（追加・削除） | 100 Media IDs / API request | 新規API上限 |

| Group親子関係編集 | 最終状態で親・子各10件 | 既存構造契約。差分入力件数制約の必要性は実装レビュー対象 |
| Community作成 | 1 Community / request | 既存契約 |
| Communityメンバーの追加・除外・役割変更 | 1人 / request | 既存API単位。追加/招待機能が未実装の場合は将来の適用値 |

## 一覧取得の上限（登録上限とは独立）

- Group一覧: default 30、maximum 100 / page（現行）
- Tag一覧: default 30、maximum 100 / page（現行）
- 他の一覧取得はAPI契約ごとに現行値を棚卸しし、上限の追加変更は別途レビューする。

## API / UI 実装上の要求

- 上限超過時は明確なValidation error（GraphQLでは既存エラー体系を尊重）を返し、対象の上限と適用単位をUIで説明できるようにする。
- 保持上限の判定は、同時リクエストでも上限を超えないようにトランザクション内で行う。
- Bulk上限は認可・DB変更開始前にチェックし、過大な入力で大きな配列・ループ・DB負荷が発生しないようにする。
- 既存のMedia Uploadのファイル単位の部分失敗、Group分類のMedia単位の結果などは変更しない。
- 境界値テスト（最大値、その+1、複数リクエスト競合、UI/API一致）を追加する。
- 既存の表示・操作・Responsive Behaviorは仕様変更に合意しない限り維持する。

2. Community参加者数30人をすべての加入経路でAPI強制しているかの検証と必要な補強。
3. Group分類入力の100 Media、10 Group、積1,000のAPI強制とUI整合。
4. Media一括Tag操作が実在するかの棚卸し。存在または新設する場合のみ100 Media上限を適用。
5. Group関係の差分入力件数、その他Mutationの一括件数、各一覧取得ページサイズの棚卸し。
6. リミット値の共有方法、エラーメッセージ、境界・同時実行テスト。

## 再現可能な上限レビュー手順

### 起動条件
- 登録・作成・更新・一括操作・一覧APIの新設や変更
- 上限値、スコープ、Quota、データモデル、認可経路の変更
- 定期的な実装棚卸し（リリース前など、実施時期は開発計画に従う）

### 1. Source of Truthとレビュー対象の固定
1. `memoria-web`、`memoria-api`、設計資料の **最新の対象ブランチとcommit SHA** を確認し、レビュー結果に記録する。既存表は参考であり、現在のコードの代わりにしない。
2. 対象はフロントとBackend API、API service/repositoryおよび契約・DB制約。worker、outbox publisherの処理単位と実行制限は除外する。
3. GraphQL Mutation、HTTPの書き込みendpoint、入力Schema、フロント呼び出し元を網羅的に列挙する。ページングと容量/サイズ制限も区別して確認する。

### 2. 制約を分類する
各操作に対して、保持（総数）、1リクエスト/1操作（処理数）、並列、サイズ/容量、構造、一覧ページサイズを個別に確認。適用Scope、計数対象、削除済みの扱い、重複ID、空配列、ユニーク件数と入力配列長のどちらを制限するかを明記する。無制限は「明示的に設計決定した」場合にのみ記載し、実装未確認と混同しない。

### 3. Frontend/API/永続化を照合する
- UIで選択・追加できる件数、送信前のValidation、無効化、超過メッセージを確認する。
- API schema、Resolver、Service、Repository、DB制約を追い、**UIを迂回しても**上限を強制する場所を特定する。
- 1操作を複数HTTP requestに分割する場合はUI操作上限とAPI単位上限を分ける。
- 一括処理は積（Media数×Group数など）、タイムアウト、メモリ・SQLパラメータ数、部分成功契約を確認する。
- 保持上限は並列要求で超過しないトランザクション・ロックの有無を確認する。

### 4. 検証する
- 最大値の直前・最大値・最大値+1、0件・重複・無効ID・異なるScopeを検証する。
- API直接呼び出し・フロント操作の両方を検証する。
- 同時リクエストによるQuota/件数超過の防止を検証する。
- 上限違反時のエラー形式と、入力検証で変更が一切起きないことを検証する。
- 既存の部分成功・UI表示・操作・Responsive Behaviorの回帰を確認する。
- 未実行のテストは「未検証」と記し、推測で合格にしない。

### 5. 証跡と未解決事項を反映する
- マトリクスに設計値、対象経路、Frontend/APIの制御箇所、テストファイルと実行結果、commit SHA、Issueを追記する。
- 設計と実装の差異・仕様の曖昧さはIssueで管理し、優先度と対応範囲を明記する。
- 上限の新設・変更、既存挙動の変更はユーザー合意後に設計正本へ反映する。
- GitHub変更後は最新状態を再読み取りし、反映を確認する。PR merge / release / 本番操作は別途承認を得る。

### レビュー完了条件
対象操作の棚卸しが完了し、各行の制約種別・適用Scope・設計値・Front/API実装状況・テスト状況・証跡が埋まっていること。未実装・未検証は明示的にIssueに紐づき、**未解決がある場合は「レビュー完了・実装未完了」** として扱う。未確認の項目を「問題なし」と結論付けない。
