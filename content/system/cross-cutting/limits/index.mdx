# 上限管理ポリシー

WebとAPIを通じてアプリケーションが保証する保持・書き込み・読み込みの制約を共通の考え方で管理します。内部の取得方式や最適化方法は個別の実装課題として扱い、仕様値を実装都合で決めません。各設計値は[書き込み系マトリクス](./write)と[読み込み系マトリクス](./read)に分けます。上限到達時の画面表現は[Collection Discovery](/design-system/patterns/collection-discovery)などのDesign Systemと画面設計が正本であり、この文書で重複定義しません。

- 対象: memoria-web、およびmemoria-api（GraphQL/HTTP）
- 対象外: worker / outbox publisherの処理バッチ・同時実行

## 原則

1. **保持上限**（Scope / User / Community に蓄積できる件数）、**操作/APIの処理件数上限**、**同時実行上限**、**一覧取得のページサイズ**を混同しない。
2. ビジネス上の理由がない保持件数上限は原則設けない。ただし容量Quota、既存の構造上限、Community関連の上限を例外とする。「無制限」はアプリ独自の件数Quotaを設けない意味であり、物理的な無限容量を保証しない。
3. UIは事前に防止・案内する。APIはUIを迂回した呼び出しも含めて境界を検証する。複数件の入力上限違反は**変更開始前**に拒否する。
4. 上限値は定数化し、フロントとAPIで定義を同期する（フロント値だけをセキュリティ・負荷制御の根拠にしない）。
5. 既存の部分成功契約がある操作は維持する。入力上限違反を部分成功として扱わず、既存の個別対象エラーと区別する。
6. 未実装の一括APIを、この文書のみを根拠に新設しない。将来追加時に該当する上限を使用する。


## 再現可能な上限レビュー手順

### 起動条件
- 登録・作成・更新・一括操作・読み込み（一覧・詳細・検索・取得条件）APIの新設や変更
- 上限値、スコープ、Quota、データモデル、認可経路の変更
- 定期的な実装棚卸し（リリース前など、実施時期は開発計画に従う）

### 1. Source of Truthとレビュー対象の固定
1. [Context map](/context)に従って対象の設計・Schema・実装・テストの最新状態を確認する。
2. 対象はWebとAPIを通じて利用者に保証する制約・状態・操作。実装の最適化方式やworker、outbox publisherの処理単位と実行制限は対象外とする。
3. GraphQLのQuery・Mutation・ネストしたConnection、HTTPの読み書きendpoint、入力Schema、フロント呼び出し元を列挙する。ページングと容量/サイズ制限も区別して確認する。

### 2. 制約を分類する
各操作に対して、保持（総数）、1リクエスト/1操作（処理数）、並列、サイズ/容量、構造、一覧ページサイズ、検索条件数、Query複雑度を個別に確認。適用Scope、計数対象、削除済みの扱い、重複ID、空配列、ユニーク件数と入力配列長のどちらを制限するかを明記する。無制限は「明示的に設計決定した」場合にのみ記載し、実装未確認と混同しない。

### 3. Frontend/API/永続化を照合する
- UIで選択・追加できる件数、送信前のValidation、無効化、超過メッセージを確認する。
- API schema、Resolver、Service、Repository、DB制約を追い、**UIを迂回しても**上限を強制する場所を特定する。
- 1操作を複数HTTP requestに分割する場合はUI操作上限とAPI単位上限を分ける。
- 一括処理は積（Media数×Group数など）、タイムアウト、メモリ・SQLパラメータ数、部分成功契約を確認する。
- 保持上限は並列要求で超過しないトランザクション・ロックの有無を確認する。
- 読み込みでは、利用者が取得できるページ件数、検索・関連情報の範囲、次ページの有無、ネストした取得によって外部に返る情報量を確認する。内部のDB取得量・最適化は別の実装課題として管理する。
- 上限到達時の状態、正常な一覧終端、追加取得失敗、通信障害、Rate limitによる制限を区別し、既存Design System・Screen Specificationとの整合性を確認する。

### 4. 検証する
- 最大値の直前・最大値・最大値+1、0件・重複・無効ID・異なるScopeを検証する。
- API直接呼び出し・フロント操作の両方を検証する。
- 同時リクエストによるQuota/件数超過の防止を検証する。
- 上限違反時のエラー形式と、入力検証で変更が一切起きないことを検証する。
- 既存の部分成功・UI表示・操作・Responsive Behaviorの回帰を確認する。
- 読み込みではページサイズ境界、無効Cursor、ネストした大量取得、読み込み中・終端・再試行、既存選択の維持を確認する。

### 5. 結果を照合する
- 対象ごとに設計値、UI操作上限、APIが強制する入力上限、保持上限、境界値テストの整合性を判定する。
- 上限が未設定、実装と設計が不一致、あるいは検証不能な箇所を区別する。
- 設計の改訂、進捗・検証結果、未解決課題の記録先と承認条件は[ドキュメント管理方針](/documentation-policy)、[開発プロセス](/development-process)、[AI支援開発](/ai-development)に従う。

### レビュー完了条件
対象の読み書きAPIとフロント操作を棚卸しし、上限の種類・適用単位・強制箇所・境界条件を確認できていること。未確認または不整合の項目は明示し、解決を推測しない。
