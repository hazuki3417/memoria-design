- Application / Domain semantics を DB・framework・library の都合で変更しない。
- 重要な技術選定は必要に応じて ADR として記録する。

## 横断照合で確定したoverride / baseline

### Community

- Community管理権限は `community_memberships.role = member | admin` で表現し、Administrator専用entity/tableを使用しない。
- Community作成時の最初のMembershipを`admin`とするが、恒久的な作成者特権は設けない。
- 最後のadminを失うrole変更・退会・除外・User削除はTransactionで拒否する。
- Invitation acceptはMembershipを直接成立させる。
- User起点Join RequestはInvitationとは独立した将来機能として扱う。

### Media / Image

- Mediaは独立entityとし、管理主体はMedia本体のUser/Community列ではなくCustody relationで表現する。
- Community shareとCustody transferを別概念とする。
- 静止画像は `Media -> Image -> Image Variant` を正本とし、Media直結の汎用`media_variants`を使用しない。
- Initial Releaseの画像入力はJPEG / PNG / WebP / HEIC / HEIF、Original上限128 MiB、100 MP、各辺32,768px、1 Upload操作100 filesとする。
- Image Variant width baselineは320 / 640 / 960 / 1280 / 1920pxとし、Originalを超えてupscaleしない。
- Processing Jobは最大3 attempts、reclaim idle 5分を初期runtime値とし、terminal failureでもMediaは残して失敗状態を観測可能にする。
- Group / Tagは分類・検索のための機能であり認可境界ではない。
- Group / TagはUser scopeまたはCommunity scopeを持つ。
- 動画は初回Releaseで機能提供しないが、Media共通層と将来拡張可能な境界は維持する。

### Async / reliability

- PostgreSQLをdurable source of truthとし、Redis Streamsをdelivery / triggerとして扱う。
- PostgreSQL commitをAPI成功条件とし、Redis配送完了を同期成功条件に含めない。
- DB更新と非同期処理の連動にはTransactional Outboxを使用する。
- Outbox配送の重複は`event_id`、Worker処理は`job_id` / `step_id`を冪等性境界として扱う。
- 複数Publisherのclaimには`FOR UPDATE SKIP LOCKED`を利用する。
- Redis消失・Worker停止からPostgreSQL上のOutbox / Processing Jobを基準に再enqueue可能にする。Redis全損時は旧Workerを停止またはfencingした後、`PROCESSING -> PENDING`と新規Outbox Event作成を同一transactionで行い、通常配送経路から復旧する。

### Frontend

- Initial ReleaseのMedia bulk操作はBrowserで明示選択したMedia ID集合だけを対象とし、Group / Tag分類、1 Communityへの共有、削除を提供する。query/filter結果全件を暗黙対象にしない。
- bulk操作はMedia単位で現在状態・認可を再検証し、全件atomic transactionを要求せず部分成功を許容する。GraphQL contractはこのsemanticsを維持する。
- server stateはApollo Client、form stateはReact Hook Form、共有可能なfilter / sort / pageはURL stateを正本とする。
- 追加global state libraryやserver stateの二重保持を前提にしない。
- Community role、Invitation、Image Variant等の画面表現は上記Domain baselineに従う。

### Infrastructure / migration

- 初期runtimeはEC2 + Docker + EBS + S3とする。
- Web、API、Worker、Outbox Publisher、PostgreSQL、Redisをcontainerとして扱い、Docker Composeで構成する。
- PostgreSQL / Redisも初回ReleaseではEC2上で自己運用する。
- DB migrationは通常process起動時に実行せず、deploy工程の一時migration containerで一度実行する。
- migration成功後にApplicationをdeployし、失敗時は後続deployを開始しない。
- rollbackは互換schema上で以前のimmutable imageを再deployする方式を優先する。

## PostgreSQL 横断レビュー

### 既設計として採用する事項

- Application-generated ULID を `varchar(26)` で保存する。
- 時刻は `timestamptz` を使用する。
- table / column は `snake_case` とする。
- column は原則 `NOT NULL` とし、NULL は domain 上の意味を明記する。
- PK / FK / UNIQUE / CHECK で表現できる invariant は DB でも保証する。
- cross-table invariant は transaction、row lock、conditional update と integration test で保証する。
- index は実 access pattern、Job acquisition、recovery condition に対応するものだけ作る。
- 外部 I/O を PostgreSQL transaction に含めない。
- Outbox と idempotency persistence を Application transaction と整合させる。

### 横断照合で解消した旧設計

- CommunityのAdministrator専用entity/tableを廃止し、Membership roleへ統一した。
- InvitationをJoin Requestの前段階とする旧表現を廃止し、Invitation acceptによるMembership直接成立へ統一した。
- Media直結`media_variants`を廃止し、`media -> images -> image_variants`へ統一した。
- 将来のCustody transferと初回ReleaseのCommunity shareを明確に分離した。

### Async / Worker

- Redis Streamは`media-processing`、Consumer Groupは`media-workers`で確定。ConsumerはWorker processごとの一意なruntime identityを使用する

- Processing Jobは`GENERATE_IMAGE_VARIANTS`、最大3 attempts・reclaim idle 5分、1分間隔の`XCLAIM` heartbeatでownershipを維持する。`NEW + PROCESSING`はduplicateとしてACKし、`RECLAIMED + PROCESSING`だけをretry実行する
- Image Variant keyは`media/{mediaId}/variants/{jobId}/{width}.webp`とし、DB参照をpublicationの正本とする
- Storage Operationは最大10 attempts、30秒開始・最大30分の指数backoff、lease 5分、COMPLETED 7日保持、FAILED自動削除なしで確定
- orphan reconciliationは1時間ごと・24時間graceでOriginal/Variantを照合し、candidateはStorage Operationへ引き渡す
- Outbox Publisherはbatch 100、poll 1秒、lease 30秒、1秒〜5分の指数backoff。transient failureは回数でFAILEDにせず恒久的配送不能のみFAILED

## Traceability作業の完了条件（履歴）

Issue #59のtraceability作業は、以下を満たした時点で完了とする。

- 共有資料に記載された設計項目が対応するGitHub正本または明示的なoverrideへtraceされている。
- 旧仕様との競合が解消され、Community / Media / Async / Frontend / Infrastructureで同じsemanticsを参照している。
- 資料にもGitHub正本にもない具体値が、推測で埋められずIssueへ分離されている。
- 各Workstreamの次の詳細設計先がIssue対応表から追跡できる。

### User Preferences / Context Accent / Account deletion reauthentication

- account同期Preferenceは `identity.user_preferences`、User × Community AccentはMembership従属の `community.community_user_settings` を設計正本とする。実装時は既存initial migrationを書き換えずversioned migrationで追加する。
- Community初期AccentはHSL（H 0–360、S 55–75%、L 40–60%）から生成し、現在所属Communityとの完全一致だけを回避する。最大10回retry後はdeterministic Hue fallbackを使用する。
- Account deletion再認証はBFFのAuth0 `prompt=login` + `max_age=0`、APIのReview-bound Server-side binding（10分・単回使用）を実装契約とする。
- Browser向けGraphQLへAuth0再認証proofを公開しない。Reviewとreauthentication bindingは`identity.account_deletion_reviews` / `identity.account_deletion_reauthentications`をPostgreSQL正本とし、最終確定Transactionで単回消費する。


### Model redesign traceability

- Screen固有の選択file、Upload進捗集約、Media Update Draft等はClient / Application stateであり、永続Domain Entityへ昇格させない。
- User SettingsのThemeだけをdevice-localとし、Personal Accent、日付形式、file size単位、thumbnail size、Media Detail preferencesはaccount同期のUser Preferencesへ統一する。
- Community AccentはMembership従属Settingsとし、Membership終了時に削除、再参加時に再生成する。
- Account deletionはReview → Review-bound reauthentication → final confirmation → Deletion Jobの順でmodelを分離する。Review / binding作成だけではUser lifecycleを変更しない。
- Media logical overviewはTag / Group / Processing Job / Outbox / Storage Operation / Idempotency Requestを含み、既存physical modelのdurable stateと一致させる。


### Media processing detailed design decisions

- 画像Originalは128 MiB、100 MP、各辺32,768pxをInitial Release contractとし、旧NFR値をこのbaselineへ統一する。
- Redis Stream / Consumer Groupは`media-processing` / `media-workers`。正常処理中は1分間隔の`XCLAIM` heartbeat、5分idleでreclaimする。
- `GENERATE_IMAGE_VARIANTS`を初回生成・reprocess共通のProcessing Job種別とする。
- Variant Object keyはJob固有namespaceを使い、Object path自体にstaging/published状態を持たせない。
- Orphan reconciliationは1時間間隔・24時間graceで実行し、削除はStorage Operation経由とする。
- 利用者向けGraphQLはProcessing Job内部状態を直接公開せず、Media-level `PROCESSING` / `READY` / `FAILED`へ写像する。

- Processing Jobの実行資格はRedis message取得経路とDB stateを組み合わせ、`NEW + PENDING`を初回実行、`NEW + PROCESSING`をfresh duplicate、`RECLAIMED + PROCESSING`を正当なretryとして扱う。Redis全損recoveryではfencing後にJobを`PENDING`へ戻して新しいOutbox Eventを作る。


### Media processing architecture guide

- [Media登録・非同期処理アーキテクチャ](/media/upload-processing-architecture)を、UploadからVariant publication・failure recoveryまでの横断的な理解を補助する入口として追加した。
- このguideは新しい仕様の正本を作るものではなく、Media transaction、Processing Job、Outbox、Idempotency、Redis ownership、Storage Operation、orphan reconciliationの既存正本が解決する問題と責務を関連付ける。
- 正常系、DB rollback compensation、Outbox delivery、Processing Job state、Redis data loss recovery、Job-scoped Variant publicationをMermaid図で可視化し、APIからRedisへ直接publishしない等の非採用理由も記録する。

## Backend API detailed design pass

今回の詳細設計scopeは `memoria-api` のPublic API、Application境界、async runtime、Persistence連携、API test contractです。Webの画面実装詳細とInfrastructureのnode配置、HA、backup / restore、監視通知等は今回のscope外とし、各正本 / Issueで別途扱います。

### 合意済みの実装境界

- dependency directionは `transport / worker -> application -> domain`。Persistence / Redis / Storage / Auth0はApplication portのadapterとし、Domain / Applicationへframework / SQL / Redis / AWS SDK typeを漏らさない。
- package責務とdependency rule、Transaction境界、port capabilityは固定するが、具体的なGo package / interface / method signatureは実装前に過剰固定しない。
- Application Use CaseがTransaction境界を所有し、同一scopeのRepositoryは同じPostgreSQL transactionを共有する。外部I/Oとの整合性はOutbox / Storage Operation等で保証する。
- Resolver / HTTP HandlerはTransport adapterとして薄くし、business authorization、state transition、transaction orchestrationをApplication / Domainへ置く。
- AuthenticationはTransport / Infrastructure、business authorizationはApplication / Domainが担当する。
- WriteはDomain invariantをRepositoryで維持し、ReadはQuery Serviceによるjoin / projectionを許可する。Initial Releaseで別read storeは導入しない。
- Workerはdelivery / execution orchestration、ApplicationはUse Case、PostgreSQLはdurable business stateを担当する。Redis messageをbusiness truthとせず、識別子からPostgreSQL stateを再取得する。
- API Server、Outbox Publisher、Media Worker、Storage Operation Worker等は論理的に独立したprocess roleとする。Docker / EC2への物理配置はInfrastructure設計へ委ねる。

### Public API contract

- GraphQLのsemantic designはmemoria-design、実行可能SDLは `memoria-api/schemas/graphql/*.graphql`、consumer operation / generated typeはconsumer repositoryが所有する。SDL全文をdesignへ複製しない。
- Schema evolutionは additive API → consumer migration → deprecated removal とし、cross-repository simultaneous deployを前提にしない。
- PaginationはRelay Cursor Connections Specificationへ準拠し、cursorはopaqueとする。sort semanticsは各Query contractで定義する。
- Mediaのpublic processing stateは `PROCESSING / READY / FAILED` のみとし、Processing Jobのattempt、PEL、lease等の内部状態を公開しない。
- Media Uploadは `POST /api/media/uploads`、`multipart/form-data`、1 request = 1 Mediaとする。`Idempotency-Key` はHTTP headerで必須とし、bodyのbusiness inputと分離する。
- Upload成功responseは `mediaId` と `processingStatus` の受付結果だけを返し、Media query modelはGraphQLから取得する。
- GraphQLとHTTPはTransport表現を分離しつつ、Clientが判断するstable Application error semanticsを可能な範囲で共通化する。
- 全GraphQL Mutationへ汎用Idempotency middlewareを一律導入せず、副作用重複が問題になるUse Caseだけ明示的なidempotency contractを持たせる。

### GraphQL protection limits

防御機構は必須とし、具体値はSchema / consumer Operation実装後に計測して確定する。実測前は暫定値としてrequest body 1 MiB、depth 12、complexity 1000、execution timeout 10秒を使用する。既存NFRのrate limitとConnection件数上限は維持する。

### Test contract

coverage percentageだけをrelease gateにせず、Domain/Application unit、real PostgreSQL integration、real Redis integration、Storage adapter integration、GraphQL / HTTP contract、migration upgrade、async duplicate / retry / restart / Redis loss recoveryを設計上の必須検証対象とする。DB lock、constraint、Redis PEL ownership等をmockだけで検証完了とは扱わない。

### Scope外 / 保留

- PostgreSQL / RedisのProduction topology、HA配置、automatic failover、backup / restore方式。
- EC2 / Dockerの物理配置、monitoring / alert delivery等のInfrastructure詳細。
- Web implementation / Apollo cache / component / routing等のFrontend詳細。

これらを今回のBackend API詳細設計で簡略化・変更しない。Infrastructureについて既存正本にある構成は維持し、別scopeで設計する。
