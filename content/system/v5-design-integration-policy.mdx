# v5設計統合方針

## 目的

`catchup_design_checkpoint_2026-08-26_v5_infra_postgres_foundation.txt` に含まれる設計項目を欠落なくMemoria設計へ取り込むための統合規約です。

v5はv4 Application詳細設計全文を継承しているため、Infrastructure / Persistenceだけではなく、Application / Domain / Authorization / Concurrency / Idempotency / Error / Transaction / Async / Observability / GraphQL / Frontend / Testing / Development / Security等をすべて統合対象とします。

## Source of Truth

GitHub `develop` の既存設計を基準とし、v5と競合しない設計は追加します。競合については2026-08-26の統合レビューで合意した内容を優先します。

### 合意済みoverride

- Infrastructureはv5のProduction HA baselineを採用する。
- DevelopmentはDocker / Docker Composeを利用し、通常軽量profileとHA検証profileを分ける。
- PostgreSQL SchemaはDomain単位で先に深掘りせず、全体Persistence Modelを先にレビューしてから横断詳細化する。
- Community Administrator専用tableは採用せず、`community_memberships.role = member | admin`で表現する。
- Community Invitationはaccept時にMembershipを直接作成する。User起点Join RequestはInvitationとは独立した将来機能として設計を維持する。
- Mediaは独立Entityとして扱い、User / Communityの管理関係を`media_custodies`へ分離する。Media本体へowner User / Community IDを持たせない。
- Media Community Access、Media Event、Custody Transfer等は将来機能を見越したDomain/Persistence Designとして維持し、Initial Release Scopeとは分離する。
- Media Groupは既存DAGモデルを維持し、Group自身がUser XOR Community scopeを持つ。
- ProcessingJob / Image / ImageVariant / atomic artifact publicationはv5の設計を取り込む。
- TagはUser XOR Community scopeを持つ独立Entityとし、MediaとのN:M associationを`media_tags`で表現する。
- User lifecycle / account deletionはGitHub現行設計を維持する。`ACTIVE -> DELETING -> physical delete`を採用し、account deletionはInitial Release対象とする。
- User削除後も保持されるMediaの`uploaded_by_user_id`はNULL化し、削除済みUserとして扱う。PII snapshotは保持しない。
- 既存Persistence共通規約（ULID `varchar(26)`等）はv5の未決定状態へ戻さない。

## Initial Release Scopeと将来設計

機能提供時期とDomain/Persistence Designを分離します。

```text
Initial ReleaseでUI/APIを提供しない
!=
将来を見越したDomain/Persistence設計を削除する
```

既存設計またはv5に合理的な将来拡張モデルがある場合、Initial Release外であることだけを理由に削除しません。

```text
1. 全Table / Relation / Responsibilityレビュー

4. FK / Referential Integrity
5. UNIQUE / CHECK
6. Deletion Strategy

```

既存GitHubで既に確定済みの横断規約はこの順序で未決定へ戻さず、既存決定として入力に含めます。
