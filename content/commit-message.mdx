# コミットメッセージ規約

> 状態: 現行

## 目的

コミット履歴だけで変更の種類と意図を把握できるようにし、人間による開発とAI支援を利用した開発で同じ記述方法を使用します。

先頭の`docs`などの種別は、変更内容を短時間で分類し、履歴検索、レビュー、リリースノート作成を容易にするために使用します。種別だけで変更の価値や重要度を判断するものではありません。

## 基本形式

```text
<type>[(scope)][!]: <日本語のタイトル>

- 必要に応じた詳細
- 変更理由、制約、影響
```

- 1行目は変更を要約するタイトルです。
- 人間またはAIが手動で作成するコミットメッセージは日本語で記述します。
- `type`、`scope`、コード識別子、固有の技術名は原表記を使用できます。
- 本文が必要な場合はタイトルの後に空行を置き、箇条書きを基本とします。
- タイトルだけで十分な場合は本文を省略できます。
- GitHubなどが自動生成するmerge commitのメッセージは、日本語でなくても構いません。

## 種別

| type | 使用する変更 |
| --- | --- |
| `feat` | 利用者または外部契約から認識できる機能追加 |
| `fix` | 不具合修正 |
| `docs` | ドキュメントだけの変更 |
| `refactor` | 外部の挙動を変えない内部構造の改善 |
| `test` | テストの追加・修正 |
| `perf` | 性能改善 |
| `build` | 依存関係、ビルド設定、生成設定の変更 |
| `ci` | CI/CDワークフローの変更 |
| `chore` | 他の種別に該当しない保守作業 |
| `revert` | 既存コミットの取り消し |

最も主要な変更を表す種別を1つ選びます。独立した目的を持つ変更が複数ある場合は、種別を並べずコミットを分けます。

## scope

`scope`は変更対象を明確にできる場合だけ任意で使用します。全リポジトリで固定のscope一覧は設けず、ドメイン、機能、レイヤーなど、他の開発者が理解できる名前を選びます。

```text
feat(media): Mediaの委譲処理を追加
fix(auth): ログイン失敗時の処理を修正
docs(versioning): バージョニング規約を追加
```

対象が明確にならないscopeや、ファイル名を機械的に付けただけのscopeは使用しません。

## タイトルと本文

タイトルは変更後の状態を簡潔に表します。

良い例:

```text
docs: Media関連のユビキタス言語を追加
```

詳細が必要な例:

```text
feat(media): Mediaの委譲処理を追加

- UserからCommunityへの委譲に対応
- 委譲時に既存の公開設定を解除
- 管理主体の変更をMedia Eventへ記録
```

避ける例:

```text
update
修正
いろいろ変更
```

変更内容だけでは理由や影響が分からない場合は、本文に背景、制約、検証内容を記載します。ただしIssueや設計書の全文は複製せず参照先を示します。

## 破壊的変更

公開契約と後方互換性を壊す変更は、typeまたはscopeの直後へ`!`を付けます。

```text
feat(api)!: Media取得APIの応答形式を変更
```

本文の末尾に、影響と移行方法を`BREAKING CHANGE:`で記載します。

```text
feat(api)!: Media取得APIの応答形式を変更

- Image中心の応答をMedia共通形式へ変更
- Web側の型生成と参照処理を同時に更新

BREAKING CHANGE: 旧Image応答形式との互換性を廃止する
```

`!`はSemantic Versioningの判断材料ですが、それだけで自動的にバージョンを決定しません。リリース対象に含まれる全変更を確認します。

## merge commit

PRは通常のmerge commitでマージします。GitHubが生成する次のようなメッセージは規約の例外として許容します。

```text
Merge pull request #123 from ...
```

PR内の手動コミットとPRタイトルは、変更内容を人間が理解できる日本語を基本とします。
